# 工作台对话：和助手同一套说话的语法

Status: active（2026-10-16 裁决 1–7 已定；票 01、02 同日合入 main、JC 真机验收通过；随下一版发，第 4 条在 deferred。2026-10-27 裁决 8，票 03 合入 main、JC 真机验收通过）

来源：2026-10-16 JC：「组对话和普通对话现在的显示体验，就是对话的渲染体验，其实差别比较大，甚至有点割裂。我现在在考虑让它们统一一下。但是呢，一个作为个人助理，一个是作为工作台，统一风格后，肯定是还是可以保留差异……从我们敲定的产品设计基底开始，就是助理作为幕僚者，其他的普通对话，即使人用也是助理可以用，AGENT 可以用。」（「组对话」是语音输入，指助手的对话，即主对话。）

上层：[助手 PRD](../assistant/PRD.md)（地基）。助手这一侧的画法见 [主对话 PRD](../main-chat/PRD.md) 裁决 60–79。
devlog：[工作台对话跟上助手的语法](../../docs/devlog/2026-10-16-workbench-conversation-grammar.md)。

## 一句话

**语法统一，密度按关系与工作分。**

## 诊断：割裂在语法，不在密度

两边的差别分两类：

- **语法**：谁在哪一边、时间挂在哪、一步怎么写。从助手点子任务卡片进工作台，你的话从右跳到左，时间从两条消息中间跳到你气泡的左上；同一个「一步」，在助手里是一行字，在工作台里是序号、工具标签与竖线。割裂感几乎都在这一类。
- **密度**：默认露多少过程、给不给数字、回复装不装进气泡。IM 和工作台读起来不同是对的，不读作割裂。

## 地基推出的分界

- **助手管关系**：只放判断和交代，过程本来就在子任务里（助手 PRD「对下游的影响」：裁决 68、69 把过程收起来「有了根据」）。
- **工作台是办公室**：「不用管，但随时看得见、接得过来……办公室是信任的来源」（助手 PRD「地基展开」）。工作台若也把过程藏起来，你核对助手交代的唯一地方就没了。
- **「Agent 也用」对界面只有一条要求**：发话的一方要标明是谁。agent 读的是 CLI JSON，不看界面；界面上的工作台会话都是给人看的，要么你在干活，要么你在查团队干的活。来源行已经有（Supervisor 图标、「来自主对话」图标）。

## 事实依据（2026-10-16，本机库，9 月以来）

- 会话来源（内置运行时）：人开的 44、CLI 24、supervisor 6、子任务 0（`subtask_dispatches` 0 行）。
- 工作台（内置、人开的 44 个会话）115 轮的回复：中位 678 字、p75 1495、p90 2310；47% 带表格、41% 带标题、14% 带代码块、23% 超过 1500 字。
- 过程：中位 2 步、p75 7、p90 11；40%（46 轮）一步就答完，这 46 轮里带推理或开场白的 0 轮（同期全部回复消息里推理 69 / 732 条、开场白 183 / 732 条有值，列本身是有人写的）。
- 中途提问：同期 `ask_user` 7 次，分布在 6 个会话。
- 你的消息：中位 19 字、最长 220（主对话 PRD 裁决 73 第 4 条）。
- 助手对话 8 轮（样本小）：回复中位 390 字、最长 1048。

## 裁决（JC，2026-10-16）

JC：「1，认可；2，按你推荐；3，按你推荐；4，这条我也还没想好；5，按你推荐，不要；6，按你推荐，P1，不用切换器；7，按你推荐。」随后主会话补了两件（第 4 条暂缓带信号、放进哪一版）与一组默认做法，JC：「按建议推进」。

1. **分界改说法**：「语法统一，密度按关系与工作分」取代主对话 PRD 裁决 73 第 4 条里的「助手像 IM、工作台是文档」。73 第 4 条的结论不变（工作台保留你的消息上的悬停复制），理由改说为密度差异：工作台常贴长文档、长提示词。
2. **工作台里你的话在右**：
   - 气泡靠栏的右缘，宽度随内容，上限同助手 `min(80%, 560px)`（一条规则；ChatGPT 的上限也在这一档）。来源图标行（Supervisor、「来自主对话」）与长消息的「展开 / 收起」跟着靠右。
   - 推翻设计文档「不要 right-align」（`docs/design/conversation.md:36`）。它的两条理由：「一份文档一个阅读左缘」——你的话中位 19 字，眼睛来回跳的代价小，ChatGPT 就是「你的在右、回复是散文」，是用户最熟的样子；「气泡右缘挤问题轨」——只在栏宽撑满主区时发生（栏 `px-8`，轨在 `right-3`、宽 20px），内缩能解，文档对 Windows 滚动条也是这么说的。
   - **悬停复制挪到气泡下方、右对齐**，悬停才出现，隐藏时照旧占位。镜像到气泡左下是助手里否掉的位置（裁决 73 第 1 条）；助手里否掉「下方」的理由是连发时同一边只隔 4px，工作台没有 IM 分组，没有这个问题。按钮那一行的高度就当你 → 回复的间距（照助手「它 → 你 30px 由行动条占着」的思路），不再另加 `my-5`。
   - 栏宽撑满主区时，问题轨不与气泡右缘相贴（内缩，做法票 01 定）。
3. **时间居中**：工作台的发送时间画成两条消息之间居中的一行，用助手同一个 `AssistantTimeDivider`；断点与格式不变（工作台没有问候，照旧只跟你的消息比；Supervisor 来源的消息照旧总有时间）。
4. **派活说明的颜色：暂缓**。助手派活的说明与打回、外部 agent 的消息，今天都穿杏沙，只靠气泡上方一个小图标分来源；挪到右边后，IM 的直觉是「右边杏沙是我说的」，设计文档也把杏沙定为「人的声音」（`conversation.md:59`）。候选是「位置按角色、颜色按身份」。JC 未定；子任务现在是 0 个，进 [deferred](../../docs/devlog/deferred.md)「派活说明的颜色」，信号在那里。
5. **回复不进气泡**：工作台的回复照旧是纸上的散文。47% 带表格、23% 超过 1500 字，装进气泡就是裁决 66 自己点名的风险（代码框里套框、表格挤在 88% 里）。
6. **过程取 P1：写法统一，露出程度不统一；不做切换器**：
   - 在跑时照旧（live 窗口）；落定后照旧折叠，折叠头照旧常显（步数、用时、工具计数）。
   - **折叠头后面的步骤一律一行一步**：点开折叠头，原来的步骤区换成助手过程卡片里的一行一步（那一句话 + 碰过的网站或文件，点一行原地展开那一步原来的样子）；不设 8 行上限、不在卡片里滚（工作台读过程是正事，p90 11 步、最多 52，嵌套滚动是负担）；卡片里不重复数字行（折叠头已经写了）。live 头「已完成 N 步」点开后同样。不在折叠头后面的照原样：live 窗口、没有回答的运行整段平铺。
   - **中途提问与你的回答留在外面**（语法的一部分，助手对话同一条）：它们是你和它的对话，不折进步骤；你的回答在右边，藏进折叠就和第 2 条冲突。一行一步里也就没有只做了提问的那一步。同期 7 次，罕见，但规则要一句话说得清。
   - 没选：P0 现状；P2 全照助手（在跑只有一行、落定后藏进悬停按钮）——工作台就不再是「看得见」的地方。
   - **与 deferred「过程区密度」B 刀的关系**（主会话讨论时漏查，写票时补上）：B「全面单行合并」2026-09-16 真机否过（JC：「太密集后，单个步骤的阅读体验其实变得更差了」），重开条件是「只能以阅读形态本身更好为由，且要同时解决同行两个披露 caret 的问题」。P1 不是 B：B 把工具标签挤进 summary 那一行；P1 一行只有一句话与对象，工具标签收进点开，整行是唯一的点击目标，没有 caret；单步的阅读形态点开后与今天一样。这一形态 JC 已在助手里真机验收（主对话票 22）。重开的理由是语法统一，不是密度。
7. **一步就答完的回复不画折叠头**：同助手（裁决 66、68：一步就答完的什么都不留）；数字照旧在回复的悬停行里。代价是那一步的推理与开场白看不到：库里 46 个一步回复里 0 个带。这就是 deferred「单步 run 的『第 1 步』前缀收敛」里的「删整行」，那一节当时留下的两条约束：DetailPanel 入口（上面的代价）、StrongHr 的「行动 → 结论」需要上方有行动列（没有行动列就不画这道线）。那一节随之撤下，来龙去脉进 devlog。

### 来源标记叫什么（JC，2026-10-27）

JC：「目前通过 galley cli 新建的消息，都会带图标……比如现在显示 Supervisor，其实对于用户并不友好，是不是直接用「galley cli」呢？」主会话先给了按发话方分四类的 C，JC：「C 有点太复杂了，为了普通用户友好，我现在更倾向于 B，比如给用户看就简洁一点就显示「galley CLI」，当然可以在用户看不到的地方保留更多信息，方便其他功能展开」。主会话同意 B，只留 Galley 自己那一类例外，JC：「按建议推进」。

8. **来源标记只分两类**：你那侧气泡上方的来源图标（今天提示写死英文「Supervisor」，`MessageUser.tsx:361`）与侧栏会话行标题右端的徽标（「Supervisor 创建」，`SidebarSessionRow.tsx:447`）改为：
   - **Galley 自己经 CLI 写的**：标签是 `galley-assistant`（助理替你答子任务、打回、开对话），或以 `galley-im/` 开头（聊天软件渠道代你开的对话）。图标 `House`，同子任务说明；提示一律「Galley 创建」：消息、侧栏、子任务说明三处同一句（子任务说明此前是「主对话派来的」，「主对话」已退为内部用语，`layout-and-chrome.md`「叫法」）。初稿是消息上「Galley 发来的」、说明「Galley 派来的」，JC：「『Galley 发来的』有点奇怪，用户会觉得我本来就是在 Galley 软件里面，不如都统一为『Galley 创建』？」主会话同意并把说明一起改：「X 发来的」是软件通知的句式（「微信团队发来的」），读成软件在给你发东西；子任务里那句是写给子任务的，「发来」还把收件人说成了你；「派」的意思面包屑「Galley ›」与主对话里的卡片已经交代。「Galley」作发话方的名字不变：内置运行时里它就是助理的名字（侧栏卡片、「回到 Galley」）。
   - **其余经 CLI 来的**：`via=supervisor` 的其他标签，以及不带标签的 `via=cli`。图标 `PlugsConnected` 不换（「智能体接入」那页讲的就是让 Agent 用 CLI 操作 Galley）；提示两处都是「Galley CLI」。推翻 2026-05-21 决策 4 的「普通 CLI 消息不标」：「Galley CLI」对人敲的、Agent 发的都成立，当年怕的误认不存在了。
   - **定时任务**（主会话补的默认做法，票 03 代理交回）：定时任务开的对话的第一条消息，上方画时钟「定时任务创建」，同侧栏那一行。它不经过 CLI，是 Core 直接走 `session.new`（`core/src/scheduler.rs:878`），读「Galley CLI」是错的。判断并进同一个函数，标签等于 `galley-scheduler` 时最先判、不看 `via`。
   - **时间**（主会话补的默认做法）：经 CLI 进来的消息照旧总有时间，范围随之加上 `via=cli`（`lib/message-time.ts:118`）。
   - **不变**：标签照旧存在库里（`messages.supervisor`、`sessions.created_by_supervisor`）与 CLI JSON 的 `origin`，界面不显示；以后的审计、按 Agent 筛选从那里读。定时任务的时钟徽标、`via=system` 不画、说明行的位置都不变。Core、CLI、Agent API 不动。外置运行时没有助理与聊天软件渠道，只会出现「Galley CLI」一类。
   - **代价**：标签是调用方自报的，外部 Agent 自称 `galley-assistant` 会被画成 Galley；本机可信边界内，同今天一样不防。
   - **没选**：C 按发话方分四类（Galley 助理、聊天软件、外部 Agent 带原标签、不带标签的命令行），JC 嫌复杂；纯 B（Galley 自己写的也标「Galley CLI」）会让没碰过命令行的人在微信里开的对话上看到 CLI，子任务里同一个发话方出现两个图标、两个名字。

### 停下的运行怎么画（JC，2026-10-30）

主对话里没有回答的一轮收成一行（[主聊天 PRD](../main-chat/PRD.md) 裁决 159）之后，JC 问：「工作台的手动终止回复的对话显示，你觉得需要和主对话对齐吗？」主会话先推荐甲（不跟，照旧平铺），JC：「我不喜欢整段铺开，目前工作台方案倾向于乙或丙」；主会话推荐丙、不做切换器，JC：「按你的推荐推进」。

9. **没有回答的运行也折起来：停下时画面原样定住**：
   1. **现状**：在跑时是 live 窗口（「已完成 N 步」头 + 最近完成的一步 + 在跑那一行）。按停止后这一轮没有回答，落进平铺（`gui/src/lib/run-fold-plan.ts` 头注释的 `flat`），头后面收着的步骤一下全部铺开：落定的收合只给有回答的运行（`gui/src/components/conversation/Conversation.tsx:412`）。
   2. **丙（定）**：停下时只拿走在跑那一行。头上的字从「已完成 N 步」换成「中途停下 · N 步」，N 不变，后面照旧是工具气味段，没有用时（没有回答的运行不存用时）；词同主对话，三种情况（中止、出错、停在步数上限）分不出，只用一个词（裁决 159 第 4 条）。最后一步照 live 窗口的阅读形态留在头下面（序号、竖线、旁白、工具行），重载、日后翻记录都一样。点开头是一行一步的卡片（第 6 条），不含留在外面的那一步；中途提问与你的回答在头前面（第 6 条）。
      理由：折叠头后面是过程，外面是结局；有回答的结局是回复，停下的结局是停在的那一步。停下以后接着给指示，要看的就是那一步（库里 4 轮里 2 轮你下一句是「继续」）。与主对话同一条规则：停下不新铺东西，只拿走「在跑」的标记。
   3. **没选**：甲不跟、照旧平铺（JC 不喜欢整段铺开。库里主对话以外你发起的 495 轮中，没有回答又不是停下来问你的有 4 轮：09-16 brew 9 步、汕尾 18 步，10-01 两轮测试句各 3 步；最长 18 步，从没停在步数上限）；乙全部收进头里（停下那一下，你正在看的那一步消失，头下面空着，头不再是谁的眉头）。不做切换器。
   4. **边角**：只落定一步就停下的，只留那一步、不画头（同第 7 条）；停下时卡片开着就保持开着；步数上限的尾行与输入框灰字「继续」照旧；出错照旧弹提示；`/btw` 与带系统消息的轮次照旧平铺；一步都没落定的照旧什么都不画。答完它的提问、下一步还没落定就停下的，提问与你的回答留在窗口里原位，不挪到头前面（票 04 代理按「停下时画面原样定住」实现，主会话推荐保留；JC 真机后说 OK，没单独表态）。
   5. **推翻**下面「不变」里的「没有回答的运行照旧整段平铺原步骤区：排查要看全貌」：全貌在卡片里，一行一步，点开就是那一步原来的样子。
   6. 外置运行时：工作台两种运行时共用，一起变。只改 GUI。票 [04](./issues/04-stopped-run-keeps-its-last-step.md)，等主聊天票 114 合入后由同一个代理接着做。

# 主聊天（主管家）

Status: active（第三轮 2026-10-12 定形：入口 / 大脑 / 出口，界面一条、上下文分段，桌面先上；票 01–06 已拆，01 先行）

来源：2026-10-09 iOS 客户端讨论中 JC 提出。参照 Meta Muse：有一个主聊天，会话长期继续，什么都跟它说；只有要同时进行、或明确另开话题时才开旁聊；
主聊天还能主动提醒、给建议。JC 的定位：Galley 从来不是 coding 或 IDE，而是用户本地的全能个人助手；主聊天更接近「长期陪伴、越来越懂你的助理」。
2026-10-12 第三轮：JC 回头问「Galley 是不是真的需要主聊天、对体验提升有多大」，重新梳理后定为下文的结构。
关联：[移动端产品定义](../mobile-product/PRD.md)（上层）、[iOS 客户端 PRD](../ios-client/PRD.md)、
devlog [10-09 方向](../../docs/devlog/2026-10-09-ios-client-and-main-chat-direction.md)、[10-12 概念重审](../../docs/devlog/2026-10-12-main-chat-concept-review.md)。

## 一句话

主聊天是助理的入口：一条一直在的对话，什么都跟它说。「越来越懂你」和「主动找你」靠事项账本，不靠这条对话有多长。

## 结构：入口、大脑、出口（第三轮）

```
入口（主聊天这一条）→ 你把日常随口说进来 → 事项账本积累（大脑）→ 联想与主动提醒（出口）
```

- **入口**：打开就说，不用想「开新的还是续旧的」；也是异步内容的落点（子任务卡片、定时任务结果、主动提醒）。
  账本只能从你说过的话里学，所以入口的价值不只是省一个决定，而是让人愿意把日常说进来。
- **大脑**：事项账本 + GA 记忆。从所有会话里学（桌面、CLI、IM），不只从主聊天里学；主聊天形态即使不成立，账本也让每个会话更懂你，所以退出成本低。
- **出口**：联想发生在对话里（账本的事项清单在上下文中，没人提它也想得到）；主动提醒是卡片（裁决 10）。

区分两种 harness：**补偿型脚手架**（摘要压缩、滚动摘要、每轮重建的案头层）在弥补模型的上下文短板，模型一升级就报废，不做；
**积累型资产**（记忆、事项账本）是用户的数据，模型越强用得越好，正是「积累在你电脑上、换模型带得走」的实体，要做。
依据：09-09 定位「脚手架越少，模型升级时要报废的东西越少」（`docs/devlog/2026-09-09-positioning-less-harness-more-model.md:27`）；
README「dense context instead of long」（`README.md:54`）。

## 裁决

### 第一轮、第二轮（JC，2026-10-09）

1. 主聊天做成 Galley 的一等会话，桌面和手机都有，进的是同一条。桌面上固定在侧栏顶部；手机首屏就是主聊天，会话列表退到第二层叫「旁聊」。
2. ~~先零成本试用一周再定形态~~（10-12 取消，见裁决 23）。
3. 只在内置内核提供；外置模式没有主聊天（与「内置优先」一致，不进 deferred）。
4. IM 渠道是否并入主聊天：放到后面再谈（10-12 细化为三级，见裁决 27）。
5. 主聊天派活给子会话，将来用内置运行时的原生工具（托管补丁给 GA 加「开子会话、等结果」），不走「读 SOP 再调 CLI」。
6. ~~主聊天的主体是三块专门设计：窗口预算、上下文编排、主聊天入口层提示词~~（10-12 改为「入口 / 大脑 / 出口」结构，见裁决 17、18；入口层提示词保留，进票 03）。
   当时的理由仍成立：普通会话的通用方案是为「做完就结束」的任务会话设计的，长期用会忘、每条消息都贵、也没有管家的身份与委派分寸。
7. ~~一周试用改定位为「通用方案的基线测量」~~（10-12 取消）。
8. ~~设计次序：先入口层提示词与窗口预算参数，再做摘要式压缩、案头层与检索~~（10-12 改为票序，见裁决 22）。
9. 旁聊 / 子会话的结果在主聊天里显示为实时卡片，完成走通知，不往对话里注入汇报轮；模型只在用户问起时用工具去查（参考 OpenMuse）。
10. 主动建议以卡片出现在主聊天时间线里：带依据，可接受 / 忽略，依据过时自动收回；卡片不进模型上下文，用户接受后才成为一条消息。
11. 「它记得我什么」页面（查看、编辑、删除 GA 记忆）：10-12 从待定升为票 04，账本上线对外前必须有。
12. 委派规则先沿用 10-06（会长时间占着主聊天才交出去），不学 OpenMuse 的硬步数上限。10-12 补：主聊天在跑时发消息给「排队 / 开旁聊」两个选择（票 02），子任务形态见裁决 25。
13. （第二轮）主聊天是 Galley 下一步的重点，不只是移动端，桌面端与移动端一起做。理由：Galley 是本机的全能 AI 助手，一个持久主会话更接近人对助理的想象与认知，也更容易上手。
    ~~建议手机 P0 带「入口层提示词 + 窗口预算参数」上线~~（10-12 由票序取代）。
14. （第二轮）主聊天不支持 `/new`，也不能归档或重开：它是助理与用户持续存在的一条会话，更像真人助理。10-12 起由上下文分段承接，用户用不上重置。

### 第三轮（JC，2026-10-12）

15. 方向确认：主聊天与「本地全能个人助手」的定位一致。使用数据既不支持也不否定它（见「事实依据」），这是产品押注，做得便宜、能退。
16. 价值三件都要（JC）：**打开就说**——不再需要想新开对话还是继续之前的会话；**主动找你**——提醒不再是必须事先设定的闹钟，
    而是从事务和信息中归纳出可能需要提醒的事；**联想**——聊某件事时它想起上周相关联的事项。
17. 结构按「入口 / 大脑 / 出口」，投资重心从上下文压缩挪到事项账本。
18. **界面一条、上下文分段**，替代「永久单上下文」：用户看到一条完整的主聊天；模型按确定规则切段（上一轮结束后空闲超过 N 小时，N 待定），
    段末确定触发记忆整理与账本增量，新段带身份、全局记忆、事项清单，配一个查主聊天历史的工具。摘要式压缩不做；案头层由事项层取代。
    查历史只管「你问起时找得到」，管不了「你没问时想得到」，所以联想靠事项清单在上下文里，不靠工具。
19. 事项账本以上游「历史重点挖掘 SOP」为起点（内置状态 `memory/L4_raw_sessions/salient_mining_sop.md`：持续活动、已消失事项、情绪事件，增量、读原文），
    情绪事件照上游记（JC：有情绪感知的助理更有温度）。账本从全部会话里学。
20. 情绪的使用规则：可以为做事引用（「上次这事让你挺着急的，这次我提前办了」），不单独评论你的情绪（「你上周三很烦躁」）；
    情绪事件在「它记得我什么」页面里可见、可删。依据：上游的标记清单大半是你对 agent 的反应（反复纠正后语气突变、预期落空），首先是反馈信号。
21. 桌面先上，不等手机。理由：账本要时间积累，手机上线时助理已经「熟」了；与移动端 PRD「桌面主聊天不能晚于手机」一致；手机线（协议、relay、SwiftUI）与主聊天线（会话类型、上下文、账本）互不卡。
22. 票序：01 账本先行（本机先跑，对外发版必须与 04 同版）→ 02 形态、03 切段 → 04 与 03 同版 → 06 子任务 → 05 主动提醒最后。
    （06 是拆票时补进来的，JC 裁的是「A 先行，B、C 跟上，D 与 C 同版，E 最后」；06 排在 05 前是因为卡片组件先在子任务里做出来，05 复用。）
23. 一周基线测量取消（JC：还在探讨概念本身）。`baseline-snapshot.py` 保留，将来量每段上下文用。
24. 桌面层级：A1（主聊天在新对话上面）与 A2（主聊天接任逃生出口、新旁聊进书眉）做切换器真机比，我推荐 A2。见「桌面形态」。
25. 子任务：主聊天里一张卡片（一次派活一张），默认不进侧栏；打开在主区、面包屑返回、侧栏选中停在主聊天；
    你在子任务里说过一句话，它就升为旁聊进侧栏；通知只发「在问你」和跑得久的完成；子任务用 Galley 会话跑，不用 GA 的文件式子代理。
26. 定时任务的结果改为主聊天里的卡片，产出的会话按子任务处理（不进侧栏）。
27. IM 三级：L0「同一个大脑、线分开」随票 01 / 03；L1「IM 当出口」随票 05；L2「并入主聊天」仍在 [deferred](../../docs/devlog/deferred.md)，
    启动信号改为「桌面主聊天 02、03 上线后，重排 L2 与 iOS 的先后」。理由：iOS 只覆盖 iPhone，安卓用户在手机上用主聊天只有 IM 一条路。

### 第三轮·侧栏（JC，2026-10-12，02 真机预览后）

28. 样式上 A3 胜过 A1、A2：A1 主次不分，A2 找不到新建入口。A3 = A1 的顺序、层级反转（主对话是首页，新对话行降为安静的一行）。
29. 界面不用「主聊天」：文案规范「用户可见的 session / chat 概念统一叫『对话』」（`docs/copy-language-guidelines.md:324`），主入口暂定「主对话」；
    另一类的叫法（旁聊 / 话题 / 其他对话）在侧栏骨架定了之后真机定。说明文字只在空的时候出现（先例：侧栏空列表「你的对话会出现在这里。」）。
30. 侧栏职责重排：回到主对话 > 看哪里需要我 > 新开旁聊 > 找回旧旁聊；不是换一个按钮一个文案。两条旧规则的前提已变：
    「不可折叠」的理由「多 session 是核心产品形态」（`layout-and-chrome.md:22`）、「不做状态区块」的理由之一「Approval Dock 兜底」（10-05 已移除审批）。
    状态区块仍不做（在跑的旁聊本来就在时间线顶部，子任务状态汇到主对话行）。
31. 侧栏骨架：主对话行（首页）→「旁聊」分区头（加号在头上）→ 置顶 / 项目 / 时间桶。
32. agent 开的对话（CLI、supervisor 等）移出「旁聊」：在项目里的留在项目组，不在项目里的收成一行「其他来源 N」，等你回复 / 出错时按 10-08 项目组的挂出规则露出。与账本「只读人说的话」同一原则。
33. 真机比 A3（对照）/ B（骨架）/ B′（骨架 + 侧栏可收起），带演示状态档。票 [07](./issues/07-sidebar-structure-trial.md)。
34. （07 真机比后）侧栏定 B′：主对话行 →「其他对话」分区头（加号在头上）→ 置顶 / 项目 / 时间桶 / 其他来源 / 更早，侧栏可收起（⌘\）。
    A3、不可收起的 B 不要。外置运行时（没有主对话）侧栏保持今天的样子，不可收起。
35. 叫法定「主对话 / 其他对话 / 新对话」：用户不用学新词，也守住「对话」这条文案规范；「主聊天」「旁聊」只作内部术语留在 PRD 与代码里。
36. 删掉主对话行空态副行「什么都可以跟它说」（JC：不太合适）。收尾见票 [08](./issues/08-sidebar-finalize.md)。
37. （08 后）「其他对话」与下面的置顶 / 项目 / 时间桶归属感不够（JC）。根因：分区头与主对话行包在同一个固定块里，分隔线画在分区头下面；
    分区头文字离主对话约 24px、离第一个子标签约 29px，距离与「一起固定」都把它归给了主对话。真机比 C1（只固定主对话、分区头回列表并吸顶、间距反转）/
    C2（C1 + 子项缩进）/ C3（C1 + 整块底色），票 [09](./issues/09-section-belonging-trial.md)。
38. （09 真机比后）归属定 C3 + 常显 + 加重：分区头回列表当吸顶第一行、间距反转；整个「其他对话」区铺 `bg-app`，主对话留在 chrome；
    主对话行下常显一条 `line-strong` 分隔线（JC：`line/60`「几乎看不太到」）。C1、C2（缩进）不要。收尾在本地直接做（`docs/design/layout-and-chrome.md`「有主对话时」）。

## 事实依据（2026-10-12 核对）

- 桌面用量（`workbench.db`）：GUI 会话 5 个月里最长 21 轮；跨天续用的会话一共 6 个，9 月起 0 个；9 月 41 个会话共 116 轮，单个最长 8 轮。习惯是「开一个，问完就走」。
- IM 用量（引擎日志，09-30 起）：31 条用户消息，多为测试（问模型、看硬盘）；10-07 有一句「我刚才问的第一个问题是什么？」，测的正是连续性。
- 记忆整理靠模型自觉，140 个会话里只 3 次（`docs/ga-baseline.md:75`）；本机 L2 只有 3 条，insight 层是工具与 SOP 索引，没有带时间的事项。
- 上游已有零件、Galley 没接：L4 归档（`managed-ga/code/reflect/scheduler.py:62-74`，每 12 小时把引擎日志压成 L4）、历史重点挖掘 SOP、
  `reflect/autonomous.py`（用户离开 30 分钟触发自主任务）；Galley 不走 GA 反射模式（`docs/ga-baseline.md:51-53`），本机 L4 只有脚本、`history_insight/` 从未生成。
- 运行中发的消息在 Core 队列里等 `run_complete`，只有 `/btw` 旁路（`docs/architecture.md:146-152`、`docs/ipc-protocol.md:544-550`）：主聊天跑长活时会被占住。
- 引擎日志满 30 天或总量超 500MB 就清（`core/src/model_responses_prune.rs:31-33`），挖掘要每天跑。
- GA 子代理 SOP（内置状态 `memory/subagent.md`）：文件式后台进程，Galley 看不见；「浏览器暂时不可并行使用，避免同时操作同一标签页」。
- `sessions` 表没有父会话字段，只有 `goals.master_session_id`。

## 桌面形态（票 02）

主聊天成为默认入口后，「逃生出口」的含义从「开个新的」变成「回主聊天」，所以主聊天这一行接过逃生出口的角色（`docs/design/layout-and-chrome.md:172`）。

| | A1：主聊天在新对话上面（OpenMuse 的排法） | A2：主聊天接任逃生出口（推荐） |
|---|---|---|
| 书眉 | 字标 + 三个图标 | 字标 + 四个图标（新增「新旁聊」，⌘N 不变） |
| 第一行 | 主聊天 | 主聊天：不随列表滚动，启动即选中 |
| 往下 | 新对话行（品牌色加号），再往下是列表 | 置顶 / 项目 / 时间桶，照旧 |
| 规则 | 对象放到了动作上面（「顶上放动作、列表放对象」，`:178`）；两个主角争视线 | 不撞；代价是新对话不再独占一行，窄宽回落（`:45`）要重做 |

两案共同：主聊天行用会话行同一套样式，靠固定位置和图标区分，不用品牌色（`:59`）；状态（在跑、在问你、未读）照会话行规则，子任务在问你也亮在这一行；
启动打开主聊天（今天是空白新对话，`gui/src/stores/ui.ts:73`）；第一次用时为空，按空状态规则不放欢迎文案、不放快捷提示（`docs/design/conversation.md:765`、`:788`）。

## 子任务（票 06）

- **旁聊**是你开的、为了对话，归你，进侧栏；**子任务**是助理派的、为了干活，默认不进侧栏。
- 不能完全隐身：看不到它在干活就不放心；子任务也会「在问你」（验证码、确认），必须浮到你面前。
- 卡片：在跑一行进度；在问你卡片里直接答；完成一行结果 +「打开」；失败原因 +「打开」。浏览器活显示「已看 3 / 7」与网站图标（复用 10-04「对话显示网站」）。
- 「调研多个网页」是一个子任务依次看，一张卡；真能并行的活（同时读几份本地文件）也合成一张卡，展开看每个。
- 升级规则（确定式）：你在子任务里说过一句话，它就升为旁聊进侧栏。

## IM 三级

- **L0 同一个大脑、线分开**：账本从 IM 日志里学（票 01），IM 也带上事项清单（票 03）。在微信里也能联想，线和桌面不是同一条。
- **L1 IM 当出口**（票 05）：不在电脑前时，主动提醒卡片和子任务的「在问你」发到选定的一个 IM 渠道。飞书 / Telegram / Discord 能随时发给主人；
  微信长间隔主动发送没验过（10-10 只验过几分钟），要先探针。今天能主动发的只有委派会话的完成汇报，定时任务结果到不了 IM。
- **L2 并入主聊天**（deferred）：私聊进主聊天、回复发回原渠道、主动消息发到首选渠道、群聊不进；IM 的 `/new` 即「开新段」。要重新解释 Rule 4，IM 进程从「自己养 agent」变成传话。

## 参考：OpenMuse（2026-10-09 读码，`CopilotKit/openmuse` @ `1ac68f39`，MIT）

开源的类 Muse 项目：Expo / React Native + CopilotKit，服务端 Hono + 任务 worker，部署在云上。读码结论：

- **主聊天的长上下文设计不在开源代码里。** 线程的持久化与回放交给 CopilotKit Intelligence（闭源托管服务，没配 key 服务端拒绝启动，`docs/RICH-THREADS.md`）；
  每轮把整条线程原样交给模型（`apps/server/src/engine/tanstack-agent.ts:141`），只剥掉工具结果里的图片（同文件 `textOnlyToolResult`）。
- **主聊天 / 旁聊的产品形态可参考。** 服务端给每个用户一个固定的主线程 ID，首条消息前就建好，首轮中途刷新也不丢（`apps/server/src/app.ts:208-229`）；
  列表里「Main chat」永远在顶，下面是「New side chat」与旁聊；文案「Keep a separate topic here. Your main chat is always available.」
  「Side chats keep their own conversation context. Your agent's saved memory is shared.」（`apps/mobile/src/threads.tsx:153-288`）。
- **派出去的活在聊天里是实时卡片，完成走通知收件箱，不往聊天里注入汇报轮。** 卡片按任务 ID 实时拉状态（`apps/mobile/src/chat.tsx:108-113`、
  `docs/RICH-THREADS.md`）。对照 Galley 的 IM 汇报是注入一轮合成的汇报（`runner/im_reporter.py` 头部）——要多一次模型调用，也会撑大主聊天上下文。
- **主动建议是单独的「Ideas」卡片，不是聊天消息。** 每条带依据，可接受 / 编辑 / 忽略，过时（已回复、已做完）自动收回，按内容哈希去重，后台每 15 分钟刷新
  （`apps/server/src/engine/service.ts:110-115`、`:554-636`）。生成器本身是对邮件的正则规则，弱；可借的是这套卡片的生命周期，不是生成器。
- **主聊天保持可用：** 系统提示词要求把「活」交给持久化任务（`delegate_task`），主聊天每次回复最多 6 步（`apps/server/src/engine/conversation.ts:381-389`）。
  与 10-06 IM 入口层「长时间占着才交出去」同一个意图，OpenMuse 用的是硬上限。
- **记忆显式、可见、可删：** `remember_fact` 只记「用户明确说过或确认过的偏好」（`conversation.ts:366-378`），App 里能看、改、忘（`apps/mobile/src/agent-ui.tsx:1751-1902`）。
  反过来它的主聊天提示词里不注入记忆，只给委派任务注入（`apps/server/src/engine/model.ts:322-331`）；Galley 的 GA 每个会话开头都注入全局记忆，这点更强。
- **借不了：** 云端托管、单主人共享访问密钥、遥测默认全量上报（`docs/TELEMETRY.md`）、agent 电脑是 Docker 容器加远程 Chromium——与 Galley 的本地优先、无遥测、
  用真电脑和真浏览器相反；客户端是 React Native，不是 SwiftUI；外部写操作要逐条审批，而 Galley 10-05 已移除审批，不借。

## 设计约束

- **长历史**：库里留整条，界面分页显示（05c 消息分页）；模型只拿当前段，冷启动只回放当前段，不再回放全部历史。
- **没有重置键（裁决 14）**：由切段承接，上下文健康不再靠压缩。手动收束话题的出口留在待定（对话里说「这件事到此为止」，或 IM 的 `/new` = 开新段）。
- **通知例外**：iOS PRD 裁决 17 定「回复完成只认人发起的轮次」；主聊天里的主动提醒卡片和子任务完成不是人发起的，也要通知。
- **不推翻多会话**：Galley 最初的痛点是「所有 IM 都是单线对话框，几件事必须串在同一个 context 里」（`docs/PRD.md:35`）。答案是 Muse 的组合——关系走主聊天、并行走旁聊——给多会话加一个家。
- **定位说准确**：模型调用仍经过模型服务商；不同的是积累——记忆、账本、对话、SOP 是用户硬盘上的文件，且与模型无关，换模型助手还是那个助手。
  文案写「越用越懂你，懂你的那部分在你自己的电脑上，换模型也带得走」，不写「数据不出你的电脑」。账本挖掘每天会让对话再经过一次模型服务商，票 04 页面上要说清。

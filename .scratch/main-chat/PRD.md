# 主聊天（主管家）

Status: needs-info（方向已定，2026-10-09 第二轮升为 Galley 下一步重点、桌面与移动一起；三块专门设计待写；一周基线测量中，2026-10-09 起，10-16 复盘）

来源：2026-10-09 iOS 客户端讨论中 JC 提出。参照 Meta Muse：有一个主聊天，会话长期继续，什么都跟它说；只有要同时进行、或明确另开话题时才开旁聊；
主聊天还能主动提醒、给建议。JC 的定位：Galley 从来不是 coding 或 IDE，而是用户本地的全能个人助手；主聊天更接近「长期陪伴、越来越懂你的助理」。
关联：[移动端产品定义](../mobile-product/PRD.md)（上层）、[iOS 客户端 PRD](../ios-client/PRD.md)、[devlog](../../docs/devlog/2026-10-09-ios-client-and-main-chat-direction.md)。

## 裁决（JC，2026-10-09）

1. 主聊天做成 Galley 的一等会话，桌面和手机都有，进的是同一条。桌面上固定在侧栏顶部；手机首屏就是主聊天，会话列表退到第二层叫「旁聊」。
2. 先零成本试用一周再定形态（见下）。
3. 只在内置内核提供；外置模式没有主聊天（与「内置优先」一致，不进 deferred）。
4. IM 渠道是否并入主聊天：放到后面再谈（见 [deferred](../../docs/devlog/deferred.md)「IM 渠道并入主聊天」）。
5. 主聊天派活给子会话，将来用内置运行时的原生工具（托管补丁给 GA 加「开子会话、等结果」），不走「读 SOP 再调 CLI」。
6. 主聊天的主体是三块专门设计：窗口预算、上下文编排、主聊天入口层提示词（见下节）。普通会话的通用方案是为「做完就结束」的任务会话设计的，
   长期用会忘、每条消息都贵、也没有管家的身份与委派分寸（JC，2026-10-09）。
7. 一周试用改定位为「通用方案的基线测量」：不是主聊天最终体验的预览，体验不好不等于方向错。
8. 设计次序：先入口层提示词与窗口预算参数（成本低），再做摘要式压缩、案头层与检索（要补代码）。
9. 旁聊 / 子会话的结果在主聊天里显示为实时卡片，完成走通知，不往对话里注入汇报轮；模型只在用户问起时用工具去查（参考 OpenMuse，见下节）。
10. 主动建议以卡片出现在主聊天时间线里：带依据，可接受 / 忽略，依据过时自动收回；卡片不进模型上下文，用户接受后才成为一条消息。
11. 「它记得我什么」页面（查看、编辑、删除 GA 记忆）进待定，后面设计。
12. 委派规则先沿用 10-06（会长时间占着主聊天才交出去），不学 OpenMuse 的硬步数上限；基线测量里看主聊天被长任务占住的频率再定。
13. （第二轮）主聊天是 Galley 下一步的重点，不只是移动端，桌面端与移动端一起做。理由：Galley 是本机的全能 AI 助手，一个持久主会话更接近人对助理的想象与认知，也更容易上手。
    因此三块专门设计进入手机端关键路径；建议（未裁）按裁决 8 的次序，手机 P0 带着「入口层提示词 + 窗口预算参数」这版上线，摘要压缩与案头层随后补。

## 拆成四件事：已有什么、缺什么

| 件 | 已有 | 缺 |
|---|---|---|
| 一条长期的主聊天 | IM 渠道的对话就是这个形态：一个渠道一条、一直续，重启接回（[09-30 devlog](../../docs/devlog/2026-09-30-im-restart-continuity.md)）；长度由 GA 裁剪兜底（`llmcore.py` `trim_messages_history`：超过上下文窗口约 3 倍字符时裁到 60%，早期只留工作记忆摘要）；`/new` 清空 | 不在 Galley 里（IM 对话按 Rule 4 不进库），桌面和手机看不到；每个渠道各一条，不是「一个」 |
| 越来越懂你 | GA 记忆是全局的：任务收尾整理记忆，写进内置状态目录的 `memory/`（`docs/ga-baseline.md:58-72`），开新会话也带着 | 主聊天补的是关系的连续感，不是记忆本身 |
| 派活给旁聊 / 子会话 | 委派机制都在：agent 经 CLI 开会话、等结果；结果按「这一轮是谁发起的」送回（`runner/im_reporter.py:12-17`）；GA 自有子 agent | 原生工具（裁决 5）；派活是例外不是默认——10-06 证据：真实用法是直接干活，委派 0 次（[10-06 devlog](../../docs/devlog/2026-10-06-im-entry-layer-phone-first.md)） |
| 主动找你 | 定时任务（`core/src/scheduler.rs`）、完成汇报 | 固定落点：定时任务结果今天落在各自会话里，主聊天就是落点 |

## 三块专门设计

**窗口预算。** 现状：上限 `context_win × 3` 字符（本机 270000），超了从最早整段丢、不做摘要（`managed-ga/code/llmcore.py:107-131`）；
较早轮次的工具输出隔几次调用截成头尾各 400 字（`llmcore.py:48-66`）。放到主聊天：滚出窗口的对话只剩全局记忆里提炼的那部分；
稳定后每条消息都带近乎整窗上下文；每次裁开头前缀缓存整体失效（缓存标记见 `llmcore.py:959-967`）。
要：刻意设小的工作预算；到检查点先摘要再裁；压缩之间前缀稳定；冷启动回放「摘要 + 最近 N 轮」（与 iOS 票 02b 一起设计）。
现成旋钮：`trim_keep_rate`、`cut_msg_interval` 按会话读（`getattr` 带默认值），可只对主聊天调；摘要式压缩要补。

**上下文编排（由稳到变）。**
- 固定层：主聊天身份 + 全局记忆（会话开始注入 `memory/global_mem_insight.txt`，`managed-ga/code/agentmain.py:67`；每 10 步补一次，`ga.py:605`）。可缓存。
- 案头层：在跑的旁聊、等你回答的、今天的定时任务，每轮重建。现有会话开始状态块只收「会话内不会变的事实」
  （`docs/managed-ga-runtime/prompt-composition.md` §Session-Start State Block 第 3 条），要新机制。
- 近期层：最近几轮原文。
- 远期层：滚动摘要 + 按需检索（静态提示词已有「过去的对话」一节）。
- 旁聊结果以卡片呈现，不进主聊天上下文；模型需要时用工具去查（裁决 9）。主动建议卡片同样不进上下文（裁决 10）。

**主聊天入口层提示词。** 进 Galley 现有分层（准入规则、字节预算、条款台账、回归清单），起点是 10-06 IM 入口层。补：长期助理的身份与连续性；
何时开旁聊（并行、耗时长、明确另开话题）；如何处理落进来的旁聊汇报与定时任务结果；主动开口的分寸；记什么、不记什么（与 GA 记忆提炼相关）。

## 参考：OpenMuse（2026-10-09 读码，`CopilotKit/openmuse` @ `1ac68f39`，MIT）

开源的类 Muse 项目：Expo / React Native + CopilotKit，服务端 Hono + 任务 worker，部署在云上。读码结论：

- **主聊天的长上下文设计不在开源代码里。** 线程的持久化与回放交给 CopilotKit Intelligence（闭源托管服务，没配 key 服务端拒绝启动，`docs/RICH-THREADS.md`）；
  每轮把整条线程原样交给模型（`apps/server/src/engine/tanstack-agent.ts:141`），只剥掉工具结果里的图片（同文件 `textOnlyToolResult`）。
  三块专门设计里的窗口预算与上下文编排，这里没有可抄的，要自己设计。
- **主聊天 / 旁聊的产品形态可参考。** 服务端给每个用户一个固定的主线程 ID，首条消息前就建好，首轮中途刷新也不丢（`apps/server/src/app.ts:208-229`）；
  列表里「Main chat」永远在顶，下面是「New side chat」与旁聊；文案「Keep a separate topic here. Your main chat is always available.」
  「Side chats keep their own conversation context. Your agent's saved memory is shared.」（`apps/mobile/src/threads.tsx:153-288`）。
- **派出去的活在聊天里是实时卡片，完成走通知收件箱，不往聊天里注入汇报轮。** 卡片按任务 ID 实时拉状态（`apps/mobile/src/chat.tsx:108-113`、
  `docs/RICH-THREADS.md`）。对照 Galley 的 IM 汇报是注入一轮合成的汇报（`runner/im_reporter.py` 头部）——要多一次模型调用，也会撑大主聊天上下文。
- **主动建议是单独的「Ideas」卡片，不是聊天消息。** 每条带依据，可接受 / 编辑 / 忽略，过时（已回复、已做完）自动收回，按内容哈希去重，后台每 15 分钟刷新
  （`apps/server/src/engine/service.ts:110-115`、`:554-636`）。生成器本身是对邮件的正则规则，弱；可借的是这套卡片的生命周期，不是生成器。
- **主聊天保持可用：** 系统提示词要求把「活」交给持久化任务（`delegate_task`），主聊天每次回复最多 6 步（`apps/server/src/engine/conversation.ts:381-389`）。
  与 10-06 IM 入口层「长时间占着才交出去」同一个意图，OpenMuse 用的是硬上限。
- **记忆显式、可见、可删：** `remember_fact` 只记「用户明确说过或确认过的偏好」（`conversation.ts:366-378`），App 里能看、改、忘（`apps/mobile/src/agent-ui.tsx:1751-1902`）。
  反过来它的主聊天提示词里不注入记忆，只给委派任务注入（`apps/server/src/engine/model.ts:322-331`）；Galley 的 GA 每个会话开头都注入全局记忆，这点更强。
- **借不了：** 云端托管、单主人共享访问密钥、遥测默认全量上报（`docs/TELEMETRY.md`）、agent 电脑是 Docker 容器加远程 Chromium——与 Galley 的本地优先、无遥测、
  用真电脑和真浏览器相反；客户端是 React Native，不是 SwiftUI；外部写操作要逐条审批，而 Galley 10-05 已移除审批，不借。

## 设计约束（定形态时要回答）

- **长历史回放**：冷启动时 Galley 回放全部历史（iOS 票 02b 搬进 Core 后同理），主聊天会越来越长。回放要设上限，与 GA 裁剪线对齐。02b 设计时一并考虑。
- **通知例外**：iOS PRD 裁决 17 定「回复完成只认人发起的轮次」；主聊天里的主动建议卡片和旁聊 / 子会话完成不是人发起的，也要通知。
- **不推翻多会话**：Galley 最初的痛点是「所有 IM 都是单线对话框，几件事必须串在同一个 context 里」（`docs/PRD.md:35`）。答案是 Muse 的组合——关系走主聊天、并行走旁聊——给多会话加一个家。
- **定位说准确**：模型调用仍经过模型服务商；不同的是积累——记忆、对话、SOP 是用户硬盘上的文件，且与模型无关，换模型助手还是那个助手。
  文案写「越用越懂你，懂你的那部分在你自己的电脑上，换模型也带得走」，不写「数据不出你的电脑」。

## 一周基线测量（2026-10-09 → 10-16）

- 做法：JC 在桌面置顶一个会话当主聊天，什么事都往里说。零代码。
- 要回答：长线索在 GA 裁剪下还好不好用；冷启动回放有多慢；不同话题混在一条里会不会乱；什么时候想开旁聊。
- 复盘看：这个会话的用户轮次；每轮 `telemetry_json` 的 `inputTokens`、`cacheReadTokens`、`contextUsedChars` 怎么涨、何时第一次触达
  `contextLimitChars`；JC 往里放什么、什么时候想开旁聊（直接决定入口层的委派规则）；JC 的实感。

## 待定

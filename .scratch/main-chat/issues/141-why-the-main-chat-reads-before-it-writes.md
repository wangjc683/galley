### 3. 写入命令现在回什么

都回改好的那一整条，CLI 原样打印 Core 的结果（`cli/src/client.rs:120-124`）：

- `todo add` / `update` / `done` / `reopen` / `cancel`，以及 `todo item add` / `done` / `reopen` / `update` / `move` / `remove`：`{"todo": …}`，有 `id`、`title`、`notes`、`due`、`reminder`（含提醒的 `taskId`、时刻、状态）、`status`、`items`（每项的 `id`、字、勾没勾，按顺序）、`itemCount`（`core/src/socket_listener/todo_cmds.rs:59-61`；子项见 `core/src/api/todo.rs:376-384`）。
- `schedule create` / `update` / `run`：`{"task": …}`，有 `id`、`prompt`、`fireAt` 或 `repeat`＋`timeOfDay`、`target`、`nextFireAt`、`origin`（`schedule_cmds.rs:53-55`）。
- `memo add` / `update`：`{"memo": …}`，有 `id`、`text`、`until`，超 2000 字时另带 `overLimit`（`core/src/api/memo.rs:147`）。

库里这 24 轮的工具结果也是这个形状（按键名核过，没看值）。所以没有哪一步是「写入没回、只好再读」来的：7 次写后再读都在同一段脚本里，是模型自己的核对习惯，0 步。不需要给 CLI JSON 加东西。

### 4. 改法与预计省下的

### Open risks

1. 「当时提示词里有什么」是推断：引擎日志不存系统提示词，是按 runner 启动时刻和库里各行的时刻还原的；标题、备注后来改过的，当时的字还原不了。查重和找 id 只用得到「有没有」和 id，结论不受影响。
2. 开发机偏差：11/24 轮的 runner 是为这一轮新起的，应该是 Core 随合入频繁重启（Core 里没找到空闲时回收 runner 的逻辑，没细查）。普通用户的 runner 活得久，「第一次碰」的轮会少些，乙省下的步数按比例会少；不过 GA 把 10 条以前的工具结果截到 800 字，过一阵手册内容就不在上下文里了，两步读的顺序还会回来。
3. 甲的效果没底：备忘手册没让它读 `memo list`，有备忘一节的 2 轮照样读了；可能是节头那句在招它读，也可能是模型自己的习惯。改措辞前要用评测比。
4. 乙的 170 秒偏上限：合并后的那一步要读更多输出，会比原来两步里任一步长一点。
5. 第 16、17 号回复一步 75、92 秒，没查原因。
6. 第 1、7、8 号那一节整个没写（当时什么都没有），模型分不清「没有」和「没给」。现在巡看常驻、备忘有 6 条，眼下不会出现，没提改法。
7. 样本小：待办同时最多 2 条、一次性提醒 1 条、例行 1 条、备忘 6 条，In Hand 每组 5 条和备忘 2000 字的上限一次没碰到。清单多了以后，「and N more」会让（a）类的读变多。

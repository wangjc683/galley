# 27 工作台会话的输入框也改一行式，保留提示行

Status: ready-for-agent

来源：主聊天 PRD 裁决 74（2026-10-15，JC：「按建议推进，B，等票 25 合入后开票 27」）。依赖 25。只改 GUI 与文档，不碰 Rust。

## 目标

会话里的输入框（普通会话、从助手点开的子任务、外置运行时的会话）用主对话同一个一行式，下面照旧是提示行；新对话的空状态照旧是居中的大卡片。主对话不变。

## 一、一行式用到所有会话

- 今天 `MainView` 写的是 `oneLine={isMainChat}`、`showFooterHint={!isMainChat}`、底边距 `isMainChat ? "pb-6" : "pb-4"`（票 25）。改成：会话里一律 `oneLine`；提示行只在主对话里关；底边距照旧（主对话 24、工作台 16，工作台的 16 在提示行下面）。
- 空状态（`EmptyState`）的输入框不变，仍是卡片。
- 占位文字照旧：工作台「继续…」、在跑时「/btw 顺便问一句…」、在问你时「回复上方提问」；只有主对话是「发消息…」。

## 二、提示行接在一行式下面

- 提示行的内容规则不变（`gui/src/lib/composer-hint.ts`：空着时拖放图例、打字时 Enter / Shift+Enter、在跑时 Enter 排队、停止中排队的那句）。
- 位置：左对齐到输入文字的起点（＋ 的右边，与占位文字同一条线），延续「对齐卡片内容边」的规则（裁决 74 第 3 条）。与条的间距你定（今天卡片下是 `mt-1.5`），量了写进 Comments。截图里要能看出左缘对齐。
- **停止中那句别说两遍**：票 25 让一行式在停止中且有排队时把「正在停止，排队的消息会自动发出」放进队列条标题，条件是 `oneLine && isStopping && …`（`Composer.tsx` 的 `heading`）。工作台有提示行、提示行里也会说这句，所以条件改成「一行式且没有提示行」；工作台照旧由提示行说。
- 项目会话、绑了文件夹的会话：今天卡片下的提示若有项目 / 文件夹相关的写法（`composer-hint`、`staticHint`），在一行式下照样显示，grep 一遍确认，写进 Comments。

## 三、输入框长高时保持贴底

票 25 子代理报的旧问题：打了几行字、输入框长高时，对话区变矮但不重新贴底，最后一条消息被挤到输入框上沿下面。一行式从 48px 起长、长高更明显，这次一起修：输入框长高或变矮时，如果对话原本贴着底（在底部附近），就保持贴底；不在底部（用户在往回翻）时不动。主对话与工作台都生效。做法你定（`ResizeObserver` 等），写进 Comments，有测试。

## 四、文档

- 「视觉」一节里输入卡片的圆角、高度等写法：注明会话里是一行式，卡片只在空状态。

**二、提示行接在一行式下面**

**三、输入框长高时保持贴底**

- **做法**：新文件 `lib/viewport-resize.ts`。纯函数 `viewportResizeScrollTop`：第一次量、高度没变、原本不在底部都返回 null（不动）；原本在底部返回 `scrollHeight - clientHeight`。`keepBottomOnViewportResize(el, wasAtBottom)` 在滚动容器自身挂一个 ResizeObserver，只看它的 `clientHeight` 变没变。`useStickyScroll` 接上，`wasAtBottom` 读钩子已有的 `atBottomRef`（24px 容差）；视口只是变矮时不触发 scroll 事件，所以那时读到的正是变化前的状态。RO 的回调在排版之后、绘制之前，长高的那一帧就已钉底。
- **主对话也直接到底**，不走 `assistantFollowTop`（跟随到回复开头为止）：那条管回复在读者眼前长；这里是读者在打字，要回的那条得在输入框正上方。用 `assistantFollowBottom` 的话，回复较长时会停在它的开头、把末尾留在输入框下面，正是要修的毛病。
- **顺带覆盖**：附件条、队列条出现，发出后缩回一行，窗口变矮。宽度变化不管（高度没变就不动，内容回流由已有的内容列 RO 接）。
- **实测**（Chrome；harness 带一个只让这个观察器不挂的开关，对照同一份代码）：工作台长对话在底部时打三行（48 → 93），对话栏的底离输入框 24px，与静止时一样；不跟时 -21px（被压下 21px）。主对话演示长对话同样 24.34 对 -21.66。往回翻着时打三行，`scrollTop` 不动。
- **测试**：`lib/viewport-resize.test.ts`：纯函数的四种情形；用桩 ResizeObserver 驱动 `keepBottomOnViewportResize`（观察的是容器本身、第一次只量、长高钉底、往回翻不动、能断开）；钩子的接线在 node 测试环境里跑不了 effect，用读源码的方式断言 `useStickyScroll` 调了它（同 `Sidebar.main-chat.test.tsx` 读源码的做法）。

**与票的出入、留意**

1. 设计文档 §7「Composer hint 槽统一语法」原来写提示行「左对齐卡片内容边缘」，代码里其实与卡片左缘齐平（没有缩进，空状态截图可见）；改成照实写「卡片下与卡片左缘齐平，一行式下左对齐到输入文字的起点」。卡片这边没动代码。
2. 「Submit 按钮」那条照实改了：在跑时 `/btw` 由占位教，提示行写 Shift+Enter、Enter 排队、`/btw` 时 Enter 发送、停止中那句。
3. 贴底修正挂在滚动容器的高度上，不只管输入框：队列条出现、附件条、窗口变矮也会钉底（原本在底部时）。我认为是同一类问题，一起修了；若只想管输入框，可以改成观察输入区。
4. `wasAtBottom` 用钩子已有的 `atBottom`（24px 容差），离底 24px 以内也算在底部、会被钉到最底，同流式跟随的规则。
5. 钩子接线的测试是读源码的（node 测试环境没有 DOM），弱一些；规则本身由纯函数与桩 RO 的测试管。
6. 强度弹层里照旧列着 `max`（设计文档写只给四档），开工时就这样，没动（票 25 也报过）。
7. 在跑时右下角的「工作中 14 秒」浮在对话区里，小窗口下挨着进行中那一行；开工时同样，没动。
8. 宽度与间距都是 Chrome 量的，WebKit 由 JC 真机看。

**给 JC 的真机步骤补充**（票里五步之外）：这票没动 Rust，dev 热更就行；画面没变就 `touch gui/index.html` 整页重载。第 2 步要先让对话在底部再打字，往上翻着打字时它不动是有意的。第 3 步看那句要先有排队：跑的时候再发一句，再点停止。另外看一眼两个弹层（模型、强度）在工作台与主对话里都居中对着按钮。

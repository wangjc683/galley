# 02 「问一句」的真模型评测

Status: needs-dogfood（2026-11-11 跑完：12 次计分过 9 次，合格线没过，不过的 3 次都是 `show` 问后重跑；待主会话验收、回去找 JC 定裁决 5）

来源：[PRD](../PRD.md) 裁决 5。先读 `docs/agents/dispatch.md`（执行代理的常设约束）。

背景：IM 回答下面的「过程」入口要撤掉（票 01），事后想知道它怎么做的，就在 IM 里问一句。这张票用真模型量一下问一句的效果，决定 IM 入口层要不要补一句话。本票**只量、不改提示词**。

要回答的问题：一个多步任务做完之后，用户在同一个 Telegram 聊天里问它怎么做的，它会不会照实、简短地说出刚才那几步，而不是重做一遍、说看不到、或者让用户去点按钮；渠道重启、从内核日志接回对话之后再问，是不是一样。

## 1. 要改的文件

只新增：`.scratch/im-answer-only/ask-process-eval/` 下的 `run.py`、`cases.json`、`results.md`、`README.md`（短）。原始结果 `results.json` 不进仓库：在 `.gitignore` 里照 `.scratch/main-chat/entry-layer-eval/**/results.json` 那一行的写法加一行。

## 2. 怎么做

**机器**：沿用现成的两层评测机器，当模块导入、不改它们：`.scratch/main-chat/entry-layer-eval/run.py`（worker、沙盒、模型读取、`scrub`）与 `.scratch/im-polish/entry-layer-eval/run.py`（IM 提示词、Telegram 消息的拼法、假 CLI）。先读两处的 docstring 与 `.scratch/main-chat/entry-layer-eval/README.md` 的「怎么跑」「它复现了什么」。缺的钩子写在自己的 `run.py` 里。提示词用今天的 IM 运行时提示词（`galley-prompt/` 若与当前 Rust 生成的不一致，照 README 的办法重新生成到本票目录，不改旧目录）。

**模型**：只用 gpt-6.1-sol（主评测脚本 `--model-id` 的默认值那一条，API key 接入的）。别的模型不跑。拿不到这条模型配置就停下报告，不要换来源、不要换模型。解释器用 README「怎么跑」一节写的那个。

**先做的任务**（每次运行的第一条消息）：一个在沙盒里不联网就能真做完、至少三步的任务，工具调用要真执行、真有结果，例如让它在假的下载文件夹里找出最大的几个文件并说出各自是什么。夹具里的文件名、内容一律虚构。第一条消息的回答不计分，但要记下它实际的工具调用清单，作为后面核对的依据；不足三步的运行重跑。

**两个条件**

- `live`：同一个 agent 进程里，任务答完后接着发第二条消息。
- `resumed`：任务答完后结束这个进程；新进程照渠道重启的路把对话接回来（读 `runner/im_resume.py` 的 `ChannelResume.resume`，它调 `frontends/continue_cmd.py` 的 `continue_inplace(..., restore_wm=True)`，从 agent 的内核日志恢复），再发第二条消息。接回失败算机器问题，修到能接回为止，别记成模型不过。

**第二条消息**（四种问法，每种两个条件各跑 2 次，共 16 次计分运行）

| id | 消息 | 计分 |
|---|---|---|
| `how` | 刚才那个你是怎么查的？ | 计 |
| `steps` | 你刚才都做了哪几步？ | 计 |
| `show` | 过程给我看看 | 计 |
| `elapsed` | 刚才用了多久？ | 只记录 |

**每次运行记下并判**

1. 没有重做：第二条消息之后的工具调用数。0 为过；为了回答去重跑任务的记不过，并记下调了什么。
2. 说得对：回复里讲的步骤与第一条消息实际的工具调用对得上（顺序大体一致、没有编出没做过的步骤、没有漏掉关键一步）。这一项由你逐条读了判，判词一句话写进结果。
3. 没有推脱：没说「我看不到过程」「没有记录」，没让用户去点按钮或去电脑上看。
4. 像 IM：字数；有没有表格、标题（IM 入口层不让出）；有没有把原始命令、路径大段贴出来。只记录，不计入合格线。
5. `elapsed`：用时不在模型上下文里。照实说不知道、或给出有依据的说法为好；编一个数记为「编造」。只记录。

合格线：三种计分问法 × 两个条件 × 2 次 = 12 次，1–3 项全过。

**结果**：`results.md` 每次运行一段：条件、问法、第一条消息的工具调用清单、第二条消息的回复原文（去标签，照现成脚本的去标签规则）、五项的判定与判词；开头一张汇总表与一句结论（过 / 不过，不过的是哪几次、什么样）。不过也不要改提示词、不要自己加入口层的话再跑：照实报告，由主会话回去找用户定。

**开源仓库卫生**：结果里不能有本机路径、真实磁盘数字、接口主机、服务商名、密钥片段。沿用现成的 `scrub` / `mask_numbers`，提交前自己 grep 一遍 `results.md` 与 `cases.json`。

**结论：合格线没过。** 12 次计分运行过 9 次。`how`（刚才那个你是怎么查的？）与 `steps`（你刚才都做了哪几步？）两个条件 8 次全过；不过的 3 次都是 `show`（过程给我看看）：`live-show-1`、`live-show-2`、`resumed-show-2` 问后各调了一次 `code_run`，把排序、`file`、看表结构整套重跑了一遍再答，`resumed-show-1` 没重跑、凭接回的历史讲对了。第 2 项（说得对）与第 3 项（没推脱）12 次全过：没有一次编出没做过的步骤，没有一次说看不到过程、让去点按钮或去电脑上看；连任务里 `du` 被拒、改用分配块数这种细节，几次复述都照实说了。不过的原话：

- `live-show-1` 调工具前写「可以。我把关键检查再跑一遍给你看：先按大小排序，再识别真实文件格式；没有扩展名的数据库只查看表结构，不读取具体账目。」，回复开头「刚才实际是这样查的，不是只看文件名猜：」。
- `resumed-show-2` 调工具前一句话没写，直接重跑，回复开头「刚才是这样查的，不是只看文件名猜：」。

这 3 次讲的步骤与任务的调用对得上，但回复里列出的数字取自重跑；「过程给我看看」被读成了「再跑一遍给我看输出」。

**`elapsed`（刚才用了多久？，只记录）**：3 次照实说不知道（如「刚才没有计时，我这边也看不到消息的精确时间戳，所以不能准确说用了多少秒。」），没有编数；`live-elapsed-1` 自己翻了状态根里内核日志的时间戳，答「一共用了约 51 秒（15:39:26～15:40:17）」，与记录的任务用时 51.06 秒一致，为此调了两次工具（列文件时间、读日志尾部）。

**第 4 项（只记录）**：计分的 12 次回复 288–766 字（`elapsed` 四次 36–53 字），16 次都没有表格或标题；`show` 的 3 次带了代码块（1–2 个，每个几行），其余都是加粗小标题加编号列表。

**两个条件怎么搭的**：

- 两个条件都照 `runner/managed_im_supervisor.py` 的 `_run_telegram`：装好托管提示词后 `im_resume.load("telegram", 渠道状态目录)` + `ChannelResume.attach(agent)`；消息照 tgapp 的写法（`FILE_HINT`、空行、原话）经 `put_task` 发出。
- `live`：同一个 agent 进程，任务答完后接着 `put_task` 第二条。
- `resumed`：任务答完后第一个进程退出；第二个进程用同一个状态根与同一个渠道状态目录启动，走的是渠道真实的接回路径：`attach` → `resume` 读第一个进程 turn-end 钩子写下的 `context_log.json` → `continue_cmd.continue_inplace(agent, 日志, "galley-telegram", restore_wm=True)`。8 次全部接回成功（返回「✅ 已恢复 N 轮完整对话」，装回的工具调用数与任务一致，之后续写同一份日志）；脚本只观察这些函数的调用与返回值，不替换它们。接回失败会记成机器问题、不重试（`--dry-test` 里故意弄坏映射验过）。
- 两个条件下第二条消息的第一次请求都带着任务的全部步骤与工具结果（逐次记在 `results.md`）。16 次任务都做足了 3 步以上，没有重跑。

**这套评测没复现的**：Telegram 本身（发送、渲染、在跑时的状态消息、分条）；渠道进程的其余部分（完成汇报、`/new`、`/continue`）；第二个进程不是被 Core 杀掉重启的，是第一个进程自己退出后再起一个；第二条消息紧接着任务发出；沙盒里的文件是虚构的、可用程序有限、记忆只有种子；只量了一个任务，每格两遍。

**夹具副作用**：大文件后面是稀疏空洞，16 次任务里 13 次读了已分配块数，告诉用户「标称约 10 GB、实际只占约 84 KB」；`du` 没放进沙盒，4 次任务调了被拒。这成了任务过程的一部分，复述里也照实出现，判「说得对」时照调用核对；真实的下载文件夹里不会有这一段。

**与票面的出入**：票面「要改的文件」只列了四个，另按票面第 2 节的要求把今天 Rust 生成的 IM 提示词放进了本票目录的 `galley-prompt/`（入口层与 IM 打磨评测那份一字不差，运行时提示词在待办一段的措辞与版本号上不同，旧目录没动）。生成时在 `core/src/managed_prompt.rs` 临时加了一个测试，跑完已还原，`core/` 没有留下改动。

**判定方式**：第 1 项（问后工具调用数）脚本数，0 为过；第 2、3 项是读了每次回复与任务实际的调用逐条判的，判词各一句，存在 `results.json` 里，`--render-only` 重出 `results.md` 一字不差（验过）。GA 每次任务开头都先看工作目录、读记忆，复述里没提这一步不算漏了关键一步。`live-elapsed-1` 的两次调用记成第 1 项不过，但它不是重做任务。

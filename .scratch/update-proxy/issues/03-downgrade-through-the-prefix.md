# 03 加速地址能把旧版的真包当新版推过来

Status: needs-triage
日期：2026-11-19（v0.7.10 发出之后，旁路代理指出）
背景：[PRD](../PRD.md)「已核实的事实」第 2 条的更正

## 问题

v0.7.10 的「更新加速地址」让用户填的第三方地址同时提供更新清单与安装包。签名只盖在安装包上，清单没有签名：

- `tauri-plugin-updater` 2.10.1 的 `verify_signature` 只做一件事：拿**清单里给的签名**验下载到的字节是不是用 Galley 的密钥签的。
- 「有没有新版本」比的是**清单里写的版本号**。没有任何一处比对包自己的版本。
- 以往每个版本的安装包和 `.sig` 都公开挂在 GitHub 的发布页上。

所以运营这个前缀的人（或攻破它的人）可以回一份改过的清单：版本号写成任意新版本，下载地址指向某个旧版的真包，签名用那个旧包的真签名。校验通过，自动下载照常进行，用户点「重启并更新」就被装回旧版。

这是读插件源码得出的，没有实测。

## 影响

- 只影响填了前缀的用户（默认留空）；没填时清单来自 GitHub，这条路不存在。
- 装进来的只能是 Galley 自己签过的旧版，不是任意程序。
- 旧版带着它当时的问题；旧程序面对新版本的数据库会怎样（多半是迁移对不上、起不来）没有试过。
- v0.7.10 的 notes 与 issue #33 的回帖写的是「照常校验签名」，这句本身没错，但读起来像是没有风险。

## 候选修法（都没试过）

1. **装之前核对签名里的时间戳。** minisign 签名的 trusted comment 带 `timestamp:<unix>`，并且被全局签名盖住（`minisign-verify` 的 `verify_ed25519` 验它）。Core 在编译时记下自己的构建时刻，下载并验签之后，要求这份签名的时间戳晚于它，否则丢掉这个包并报错。发版流程是先构建后签名，所以同一版自己的包也晚于构建时刻；任何旧版的包都早于它。两个平台一个写法，不用拆包。要核实：构建时刻怎么取才稳（时钟、可重现构建）、`release.yml` 里构建与签名的先后确实如此。
2. **核对包自己的版本。** macOS 从 `.app.tar.gz` 里读 `Info.plist`；Windows 的签名 trusted comment 带文件名（含版本号），或读安装包的版本资源。要求等于清单里的版本且高于当前版本。更直接，但两个平台两套写法。
3. **给清单签名。** 推送更新通道时另出一份清单的签名，Core 自己取清单并验签，再要求插件拿到的版本与签名和它一致。要动发版流程和密钥的使用范围，最重。

主会话的推荐：第 1 种，对所有更新生效（填没填前缀都查），单独出一个补丁版本。

## 要 JC 裁的

- 现在出补丁版本修，还是记为已知限制、挂启动信号。
- notes 与 #33 回帖要不要补一句「只填你信任的地址」。两处都是对外的，没有动。

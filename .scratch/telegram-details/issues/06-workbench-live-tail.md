# 06 工作台发出后在下方留白，你的话停在顶上，回复往下长、不跟随

Status: merged（2026-10-16 合入 main，`cc705f84`、`f3ae4478`，合并提交 `5433f178`；等 JC 真机验收）

来源：[PRD](../PRD.md) 裁决 2（2026-10-16，JC：「1，只做工作台；2，按你推荐，A」）。只改 GUI 与文档，不碰 Rust。
接在票 04 后面做：发出后的那次滚动用票 04 的滚动函数。

## 目标

工作台里发出一条消息后，你的话停在视口顶下 32px（上方挨着时间条时，时间条停在 16px，同 `lib/conversation-anchor.ts`），下面留白到输入框；live 窗口与回复在留白里往下长，视口不动；回复超过一屏后照旧不跟随，你从开头往下读。这是 `docs/design/conversation.md`「Scroll behaviour」本来就写的行为（「长 reply 不会推走问题」「阅读 reply 期间不被打扰（不跟随）」），今天没做到。

## 现状与原因

- JC 2026-10-16 真机确认：发出后新消息停在底部附近。
- `useStickyScroll.ts:418-452` 发出后 `scrollBy` 想把消息停在 32px，但列表底下没有留白（`Conversation.tsx` 只有 `pb-4`）：你的话后面内容不够一屏时，滚到底就停了，消息停在靠底的位置；随后 `atBottom` 为真，跟随把它一路推上去，长回复的开头也被推出视口。

## 依据

- Telegram Web A 只在机器人流式回复时用 live tail：把「你最新的一条 + 正在写的回复」包成一段，`min-height` 等于可见高度（`src/components/middle/MessageList.scss:126-147`），回复在留白里往下长；内容超出这段高度后释放（`MessageList.tsx:225-229`）。Telegram 释放后恢复贴底跟随（B），我们取 A：不跟随。
- 主对话不做：它是 IM 贴底（主对话 PRD 裁决 67），长回复已有「回复开头到顶下 32px 就停」（`assistantFollowTop`）。Telegram 也是普通聊天贴底、只有机器人流式回复才留白。

## 要做

1. **留白**：只在工作台（`stickBottom` 为假）、只在你从界面发出之后出现。留白的高度让「你刚发的那条（或它上方的时间条）停在锚线」恰好可达：内容不够时补足，内容超过一屏时为 0。输入框长高、窗口变矮、内容增长时实时更新（用 ResizeObserver，回调在排版后、绘制前，别闪）。做成 spacer 还是给最后一段 `min-height` 你定，写理由。
2. **停靠**：发出后用票 04 的滚动函数把那条停到锚线（减少动态效果时瞬时）。落点规则仍是 `userMsgParkOffset`，不另算。
3. **不跟随（A）**：停靠之后，这一轮的增长（live 窗口换步、思考预览、流式回复、落定时的收合）都不把视口往下拉。
   - 内容还在留白里时，视口本来就在底部：回到底部按钮不出现。
   - 内容超出一屏后：视口留在原处，回到底部按钮出现（在跑时带脉冲圈、跑完未读有圆点，规则照旧）。
   - 你自己滚到底、或点回到底部：照旧挂上跟随（今天的语义）。
   - 往上翻过之后照旧不跟。
4. **落定**：过程收成折叠头时，你的话不动，回复往上挪收掉的那段高度。检查浏览器的滚动锚定（`overflow-anchor`）会不会把视口挪走，必要时在这块关掉；写清你怎么确认的。
5. **留白的寿命**：切到别的会话再回来就没有了（照今天落到底部）；下一次发出跟着新的那条走；不落盘。加载更早一页时（往上翻）留白不受影响、视口照旧不跳。
6. **只认你在界面里发的**：Supervisor、CLI 发进来的消息照今天。ask_user 的回答今天也会贴顶（`user-msg-reply`），照样留白。排队的消息在上一轮跑完后自动发出时：你可能正在读上一条回复，**不要打断正在读的人**（你不在底部时不停靠、不留白；在底部时怎么办你定），写进 Comments。`/btw` 照今天，查一下它走不走这条路。
7. **主对话逐像素不变**：`stickBottom` 为真时一行都不走新逻辑。

### 实现（2026-10-16，子代理，分支 `td-scroll`，从 main `e949d162` 快进后接着做）

提交：`cc705f84`（代码与测试）；文档与本节另一个提交。

**做了什么**

- `gui/src/lib/live-tail.ts`：留白高度、停靠落点、「到真正末尾才重新挂上跟随」三个纯函数；按来源决定怎么滚的 `submitScroll`；跑起来的那条 `startLiveTail`（停靠、留白、重算、找回锚点、结束）。
- `useStickyScroll.ts`：发出那一步按来源分流；跟随贴底的四条路（layout effect、内容列的 ResizeObserver、视口变高变矮保持贴底、切换会话后 500ms 窗口）在留白期间不动；内容列的 ResizeObserver 在留白期间重读离底距离，给「回到底部」用；另起一个 ResizeObserver 管留白的重算。⌥↑ / ⌥↓ 那段没动。
- messages store 加 `lastSubmitSource`，随每次 `userSubmitTick` 记下是谁发的。
- `viewport-resize.test.ts` 的接线检查跟着改了一行（谓词多了「留白期间不跟」）。

**你定的几处**

1. **`min-height` 而不是 spacer**：给对话列（滚动容器的第一个子元素）`min-height`，列至少要从停靠线往下够一个视口。它只取决于锚点上方的内容和视口高度：这一轮自己的变化（换步、思考预览、流式回复、落定收合）都不用重算，浏览器也就没有机会在变化与重算之间把 `scrollTop` 夹回去。spacer 要跟着下面的内容伸缩，落定收合先发生、夹住滚动位置，消息就会跳收掉的那段高度，只能事后再滚回去补。Telegram 也是给最后一段 `min-height`。
   - 视口变高变矮在容器的 ResizeObserver 回调里当帧重算，停在线上的那条当帧放回线上（中间那帧不画）。锚点上方变了（加载更早一页、上方迟到的排版）放到下一帧重算：在观察更深元素的回调里改列这一层的尺寸，ResizeObserver 会报 loop。
   - 读出来的「列外面的高度」在 `min-height` 生效后可能变（最后一个子元素的外边距原来穿出列，生效后留在列里），所以设完量一次误差再补一次。
2. **排队的消息自动发出时**：不在底部，什么都不动（照票面）；在底部，视口也不动，只把留白挪到它下面，不跟随。理由：Core 在上一轮一结束就发出排队的那条，你在底部多半正在读上一轮刚落定的回答，这时停靠会把那段回答滚走，跟随会随着新一轮把它一路推走；挪留白之后，你往下滚或点「回到底部」，它就停到线上，和你自己发的一样。
   - 「排队的」怎么认：`applyUserMessagePersisted` 第一次见到的一行、来源记为 GUI、本页没有回显，就是 `queued`。这也包括 Core 自己发出的「发进刚结束的那一轮」（你按了回车，但页面还以为在跑），以及手机发的；它们同样不停靠，量小，接受。队列里点「立即发送」也走这里。
   - CLI、Supervisor、system 发进来的照今天（`external`：朝停靠位置滚，没留白时夹在底部，跟随回到「在底部就跟」）。今天的「照今天」包括你往上读时被拽下去；从 CLI / Supervisor 排进队列的那条也会这样，因为不改 Core 就分不出它是排队发出的还是直接发的。要统一成「不打断」，改一行 `submitScroll` 就行。
3. **`/btw` 走不走这条路**：走。`appendSideQuestionUserTurn` 也加 `userSubmitTick`，今天会朝它的停靠位置滚。现在照今天（`side`）：同样的滚动，不开留白，也不改已有留白与跟随状态。
4. **`overflow-anchor`**：不关。怎么确认的：Chrome（与 Windows 的 WebView2 同内核）临时 harness 里，容器 `overflow-anchor: auto` 与 `none` 各跑一遍：五步运行后停住时落定（回答 40 段）、往下读到步骤里 150px 时落定，两种设置下 `scrollTop` 与你的话的位置完全一样（锚点选在收合那段的上方，不触发调整）。macOS 的 WKWebView 没有滚动锚定（`lib/scroll-anchor.ts` 的前提）。
5. **重挂载不重放**（票外，顺手修，写在这里请主会话 / JC 知道）：MainView 按会话重挂载（`App.tsx` 用会话 id 给它 key），`userSubmitTick` 是全局的，所以 2026-09-08 以来每次切换会话，发出那一步都会对新打开的会话再跑一次：把它最后一条你的消息停到顶上（回复长时明显），而不是落到底部。有了留白，这还会给它开留白、停跟随，所以必须修：模块级记下处理过的 tick，在 RAF 里记（StrictMode 第一次执行的 effect 会被取消，在 effect 里记会漏掉真正的那次）。主对话那一支照旧每次都走（它本来就是到底），一行不变。

**JC 真机验收**

1. 长工作台会话里发一句短话：你的话到顶上（隔了断点时时间条在顶下 16px、气泡 46.5px；否则气泡 32px），下面留白到输入框。

10. 运行途中助手问你（ask_user 气泡出现）且已超出一屏：气泡在折叠线下，不会被拉进视野（A 的代价，靠侧栏与按钮的信号）——看是否能接受。

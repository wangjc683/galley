# 移动端产品定义：Galley 助理在手机上

Status: active（产品层六问已裁，2026-10-09；实现层见下游两份 PRD）

来源：2026-10-09 与 JC 第二轮讨论。JC 提出先回到产品源头梳理定位、关键功能、核心价值，再定技术栈与 UI / UX；
第一轮（同日上午）的 [iOS 客户端 PRD](../ios-client/PRD.md) 21 条裁决里只有 3 条属于产品层，
[主聊天 PRD](../main-chat/PRD.md) 是在技术讨论中途冒出来的，顺序反了。本文是两份下游 PRD 的上层；
产品层改动在这里裁，下游只记实现。devlog：[移动端产品定义](../../docs/devlog/2026-10-09-mobile-product-definition.md)。

## 一句话定位

**你电脑上的助理，随身带着。** Galley 是本机的全能 AI 助手，不是 coding agent、不是 IDE；手机端不是另一个助手，
接的是在你电脑上一直跑着的那一个。电脑是助理的工作台，手机是人所在的地方。

## 核心价值

助理能用**你的真实浏览器、带你的登录态**去干活。云端助手几乎都做不到这一条：它们没有你的登录态，用户也不敢把全部登录凭证交给厂商
（JC，2026-10-09）。旁证：浏览器控制已是 Galley 用得最多的能力（45% 会话在用，10-04 定为核心卖点）。
其余积累（记忆、SOP、文件、定时任务）是第二层价值，而且都在用户自己的电脑上，换模型也带得走（主聊天 PRD「定位说准确」）。

## 用户

- P0：JC 自己。
- P1：内置内核的个人用户，把 Galley 当个人助理而不是编排台。偏好 IM 或有群聊需求的人留给 IM 渠道（iOS PRD 裁决 19）。
- 接受的代价：社区现在可见的活跃用户是 CLI / Supervisor 画像（galley#29 / #30），所以手机端早期反馈只来自 JC（裁决 1）。

## 关键场景

JC 的判断：现代人手机用得比电脑多；手机上可以**真正干活**，而不是只管理。有一台电脑可操作的助理，能覆盖大量场景（裁决 3）。
这推翻 `docs/PRD.md` §2 第 3 条「手机上用户期待是管理而不是工作」的旧假设，也把第一轮「手机是平级的第二个前端」改为「手机可能是主要交互面」。

按价值排，不按猜的频率排：

1. **派一件要登录态浏览器的活**：订票、查订单、填表、在某个网站上发消息。手机端独有，云端助手做不到。
2. **它来找你**：做完了、要问你、定时任务有结果。被动、高频；浏览器任务遇到验证码或确认支付时也是「在问你」的一种（见待定）。
3. **随口一句**：记一下、提醒我、查个东西，主聊天里说完就走。IM 证据支持（58 条 IM 对话基本都是这种，10-06 devlog）。

证据边界：IM 日志只有一天、基本是试用；场景 1 的频率要靠 JC 的实感与基线测量验证。

## 与主聊天的关系

主聊天是 Galley 下一步的重点，不只是移动端，桌面端与移动端一起做（裁决 4）。JC 的推理：Galley 定位是本机的全能 AI 助手，
一个持久的主会话更接近人对「助理」的想象与认知，也更容易上手、理解与使用。

推论：
- 手机 v1 是「主聊天 App」，不是「会话列表 App」；旁聊退到第二层（与 iOS PRD 裁决 4、20 一致，且加强）。
- 「同一条主聊天」两端都要有；桌面主聊天不能晚于手机。
- 主聊天的三块专门设计（窗口预算、上下文编排、入口层提示词）因此进入手机端的关键路径。
  建议的次序（未裁）：按主聊天 PRD 裁决 8，先做成本低的入口层提示词与窗口预算参数，手机 P0 带着这版主聊天上线；
  摘要式压缩、案头层与检索随后补，不卡手机 P0。

## 关键功能（P0 的产品描述）

1. 主聊天首屏，与桌面同一条，往返无缝。
2. 它来找你：推送通知；「在问你」时手机上直接答。
3. 从手机派活：发一句话，助理在电脑上用浏览器、文件去做；手机上看得到进度与结果。
4. 旁聊列表与旁聊对话（第二层）。
5. 电脑离线时的明确提示。

## 非目标与离线

非目标：设置与模型配置、外置 GA、群聊与多人、文件管理与编辑、把手机当第二台「电脑」给 agent 用、离线独立工作、手机远程操作电脑浏览器（滑块类验证留给助理自己试）。

离线：电脑离线等于助理没法工作，因为没有电脑就没法调模型（裁决 5）。手机端给出明确提示即可；
最多做到可读历史与排队发送，等电脑醒来再发。P0 做提示与可读历史（本地缓存自然带来），排队发送放 P1。

## 北极星与成功标准

北极星（JC，裁决 6）：让用户习惯于在手机上和 Galley 助理沟通，甚至愿意为它单独买一台 Mac mini 24 小时供它使用，
实现每个人都可以拥有自己的全能助手、秘书、管家和私人导师。

可观测的代理指标（我的建议，JC 未逐条裁）：
- 硬标准：原生端上线后，JC 是否关掉了 IM 渠道。
- 场景 1：一周里「手机发起、电脑用浏览器干」的会话数。
- 场景 2：推送通知在手机上被点开并回答的比例。
- 场景 3：主聊天里 `client = ios` 的用户轮次。
- 附带：原生端轮次是否多于 IM（第一轮的唯一指标，降为附带）。

「专用机」场景的产品含义：电脑是一台无人值守、常年开着的机器。这让 iOS PRD 裁决 10 的保持唤醒从「一个开关」升为产品场景，
裁决 17 的「后台运行模式且已配对时桌面静默」正好匹配；但「设置只在桌面」（裁决 8）在专用机上会别扭，进 deferred，不在 P0 解决。

## 方案总览与次序

层次，自上而下，每层只依赖上层：

```
产品定位（本文）：你电脑上的助理，随身带着；核心价值是登录态浏览器
  └─ 主聊天（main-chat/PRD）：持久主会话，桌面与手机同一条；三块专门设计
       └─ 手机端（ios-client/PRD）：主聊天 App，SwiftUI，内容层与桌面一致
            └─ Core 同步与远程（ios-client 票 02、05、06）：Core 接管发送与广播、Core 内远程模块、frankfurt relay + APNs
                 └─ 宪法 Rule 2 修订（ios-client 票 01）
```

次序与依赖：

| 步 | 内容 | 依赖 / 等谁 | 状态 |
|---|---|---|---|
| 1 | 票 01 宪法与 PRD 远程叙事改写（[措辞稿](../ios-client/issues/01-rule2-and-prd-rewrite.md)） | JC 过目措辞 | ready-for-human |
| 2 | 票 02 Core 接管发送 + 所有写入都广播（02a–02d） | 无；是 Rule 5 的债 | ready-for-agent |

| 4 | 主聊天入口层提示词 + 窗口预算参数（主聊天 PRD 裁决 8 的前半） | 步 3 | open |

对齐后仍开着的点（JC 侧）：Apple 开发者账号主体；票 01 Rule 2 拟文的接受；成功标准的可观测指标是否照我的建议；旁聊分出的手势（主聊天 PRD 待定）。
已关：§5 目标用户改动 JC 10-09 认可；主聊天不支持 `/new`（主聊天 PRD 裁决 14）。

## 待定

- **浏览器任务要人介入**：已研究，见 [issues/01](./issues/01-browser-intervention.md)。结论：二次验证码与确认操作今天的「在问你」就通，且验证码本来就在手机上，是手机端最强的用例；
  扫码登录与图形验证码只差「问题带一张图」。已裁：A 约定式（提示词一条 + Core 抽图 + 手机渲染）；滑块类定为非目标。iOS 票 09。
- **手机上看浏览器进度**：派活后手机上看什么（步骤条、截图、还是只看结果）。桌面现有「对话显示网站」与步骤预览（10-04 浏览器控制一轮）是起点。
- 专用机的首次配对与远程设置（deferred）。
- 场景 1 的真实频率：10-16 基线复盘时一并看 JC 一周里有几次想在手机上派浏览器活。

## 裁决原文（JC，2026-10-09）

1. 用户：接受「P1 画像 = 内置个人助手用户」与「早期反馈只来自 JC」。
2. 核心价值：调用有我登录态的真实浏览器的能力，目前几乎所有云端助手搞不定，我也不敢把登录凭证全给这些厂商。
3. 场景：现代人很多时候手机比电脑用得多，所以在手机上可以真正干活；有电脑可以操作的助理，能满足大量场景。
4. 主聊天：是 Galley 下一步重点，甚至不只是移动端，桌面端和移动端一起。Galley 不是 coding agent、不是 IDE，定位是本机的全能 AI 助手，
   一个持久主会话更接近人类对助理的想象和认知，也更方便上手、理解与使用。
5. 离线：电脑离线相当于助理没法工作，有相关提示就行；最多可读历史和排队发送，因为 agent 离线时没办法调用模型回复。
6. 成功：让用户习惯于 Galley 助理在手机上沟通，甚至愿意为 Galley 助理单独买一台 Mac mini 来 24 小时供使用，
   实现每个人都可以拥有自己的全能助手、秘书、管家和私人导师。

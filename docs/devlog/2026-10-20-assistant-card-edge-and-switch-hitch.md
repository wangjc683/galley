# 助理卡片的边，与回主对话的卡顿

日期：2026-10-20
关联：[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 122、123，票 [71](../../.scratch/main-chat/issues/71-assistant-card-edge-and-press.md)、[72](../../.scratch/main-chat/issues/72-main-chat-switch-cost.md)；设计文档 [layout-and-chrome](../design/layout-and-chrome.md) §4.2「助手卡片」、[foundations](../design/foundations.md) §2.5；暂缓 [deferred](./deferred.md)「主对话常驻不卸载」

## 起因

JC 担心新用户看到侧栏顶上的主对话卡片，不能马上知道这是一大块能点的入口：它本身不是常规按钮的样子。

## 现状核对（裁决 122 第 1 条）

- **能点的信号都在动态里**：悬停整块铺底、鼠标移上去时脸看你一眼、选中时头像外一圈品牌色在卡片和会话行之间换位置、未读徽标。
- **静止的画面缺一条边**：不铺底、不加边框、不加阴影（票 67 的写法）。居中的大头像加名字更像资料页头，又坐在和书眉同一块的 chrome 上，第一眼像窗框或装饰。我们在文档里叫它「卡片」，但静止时用户看不到一张卡。
- **风险窄，但真实**：启动就开着主对话（`gui/src/lib/hydrate.ts:112`），新用户第一次需要点它，是离开主对话之后想回来的那一刻。主会话估计多数人靠悬停能找到，问题是第一眼读成装饰、慢一拍。这是推测；主会话也指出，这类问题我们两个都是最差的裁判，因为都知道它能点。
- **给的三条路**：A 先做五秒测试，找没用过的人看截图；B 静止时给它一个看得见的边；C 离开主对话时让脸看你一眼。主会话推荐 A，JC 要先看 B。

## 第一轮：静止时的边

- **三档**：现状 / 轮廓（内侧 1px，`line-strong` 六成）/ 铺底（工作台的 `app` 底色）。
- **JC**：「轮廓最接近我想要的」。主会话同意，理由有三：
  - 轮廓只补「边」这一件事。
  - 它不占「选中」专属的底色通道；铺底档会读成「这块被选中了」，深色下还是凹下去的槽。
  - 输入框、代码块也是圆角细线框，和 Galley 自己的写法一致。
- **主会话提醒的翻车点**：卡片被两条线夹住，书眉线 44、卡片上沿 52、下沿 180.8、通栏线 186.8。设计文档当初不加边框就是为了这个。

## 第二轮：选中与按下

- **JC 的追问**：有了轮廓，选中和没选中是不是该有区别，选中的过程是不是该更扎实？
- **主会话查出来两个问题是同一个毛病**：
  - 悬停整块铺灰；选中只有头像外一圈 2px，选中比悬停还轻。`globals.css` 记着 08-21 会话行出过同一个毛病。
  - 卡片在 pointerdown 那一刻就打开，按下时悬停底消失，按的动作反而让卡片变空。
  - 1px 的下沉放在三行高的卡片上几乎看不见。
- **切换器两组**：选中（头像圈 / 品牌边 / 米底）× 按下（1px / 压缩 / 点头）。主会话推荐米底加压缩。
- **JC 真机**：「米底 + 压缩 感觉是最舒服的」。
- **定档**：
  - 选中铺会话行同值的选中色，不加阴影，轮廓同色系深一档，头像圈去掉。
  - 按下下沉 1px 并缩到 98%，按住时底色再深一档。
- **顺带发现**：Tailwind v4 把 `translate-y-*`、`scale-*` 写成独立的 `translate`、`scale` 属性，而按钮写的是 `transition-[transform,box-shadow]`。所以 foundations 写的「下沉走 70ms + ease-firm」全应用都没生效，实际是瞬时的。卡片按正确的属性写；全局那处另议。

## 回主对话会卡一下（裁决 123）

- **JC**：「多试了几次，感觉从其他对话点击回到主对话时，总会卡顿一下」。
- **怎么量的**：WKWebView 没有调试端口，主会话在 dev 里挂了临时探针：
  - 每次 pointerdown 落在卡片或会话行上，记 1.5 秒内的帧间隔、`activeSessionId` 翻转时刻和 React Profiler 的各子树提交。
  - 统计布局读取（`getBoundingClientRect`、`scrollHeight` 等）的次数、耗时与调用栈。
  - 数据发给 scratchpad 里的本地小服务；探针也能收指令、自己派发切换，不用 JC 点。
- **数字**：
  - 切到主对话（19 轮）后，第一帧要等 165–461ms，多数约 200ms。
  - 切到 28 轮的「国庆带娃」要 107–177ms，切到 2 轮的对话要 95–122ms。
  - 主对话更短却更慢，所以长度不是原因。
- **时间线（去掉 StrictMode）**：
  - 渲染约 66ms：主区按 `key={activeSessionId}` 整块重挂，两种对话都这样。
  - 贴底计算强制新 DOM 第一次布局，20–84ms。
  - 副作用里 setState 引发 2–3 次连锁重渲染；打字气泡交接与贴底又各强制布局约 10ms。
  - 第三段只有主对话有。
- **StrictMode 的单变量对照**：去掉后首帧时间几乎没变，大头在提交之后，是浏览器真实的布局开销和连锁重渲染。
- **和卡片改动的关系**：
  - 不是它引起的：侧栏每次约 25ms，改前改后一样。
  - 但被它放大了：按压的缩放和底色要等这 0.2 秒结束才画得出，鼠标往往已经松开；侧栏那张脸的动画也跑在主线程上，一起停顿。
  - 改之前 1px 的下沉几乎看不出，停顿被藏住了。
- **三条路**：
  - **A 先画按下再切换**：主会话已做。卡片等按压那一帧画出来再打开主对话，pointerdown 到第一帧从约 200ms 降到 3–5ms。只改卡片：会话行没有按下样式，推迟它们只会白白晚一帧。
  - **B 砍主对话独有的那段**：票 72，后台代理在 worktree 里做。
  - **C 主对话常驻不卸载**：暂缓，进 deferred。
- **JC**：「按你推荐推进」。
- **B 合入后复测**（票 72，`10b8e005`；同一个探针回路，dev、StrictMode 开、A 已做）：
  - 按下后的停顿从 192–237ms 降到 145–150ms，与切到 28 轮工作台对话的 141–148ms 持平。
  - 挂载后整段对话的重渲从 2–3 次降到 0；强制布局从 3 次降到 1 次。
  - 连锁的主要来源出乎预料：不是贴底，而是每条消息操作行上的 Radix 根（tooltip 与 ⋯ 菜单，19 轮里 137 个），挂载时在自己的 ref 回调里 setState。改成每一行第一次悬停时才挂。
  - 代理还发现票面「⋯ 能 Tab 聚焦」与设计不符（悬停才出现的动作本来就不进 Tab 顺序），保持原状；为了回归测试，加了开发依赖 jsdom。

## 没选

- 静止时铺工作台底色（第一轮的「铺底」，也是裁决 117 第 7 条收回的常驻白卡）。
- 选中时轮廓变 1.5px 品牌色（只靠色相、线又细）。
- 切到主对话时脸点一下头（第二轮的「点头」）。
- 小手光标（foundations §2.6 禁 `cursor-pointer`）。
- 卡片下放一个假输入框（新容器，10-14 已否过这类）。
- 名字后加「›」：侧栏里「›」是展开的意思，居中时也别扭。
- 五秒测试没做：轮廓已补上静止画面的边，真有新用户认不出再做。

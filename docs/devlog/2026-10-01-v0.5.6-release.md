# v0.5.6 发布

**日期**：2026-10-01
**上下文**：v0.5.5 后一天，main 上是社区 #29–#32 一轮修复。JC：「发版，我们讨论下版本号」→「按建议推进」。

## 裁决

- **发，patch（v0.5.6）。** 按最大单个功能的量级分（`v0.4.1` 起的规则，不看批量）：最大的两项是 #30（supervisor 回答子会话的
  提问，附带 Agent API 增量字段与 `wait --until-idle`）和 #32（「自定义」provider 入口），都是既有能力上的增强，不是新产品线。
  Agent API 的变化全在 `schemaVersion: 2` 内、只增不改，先例 `v0.4.13`（CLI `live`）、`v0.5.5`（`llm list --runtime`）都裁
  patch。`0.6.0` 不取：能举的理由只有 CLI 面和入口变多，属于批量，规则不计。
- **Windows CLI 版本滞后不挡发版。** `.scratch/windows-cli-version-lag/`（needs-triage）不是本版引入的回归；但 #30 的修复主要经
  CLI 送达，报告人恰在 Windows 上，所以冒烟顺带复现（见下），#30 回帖请报告人确认 `galley version` 与 `where galley`。否掉
  「先查清再发」：#29 / #31 / #32 不该陪等一个既有问题。
- **打包门禁必须跑**：`managed-ga/`（`llmcore.py`、补丁 `0027`、manifest）与 `runner/` 都动了。本机 `mac-x64` 通过。
- **GA baseline 本次不审计（连续第五次），理由如下。**
  - 上游 `main` 仍是 `f308ee7`，与 v0.5.5 核对时同一提交（`gh api` 查于 2026-10-01；本机 `git ls-remote` 连不上 github.com，
    改走 API），之后没有新提交，引擎三处改动与 [v0.5.5 devlog](./2026-09-30-v0.5.5-release.md) 所列相同。
  - **记忆提炼提示词单列结论**（v0.5.5 留的要求）：旧版要求「先读现有、最小化更新、无新内容跳过」，新版改成「融入旧条目、合并
    重复、压缩冗述」，即允许模型改写已有记忆条目。它改的是每个内置用户的记忆内容，属于用户状态；按「代码可替换、用户状态不可」，
    应单独一次审计、引入后观察几次长期记忆整理的实际改写，不夹在一个修复版里。新增的「整理完仍须向用户报告原任务结果」是正向
    修复，但没有用户报告对应缺陷，不构成立即审计的理由。
  - claude-cli UA 升级不是关键修复；`agentmain.py` 一行只作用于 reflect 模式，Galley 两种模式都不起 reflect。上游 `memory/` 两个
    SOP 改动随种子只补缺，到不了老用户。
  - v0.5.5 的「上游当天仍在动」这条理由已不成立（`f308ee7` 之后静止一天），不再沿用。连续五次跳过之后，建议基线审计单独起一次、
    不随发版，审完把记忆提示词的观察写进 [ga-baseline](../ga-baseline.md)；起不起、何时起待 JC 定。
- **更新渠道**：stable patch，publish + 冒烟后推 stable。

- app-update hop `v0.5.5 → v0.5.6`（SOP step 10）：JC 在 Windows 的 0.5.5 上第一次检查显示「已是最新」。原因是 raw CDN 缓存：
  promote 在 12:17:41 UTC 推送（`32504293`），CDN 在 12:17:40 刚缓存了一份旧清单（12:22:19 不带缓存参数取到 `x-cache: HIT`、
  `source-age: 279`、`version: 0.5.5`），按 `max-age=300` 一直发到 12:22:40 过期；12:22:46 三次取都是 0.5.6。应用侧每次检查都真请求
  （`app-update.ts`），不另缓存。step 8 的核对脚本带 `--cache-bust`，正好绕过了这层缓存，所以没发现。过期后 JC 再查到 0.5.6、开始
  更新，重启后的版本待回报。SOP step 10 补一行：promote 后至少等 5 分钟，或先用不带缓存参数的 `curl` 确认（JC 同意）。

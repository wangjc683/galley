# 项目文件夹：告诉模型它就是用户的文件夹

日期：2026-11-23
关联：GitHub issue #34；`.scratch/project-folder-path/`（PRD 与票 01，发版并回帖后删）；补丁 `0036`
（[patch ledger](../../managed-ga/patches/manifest.md)）；`runner/tests/test_managed_ga_project_mode.py`；
[GA baseline](../ga-baseline.md) 耦合点 27；[2026-06-18 Project Workspace](./2026-06-18-project-workspace-and-ga-upstream-12655687.md)

## 起因

issue #34（Windows，v0.7.11，内置内核）：用户给项目选了文件夹，在对话里说「工作目录下有个某某文件，读取并……」。模型先查
temp、再查用户目录、再全盘搜，最后才在「项目私域目录」里找到，整轮 104 步；回答里报的交付路径在状态目录下的
`temp\projects\<名字>-<哈希>\`，用户读成「产物没放进我的文件夹」，标题写的是「工作目录形同虚设」。追问后，模型又把那个目录
说成「纯冗余副本」。

## 根因

1. **产物其实在用户的文件夹里。** `temp/projects/<名字>-<哈希>` 是上游 `frontends/workspace_cmd.py` 的 `prepare` 建的链接
   （Windows 是 `mklink /J` 的目录联接，其他平台是符号链接），指向用户选的文件夹。两个路径是同一份文件。
2. **模型从没被告知真实路径。** 每轮注入只有上游 `plugins/project_mode.py` 的一段：「项目私域目录：<链接路径>（todo、草稿、
   产物一律放这里……）」。runner 拿到了真实路径，存在 agent 的 `_ga_project_mode_workspace_path` 上，但没有任何代码读它。
3. **系统提示词写的工作目录是 temp**（`cwd = <状态目录>/temp (./)`），工具基准目录也是 `./temp`。用户说「工作目录」，模型按
   temp 去找。
4. **模型把链接当成副本。** 用户若让它「清掉冗余」，某些删除方式会穿过链接删真实文件。

06-18 那篇的「Next」里写的「在带文件夹的项目里 dogfood」没有走过：JC 本机库里项目数是 0。

## 裁决（JC，2026-11-23）

- **做方案甲**：内置内核加补丁 `0036`，注入段落里的路径换成真实路径，说明「用户说的工作目录 / 项目文件夹 / 项目目录指的就是它，
  用户提到的文件先在这里找，对用户说路径时用这个路径」，再加一句「<链接路径> 是指向这个文件夹的链接，不是副本，不要清理或
  删除它」。
- **不做方案乙**：把项目会话的工具基准目录（`handler.cwd`）指到项目文件夹。那要改系统提示词里的 `cwd` 一句并审计所有用
  `../memory`、`./` 的种子 SOP，是 05-14 故障模式在工具层重来一遍，也就是 deferred「Session Workspace」那一套。本 issue 记作它
  的一条旁证。
- **不做方案丙**（只回帖解释）：界面文案承诺了「AI 也会把草稿和产物放在这里」，而任何用户说「工作目录下的某某」都会踩到。
- **回帖**：等修复发版后再回。

主会话在票里补的一条规则（JC 未裁，不要可撤）：只有属性是非空字符串、且 `os.path.samefile(<链接路径>, <属性值>)` 为真时才用
真实路径，否则整段与补丁前逐字节相同。它挡的是这种情况：会话绑着文件夹 A，用户口头让模型
`handler.enter_project_mode('别的项目')`，名字换了而属性还是 A。

## 影响面

- 内置内核、绑了文件夹的项目会话：每轮注入多一条规则（链接那一句），路径变成真实路径。
- 没绑文件夹的项目模式（口头「进入某某项目」）：逐字节不变。
- 外置 GA：不打补丁，零变化。少数能启用项目文件夹的外置环境仍是旧说法，这是显式代价。
- CLI 契约、数据库、GUI 文案都没动。

## 验收

门禁：补丁栈从上游基线全新克隆重放后工作树干净；`pytest` 902 过（新测试 17 例）；`mypy`、`ruff`、
`check-managed-ga-payload`、`git diff --check` 过。

macOS dev 真模型对照（主会话代验，`gpt-6.2-sol`，同一个临时项目、同一句话「工作目录下有个某某文件，读取并说说它是做什么的，
再在工作目录里写一份摘要」，各一轮）：

| | 补丁后 | 补丁前的写法 |
|---|---|---|
| 第一步 | 直接读真实文件夹下的文件 | 按相对路径在 temp 读，没读到，下一步跑代码列目录找 |
| 步数 | 4 | 7 |
| 写摘要 | 在真实文件夹里（`code_run` 的 `cwd` 就是它） | 经 `projects/<名字>-<哈希>/` 相对路径写 |
| 回答里报的路径 | 真实文件夹下的路径 | 状态目录下的链接路径 |

引擎日志确认补丁后那一轮收到的是新写法。各只跑了一轮，不是统计结论；补丁前那一轮复现了 issue 里的两个现象。测完两个会话、
临时项目、状态目录里的链接与注册表条目都已删除。

没验到的：

- **Windows**：目录联接上 `samefile` 的结果（判不出来时会静默回到旧写法）、反斜杠路径、项目与状态目录不同盘。CI 的 runner
  测试只在 ubuntu 跑。留到发版冒烟在 Windows 真机上走同一句话。
- 模型写相对路径（`./xxx`）或不带目录跑命令时仍落在 temp 根（方案乙才解）。
- 种子记忆 `project_mode_sop.md` 仍写着 `./projects/<项目名>/`；补丁后那一轮模型读了它，仍按真实路径做，只此一轮。
- 上游若改掉 `_ga_project_mode_workspace_path` 这个属性名，注入会静默回到旧写法（已写进补丁清单的 rebase 风险与耦合点 27）。

## 票外发现（未裁）

- **删掉项目后，状态目录里的链接和注册表条目留着。** 验收清理时看到：`galley project delete` 之后，
  `temp/projects/<名字>-<哈希>` 与 `temp/workspaces.json` 里的条目还在。上游的 `workspace_cmd.cleanup()` 只在它自己的 TUI 启动时
  跑，Galley 不调。留下的只是一个链接，不占空间；但模型列 temp 目录时会看见它。
- `docs/ga-baseline.md` 07-15 升级记录里「`_ga_project_mode_workspace_path` remains Galley-only」已不成立（上游两个 TUI 现在也设
  这个属性）。历史记录不往前改，现状写在耦合点 27。

# Dark theme 换冷色相：底色与墨色转冷蓝灰，明度阶梯不动

**日期**：2026-10-07
**状态**：已实现，经 JC 真机两轮变体实测裁决
**范围**：`gui/src/styles/globals.css`（`html[data-theme="dark"]` 块、dark `.chrome-hover-scope`）·
`docs/design/foundations.md` §2.1 Dark theme /「Chrome 的方向随主题翻转」· `docs/design/conversation.md` 代码块底色

## 背景

JC：「总感觉 dark theme 偏黄偏暖，阅读可见性不如那些经典的 dark theme 配色。」
我追问「可见性」指的是亮度问题（字发刺、发虚）还是色相问题（字发黄、发脏），JC 答：**更接近字发黄、发脏，
而且背景色也比较黄黄的感觉**。

## 测量（OKLCH + WCAG，与经典暗色主题同坐标）

| 主题 | 底 L | 底色相 | 正文 L | 正文对比 |
|---|---|---|---|---|
| Galley dark（旧） | 20.3 | 暖 56°，C .006 | 93.1（暖 72°，C .011） | 14.67 |
| VS Code Dark+ / Dark Modern | 23.5 / 23.9 | 纯灰 | 87.0 / 84.5 | 11.25 / 10.26 |
| Notion dark | 21.3 | 纯灰 | 86.7 | 11.74 |
| Catppuccin Mocha | 24.3 | 冷 284° | 87.9 | 11.34 |
| Gruvbox Dark | 27.7 | **纯灰** | 89.4（暖 89°，C .057） | 10.75 |
| Tokyo Night（VS Code 版） | 22.6 | 冷 280° | 76.7 | 8.10 |
| GitHub Dark | 17.6 | 冷 258° | 94.3 | 16.02 |

三条诊断：

1. **全屏彩色都挤在 43–77°**：表面、墨三档、杏沙、行内代码、warning、用户消息带、选中行同处橙黄一带。经典主题
   底色要么中性要么冷；连公认最暖的 Gruvbox，底也是 C=0 的 `#282828`，暖只放在字上。Galley 是底、字、点缀三层同暖。
2. **dark 比 light 暖得多**：light 底 C ≈ .0017，dark 表面 C .006–.009；07-25 只收到 0.6×，08-21 又松回 0.73×。
3. **正文偏亮**（14.67:1，经典阅读型主题在 10–12:1）。JC 的回答把这条排到了次要，故只放进变体当对照。

### 撤回 07-25 的一条结论

[07-25 降暖](./2026-07-25-dark-theme-dewarm-pass.md)用 C/L 比较两个主题的墨色，结论是「墨色基本对齐，奶油白字
不是元凶」。但 light 的墨是深色（L 24）、dark 的墨是浅色（L 93），除以明度把 light 侧放大近 4 倍。按绝对 chroma：
dark 墨 C .0114，light 墨 .0064，**1.8 倍**；sRGB R−B 13 vs 5。奶油字正是「字发黄」的来源之一，那条「数据推翻」
是度量选错了。

## 两轮真机变体

`tauri dev` 里临时挂底部切换条（`html[data-dark-variant]` + 一张独立 CSS），只动底色 / 线 / hover / 墨，品牌家族、
行内代码、语义色、阴影高光三者锁住不动以隔离变量；所有变体保持各 token 的 OKLCH L。

**第一轮**：现状 / B 近中性（表面 chroma 0.3×，即 light 的 C 水平；墨 C ≈ .005）/ B′（B + 墨降亮到 L 88.5，
12.8:1）/ C 冷相（H 262，底 C/L ≈ .045，冷白墨，L 不动）。讨论阶段 JC 已明确接受「近中性炭 + 暖点」，C 只是
对照档。**JC 真机选 C。**

**第二轮**围绕 C：C / C+ 加色（底 C/L .07，介于 One Dark .054 与 TN .095 之间）/ C+ 降亮（墨 L 88，冷色 chroma
加大，12.5:1——暖色下降亮会发脏，冷白在低明度仍能保住清晰，这是 TN 的做法）/ 紫（C+ 降亮换 TN 的 H 280）。
我推荐 C+ 降亮。**JC 仍选 C。**

## Decisions

- **落地第一轮 C**：表面、线、hover、墨三档、`ink-hover`、`line-subtle`、dark `.chrome-hover-scope` 的 hover
  转到 H ≈ 260，OKLCH L 保留到 ±0.1。
- **底色 chroma 基本不变**（≈ .009，与旧暖底同级），**墨色 chroma 减半**（.0114 → .0063）。JC 两轮都拒绝了加色，
  说明问题出在色相上，不在色度的多少。
- **正文对比不动**：14.67 → 14.64:1（8-bit 取整）。两轮里的降亮档都没被选中。
- **阴影高光 inset 跟随墨色**：`rgba(237,231,224,…)` → `rgba(229,232,236,…)`，现 18 处（08-21 记 17 处）；
  `line-subtle` 另算一处，同步更新。
- **定位改写**：foundations 的「暖炭黑，不走冷灰蓝 IDE」改为「冷蓝灰」，并写明两个主题的冷暖不对称是裁决结果。

落地值（旧 → 新）：`app #191614→#14171a` · `chrome #1e1b17→#191c20` · `surface #201b19→#1a1c21` ·
`code-surface #24201c→#1e2126` · `elevated #27231f→#212429` · `hover #2a2622→#24272c` ·
`line #353029→#2d3137` · `line-strong #4d443c→#41464e` · `ink #ede7e0→#e5e8ec` · `ink-soft #c6bdb2→#babfc5` ·
`ink-muted #92897d→#858b93` · `ink-hover #f7f1e8→#eff2f6` · sidebar hover `#2f2b27→#282c32`

复核：

- 阶梯严格单调（OKLCH L）：app 20.3 → chrome 22.5 → surface 22.7 → code 24.7 → elevated 25.9 → hover 27.2 →
  line 31.2 → line-strong 39.3
- chrome→app ΔL\* 2.46 → **2.57**（方向不变，仍是 chrome 更亮）
- 正文 / 次级 / 提示对比：14.64 / 9.72 / 5.24:1；用户消息带上正文 10.97:1
- sidebar：chrome→hover ΔL\* 7.72（主区 app→hover 7.98）；选中 `#4d3b2b` 比 hover 高 8.55、比 line 高 6.23、
  比 line-strong 低 3.16，选中行关系保持

## Rejected alternatives

1. **B 近中性 / B′ 近中性降亮**：在纸面上最符合「dark 是 light 的夜间版本、同一策略」，讨论阶段也被 JC 接受，
   但真机输给冷相。
2. **C+ 加色 / C+ 降亮（我的推荐）/ 紫**：JC 真机都不如 C。我推荐的依据是「经典冷色主题底色更饱和、正文 L 85–88」，
   但这条依据没能替 JC 决定他想要的冷度。
3. **只降墨色、表面不动**：JC 明确说背景也黄，单动墨色解决不了。

## 方法教训

- **跨明度比较色偏，别用 C/L。** 近白和近黑互比时，除以 L 会把深色一侧的色度放大数倍。判断「字看起来偏不偏色」
  看绝对 chroma；C/L 只适合在同一明度带里比较。
- **讨论阶段接受了的方向，到真机上仍可能被推翻。** JC 口头接受了近中性，真机却选了冷相；对照档值得放进去。
- **JC 两轮都选了最克制的那档。** 第二轮的加色、降亮、换紫都没赢。往后提视觉方案时，变体之间的跨度可以更小，
  从最克制的一端排起。

`.chrome-hover-scope` 双主题分支）· `docs/design/foundations.md` §2.1 Dark

兑现并移除 [deferred](./deferred.md) 的「Dark theme 抬画布」

## Context

JC 在 dark 下提出：sidebar 和 mainview 的背景色是不是该**对调**——sidebar
浅一点、mainview 更深更黑，「sidebar 太重，有点头重脚轻，主对话区才应该是
视觉重心」。并给出参考：「我平时用 Tokyo Night 比较多，这个配色也已经得到
大众认可，是不是可以参考？」

## Tokyo Night 参考的实际结论（与 JC 的归因相反）

**TN 的 sidebar 也比主区暗。** nvim 版 `bg_dark #16161e`（sidebar / float）
vs `bg #1a1b26`；VS Code 版 `sideBar` / `activityBar` / `panel` / `statusBar`
全部 `#16161e`，`editor.background` 是 `#1a1b26`。两版一致，方向与 Galley
现状**相同**。「顺序错了」这个归因被 JC 自己给的参考证伪。

但体感不假。同样的顺序，TN 不硌人、Galley 硌人，差别在三处：

| | TN sidebar | TN 主区 | Δ | Galley 旧 sidebar | Galley 旧主区 | Δ |
|---|---|---|---|---|---|---|
| OKLCH L | 20.4 | 22.6 | **2.2** | 15.6 | 19.3 | **3.7** |
| C | .0158 | .0214 | 冷蓝紫 H≈283 | .0054 | .0051 | 近纯灰 H≈67 |
| 正文对比 | — | **10.59:1**（VS Code 版 8.10:1） | | — | **14.95:1** | |

1. **绝对深度**：TN **最暗**的那块 UI（20.4）比 Galley 的整个对话画布（19.3）
   还亮。Galley 的 sidebar 在 15.6，比 TN sidebar 低 4.8 点，贴着地板。
2. **差值过大**：3.7 vs 2.2，我们是 TN 的 1.7 倍。同样是「sidebar 更暗」，
   我们喊得响得多。
3. **地板处没有色彩**：TN 在近黑处仍留 C≈.02 的蓝紫；Galley dark 的 C 只有
   .005。**近黑 + 近零饱和的大色块读作「重物」，不是「后退」**——这正是
   「头重脚轻」的物理成因。

也就是说，`deferred.md` 里挂了近一个月的「抬画布」条目，其启动信号
（「整体太沉太黑」）以「sidebar 太重」的外衣到达了。2026-08-05 的 chrome
加深还把 chrome 从 L 17.5 压到 15.6，让那条 deferred 描述的地板问题又恶化
了 1.9 点。

## Decisions（JC 逐条裁决）

1. **抬升幅度：直接对齐 TN 高度带**，不走一半。半步大概率重演 08-05
   「规则写了但没兑现」那种 ΔL\* 2.11 的尴尬。整条阶梯 +3.3 OKLCH L 点，
   chrome 单独 +4.7。
2. **chrome→app 差值收到 2.2**（抄 TN 的 sidebar→editor 差值），ΔL\* 3.04 →
   2.52。
3. **正文对比这轮不动**：墨色明度不改，对比是画布位置的因变量——抬画布后
   13.96:1（原 14.95）；后续翻转让画布回落，落到 **14.67:1**（见「真机推翻」）。
4. **加回一点色度**：~0.73×（见下）。

### 关于第 4 条：这是对 07-25 「0.6×」的有意部分重开

两个必须分清的量：

- **抬 L 会自动稀释 C/L**。app 的 L 从 19.3 抬到 22.4，C 不动的话 C/L 从
  .0264 掉到 .0224——等于顺手又降了一档到 0.51×。所以「加回色度」里有一半
  只是**补偿**，不算翻案。
- 在补偿之上再松 **1.21×**，落到 **~0.73×**（C/L .0321）。这一半才是真的
  重开 0.6×，理由是上面诊断的第 3 条。

JC 在带 hex 阶梯的三档预览中选定档 2（档 1 = 纯补偿维持 0.6×；档 3 =
撤销降暖回 1.0×）。

**仍远低于 TN（C/L .078–.095），且这是刻意的**：差的不是幅度是色相。暖色
在冷蓝紫还撑得住的 chroma 上就已经发闷——那正是 07-25 诊断的 muddy brown。
另一半好消息是抬亮本身在治 muddy：发闷的成因是「暗 + 中饱和」，地面上浮后
同样的 C 更容易读成「暖炭」而非「脏」。

### 沿用 07-25 的两条既有规则

- **墨色必须与表面同向同幅**：ink 系同取 1.21× chroma，**明度不动**，故
  对比度漂移 ≤0.03。同批跟随 ink 的 `--color-line-subtle` 与 17 处
  `--shadow-*` 高光内嵌一并更新为 `rgba(237,231,224,…)`（该 17 与 07-25
  devlog 记录的处数吻合，是一次交叉验证）。
- **品牌填充不吃 chroma 档位**：`selected` / `brand-soft` / `brand-tint`
  随阶梯抬明度，chroma 只做纯 L 补偿。它们当初就被排除在 0.6× 降暖之外，
  再乘 1.21× 等于给从未降过的东西净加暖。

## Rejected alternatives

1. **对调（JC 的原提案：sidebar 更浅 / mainview 更黑）**——被 TN 直接证伪：
   参考主题自己就是 sidebar 更暗。且它会把**长文阅读面**推到地板（正文对比
   从 14.95 升到 15.9，方向与「读久了累」相反），同时 `bg-app` 不只是画布、
   还是卡片内部的凹陷填充（`MessageAgent` 工具输出块、`GoalConfirmDialog`
   分段），画布下沉会带着它们一起沉。
2. **对调 + 抬画布（保住正文亮度的翻转版）**——气质上成立（macOS 原生侧栏
   的 vibrancy 材质在 dark 下确实比内容区亮），JC 也明确表示能接受「一列
   浮起来的材质」。否掉是因为 1 的证伪成立后，翻转不再有硬理由，而代价是
   chrome 挤进 surface / code-surface 的明度带、hover / selected / brand-soft
   全套重调。**保留为未来可选路径**：若抬画布之后 JC 仍觉得两栏关系不对，
   这是下一个候选，且届时不必再抬。

   > **改判（同日，见下方「真机推翻」一节）**：JC dogfood 抬画布版本后仍要求
   > 对调，本条已落地为最终状态。**第 1 条的两条硬伤依然为真**——它们没有被
   > 反驳，是被接受了：正文对比确实回升（13.96 → 14.67），凹陷填充确实跟着
   > 画布一起沉。这一整节保留原样，不改写成事后正确的样子。
3. **顺势把正文对比降到 TN 的 10.6:1**——需要把 ink 明度从 OKLCH 93 压到
   ~84（`#cecac4`）。否掉的核心理由是 **TN 抄不过来**：它的 fg `#c0caf5`
   是 C=.061 的**有饱和冷蓝白**，靠色彩撑住低亮度下的清晰感；我们的
   `#ece7e1` C 只有 .0097，暖米灰同样降亮，TN 变「柔和」我们大概率变
   「脏」。且这会重开 07-25 的暖轴裁决，属独立一轮。JC 裁决这轮不动。
4. **档 1（纯补偿）/ 档 3（撤销降暖回 1.0×）**——档 1 不满足「加回一点」的
   字面要求；档 3 是完全推翻 07-25，且会把 `selected` / `brand-tint` 之外的
   表面推到 C/L ~.04-.05，接近当年被判为发闷的水平。

## 未动但已标注的观察项

- `--opacity-*` 的 dark 覆写（`.10/.20/.28/.46`）当年的理由是「dark 背景吞
  低 alpha 叠层」。地面抬亮 3.3 点后这个论据略微减弱，语义填充可能显得比
  以前响一点。**本轮不动**，dogfood 觉得吵再回调。
- `--shadow-*` 的黑色分量在更亮的画布上会显得更重（deferred 原条目已预警）。
  本轮不动，先看实感。
- deferred 的「Sidebar selected 行明度持平」是 **light** 侧问题，本轮未触及；
  dark 侧的 selected↔hover 关系已复核保持。

## 方法教训

**用户给的参考可能证伪他自己的归因，但同时把真因交出来。** 这次如果直接
按提案对调，会得到一个方向正确性存疑、且让长文阅读面更黑的结果；而如果
只因为「TN 也是 sidebar 更暗」就回答「现状没问题」，则会漏掉真实存在的
三条缺陷。**把参考放进同一套坐标系（OKLCH L / C/L / 对比度）逐项对表**，
才能同时做到不照抄提案、也不驳回体感。

## 真机推翻：JC dogfood 后仍要求对调

上面整篇的结论是「不翻转」，理由是 TN 证伪了「顺序错了」这个归因。JC 在
`tauri dev` 里看过抬画布版本后的裁决是：**还是要对调，sidebar 更浅、mainview
更深。**

这不构成对上文分析的反驳，两件事同时为真：TN 确实不支持「sidebar 必须更浅」
这条**归因**，抬画布确实治掉了三条真因中的绝对深度与地板 chroma；而 JC 要的
是另一件上文没有否认过的东西——**两栏的相对角色**。Rejected #2 早就把这条路
留着了（「若抬画布之后仍觉得两栏关系不对，这是下一个候选，且届时不必再抬」），
现在正是那个分支。

### 落地方式：交换，不是重新设计

chrome 取抬画布后的 app 值、app 取原 chrome 值，差值 2.2 原样保留、只换符号；
主区阶梯（surface / code / elevated / hover / line / selected / brand-tint）
保持内部步进，随 app 下移 2.1。

`chrome #191613→#1e1b17` · `app #1e1b18→#191614` · `surface #25201e→#201b19` ·
`code-surface #292520→#24201c` · `elevated #2c2824→#27231f` ·
`hover #2f2b27→#2a2622` · `line #3b352e→#353029` ·
`line-strong #534941→#4d443c` · `selected` / `brand-soft` `#44352a→#3e3026` ·
`brand-tint #54402f→#4d3b2b`。墨色与 shadow 高光不动。

**画布净值 19.3 → 22.4 → 20.3**：抬画布没有被撤销，仍比本轮起点高 1.0 点。

### 规则改写：chrome 的方向从此随主题翻转

这不是调了个数，是**改了一条规则**。旧表述「chrome 永远比 app 沉」被替换为
**「content 走极端、chrome 走中间调」**：light 的纸近白故 chrome 更暗，dark 的
画布近黑故 chrome 更亮。macOS 原生侧栏材质就是这么工作的——它在两个外观下都
往中灰靠，于是相对内容区自动反向。

这条改写反过来解释了旧规则一直在硬撑的那件事：翻转前的注释必须自己承认 dark
做不到 light 的 ΔL\*，否则侧栏会掉进纯黑。**一条需要在某个主题里自我收敛才能
成立的规则，本来就不是对称的。**

### 连带处理（翻转的真实代价，都是事先预警过的那几条）

- **`.chrome-hover-scope` 从 light-only 变成双主题。** 翻转把
  `chrome→hover` 从 ΔL\* 10.35 压到 **5.49**，与 08-07 light 侧那次失明同型
  （只是还没到不可见）。dark 分支的两个值就是**翻转前的全局值**
  （`hover #2f2b27` / `selected #44352a`），推导只有一句：sidebar 的地面现在
  恰好等于翻转前的 app 底，按那个地面标定过的交互色原样成立。结果
  `chrome→hover` ΔL\* **7.85**、`hover→selected` **5.66**，与主区的
  7.95 / 5.67 几乎重合。
- **`--color-selected` 首次进入 scope 覆写**（light 没有）。不覆写的话它只比
  sidebar hover 高 3.0 OKLCH L，选中态就只剩色相在撑——正是 `deferred.md`
  记着的 light 侧已知弱点，不能在 dark 侧再造一个。
- **chrome（22.4）与 surface（22.7）基本持平**，sidebar 与主区卡片共处同一
  明度带。这是「浮起来的材质」的必然读法，**有意接受**，已在 token 注释里
  写明「不要通过挪动其中一个来消除碰撞」。
- **正文对比 13.96 → 14.67:1**（抬画布前 14.95，TN 10.59）。翻转必然让长文
  阅读面变暗，这是 Rejected #1 列过的硬伤之一，现在是已接受的代价。若日后
  读着发刺，解法是墨色那一轮，不是把画布再抬回去。
- 三处组件注释里「Sidebar 更暗」的描述已改成方向随主题翻转
  （`AppShell.tsx` ×2、`MainHeader.tsx`）；`ComposerActionSlot.tsx` 那条
  「为什么不借用 chrome」的注释里，**第二条理由（chrome 在 dark 下比画布暗）
  已被翻转作废**，但结论更硬了——chrome 十七天内移动两次，正是不该借用它的
  最好证据，注释已按此重写。

### 方法教训（补充上文那条）

上文写的是「用户给的参考可能证伪他自己的归因，但同时把真因交出来」。这一节
补上后半句：**归因被证伪不等于诉求被满足。** TN 的数据推翻的是「顺序错了」
这个解释，而 JC 真正要的「主对话区是视觉重心」在抬画布之后依然没拿到。分析
做对了、真因也确实治了三分之二，但最终仍需要真机把剩下那三分之一裁出来——
**数据能决定一个解释成不成立，不能替用户决定他要什么。**

# PRD 非目标清单对账：两条漂移，一条新增维护规则

日期：2026-08-12
关联：[PRD](../PRD.md) §6.2 / §6.3 / §6.3a

## 起因

讨论「artifact 名字要不要做视觉处理」时查 PRD，发现 §6.3 把
**Artifacts 一等公民**列为非目标——这条仍然成立，是有效约束。但同一份清单里
还写着 **Follow-up Queue**，而那正是 8/12 刚发的 `v0.4.6` 主功能。

PRD 是 v0.3（2026-05-15）写的，两份非目标清单都以 v0.2 为锚点。到 `v0.4.6`
已经过去三个月、四个 minor/patch 版本。

## 逐条核对

### §6.2 V1.0 Non-goals

全部仍然成立，问题只在**死锚点**：五条里有三条写着「v0.2 不做」。v0.2 早已
发运，这个措辞现在只会让读者困惑「那 v0.3 之后呢」。

订正方式：删掉死锚点，保留强度。原文写「留 v0.6++」的仍然留 v0.6++——
**不借对账之机偷偷调整任何一条的强度**。另外给两条补上宪法引用（localhost
only = Rule 2，不做 chat platform = Rule 4），它们本来就是宪法条款的投影。

### §6.3 继承自 v0.1 的 Non-goals

| 条目 | 核对结果 |
|---|---|
| 自动安装 / 升级 / 修复 GA | **已漂移**，见下 |
| 完整 IDE（文件树、编辑器、git diff） | 仍成立（补了一句说明 `PatchView` 不算） |
| Context Window 占用展示 | 仍成立（`design/conversation.md:543`、`layout-and-chrome.md:60` 都明确「不显示」） |
| Follow-up Queue | **已发运**，移除 |
| Artifacts 一等公民 | 仍成立 |
| 完整 tracing / 多人审批 / 复杂 policy / RBAC | 仍成立 |

**「自动安装 / 升级 / 修复 GA」的漂移最值得记**：这条现在同时是真和假，取决于
哪个 runtime。

- **attach 模式**：仍然成立，而且是宪法 Rule 1 的硬约束——不碰用户自己的
  GA checkout。
- **managed 模式**：**恰恰相反**。managed runtime 自 `v0.2.0` 起随包发运，
  Galley 装它、升它、给它打 patch，那是产品引擎和开发重心（CLAUDE.md 的定位
  段和 `docs/managed-ga-runtime/README.md` 都写得很清楚）。

一条无条件的非目标，在产品长出双 runtime 之后变成了有条件的。这类漂移比
「发运了忘删」更隐蔽，因为条目字面没错，错的是它丢了限定词。

### Follow-up Queue 确认

`v0.4.6` 的会话消息队列（galley#19/#20）就是 Follow-up Queue：运行中 /
stopping 中发送默认排队、`run_complete` 自动发出、chips 可取消或取回编辑、
一键插队，CLI 增 `dispatch: "queued"` 与 `--jump`。waku 把同一个东西叫
"pending follow-up chips"，概念一致。

## 新增的维护规则

光删掉发运的条目是不够的——读者之后无法区分「这条本来就没说过」和
「说过又反悔」。而 PRD 的非目标清单**主要读者是跨 session 的 agent**，
它会拿这份清单去判断「这个提议是不是早就被否过」。一条被静默删除的非目标，
下次会被当成从未讨论过的新提议重新提上来。

所以加了 §6.3a「已发运，不再是非目标」表：非目标发运后**从清单移除并在表里
留一行**（发运版本 + 实际形态 + devlog 链接）。规则本身也写进了 §6 顶部的
校准注里。

## 没做的

只订正 §6.2 / §6.3。PRD 其余部分（§17 路线图、§20 默认决策表、§21 future
direction）同样以 v0.2 为锚点，也存在漂移，但那是一次独立的对账，不该混进
本次改动。**本次严格限定在「事实订正」，不含任何强度调整或范围变更。**

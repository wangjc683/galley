# 主聊天概念重审：入口、大脑、出口

日期：2026-10-12
关联：[主聊天 PRD](../../.scratch/main-chat/PRD.md)（第三轮裁决 15–27、票 01–06）、[移动端产品定义](../../.scratch/mobile-product/PRD.md)、
[10-09 方向讨论](./2026-10-09-ios-client-and-main-chat-direction.md)、[deferred](./deferred.md)「IM 渠道并入主聊天」

## 起因

10-09 定了主聊天是 Galley 下一步重点，JC 回头又没想好：它到底和 Galley 的定位方向一致吗，对用户体验的提升有多大。
全程讨论与落文档，代码未动。

## 先看用量

- 桌面 GUI 会话 5 个月里最长 21 轮；跨天续用的一共 6 个，9 月起 0 个；9 月 41 个会话共 116 轮，单个最长 8 轮。
- IM 引擎日志（09-30 起）31 条用户消息，多为测试；10-07 有一句「我刚才问的第一个问题是什么？」。
- 基线测量第 3 天：库里没有置顶会话，10-09 以来桌面 GUI 只开过 1 个会话。
- GA 记忆整理靠模型自觉，140 个会话 3 次（`docs/ga-baseline.md:75`）；本机 L2 只有 3 条。

结论：数据既不支持也不否定主聊天，这是产品押注；押注就做得便宜、能退。

## 拆成五件事

打开就说（a）、异步内容的落点（b）、关系的连续感（c）、一条永不重置的上下文（d）、管家派活（e）。a、b 与定位一致且便宜；
d 是冲突与成本的源头：每条消息带近乎整窗上下文、每次裁剪前缀缓存失效，靠摘要压缩、案头层、检索续命——
正是 09-09 定位里「模型升级时要报废」的脚手架，也与 README「dense context instead of long」相反。

另两处张力：核心价值是浏览器长活，而运行中的消息在 Core 队列里等 `run_complete`（`docs/architecture.md:146-152`），主聊天跑长活会被占住；
单线程是手机习惯，桌面上的真实习惯是多个短会话。

## 裁决与理由

**界面一条、上下文分段（替代永久单上下文）。** 我提四案：A 维持 10-09 的永久单上下文、B 分段、C 只做入口与落点、D 暂缓；推荐先 C 后 B。
JC 接受分段，并问「需要时 Agent 可以查主聊天历史，再放更主动的记忆 system prompt」——我修正了前半：JC 最看重的那一刻是
「聊某个东西时它联想到上周相关的事项」，没人提起、它自己想到；查历史只管「问起时找得到」，所以联想要靠事项清单已经在上下文里。
后半（更主动的记忆）方向对，但 GA 现有记忆是「你是谁、事情怎么做」，没有「你最近生活里在发生什么」。

**三件价值都要，结构定为入口 / 大脑 / 出口。** JC：a 让他不再想「新开还是继续」；b 是「提醒不再是闹钟（必须由我事先设定），而是从事务和信息中归纳总结出可能需要提醒我的事」；
c 是上面的联想。三者是一条链：入口让人把日常说进来，账本积累，联想与提醒才有材料。由此得出：主聊天形态便宜，贵的是账本，
而账本即使主聊天不成立也让每个会话更懂你，退出成本低。我提了一个区分，JC 认可：补偿型脚手架（压缩、滚动摘要、案头层）不做，
积累型资产（记忆、账本）要做——后者模型越强用得越好，正是「积累在你电脑上、换模型带得走」的实体。

**上游已经备好零件，Galley 没接。** GA 自带「历史重点挖掘 SOP」（`memory/L4_raw_sessions/salient_mining_sop.md`：「你在建模的是：这个用户的生活里现在有什么、曾经有什么」）、
L4 归档（`managed-ga/code/reflect/scheduler.py:62-74`）与 `reflect/autonomous.py`；Galley 不走反射模式（`docs/ga-baseline.md:51-53`），本机 L4 无归档、`history_insight/` 从未生成。
JC 定以上游 SOP 为起点。

**情绪事件照上游记，我收回「先不记」。** 我原建议先不记情绪（被记下「你上周三很烦躁」越界感大于帮助），JC 问「有情绪感知的助理是不是更有温度」。
回看上游标记清单，大半是用户对 agent 的反应（反复纠正后语气突变、预期落空），首先是反馈信号；越界只在一种用法上成立。
定为使用规则：可以为做事引用（「上次这事让你着急，这次我提前办了」），不单独评论情绪；情绪事件在「它记得我什么」页面可见可删。

**桌面先上，基线测量取消。** JC 提出不等移动端。我同意且认为次序更好：账本要时间积累，手机上线时助理已经「熟」了；与移动端 PRD「桌面主聊天不能晚于手机」一致。
风险是 JC 在桌面上不住进主聊天、账本学不到东西；对冲是账本从所有会话学（桌面、CLI、IM），不只主聊天。
基线测量 JC 定不做：还在探讨概念本身。票序按推荐：账本先行（本机先跑，对外必须与「它记得我什么」页面同版），形态与切段跟上，主动提醒最后；
子任务票拆票时补入，排在主动提醒前（卡片组件先在子任务里做出来）。

**桌面层级：A1 / A2 切换器真机比。** 主聊天成为默认入口后，「逃生出口」（`docs/design/layout-and-chrome.md:172`）的含义从「开个新的」变成「回主聊天」。
A1 照 OpenMuse 把主聊天放在新对话上面，撞「顶上放动作、列表放对象」（`:178`）；A2 让主聊天行接任逃生出口、新旁聊进书眉，不撞规则，代价是窄宽回落要重做。
我推荐 A2，JC 定两案做切换器真机比。

**子任务：一张卡，不进侧栏，说过话升为旁聊。** 先分清旁聊（你开的、为了对话）与子任务（助理派的、为了干活）。子任务不能完全隐身：
看不到在干活不放心，且「在问你」必须浮上来。GA 子代理 SOP 写明「浏览器暂时不可并行使用」，所以「调研多个网页」是一个子任务依次看、一张卡。
子任务用 Galley 会话跑，不用 GA 文件式子代理（Galley 看不见）。定时任务的结果也改为主聊天卡片。JC 全按推荐。

**IM 三级。** 每个渠道是独立进程、自己养一个 GA agent（`core/src/im_supervisor/manager.rs:246-258`），对话不进库，主动发送只有委派完成汇报。
L0 同一个大脑、线分开；L1 IM 当出口（主动提醒与「在问你」发到首选渠道，微信长间隔要先探针）；L2 并入主聊天仍 deferred，
但 IM 的 `/new` 因分段有了不破坏的语义——「开新段」。我指出 deferred 的启动信号低估了 L2：iOS 只覆盖 iPhone，安卓用户在手机上只有 IM。
JC 定 L0 随账本与切段、L1 随主动提醒、L2 改启动信号为「桌面主聊天形态与切段上线后重排 L2 与 iOS 的先后」。

## 被否 / 收回

- 10-09 的「三块专门设计」（窗口预算、分层编排、入口层提示词）与摘要式压缩：由入口 / 大脑 / 出口与分段取代；入口层提示词保留进票 03。
- 永久单上下文（方案 A）、暂缓主聊天（方案 D）。
- 一周基线测量。
- 我的「情绪先不记」（JC 推翻）；我的「需要时查历史就够」（自己修正）。
- 「忙时新消息一律自动开旁聊」：补充说明应进正在跑的任务，改为「排队 / 开旁聊」两个选择。

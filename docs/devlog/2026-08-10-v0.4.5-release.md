**日期**：2026-08-10

## 背景

`v0.4.4`（2026-08-07）之后三天的工作有一条此前没有过的主线：**这是第一
批真实用户 issue 落地的版本**。galley#15 / #16 / #17 / #18 四条都不是我
们自己 dogfood 找出来的，而是装了 Galley 的人报回来的。

这改变了发版的性质。前几个 patch 版本发不发是我们自己的节奏问题；这一
版有人在等——`#17`（通知静音）意味着他们此刻收不到提醒，`#15`（找不到
反馈入口）意味着下一个问题他们可能根本报不上来。反馈通路本身是坏的，
这条要优先修完。

同一批里还夹了一次引擎升级（GA baseline `d8d90ee` -> `308153b`），它是
本次唯一的回归风险来源，单独在下面记。

## 版本决策：patch

沿用 `v0.4.1` 确立、`v0.4.2` / `v0.4.3` / `v0.4.4` 复认的定级规则（按
最大单功能量级判，不按批次总量判）。本批最大单项是 Settings 报告问题
tab——用户可见但属既有 Settings 面上的增量，撑不起独立产品线。

产品形态、Agent API schema（`schemaVersion: 1`）、更新渠道策略均不变。
**GA baseline 变了**（`d8d90ee` -> `308153b`），这是与 `v0.4.4` 最大的
不同，也是本次 bundled runtime gate 从「可跳过」变成「必跑」的原因。

## 本次唯一的回归风险：引擎升级的工具输出上限

`308153b` 里上游抬高了 `default_context_win`（30000 -> 35000）。升级当
天的初判是「裁剪推迟，dogfood 看长会话」，**这个判断是错的，而且方向
相反**，JC 追问后当天更正：

Galley 显式设 `context_win = 90000`，trim 的 `cap = context_win * 3` 只
看显式值，所以裁剪阈值一动没变。真正变的是把上游默认值当**分母**的
`maxlen_multiplier`（2.25 -> 1.93，降 14%），经 `_get_tool_maxlen` 把
**工具输出上限压了约 14%**（`file_read` 33750 -> 28928）。

对用户的观感就是：**`...[Truncated]...` 会比以前来得早**。draft smoke
时这是要专门盯的一条，不是「顺便看看」。

留下的通用教训已记进 baseline devlog：判断上游默认值变化，先查下游有没
有显式覆盖；一旦覆盖，该常量通常只作为分母间接生效，方向可能反转——上
游是为了更慷慨才抬高它，对设了更大显式值的人反而是收紧。

# 流式 markdown 补全：只补代码 span 和链接目标

日期：2026-08-12
关联：`lib/mend-streaming-markdown.ts`、`MainView.tsx`、`markdown-image-src.ts`、
[design/conversation.md](../design/conversation.md)「流式回溯抖动」

## 问题

同一轮 [waku 对照](./2026-08-12-inline-code-warm-ink.md)里的 A 条。流式输出时
未闭合的行内标记按字面渲染，闭合瞬间标记字符消失 + 字体切换，**已经排好的
文字被改写，段落在光标后面重排**。这跟「文字不断变长导致的自然重排」不是一回
事——那个是往后长，读者预期之内；这个是回头改已经稳定的内容，所以扎眼。

## 先测再修

上一轮说了「先实机确认抖动有多明显再决定」。实际做法是把它变成一个可测的量，
而不是让 JC 盯屏幕：

> **回溯改动** = 某一帧渲染出的纯文本，不是上一帧的纯追加。

按 20Hz 节奏逐前缀渲染一段典型中文技术回答（509 字符，含行内代码、`**`、
一条长链接），得到：

```
84 帧 @ 6 字符/帧
回溯事件：16 次（19.0% 的帧）—— 约每 32 个字符重排一次
累计位移：230 字符，单次最大：75 字符
```

按构造归类：**行内代码 ~59%，链接 ~35%，强调 ~6%**。而且这是下界——计数器只
看字符，看不见行内代码闭合时 serif→mono + 0.92em + 药丸 padding 的额外宽度
变化。

这个数字直接改掉了原方案。

## 范围裁剪（数字驱动）

原计划补 `**` / `*` / `` ` `` / `~~` 以及链接目标，约 100–120 行。数字出来后砍成
**只补代码 span 和链接目标**：

- **强调只占 6% 的位移，却是复杂度的大头**。waku 那 430 行里绝大部分是
  CommonMark 定界符消解——`OpenDelimiter` 栈、`owed` 欠闭合计数、嵌套顺序
  判定。而且它最容易补错：补错了文字会先斜后粗地闪一下，等于用一种抖动换
  另一种。
- 代码 span 和链接目标的扫描简单得多：前者数 backtick run 长度，后者找 `]`
  紧跟 `(` 却始终等不到 `)` 的位置。最终 ~230 行（含大段注释）+ 18 个单测。
- **表格补不出来**：`| a | b |` 在分隔行到达前是段落，这是 GFM 语法要求，
  不是悬挂标记。接受。
- **`[文字` 后面还没跟上 `(` 时不碰**：散文里的方括号远多于链接，猜错会把普通文字
  渲染成链接。

## 一个被推翻的前提

上一轮我说「Galley 现在半截 URL 渲染不成链接，所以点不到；这个风险是补全
造出来的」。**实测推翻**：

```
见 [文档](https://exa
→ 见 [文档](<a href="https://exa">https://exa</a>)
```

`remark-gfm` 的 autolink literal 已经把裸 URL 变成真锚点了。**半截 URL 现在
就能点**，跟补全无关。所以 pending 哨兵不是补全的附属安全阀，它同时在修一个
已经存在的问题——这也是最后决定把它并进本次改动、而不是单独做一遍的原因。

哨兵实现：补全把未完成的目标换成 `galley:pending-link`，
`markdownUrlTransform` 把它映射成 `null` → `href` 属性整个不出现。锚点仍匹配
`[&_a]` 的 prose 规则，所以 URL 落定时**零位移**，但既不可点也不可聚焦。

## 显示态 / 落定态的分离是白得的

waku 要显式维护「显示树 vs canonical 树」两套解析，就为了让永远不闭合的标记
在结束时诚实地翻一次而不是全程抖。

Galley 不需要：流式 partial（`MainView` → `useMarkdownStream` → `MarkdownView`）
和落定后的 turn 本来就是两条渲染路径。补全只挂在前者，后者渲染原文。所以
只要「补全对已闭合的输入是恒等」，落定语义自动成立——这条被写成了单测。

## 结果

回归测试 `mend-streaming-markdown.stream.test.tsx` 把上面那个计数器沉淀下来，
同一段回答跑补全前后：

| | 回溯次数 | 累计位移 |
|---|---|---|
| 补全前 | 16 | 230 字符 |
| 补全后 | 6 | 20 字符 |

**次数降 63%，位移降 91%。** 这个差距本身说明问题：剩下的 6 次全是强调，
而且都很小——让重排显眼的是**移动幅度**，不是变化频次。

断言写成相对阈值（位移 ≤ 25%）而非硬编码数字，避免 react-markdown 升级时
误报；实测基线写在测试文件注释里。

## 遗留

- 强调（`**`）的 6 次小抖动：**明确不做**，理由见上。除非日后有实机反馈说
  「粗体闪」，否则不要重提。
- 表格弹跳：GFM 语法所致，无解。
- `lastBlockStart` 每次 flush 全文扫一遍（O(n)）。它喂的 markdown 解析本来
  就是 O(n)，所以只是常数因子。真正的 O(n²) 问题是**增量解析**，那条仍在
  [待议](./2026-08-12-inline-code-warm-ink.md)，先测再修。

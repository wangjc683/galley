# 向 Telegram 学对话细节：看不见的规则比装饰值得学

日期：2026-10-16
关联：[telegram-details PRD](../../.scratch/telegram-details/PRD.md)（裁决 1–7、2a、3a）、票 01–09（`.scratch/telegram-details/issues/`）、[conversation.md](../design/conversation.md)、[foundations.md](../design/foundations.md)

## 起因

JC：「现在其实我们的主对话和普通对话都已经基本更接近于 IM 化设计了，主对话完全就是按 IM 标准去做的 UI/UX。我听说 Telegram 的前端是开源的？我一直觉得它的 IM UI 很不错，尤其是一些小细节……找找哪些前端细节 UI 设计是我们可以参考学习的吗？」随后划定范围：「学设计思路和具体数值（间距、时长、阈值、交互规则、动效），不是搬代码。」

## 怎么查的

- 两个官方网页客户端：Web A（`Ajaxy/telegram-tt`，写法接近 React，主看）、Web K（`morethanwords/tweb`，交叉核对）。**两者都是 GPL-3.0，Galley 是 MIT**：只学思路与数值，实现一律自己写，票与代码注释里只引出处。
- 三个只读子代理并行：Telegram 的消息列表、Telegram 的输入框与外壳、Galley 两种对话在同一组细节上的现状（带代码位置、设计禁令与 deferred 里否过的项）。第三份是吸取 10-16 上午工作台过程 P1 漏查 deferred 的教训，先把「别再当新点子提」的清单列出来。

## 结论

Telegram 强在看不见的规则：滚动怎么走、焦点给谁、各种阈值。尾巴、阴影、时间嵌进气泡这些装饰我们早就有意不要。另一个发现：Web A 已经为机器人的流式回复做了整套交互（live tail、停止键与发送键共位），和我们的场景几乎一一对应。

已经一样或更好、不动的：中文输入法（我们 `lib/ime.ts` 同时认 `isComposing` 与 `keyCode 229`，Telegram 只认前者）；在跑时按钮是停止、Enter 照样能发；加载更早的消息保位不转圈、会话切换不出骨架屏、不做逐条虚拟化。

## 裁决与做了什么

JC：「1，做；2，……我们继续讨论；3，做；4，做；5，做；6，按推荐比；7，按推荐」，之后逐条讨论。

1. **草稿存盘**（票 01）。`composer-draft.ts` 原注释说不存是「same contract as every chat client」，Telegram 推翻了这个前提（每个对话存草稿，清空立删，切走、失焦、关窗必存）。存 localStorage、只存文字（图片的对象 URL 关 App 就失效，配额也撑不住），每次改动当场写；删会话时在 `forgetDeletedSessions` 清键（没选「会话列表加载后比对」：列表按当前运行时过滤，会误删另一个运行时的草稿）。
2. **工作台发出后留白**（票 06）。JC 真机确认今天新消息停在底部附近：设计文档要的是你的话停在视口顶下 32px、阅读回复期间不跟随，但列表底下没留白，滚到底就停了，随后跟随把它一路推上去。Telegram 的 live tail 用 `min-height` 留白；我们同样用对话列的最小高度（没用 spacer：落定时过程收起会让滚动位置被夹住、你的话跳一段）。JC：「只做工作台；按你推荐，A」：主对话是 IM 贴底（主对话 PRD 裁决 67），Telegram 自己也是普通聊天贴底、只有机器人流式回复才留白；回复超出一屏后**不跟随**（没选 Telegram 释放后贴底跟随：那正是长回复要往上翻才能读的原因）。排队的消息自动发出时不停靠（你多半在读刚出来的回答）；CLI、Supervisor 发进来的照旧。
   - 顺带修了一个从 09-08 起的老问题：发出计数是全局的、`MainView` 按会话重挂载，每次切换会话都会把那个会话最后一条你的消息停到顶上，而不是落到底部。
   - **2a**（票 09）：不跟随之后，跑的途中 ask_user 若出在屏幕以下不会被拉进来。JC：「工作台跑的途中，要自动滚过去让用户看到」。问题一出现、没完整露出就滚到完整可见；你往上翻过这一轮你发出的那条就不动（判断式：`userMsgParkOffset > 8px`）。
3. **选中文字可以引用进输入框**（票 02），两边都上。第一版把 `> ` 写进文字，JC 真机：「这个引用文字的显示 UI 我觉得不好看，有点简陋」；发出后气泡按纯文本显示，也是一行行 `>`。**3a**（票 07）：引用不进文字，在输入框卡片内文字上方单独一条（上限 3 段、同一段不重复），发出时才拼成 Markdown 引用（助理收到、库里存的、CLI 读到的都照旧是文字）；气泡里认出开头的引用单独画。没选只改气泡（输入框照旧简陋）、富文本输入框（输入法、粘贴折叠、文件引用都建在纯文本框上，等于重写）、点引用跳回原文（要么改库，要么按文字匹配去猜）。`/btw` 要拼成 `/btw` 在最前，否则侧问会变成主任务。
4. **打字即聚焦、点按钮与空白不失焦**（票 03）。输入框为空时 ⌥↑ / ⌥↓ 照样跳（否则输入框更常有焦点后跳转就用不上了）。中文输入法真机测：第一键落成英文字母（WebKit 的输入法只在焦点已在输入框里时才接手）。JC 起初觉得「用户只要去输入框点一下再输入，就是正常的」；主会话拿这句当尺子：先点一下时 `off` 与 `pass` 一样，忘了点时 `off` 什么都不发生、`pass` 多出错字要删，对中文用户 `off` 处处不差。JC：「按你推荐，改成 off」。打字即聚焦关掉（开关 `TYPE_TO_FOCUS_MODE`，另两档留着），按下不失焦与空输入框里的 ⌥↑ / ⌥↓ 照常。
5. **我们自己的平滑滚动**（票 04）：时长 300–600ms 按距离，远于 800px 先瞬移，开了减少动态效果一律瞬时（我们 `foundations.md` 本来就这么要求，对话里四处 smooth 写死没守）。顺带修了四处文档与文案出入；「轮间距层级」重量后已不倒挂（轮间 50px、对内 30px）。
6. **切换器真机比**（票 05、07、08）：
   - A 输入框长高：选 **A3**，时长 `round(50 × ln|Δh|)` ms（两个客户端同一个公式），缓动用我们的 `--ease-firm`（JS 里从 token 读）。理由：输入框长高时对话保持贴底，每长一行整片对话跟着挪，动画缓的是整片对话；固定 100ms 让贴一整段时 100ms 冲 157px。照 Telegram 用 CSS transition 时 Chrome 里有一帧没贴底（低 17px），改为逐帧写高度。在 `foundations.md` 与程序滚动记同一条例外：时长随距离变。
   - B 主对话连发的组内圆角：选 **B1 不改**。JC 的主对话一次连发都没有、全库 5 处都在工作台；在跑时发的话进队列、隔着回复单独跑；助理一侧有 30px 行动条，按规则凑不成组。若排队的消息改成对话里的气泡（主对话 PRD 裁决 71 第 6 条），连发会变常见，那时重比（若做取 6px）。
   - C 输入框里的引用条：选 **C2**（↳ 在 ＋ 那一列、一行；C1 的竖线占了文字那一列，引用的字比输入的字右缩约 20px）。
   - D 气泡里的引用：选 **D2 气泡内顶部**。JC 第一次切 D 看不出区别：查库发现票 07 合入后没发过带引用的消息，D 只画在以引用开头的消息上。JC 带引用发了之后：「有点选不出来，你说说你的独立意见」。主会话改推 D2、推翻原推荐 D1：JC 起头的原话是「有点简陋」，D1 灰字加竖线仍是朴素那一路；引用就写在你这条消息里，气泡装的应该就是你发出的东西；原推 D1 的理由「杏沙是人的声音，D2 混两种声音」站不住，引用是你的动作，像邮件回复里引用原文；D1 还要为「你的消息停在顶上」在五条路径上开例外。代价：短回话被引用撑宽、气泡变高（三行省略）。
7. **滚动时浮动日期**：进 [deferred](./deferred.md)「滚动时浮动日期（主对话往回翻）」。主对话只有 8 轮，没东西可翻也没法真机比。

## 没学的

尾巴、阴影、时间嵌进气泡、悬停看时间（与已定规则冲突）；大号 emoji（没人这样用）；流式匀速显示（主对话有意不流式，匀速会人为拖慢）；表格等宽列（我们的表格常是一列短一列长）；未读条数、打字三点（否过）；↑ 编辑上一条、Esc 逐层关闭（没有对象）；回到底部的 50px 阈值与防闪（没见过闪）。

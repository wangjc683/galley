# v0.4.6 发布：把 composer 从运行状态里解耦出来，把失败从一整段里拆开

**日期**：2026-08-12
**范围**：v0.4.6 发布叙事，聚合 `v0.4.5..HEAD`（3 个提交，其中 2 个代码）

## 背景

`v0.4.5` 是第一个由真实用户 issue 驱动的版本，`v0.4.6` 是第二个——而且
**四条 issue 全部来自同一位报告人（Kinda2419）**：#19 / #20 / #22 是
本版内容，#21 只落了 PRD 与三个子 issue，未实现。

这一批的性质和 `v0.4.5` 不同。上一版修的是**通路**（收不到通知、找不到
反馈入口），这一版修的是**工作流本身**：

- #19 / #20：运行中想补一句话必须先暂停，误伤正在跑的任务；点了暂停
  之后输入区还锁着，把实现细节的等待成本转嫁给用户。
- #22：任何失败都以一整段无差别文本砸进 transcript——报告人原话
  「我看不懂，我也不知道问题出在哪里，不知道如何继续」。

两条线的共同点是：**功能都在，坏的是人机之间那一层。** #19/#20 的能力
（串行排队）在 GA 引擎层本来就有，只是不可控；#22 的数据在 payload 里
一个字段不少，只是渲染方式让人读不了。

## 版本决策：patch

沿用 `v0.4.1` 确立、后续四版复认的规则（按最大单功能量级判，不按批次
总量判）。本批最大单项是会话消息队列——它有 Core 侧新模块、新命令、新
事件、新 CLI 契约字段，体量不小，但落在 composer 这个既有 surface 上，
是「发消息」这件事的增量，撑不起独立产品线。

产品形态、Agent API `schemaVersion: 1`、GA baseline（`308153b`）、更新
渠道策略均不变。**managed GA 未触碰**，故 bundled runtime gate 本次
可跳过（与 `v0.4.4` 同，与 `v0.4.5` 不同）。

## 这一版最值得记的一件事

**调查推翻了「运行中 send 是错误路径」这个前提。**

原本的 CLI 设计定案是「不动现有行为，加一个 `--queue` 显式排队」——
这是保守且正确的默认姿势。但拿 file:line 核实现状后发现：Core 的
`dispatch_session_send` 压根不检查 `agent_running` 就透传给 bridge，
而 bridge 一收到 mid-run 消息就 `run_in_progress.set()` +
`_emit_turn_start(1)`。**消息其实还排在 GA 队列里没开跑，事件流已经
谎报它开跑了**，两个进度 drain 线程互踩。

现状不是「错误路径」，是**事件流损坏的 de facto 排队**。保它没有意义，
于是 CLI 改为默认走 Core 队列。

教训写成一句：**「保持现有行为不变」的前提是现有行为是对的。** 兼容性
默认值不该盖过对现状的核实——尤其当那条路径从来没人显式设计过，只是
「碰巧能跑」。

## 真机验收（2026-08-12，JC）

两条线都过：

- **队列**：运行中发送入队 → 任务结束自动接续；停止中发送 → 停止后
  自动发出；插队打断；chips 编辑 / 删除；CLI 对运行中会话返回 queued
  形状；ask_user 挂起时队列不抢跑。边界「插队抢占后提问气泡残留」当场
  发现并已修。
- **错误呈现**：四个 summary 消费点的占位、`code_run` 抛异常的
  `failed-historical` callout（含恢复路径折叠态）、泄漏 markup 正文的
  `ProtocolFailureNotice`、en 语言下三处文案。

验收方法上留一条经验：**前两类场景没法靠真实模型稳定复现**（要的是
历史脏行和第三方代理的透传行为），用 SQLite 夹具会话造；但
`code_run` 报错那条坚持真跑——它验的是「GA 错误信封形状」这个
coupling point 本身，用夹具造等于自证。

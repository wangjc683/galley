# 主对话删单条消息：推翻「删单条不做」

日期：2026-10-16
关联：[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 59、83，票 [32](../../.scratch/main-chat/issues/32-delete-single-message.md)；[deferred](./deferred.md)「主对话里删单条消息」（出列）、「工作台会话删单条消息」（新）

## 起因

JC：「普通会话是可以整个 Session，直接用户自己就删掉归档。那现在如果是主对话里面，有部分用户想要删除，不，至少是不太显示的消息。你觉得需不需要加这个删除消息功能呢？」

10-14 定重置时（裁决 59）删单条判为不做：删掉记录，当前这一段的上下文、长期记忆、模型服务商那里都还在，等于许诺做不到的事。

## 三条理由倒了两条

1. **当前这一段的上下文能清掉，而且不用切段。** runner 的历史本来就是 Core 从库里重放的（`core/src/session_runner/replay.rs`），切段也只是退掉在跑的 runner 再重起（`core/src/session_runner/segment.rs`）。删库里那几行、悄悄退掉 runner，下一句起它就看不到了，这一段别的话都在。deferred 原方案「从下一句起换新段」会连别的话一起丢。
2. **服务商那里是 IM 的老规矩。** 微信的「删除」只删你这边，「撤回」才是两边都没；主对话照 IM 做（裁决 60），用户本来就懂。
3. **长期记忆确实收不回**，照实承认。

另一个理由：主对话长久存在，出口只有连长期记忆一起清空的重置；工作台的会话本身就是删除的单位。对话越长久越需要单条删。

不做「只隐藏」（库里现成的 `visibility` 列，很便宜）：它仍在上下文、库、搜索、查历史里，助手可能接着提起你看不见的话；想删的最强理由是误发密钥、证件号，隐藏恰恰解决不了。

预防性：没有用户提过，JC 库里 10-14 重置后的 12 句没有敏感内容。

## 裁决

- JC：「整体方案我认可你推荐的 C」：右键主对话里任意一条气泡 →「删除」→ 确认框点一下；你的话与它的回复各删各的，回复连同过程算一条；在跑、在等你回答、带子任务卡片的回复置灰；只做主对话。
- **确认框只有标题**「删除这条消息？」。主会话推荐写一句收不回的代价（「它之后也看不到这条了。已经发给模型服务商、记进长期记忆的收不回。」），JC 选不写正文：「对于用户来说，负担最小最容易理解」。设计文档「正文写全删什么」加一条例外：只删一条、标题已说全时可以没有正文。
- **工作台不跟**（JC：「按你推荐」），进 deferred：工作台会话短（9 月以来 78 个，最长 8 句你的话，54 个不超过 2 句），删整个会话代价小；同期 30 个是 CLI、Supervisor 或系统建的，在别人读着的会话里删消息打破「记录就是发生过的事」；还有步骤与折叠头的结构、外置运行时的验证面。

## 实现要点（票 32）

- 界面只传被右键的那一行，Core 按桌面同一套分组规则算出整条气泡、删掉、把行 id 报回来；叫醒那一轮连同看不见的叫醒行一起删。
- 重放不加规则：Core 重放与 `llmcore.py` 的 `_fix_messages` 都会合并相邻同角色，删掉一条后照样一问一答交替；夹具加三条用例。
- 附件目录先原地改名挪开，挪不开就整个不删；`turn_index` 只升不降（下一条取「最高下标 + 1」与 `turn_count` 的大者）。
- 主对话里打开 `splitAfterAnswer`：收尾的回答之后又来一条它的话（中间那句你的话被删了），另起一个气泡。工作台不开：GA 偶尔在看似收尾的一步之后接着跑。主会话核对过 JC 主对话里那一轮带三段回答的（10-15 DAED），中途两段都带工具调用、不算收尾，不受影响。
- 远程协议加 `message.deleted`，旧端忽略不认识的事件；删的是最新回复时会话摘要改取剩下最新的一条。
- 留下的：被删原文可能留在库文件的空闲页里直到被覆盖、引擎日志 30 天、迁移前的自动备份；检查与退掉 runner 之间有毫秒级竞态（CLI 绕过排队直接派发时那一轮会被中断）；整段平铺的中止运行没有右键菜单。

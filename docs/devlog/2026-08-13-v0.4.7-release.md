## 版本决策：patch（JC 裁决，2026-08-13）

这一票有真实分歧，值得留痕，因为**先例指向 minor**。

支持 minor 的两条：Telegram 作为第三渠道当年是 `v0.3.0` 的头条特性；
且 Discord 比 Telegram 多带一个语义变化——**并行监督上下文**，一个
频道 = 一个独立 supervisor 上下文、独立 GA 实例、独立历史，reporter
因此从「按 session origin 路由」重写成「进程级单 dispatcher 按消息
origin 路由」。

裁决走 patch，两条理由：

1. **Telegram 那个先例有杂质。** `v0.3.0` 同批还塞了并发审计
   CONC-1..8、55 条代码审查、以及 Galley 独立产品定位重写。按 `v0.4.1`
   之后确立的规则，「批次总量大」恰恰不构成 minor 理由——所以 v0.3.0
   的 minor 大概率是批量给的，不是 Telegram 给的，援引它是弱的。
2. **并行监督上下文只在 Discord 一家生效。** 微信 / 飞书 / Telegram
   的单线对话语义原样不动。称其为「Channels 产品线的形态升级」有抬高
   之嫌；它更准确的描述是「第四张卡，附带一个该渠道专属的路由语义」。

沿用 `v0.4.1` 规则（按最大单功能量级判，不按批次总量判），产品形态、
Agent API `schemaVersion: 1`、GA baseline（`308153b`）、更新渠道策略
均不变。CLI / Agent API **零改动**——supervisor id 是不透明字符串，
按频道路由复用既有 message origin schema 字段。

## 这一版最值得记的一件事

**发布前的门禁讨论里，一个「成本论证」差点替代了验证。**

发布评审时列出的未闭合门禁有一条是「补丁 0018 未过全栈重放」——本机
GA checkout 脏且不在 pin 的 baseline 上，当时只做了隔离重放（0018
单独应用到 checked-in 的 pre-patch `dcapp.py`，产出逐字节相同）。

第一版判断是**接受隔离重放、不阻塞发布**，论证是「零重叠」：全栈重放
要抓的是补丁间互相干扰，而 baseline 这版没动，0018 只碰
`frontends/dcapp.py`，前面的补丁没有一个碰它，所以隔离重放在数学上
等价于全栈重放的那一段。

论证本身没错，但**覆盖不全**。落实「前面的补丁没有一个碰它」这句话时
才发现栈里还有个 `0019-managed-im-strip-next-suggestion.patch`——它改
`frontends/chatapp_common.py` 和 `frontends/fsapp.py`，而后者是
`0009` / `0011` / `0012` / `0013` 都改过的文件。0019 同样没过全栈重放，
且它落在四个补丁改过的同一文件上、靠模糊上下文匹配落位，**正是全栈
重放要抓的那类情况**。同时查出 `patches/manifest.md` 的重放状态段漏记了
0019 的存在（还写着「17 patches from here on」），台账行倒是写全了。

改口的理由不是「风险变高了」——0019 自评 Low，实际风险确实低——而是
**验证成本比预估低得多**：`build-managed-ga.sh` 第 45 行自己写着出路
（`Use a clean temporary clone at the audited upstream commit`），
clone 一份干净 GA 到临时目录就能跑，全程不碰维护者的 checkout，而且
`git diff` 干净本身就是通过判据。用一次 clone 换掉一个覆盖不全的论证，
划算。

跑完的结果是最好的那种：18 个补丁全部干净应用，重建 payload 与仓库中
成品**零差异**。0018 / 0019 的重放债不是记账了，是还清了。

教训：**当一个论证被用来替代一次廉价的验证时，先核实它的覆盖范围。**
这次覆盖漏洞是在核实论证前提时撞见的，不是被门禁抓到的——如果当时省掉
那一步核实，0019 会带着一笔未验证的债发出去，并且台账上根本查不到它。

## 门禁与本地验证（打 tag 前）

- **bundled runtime gate（本版强制）**。本版动了 `GA_DEPS`
  （新增 `discord.py==2.7.1`、补回 `python-telegram-bot==22.8`），
  `bundle-python.sh mac-x64` 从零重跑绿，`import discord` +
  `find_spec("frontends.dcapp")` 在 bundle 自带 python 下验过。
  **`mac-arm64` / `win-x64` 本机不可验**——脚本靠运行 bundle 里的
  python 装依赖，而维护者机器是 Intel x86_64；这两个 arch 由
  `release.yml` 在各自 runner 上跑同一脚本覆盖（tag 时硬失败）。
  这道门禁是本版唯一有历史实证会翻车的一条：`python-telegram-bot`
  上次接 Telegram 时就漏进 `GA_DEPS`，导致 Telegram 在正式包里起不来，
  直到本次外审读代码才发现。dogfood 跑的是开发模式，验证不到这一层。
- **全栈补丁重放**：18/18 干净应用，payload 零差异（见上节）。
- **真机 dogfood**：JC 已完成，未发现问题。
- `cargo check` / `cargo test --workspace`、runner `pytest` /
  `mypy strict` / `ruff`、gui `typecheck` / `lint` / `test`、
  `check-managed-ga-payload.mjs`、`git diff --check` 全绿。
- `check-version-consistency.mjs --tag=v0.4.7`：5 个文件一致。

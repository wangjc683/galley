## 起因

JC 提出：iOS 原生 App 的讨论应回到产品设计的源头，把定位、关键功能、核心价值理清，再落技术栈与 UI / UX。
我对表后同意：上午 iOS PRD 的 21 条裁决里只有 3 条属于产品层（4 首屏、19 IM 定位、20 主聊天），其余是传输、存储列、字体、渲染、通知路由；
「定位」只有三行；核心价值没有一句话版本；主聊天 PRD 是在技术讨论中途冒出来的，而它才是关系层的产品定义；成功标准只有「比 IM 多」，
只能证明原生比 IM 好，证明不了手机端值得做。

推进方式三选一，JC 按建议选 A「先聊后写」：六问逐条给初答与反方，JC 裁，结论落一份上层文档，两份下游 PRD 回填依赖。
否决 B「我先写草稿」（初答全是推断，容易把推断写成结论）、C「等 10-16 基线复盘」（场景问题不靠基线也能先答）。
约束：产品梳理可以推翻裁决，但要点名条号与依据，默认保留。

## 六问与裁决

1. **用户**：P0 JC；P1 内置内核的个人用户。接受早期反馈只来自 JC（社区活跃用户是 CLI / Supervisor 画像）。
2. **核心价值**：我给的候选句「你电脑上的助手，随身带着」，反方问「桌面上到底哪项能力撑得起这句」。JC 给了锚：调用有自己登录态的真实浏览器，
   几乎所有云端助手搞不定，用户也不敢把登录凭证全给厂商。旁证：浏览器控制已是用得最多的能力（10-04）。
3. **关键场景**：我按猜的频率排「它来找你 / 随口一句 / 派回家才能干的活」，反方说只有第三条独有且低频。JC 推翻我的前提：现代人手机比电脑用得多，
   手机上可以真正干活，有电脑可操作的助理能满足大量场景。于是场景按价值重排，派浏览器活排第一；并推翻 `docs/PRD.md` §2 第 3 条「手机上是管理」
   与上午「手机是平级的第二个前端」，改为「手机是人所在的地方，电脑是助理的工作台」。
4. **与主聊天的关系**：我问「手机等主聊天，还是先做随身端再接」。JC 的答案在两者之外：主聊天是 Galley 下一步重点，不只是移动端，桌面与移动一起；
   理由是 Galley 不是 coding agent、不是 IDE，是本机的全能 AI 助手，持久主会话更接近人对助理的想象与认知。
   推论：手机 v1 是主聊天 App；三块专门设计进入手机关键路径。我建议（未裁）按主聊天 PRD 裁决 8 的次序，P0 带「入口层提示词 + 窗口预算参数」上线。
5. **非目标与离线**：电脑离线等于助理没法工作，提示即可；最多可读历史 + 排队发送。P0 提示与可读历史，排队发送 P1。
6. **成功标准**：JC 给的是北极星：用户习惯在手机上和 Galley 助理沟通，甚至愿意单独买一台 Mac mini 24 小时供它用，
   每个人都有自己的全能助手、秘书、管家和私人导师。可观测指标（硬标准「关掉 IM 渠道」+ 三个场景用量）是我的建议，JC 未逐条裁。

## 新发现的待定

- 浏览器任务卡在验证码、二次验证、确认支付时，人在手机上怎么介入。这是核心价值场景的关键一环，上午没有任何一条裁决覆盖它。
  先查内置运行时现有的「在问你」能不能承载，再定要不要专门的介入形态（截图回传、一次点击）。
- 派活后手机上看什么进度。
- 场景 1 的真实频率，10-16 基线复盘一并看。

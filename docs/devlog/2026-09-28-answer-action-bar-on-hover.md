# 回答操作栏：悬停回答时才显示

Date: 2026-09-28
Status: implemented; four-variant switcher live-tested on JC's desktop the
same day, hover picked; switcher removed; static gates green; unreleased
Related: [conversation design §Message Actions](../design/conversation.md),
[同日用户消息发送时间](./2026-09-28-user-message-send-time.md),
[06-29 指针优先的按钮焦点](./2026-06-29-pointer-first-button-focus.md)

## 起因

JC 截图回答下方的操作栏（复制、保存 | ↑ 5k ↓ 314 ⊙ <1%）：「有的时候我其实觉得
这一块也有点吵，但是长答案的时候又还好」，提议改成悬停才显示，还没想好。

## 旧裁决

- 常驻是 V0.1 按试用反馈定的：只在悬停出现，用户得到处找（`MessageActions.tsx`
  顶部注释；设计文档「常驻可见（不 hover-only）」）。针对复制、保存能不能被发现。
- token 行 2026-06-25 加（`6437162e`），没有 devlog 记为什么常显。
- run-fold 领土划分：Footer = 机器成本（token、上下文）+ 复制 / 保存。

## 数据（workbench.db 只读，截至 2026-09-23）

- 每轮最终回答 397 条：<50 字 67（17%）、50–150 字 38（10%）、150–400 字 61、
  400–1000 字 107、≥1000 字 124（31%）。约 27% 的回答只有一两行，栏的体量和回答
  相当，这解释了「短答案吵、长答案还好」。
- 上下文占用 168 条：65% 在 10% 以下，≥50% 只有 8%。历史回答上的读数是过期状态。

## 我的推荐与真机结果

四个方案：A 整条悬停；B 最新一条常显、历史悬停；C 常显但只留复制、保存、仪表三个
图标，token 与上下文收进仪表图标的悬停提示，上下文 ≥50% 时百分比常显；D 按答案长度
分（同一组件随内容变行为，不推荐，没进切换器）。

我推荐 C，理由里最重的一条是同日的反证：用户消息的悬停时间刚被 JC 砍掉（「有点吵，
也没有必要」），我推断悬停浮现在他那里本身算吵，悬停整条栏会在读长答案时随鼠标
进出而闪。临时切换器（现状 / A / B / C，默认 C）真机比较后，**JC 选 A：「悬停最
舒服」**。我的推断被真机推翻：用户消息旁的悬停时间和回答下的悬停操作栏，在他那里
不是一回事。以后别拿「悬停时间被砍」去推断别的悬停方案。

## 落地

- 悬停区是 `MessageAgent` 外层 `group/answer`（答案正文 + 操作栏）；栏平时
  `opacity-0 pointer-events-none`，悬停时显示，隐藏时保留占位，悬停不引起位移。
- 「已复制 / 已保存」反馈的 1.5s 内保持可见。
- 不做键盘聚焦显形：06-29 指针优先规则定过悬停才出现的动作不进 Tab 顺序，chip 本就
  `tabIndex={-1}`，子代理加的 `focus-within` 实际不起作用，定稿时删掉。
- 栏的内容不变（复制、保存 | token 与上下文）；C 的仪表图标合并提示、50% 门槛等
  代码随切换器一起删掉。
- 注释跟着改：`MessageActions` 顶部「Always-visible」段、`ActionChip` 的「persistent」
  类别、`MessageUser` 里两处提到「回答操作栏常显」的句子；设计文档 Message Actions
  一节；deferred「长时间运行的完成时刻」的背景（操作栏当时常显，现在悬停栏成了
  放完成时刻的另一个候选位置）。

## 已知代价

- V0.1「用户得到处找」的顾虑重新成立，对第一次用的人尤其如此。复制最新回答要先把
  鼠标移到回答上。
- 上下文占用平时看不到。接近上限时没有常显提醒（C 的 50% 门槛随之放弃）。

纯前端，内置 / 外置两种运行时模式零差异。

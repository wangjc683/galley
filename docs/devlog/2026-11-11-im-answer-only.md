# IM 回答里只有回答：撤掉过程入口，问它就说

日期：2026-11-11
关联：`.scratch/im-answer-only/`（PRD 裁决 1–6、票 01–02，发版后删）、补丁 `0023`、`0024`、`0026`、`0029`、`runner/im_wechat.py`、`core/src/managed_prompt.rs`；
[IM 打磨](./2026-10-21-im-polish-process-button-and-feishu.md)（本条推翻它的裁决 1、裁决 2 的按钮部分、裁决 3 的过程入口部分）、[§9 Channels](../design/overlays-and-settings.md)、[提示词组成](../managed-ga-runtime/prompt-composition.md)「IM Entry Layer」

## 起因

JC 在 Telegram 点最近一条消息的「过程」，得到「过程已不在了（渠道重启过）」：「我现在考虑是要修复这个问题，还是直接去掉过程，让 Telegram 更有真人 IM 对话的体验，只剩下最终消息回复。」他这次点是想试按钮可不可用。

渠道只跑在内置内核上，外置零变化。

## 诊断

- 按钮背后的步骤只存在渠道进程的内存里（Telegram、Discord 各 256 条的 LRU），渠道一重启就没了。这是 10-21 认下的代价，当时估轻了。
- 重启有多频繁：维护者机器的渠道日志里，10-21 以来有记录的 16 天共启动 94 次，约每天 6 次（开发机偏高）；普通用户每次退出重开、每次更新也都重启渠道。按钮的寿命是「到下次退出 Galley 为止」，机制上必然。
- 点击量量不了：点击不写日志。
- 10-21 的前提「IM 是唯一能看过程的地方，所以只能藏，不能删」把「有界面入口」和「看得到」混在了一起。渠道重启后，`runner/im_resume.py` 会从内核日志把完整的原生历史（含每步的工具调用与结果）装回 agent，所以 agent 自己一直记得怎么做的。按钮做不到的事，问一句做得到。
- 按钮展示的本来也是模型每步写的摘要（60 字截断、最多 30 步），不是工具级记录。
- 四个渠道当时的样子：Telegram 按钮（内存）；Discord 按钮、ephemeral（内存）；飞书卡片里的折叠面板（不依赖内存）；微信末行「N 步 · 用时 X」，从 10-10 起就没有过程入口。

## 裁决（JC）

1. **删掉过程入口**。回答下面什么都不挂；在跑时的状态消息照旧；想知道怎么做的就问。这是换通道，不是删信号。
   没选：持久化（把步骤摘要写进渠道状态目录，越过 `im_resume` 自己画的「只存文件名，不存对话内容」那条线；或只存日志指针、点击时从内核日志重建，新增一处日志格式耦合；两者都要在 tgapp、dcapp 各做一遍，是为一个展开入口新增持久状态，而内容 agent 本来就有）；小补丁（点到失效的按钮时摘掉、提示改成实话：昨天的过程照样看不到）。
   认下的代价：问一句要花一轮模型，得到的是复述不是清单；用时不在模型上下文里，「N 步 · 用时 X」事后没处看；`/new` 之后之前的过程问不到；Discord 频道里问是公开的、还会触发一轮运行；IM 与桌面有意分叉（桌面主对话保留过程卡片）。
2. **飞书也跟**：撤掉回答卡片里的折叠面板。代价是删掉一个没坏的东西，换来四个渠道一条规则。
3. **微信末行「N 步 · 用时 X」一并去掉**。
4. **不动的**：停止回执「⏹ 已停止 · N 步 · 用时 X」、提问消息的「⏸ 等你回复 · 已完成 N 步」一类、出错消息上面那行「N 步 · 用时 X」。它们是状态，不是过程。
5. **IM 入口层加一段**。先定的是不加、用真模型评测问一句的效果；评测没过（见下）后改为加：
   > The user sees only your final reply, never your steps. Asked how you did something, or to see the process (过程), recount it in a few lines from what you already did; do not run it again.
6. **已发出去的旧按钮**：点了静默应答并摘掉按钮，照 Discord 旧「停止」按钮的先例。

认下的两处小缝：重启前展开着的 Telegram 旧消息，点「收起过程」只摘按钮、文字收不回去；旧的飞书卡片里的面板在客户端里，照旧能开。

## 评测：问一句的效果（票 02）

gpt-6.1-sol，Telegram 的 IM 提示词，沙盒里真做一个至少三步的只读任务（在假的下载文件夹里找最大的几个文件），答完再问一句。两个条件：同一进程接着问；进程退出后照渠道真实的路接回（`ChannelResume.resume` → `continue_inplace(..., restore_wm=True)`）再问。四种问法各条件 2 次。

| | 不加那一段 | 加那一段 |
|---|---|---|
| 计分 12 次里三项全过 | 9 | 12 |
| 「过程给我看看」不重跑 | 1/4 | 4/4 |
| 问完之后的工具调用合计 | 3 | 0 |
| 回复字数中位数 | 379 | 281 |
| 代码块 | 5 | 0 |

- 两边都没有一次编出没做过的步骤，没有一次说看不到过程或让人去点按钮；重启接回 16 次全部成功，答得和进程内一样。
- 不加时不过的 3 次都是「过程给我看看」：模型把「给我看看」理解成再跑一遍给人看输出（「可以。我把关键检查再跑一遍给你看」）。「过程」正是旧按钮上的字。
- 「刚才用了多久？」只记录：两边都没有编数。不加时 4 次里有 1 次自己翻内核日志的时间戳答对了，加了之后 4 次都照实说没计时。各只有 4 次，分不出是这一段的作用。
- 没量的：有副作用的任务会不会被再跑一遍；只量了一个任务，每格两遍；判词是执行代理读了判的，主会话抽查了两条。

入口层 1630 → 1821 字节（`IM_PROMPT_BUDGET_BYTES`），Rust 写出的入口层与评测用的一字不差。

## 实施

组合拳：主会话写票、两个后台代理各在自己的 worktree 里做，机器验收后 `--ff-only` 合入。入口层那一段是单文件改动，主会话自己做。

- **票 01（四个渠道）**：Telegram 的回答不挂按钮，最后一段不再为过程留空间，分段与 1 步的回答一样；`^proc:` 的点击留下来当墓碑。Discord 的旧按钮不再是「旧按钮处理」里的例外。飞书的回答卡片只有可选的提示行与正文；步骤摘要只供面板用，一并删了，计步改写成等价的形式。微信的回答就是收尾那一步。`galley_im_display.py` 删掉过程块的函数与文案常量，`fold_label`、`stopped_text` 留着。Telegram 跨提问的步骤摘要留着（续跑时状态消息第一行要它），Discord 的那份逐步摘要表只给按钮用，删了。
- 补丁：`0023`、`0024`、`0029` 在提交链上改，`0026` 在新的 `0023` 上重导出（两处冲突，位置与 10-21 相同，两边都留）。从新克隆的上游重放整个补丁栈，工作区无差异。
- 测试：删掉只测过程的用例，四个渠道各加「多步回答什么都不挂」，旧按钮点击与摘除失败各有用例。提问前后的步数与用时累加、等待不计，原来靠点开过程断言，改成在停止回执与出错行上断言（Telegram、Discord 各两条，微信一条）。

## 没做的、留着的

- 四个真渠道的验收等 JC。旧按钮的摘除只在假对象上测过：Telegram 对很旧的消息摘按钮会不会报错、Discord 能不能摘掉，靠吞错兜底。
- 飞书上游原有的 `_step_panel` 不在任何运行路径上，没动。
- tgapp 里的 `_PROCESS_CALLBACK_PREFIX` 留着但没人引用，注册处用的是字面量。
- `scripts/rebase-managed-ga-patches.sh` 的工作目录写死，这次照它的步骤手工做的。
- 评测里一条回复许诺「下次我可以记录起止时间」，没有机制兑现。

## 教训

- 「只能藏，不能删」这类前提，下结论前核对「看得到」有几条路：有没有界面入口是一回事，内容还在不在是另一回事。
- 定「先不加提示词」时把评测一起定下来，结果出来能直接对上：这次不过的只有一种问法，一段话的对照当场就能跑。

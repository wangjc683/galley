# Footer 三个数字：单位不一致，以及仪表到底在量什么

Date: 2026-08-10

## 起点

JC 问主对话区 footer 里那几个数字是 token 还是字符。查下来是**混的**：

- `↑` = `inputTokens + cacheCreateTokens + cacheReadTokens`，**token**
- `↓` = `outputTokens`，**token**
- `⏲` = `contextUsedChars / contextLimitChars`，**字符**（字段名就写着 `Chars`）

三个数字并排、同字号、同色、同 `tabular-nums`，视觉上宣告「我们是同类」，但第三个的单位不同。JC 判定这是问题，要优化。

## 第一层：不只是单位，是两个范畴

单位不一致只是表征。底下是：

- **`↑↓` 是流量（flow）**：这一轮花了多少，per-turn，一次性
- **`⏲` 是存量（stock）**：会话历史攒到现在多少，累积

所以读者不但会假设单位相同，还会假设**时间尺度相同**——把仪表的数当成「这一轮的上下文」，而它是「这个会话攒到现在的历史」。

## 否决：统一成同一个单位

最直觉的修法是把仪表换算成 token 显示。**这条路是陷阱**：

`context_win × 3` 里的 ×3 是 GA 自己的字符/token 启发式，字符才是它 trim 时真正测量的量。把字符除以 3 得到的「token」是在真实测量值上套反向估算——而它旁边的 `↑` 是 provider usage 返回的真值。两个都叫 token，可信度差一个量级，比不统一更误导。

反方向（把 `↑↓` 转成字符）同样不行：token 是计费单位也是 API 原生返回，转字符纯属自找。

**结论：两个范畴天然用不同单位，强行统一都会引入假精度。正确方向是让它们看起来不同类，而不是让单位相同。**

于是行内仪表改成**只显示百分比**——无量纲，`%` 符号本身就把它和旁边两个裸数字区分开，绝对值退到 tooltip。

## 反转一：tooltip 里反而该用 token

我原本建议 tooltip 保留字符并标注单位。JC 裁决 tooltip 统一用 token，理由是免得用户在两种单位间切换。

**他是对的，而且理由比「少一种单位」更强**：`270,000 字符 ÷ 3 = 90,000 token`，**而 90000 正是用户在 Settings 里配的那个 `context_win`**。换算回 token 之后，仪表的分母不再是一个凭空出现的数，而是用户自己设过的数——对得上号，这是字符版给不了的。

代价是保留一个「约」/「~」标记，让它和真值 `↑` 的精度区分开。一个字换掉一类困惑。

## 拆 `↑`：只拆 cacheRead

`↑` 是三项相加，但三项的计费权重差 12.5 倍（fresh 1× / cache create ~1.25× / cache read ~0.1×）。一轮 `↑ 118k` 里若 95k 是缓存命中，真实成本约等于 24k；若 95k 是缓存写入，约等于 143k。同一个数字，钱差六倍——**这个加总数不能当成本读，但它长得就像成本**。

裁决用的判据是「你不会因为看到这个数做任何事」（同一条判据砍掉了行内绝对值）：

- `cacheCreateTokens` **不拆**：一次性投资，用户无法干预，且计费近似 fresh input（1.25× vs 1×），折进总量失真很小。
- `cacheReadTokens` **拆**：它过得了这一关。一是正面信号——「118k 里有 95k 命中缓存」让人知道数字大不等于烧钱；二是可诊断——缓存长期为 0 意味着 prefix 被打乱，`0017` 那个 bug 当初就是靠 footer 的 `↑0` 暴露的。

## 第二层：仪表根本不在量「上下文」

dogfood 第一轮 JC 就发现新问题：`↑ 3.5k`，但仪表 `约 59 / 90k tokens`。差 60 倍。

两个数都是准的，但量的不是同一样东西。`context_usage()` 只测 `backend.history`；system prompt 和 tool schema 每次调用都发，却不在 history 里。实测体积：`sys_prompt.txt` 1461 字符 + `tools_schema.json` 5747 字符 + managed prompt profile ~10000 字符 ≈ 3.4k token——正好是那个差额。

**这不是计算 bug，是命名问题。** 而且仪表**必须**只测 history：它的用途是预警裁剪，而 `trim_messages_history(history, sess)` 只收 history，system prompt 和工具定义永远不参与裁剪。把固定开销加进分子反而会让它和裁剪阈值脱钩。分母 90k 同理——那是 history 的裁剪线，不是模型窗口；128k 窗口里剩下的正是留给这 3.4k 开销和响应的 headroom，就是 `managed-model-presets.ts` 注释里写的设计意图。

## 反转二：负面表述在这里更好

裁决保留「上下文」这个词，在 tooltip 补一句说明。我提的措辞是「仅计会话历史」（正面表述，更短）；JC 提「不含系统提示与工具定义」。

**他又是对的。** 用户的困惑不是「这个数是什么」，而是「**为什么它比 `↑` 小 60 倍**」——这是个关于**差额**的疑问。正面表述只回答了它是什么，用户还得自己反推那 3.4k 去哪了；负面表述直接点名缺失的那部分，问题当场闭合。

我原来那句「正面表述优于负面表述」在一般情况下成立，但这里用户问的本来就是「少了什么」。判据是**用户实际的疑问形态**，不是措辞长度。

## 层级：注解 vs 数据

JC 要求这句说明的视觉层级「非常低，纯粹给好奇的用户解释」。同意，而且它有个额外理由：这是**一次性信息**——看懂一次就永远不用再看，但 tooltip 反复弹出。同权重的话就成了每次都要用眼睛跳过的噪音。

实现用**最低墨色（`ink-muted`，三档里的底档）+ 6px 间距**，没有再压字号：11.5px 的中文已经到舒适阅读的地板，再小是拿可读性换层级。

接着 JC 问 `↑` 要不要也拆成两行、把缓存那句一并压低。**否决**，理由是那两句性质不同：

- 仪表第二行是**注解**——解释指标边界，内容永不变，读一次就够 → 压到最低档正确
- `↑` 第二行是**数据**——`95k` 每轮都在变，且正是用户打开 tooltip 想要的答案 → 染成最低墨色等于说「这个数可略过」，是错误信号

还有个实际因素：`↑` 的第二行是**条件性**的（无缓存命中时不存在），改两行会让 tooltip 在一行/两行之间跳；仪表第二行常显，高度稳定。

由此立了一条规则，写进了 `tooltip.tsx`：

> 第二行是**注解** → 最低墨色；第二行是**数据** → 与主行同权重。
> 额外行是条件性的，通常该留在一行——同一位置忽高忽低读作抖动。

比「所有第二行统一弱化」信息量更大：用户能从墨色直接读出「这是个数，还是对上面那个数的解释」。

## 顺带：`<1%` 而不是 `0%`

`59/90000 = 0.066%` 四舍五入成 `0%`，会让仪表在整个会话早期显示 `0%`——看起来像坏了，而那恰恰是历史最小的时候。改成非空历史至少显示 `<1%`，真正空历史才是 `0%`。

## 一个静态检查抓不到的坑

`Metric` 原来是普通函数组件，不转发 ref 也不 spread props。Radix `asChild` 要把 `onPointerEnter` / `onFocus` / `aria-describedby` 交给 child——不接的话 **tooltip 静默地永远不弹**，typecheck 和 lint 全绿。按 `TopBarIconButton` 的既有写法改成 `forwardRef` + `...rest`。真机确认过三个 tooltip 都能弹。

## 遗留

`aria-label` 用了完整文案，Radix 又会加 `aria-describedby` 指向 tooltip 内容，屏幕阅读器会重复读一遍。另一条路是 `aria-label` 保持简短——但它原来是硬编码英文（`input 118k`），中文用户反而更差。选了本地化 + 冗余。

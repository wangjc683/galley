# iOS 原生客户端与主聊天：方向讨论

日期：2026-10-09
关联：[iOS 客户端 PRD](../../.scratch/ios-client/PRD.md)、[票 02 拆分](../../.scratch/ios-client/issues/02-core-send-takeover.md)、
[主聊天 PRD](../../.scratch/main-chat/PRD.md)、[deferred](./deferred.md)「IM 渠道并入主聊天」「设置 Agent 页去掉 Supervisor 叙事」

## 起因

JC 用 Meta Muse（2026-09-08 发布的 iOS agent app）后，认为现有 IM 渠道都不是为 agent、为 Galley 做的，达不到原生契合；
设想做一个 iOS 原生客户端，只做前端，会话和 agent 仍跑在用户电脑上。讨论中 JC 又提出一个长期的主聊天（主管家），以及
移动端只服务内置 GA、Supervisor SOP 可以退；最后读了开源的类 Muse 项目 OpenMuse 作参考。全程只讨论与落文档，没有改代码。

## 裁决与理由

**架构：手机是第二个前端，桌面 Core 是后端。**
- 起初我提「connector 是 socket 客户端，线路上跑 Agent API」，JC 指出应是两端完全同步、桌面是手机的后端——我收回：Agent API 是为 agent
  设计的（轮询、写入只有文本、`watch` 无续传、契约冻结）。架构本来就给第三个前端留了位置：`GalleyApi` 单一来源（`core/src/api.rs:1-8`）、
  `Notifier` 事件出口（`core/src/notify.rs`）；10-07 起 Core 自己写 turn 行，是手机能当前端的前提。
- 远程模块放 Core 进程内、只向外连；否决独立 connector 子进程（得把 socket 扩成完整前端接口，内部接口变半公开契约）。
- 中转：自建端到端加密 relay，放 frankfurt。必须有服务器的主因是推送（iOS 后台会断连接，只能走 APNs）。否决 Tailscale 直连
  （桌面要开 TCP 监听，撞 Rule 2，推送仍要服务器）、CloudKit 当中转（只覆盖 Mac、延迟秒级）。宪法 Rule 2 要改（票 01，措辞落地前给 JC 过目）。

**同步缺口与票 02。** 子代理调研、主会话逐条复核：历史回放完全靠 GUI 驱动（Core 里没有 `load_history` 的发送方）；由此推出一个
存量 bug——有历史的冷会话上开 Goal，GA 在空历史上开工；当天用打包版 + CLI 复现坐实（记住「蓝鲸 4721」→ 重启 → Goal 回答「不知道」，
GA 记忆无匹配排除干扰），02b 修。ADR-0002 否决过合并 socket 写入，所以新的统一 send 只给
GUI 与手机，socket 保持冻结、另写 ADR-0003。拆为 02a–02e，02e 暂缓到 P1，其中标题派生提前到 02c。复核中三条推荐翻转：
自动标题挂全部 Core 拉起的 runner（`title_source` 本身已护住 `user` 标题，「CLI 会话本来就有真标题」与数据不符：CLI 建的 22 个里 19 个是截断标题）；
`/btw` 进新 send 走不落库分支（否则手机打 `/btw` 会被当普通消息落库）；socket stop 误报的疑虑撤销（bridge 预发下一步 `turn_start`，
「假」只是一瞬）。

**来源标记：`via` 照记 `gui`，新增可空列 `client`。** 否决 `via = mobile`：两张表的 CHECK 约束要重建表；`parse_origin_via` 遇未知值报错
（`core/src/db/helpers.rs:204-215`），而 CLI 链接同一份代码、直读数据库，版本滞后真实发生过（galley#30）；外部 SOP 可能把手机消息误判为
agent 动作。否决什么都不记：P0 要统计手机用量。

**视觉：内容层与桌面一致，外壳原生。** 我先推荐「原生控件 + 系统字体」，JC 要求与 Desktop 统一、两端无缝衔接后收回一半：桌面对话区的辨识度
靠字体（用户 Inter 500 / agent Newsreader 400 的三重区分）。切法用桌面自己的「content 是纸、chrome 是材质」（`docs/design/conversation.md:34`）。
JC 附加：内容层为手机屏幕优化调整，照搬规则和比例、不照搬像素。颜色 token 与文案从桌面源文件生成。

**对话区渲染：Swift 原生 + 一致性语料。** 用真实数据量了最大风险：`workbench.db` 2147 条不重复回复里 635 条含加粗，39 条在不带中文规则的
标准 GFM 下渲染不同（典型 `**…"…"**一样`）。否决 WKWebView 复用桌面组件（对话区是主界面，手感正是选 SwiftUI 要避开的）；否决桌面预解析成
内容块（解析只能在 Core，Rust 里仍是第二个家）。

**通知：确定的规则，不推断。** 我先提「2 分钟内有键鼠操作且没锁屏算在电脑前」，JC 否决：过于复杂且不准（看视频不碰键鼠、坐桌前看手机）。
定为：手机永远收；桌面主窗口开着时照旧；主窗口关掉进后台运行模式且已配对手机时桌面不弹。JC 确认的推论：人在电脑前一直用时手机照响，
但未读与「在问你」都是 Core 状态，打开手机没有待处理内容；锁屏上已弹出的那几条，P0 在打开 app 时清掉。交互类（通知上回复、时效性级别、
角标、跨端撤回）放 P1。

**主聊天（JC 提出）。** 一条长期的主聊天，什么都跟它说，只在要并行或另开话题时开旁聊，还能主动提醒。拆开看零件大多已有：IM 渠道的对话就是
这个形态（只是不在 Galley 里、每个渠道各一条）；GA 记忆是全局的；委派与汇报机制都在；定时任务可以把主聊天当落点。它回答了 Galley 最初的
痛点「IM 是单线对话框」（`docs/PRD.md:35`）——关系走主聊天、并行走旁聊。定位上说准确：模型调用仍经过服务商，不同的是积累在用户自己的电脑上、
与模型无关。方向定下，先零成本试用一周（桌面置顶一个会话当主聊天，10-16 复盘）再定形态；只在内置内核；IM 并入放后面。

**移动端只服务内置 GA；Supervisor 分三层。** JC 定移动端与后续主力开发都在内置方向。对「取消 Supervisor SOP」，数据显示本机 161 个会话里
CLI / supervisor 建的 42 个，带标签的几乎全是试用和测试；但社区 galley#29 / #30 作者在用，且 IM 汇报、IM 委派、galley-supervisor skill 都靠 CLI。
定为：退远程叙事（随票 01 改 PRD）、降 SOP（进 deferred）、留 CLI 契约；SOP 在内部真正退场要等主聊天派活改用内置原生工具。

**主聊天要专门设计（JC 追问后定）。** 我先提「桌面置顶一个普通会话当主聊天试一周」，JC 指出主聊天的上下文编排、窗口设计和系统提示词都该专门调优——成立：
普通会话的通用方案是为「做完就结束」的任务会话设计的。读码：GA 超过 `context_win × 3` 字符就从最早整段丢、不做摘要（`managed-ga/code/llmcore.py:107-131`），
滚出窗口的对话只剩全局记忆提炼的部分；稳定后每条消息都带近乎整窗上下文，每次裁开头前缀缓存失效。定为三块专门设计（窗口预算、分层编排、主聊天入口层提示词），
先做提示词与按会话读的裁剪参数，再做摘要式压缩、案头层与检索；一周试用改为「通用方案的基线测量」，按 `telemetry_json` 量上下文与成本，体验不好不等于方向错。

**OpenMuse 参考（`CopilotKit/openmuse` @ `1ac68f39`）。** JC 找来的开源类 Muse 项目。最要紧的发现：主聊天的长上下文设计不在开源代码里——线程持久化与回放交给闭源的
CopilotKit Intelligence，每轮把整条线程原样交给模型。可借的是产品形态：固定的主线程 ID 与旁聊；派出去的活在聊天里是实时卡片、完成走通知而非注入汇报轮
（Galley 的 IM 汇报是注入合成汇报轮，多一次调用且撑大上下文）；主动建议是带依据、可接受 / 忽略、过时自动收回的卡片；记忆只记用户确认过的、可看可删。
JC 全按推荐：旁聊结果用卡片、主动建议卡片不进模型上下文、「它记得我什么」页面进待定、委派先沿用 10-06 规则不学它的 6 步硬上限。借不了的是云端托管、
默认全量遥测、容器电脑、React Native 客户端、逐条审批（Galley 10-05 已移除审批）。

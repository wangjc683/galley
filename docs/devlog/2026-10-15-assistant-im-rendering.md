## 起因

侧栏卡片已经是 IM 列表的一行（裁决 65），主区仍是工作台的任务记录。最重的气味是每条回复上面的折叠头：人发起、跑完的运行一律折叠，不看步数（`gui/src/lib/run-groups.ts:243`），一步就答完的「你好！」也有「1 步 · 用时……」。其次是发出后你的话被顶到视口顶部，短回复下面空一大片；IM 是贴着输入框从下往上长。

JC（10-14）：「我们来讨论主对话的 IM 化改造，之前这个 session 你有提到的一些方向我就觉得不错」。主会话的提案 JC 按建议推进（裁决 66）。

## 提案与比法（裁决 66）

四件，每件从最克制排起：

- **气泡**：现状 / B 只把你的话挪到右边、回复照旧是散文 / C 两边都是气泡。推荐 C：B 读起来仍是「在问 AI 工具」，和工作台只差你那句话在哪一边。风险是长回复（表格、代码进气泡会挤），所以 B 留在切换器上作对照。
- **过程**：现状 / 一行。在跑时只有一行，写它最近写出的那句旁白；落定后两步以上留一个「N 步 · 用时 ›」入口。「完全不留入口」没列：出错时会没处查。
- **时间**：现状 / 居中。断点不变，从你的气泡上方挪到两边中间；问候上面也给一条。
- **滚动**：现状 / 贴底。短对话贴着输入框，发出后滚到底，回复开头快滚出视口时停住。

输入框放第二轮：模型与推理强度要挪进顶栏的菜单，改的是切换模型的习惯，等前四件定下来、JC 用几天再说。

设计文档写着「单侧容器，不是 IM 双侧气泡」「不要 right-align」，理由有两条：一是「对话是一份文档、一个阅读左缘」，助手要改掉的正是这一点（裁决 60）；二是气泡右缘会和问题轨相撞，而主对话已经没有问题轨。所以助手分出去不守这两条，工作台照守，不算推翻。「不要边框、不要投影、不要小尾巴」两边都守。

比法：tauri dev 里一个切换器，四件各自切，另有「全部现状」「全部推荐」两个快捷。JC 的主对话 10-14 早上刚重置，只有 4 问 4 答，所以加了演示对话。演示全部合成、中英两版，跨三天，带表格、代码、提问、子任务卡片、图片和连发，另有在跑、在问你两档。只换显示、不存库，演示时输入框禁用。

## 试验（票 19）

子代理定下的做法与数值：

- **宽度上限**：你的 `min(80%, 560px)`，560 约一行 37 个汉字，是手机 IM 的行宽；它的 `min(88%, 680px)`，放得下 5 列的表格，右边至少留 12%。
- **它的气泡底**：票里要求从现有 token 挑，选了 `bg-hover`（浅 #F0F0F0、深 #24272C）：离页面底 ΔL* −3.2 / +8.0，离杏沙 ΔE 约 12，两边靠色相分开。`code-surface` 在浅色纸上太淡。
- **气泡里的代码与表格**：在纸上比纸深一级的，进了气泡就比气泡再深一级。行内代码和代码块换成 `bg-line`，代码块去掉 hairline，免得框里套框；表头去掉比气泡亮的 `bg-surface`。
- **分组间距**：同一边 4px，你 → 它 20px，它 → 你 30px。回复的行动条本来就占着 30px，再加间距会让对话读成一问一答的一对对。
- **一行**：
  - 取「你最后一条消息之后」它最近写出的一句，正在流出的取第一行；超过 3 秒带计时。
  - 回复一收口这一行就消失，不等 `run_complete`；「N 步 ›」常显在行动条最前面。
  - 不用启发式猜流出的那段是不是回复（JC 要确定的规则），代价是长回复要写完才整条出现。
- **贴底**：「回复的开头」是你的话后面第一个有高度的元素，跟随到它离视口顶部 32px 为止。

「全部现状」与开工前的 main 逐像素比 48 个画面，全部一致（主对话、普通会话、子任务、外置运行时）。

## 裁决（67）

JC 真机比完：「真机看了，全部按你推荐」。

- 四件都取推荐档：C、一行、居中、贴底。B 与各件的现状不进定稿；工作台和子任务本来就是现状画法，照旧。
- 主会话上一轮只列出、没给推荐的几处，这次推荐照试验保留：间距、入口的位置、子任务卡片紧贴气泡、答完提问后那一行回到「思考中」、回复一收口就消失。
- 补两处：
  - 问候上面给时间条：`rowsToTurns` 带上问候那一行的 `created_at`。第一条用户消息改成跟问候比，60 分钟内、同一天不另起，免得一打开就是两条挨着的时间（演示里是 08:40 与 09:12）。
  - 气泡底单立一个 token `--color-assistant-tint`，值同 `bg-hover`。这样以后调悬停色，气泡不会跟着变。

## 顺带：回复里的拉丁字从来不是 Newsreader

子代理在 harness 里量到，主会话在 JC 正在跑的 dev 的 CSS 里核实：`MarkdownView` 的 `font-[var(--galley-prose-serif)]` 共 8 处（`caf1c1a4`，06-09 起），Tailwind v4 推断不出类型，默认当成字重，编译成 `font-weight: var(--galley-prose-serif)`，字体族继承了 Inter。中文本来就落到苹方 / 雅黑（06-20），受影响的是拉丁字母和数字，英文界面的回复整段都是无衬线。裁决 66 写的「它的字体照旧 Newsreader」因此是错的。

我推荐先不动：所有对话都受影响，混进 IM 画法的比较会干扰「像不像 IM」的判断。JC 按推荐，进 [deferred](./deferred.md)「回复正文的拉丁字体」，等 IM 画法定稿后单独比「修好」与「现状」，或者把文档改成 Inter。foundations.md 的字体表下面加了一句指向，免得后来的人照着文档再写错。

## 宽松下回复跟着变宽（裁决 79）

JC：「我们阅读宽度是看设置两档的，现在如果改成宽松好像有问题」。主会话用票 22 的 harness 在 Chrome 里拍了三种窗口、两档宽度：没有溢出或错位，问题是宽松在主对话里几乎没有作用。回复的上限 `min(88%, 680px)`，紧凑栏 760 的 88% 是 669，所以 680 只在宽松下起作用，作用是把宽松抵掉：回复只宽 11px，你的气泡被推到栏的最右，回复右边空出 435px（1480 窗口）到 520px（1920）。宽松 05-13 加进来是给代码块与工具输出更多地方，主对话里这些都在回复气泡里。680 是票 19 定数值时写下的「宽屏下也停在 680，不拉伸」，票 20 的自查截图拍了宽屏，只查了溢出，没问宽松在这里还剩什么。

三案：回复跟着栏变宽（推荐）；主对话固定 760，显示里的阅读宽度置灰；维持现状只改文档。JC：「直接定 A」。去掉 680，回复、子任务卡片、过程卡片只按栏宽的 88%，宽松 1200 栏下 1056；紧凑三种窗口的截图改前改后逐字节相同。你的气泡留在 560。顺带把在跑时那一行的取字上限从 160 提到 240：那一行本来就跨整栏，160 是按 680 宽算的，宽松下英文长句会断在半截、不出省略号。

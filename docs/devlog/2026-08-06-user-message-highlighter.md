# User 消息重设计：callout 色板 → 高亮笔（b-fused）

日期：2026-08-06。起因：JC 对 MainView 用户消息的「生硬大棱角矩形」
再次不满——2026-08-05 的 shrink-to-fit 只治了底色面积与内容量脱钩，
没治好体感。本次从「用户消息在文档隐喻里究竟是什么」重新推，经两轮
真机 A/B 落定高亮笔形态。

## 诊断

圆角不是病根（此前已两次量化否决：17:1 slab 上 4px 圆角只动 0.04%
像素 + `border-l-4` 削楔）。病根是 **slab 本身**：大面积平涂矩形读作
UI 机件；且 ToolCallout 是 `rounded-md` 圆角盒子，全视图唯一硬直角
的块恰是用户的声音——寄存器倒挂，机器圆润、人方正。

「一眼认出用户消息」拆成三个任务：滚动回找（靠前注意信号：颜色 /
朝向 / 尺寸，扫视者不读字）、静读辨声（排印足够，访谈体范式）、
略读边界感知（中间态，slab 移除后唯一真缺口）。

候选身份三个方向：**访谈体**（《巴黎评论》范式，纯排印无底色）、
**高亮笔**（底色逐行贴文字）、保块调压（继续微调，被判为隔靴搔痒
不试）。

## 实验（真机两轮，MessageUser 内临时 ⌥V 变体切换器）

- **Round 1**：访谈体 a1（删底色留竖条）/ a2（竖条悬挂栏外）/ a3
  （a2 + Inter 600）vs b（高亮笔）。**b 抓眼度遥遥领先**——色彩面积
  才是滚动扫视依赖的信号，竖条「颜色+朝向」的前注意信号敌不过色域。
  推翻了「排印+竖条足以承担锚」的预判，反向验证旧文档「杏沙底保证
  滚动可扫视」的断言。访谈体虽概念上最忠于文档隐喻，被实测干净否决。
- **Round 2**：b-gap（行间留 ~3px 细缝的笔触版）vs b-fused（纵向
  padding 5px 融合成片）。dev 实测 **b-fused 胜**。

## 定案

逐行杏沙笔触：`bg-brand-tint` + `box-decoration-clone`，按硬换行分
段、每个非空白行段独立笔触（软换行由 clone 自动逐视觉行描），纵向
padding 5px 在三档字号（leading 1.65–1.75）下都融合成片，右缘随文字
参差；**无竖条**（高亮即色彩锚，双锚冗余，4px 竖条退出 user
register）；笔触 2px 圆角（反圆角论证是 slab 几何产物，不迁移——
笔触上的圆角可见且读作笔感）；纯空白行不上色（粘贴内容的空行不渲染
成无字色块）；横向 4px 出头用偏移 box-shadow 绘制（见下方 dogfood
修正）。滚动锚机制（`data-role` / submit 置顶 / Question Rail /
`line-clamp-6` / copy chip 悬浮位）全部不变，只换皮。

- **2026-06-20 排印统一不动**：色彩仍承担区分职能，只换形状，Inter
  medium 同字号保留。
- **回找提问与形式同构**：滚动回找从此是字面意义的「找到被划过的
  句子」。
- **GoalCommissionMarker 故意不跟**（翻转原「必须同步」约定）：委派
  标记保留竖条 + 色板 + 硬边作**加冠正装**，平民笔触 vs 加冠色板的
  对比本身成为「Goal 委派 vs 普通消息」辨识度的一部分。

## Dogfood 修正（同日）

首版笔触用 `px-1 -mx-1` 做横向出头，历史 session 里「hey」被折成
「he / y」：WKWebView 计算 `w-fit` 块的内在宽度时不计行内元素的横向
padding，布局时又实际占用它，块因此短 8px，`break-words` 随即拦腰
折行。改为一对偏移 box-shadow（`±4px 0 0 var(--color-brand-tint)`）
绘制出头——完全不参与布局（行盒是纯文字宽），随
`box-decoration-clone` 逐段克隆并继承笔触圆角，视觉结果不变，token
主题感知（明暗自动切换）。

## 被否

- **访谈体（纯排印，a1/a2/a3）**：滚动可发现性实测不足，Round 1 出局。
- **b-gap 细缝笔触**：「一笔一笔划过」的质感近看更字面，实测 JC 倾向
  融合版。
- **给普通消息加 eyebrow / 图标**：稀释委派标记加冠行的对比度。
- **高亮 + 竖条双锚**：信号冗余。
- **保块调压**（减淡底色等参数微调）：shrink-to-fit 已证明调参不触及
  病根，未进实验。

## 后续修正（2026-08-10）：copy chip 没跟上换皮

定案时把「copy chip 悬浮位」列进了「全部不变，只换皮」的清单。位置确实
不用变，但**皮和间距都该变**，当时没查——两条都是这次换皮的隐藏副作用。

**间隙被 box-shadow 吃掉。** chip 定位是 `left-full ml-1.5`，而
`left-full` 落在**文字**右缘：横向 4px 出头改用偏移 box-shadow 绘制后
完全不参与布局（正是上面 dogfood 修正的目的），墨色却实实在在向右多走
4px。写下 `ml-1.5` 时它是 6px 间隙，换皮之后它是 **2px**。改 `ml-3`
补回净 8px。

可推广的形态：**凡是用 box-shadow / outline 画出的视觉延伸都不进布局，
所有基于布局边缘（`left-full`、`right-0`…）的定位都会悄悄少算这段**。
下一个想贴着高亮块放东西的人会再踩一次。

**chip 穿错了皮。** 它用 `variant="floating"`——实边框 + 实底
`bg-elevated` + 投影。那身装甲是给选区 chip 的：它要 portal 到任意文字
之上，必须把自己从底下内容里切出来。用户消息的 chip 待在干净留白里，
不需要装甲；而一个带边框的控件盒紧贴笔触，正是本次改造要治的**寄存器
倒挂**又犯了一次（机器该克制，人的声音是手划的）。改 `inline`（裸图标
24px，hover 才有淡底）。

根因是 `ActionChip` 的文档把两件事绑成了等式：「persistent = inline，
transient = floating」。于是「瞬态」自动推出「要边框实底」，错的变体看
起来天经地义。拆成两个独立维度写回注释：

> **何时出现**（persistent / transient）与**穿哪身皮**由不同问题决定；
> 皮肤只看**背后是什么**——落在任意内容之上、需要把自己切出来的才用
> `floating`，坐在干净画布留白里的一律 `inline`。

按这条，用户消息 chip（瞬态 + 干净留白）与选区 chip（瞬态 + 压在文字上）
同为瞬态而皮肤不同，各有其理由。

顺带把 `ACTION_HIDE_DELAY_MS` 1800ms 收到 600ms：这个延迟当初是为「从
消息移到按钮不用追」设的，而 chip 就在 8px 外，1800ms 只是在鼠标离开后
留一条尾巴。

**锚点保持右上**（JC 真机复核后裁定）。`left-full top-1.5` 的两个假设
其实都是 callout 时代的——`left-full` 锚的「块右边缘」在参差右缘的笔触
形态下已不是视觉对象，`top-1.5` 锚第一行则在多行长粘贴时离阅读终点最远，
而多行长粘贴恰是这个按钮最有用的场景。判断是绝大多数用户消息为单行短句、
此时两者无差别，不值得为长尾改动；留作已知的待议项。「移到块下方成行」
被否：会与 assistant 那条持久 action bar 的形制靠近，冲掉「持久在回复栏 /
瞬态是浮动 chip」这个模型。

# 2026-11-03 回复下的卡片：从撑满气泡到一框列表

一个主会话，三条裁决（[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 180–182），四张票（131、132、132b、133），全部合入 main，没有发版。接在同日上午的[子任务可见性](./2026-11-03-galley-name-and-subtask-visibility.md)后面：179 把子任务卡片降成一行回执，下午 JC 看真机截图，嫌回复下的卡片仍然太大。

## 起因：大在宽，不在高（裁决 180，票 131）

JC：「作为 IM 向的主对话，我觉得目前子任务和 artfacts 的卡片，稍微有些太大，尤其是子任务的卡片，空间浪费比较大，标题一般比较短，后面都是大片空白。」

- **查下来**：回复下五种卡片（文件、子任务、待办、提醒、备忘）都包在 `Conversation.tsx` 的 `max-w-[88%]` 块里，块级元素默认撑满，每张都和气泡上限一样宽（紧凑栏 669px，宽松栏 1056px）。注释与设计文档写的都是上限（「最宽同气泡」），撑满是块的默认行为；写过撑满理由的只有过程卡片（点开一步会忽宽忽窄）。179 拿掉「打开」与第二行之后，回执不会展开，撑满的前提已经不在。字的实际宽度：两张子任务 158、186px（后来 WebKit 实测 160、191.5），空 72–76%。
- **切换器**比宽度（现状 / 甲 随字宽 / 乙 同组同宽 / 丙 固定 320）与高度（40 / 32），带演示状态。旁路代理指出乙的代价没说：同一条回复里最长的那张把短卡片一起撑宽，而 JC 的真实对话里文件卡片与子任务卡片从没挂在同一条回复下，看不出来；追加「数据：混排」把它摆出来。
- JC 倾向乙 + 32，主会话同意（库里挂卡片的 32 条回复中挂两张以上的只有 3 条，文件与别的卡片同在一条回复 0 次）。

## 卡片以外还有什么：结构不换，只换画法（裁决 181，票 132）

JC 往前问了一步：除了卡片还有什么方案。主会话按「放在哪」列了七条路，各有一个硬伤，都不是看真机能消掉的：

| 路 | 硬伤 |
|---|---|
| 写进字里（行内小签） | 交文件的约定是标记单独一行（票 73），改要动手册、跑评测；长回复里成果埋进段落 |
| 收进气泡（附件区） | 悬停色与回复气泡同值（`globals.css` 的 `--color-hover`、`--color-assistant-tint` 都是 #f0f0f0）；气泡被长文件名撑宽 |
| 文件单独成一条消息 | 比现在更大，与这次的方向相反 |
| 子任务不画回执 | 裁决 176、177 把它定为做完的子任务的常设去处，裁决 101 的兜底在它里面答提问 |
| 回执挪到交代那条回复 | 派出时没有确认；挂哪条要靠模型或 Core 去对 |
| 一条回复一个清单框 | （当时）比乙 + 32 省得不多 |
| 搬出对话 | 交出时看不见，正是票 74 的起因 |

JC 认同「卡片的毛病只是大」，问更轻的画法。主会话给无框行、分层、小气泡、胶囊，推荐无框行；JC 提出主对话里「进度显示」那种一行一步的样子（过程卡片），主会话认为它比自己推荐的无框行好：回复下的框只剩一种（上面是这条回复做了什么，行动条下面是怎么做的），几件共用一个框，有框就不会读成正文、不和悬停时的行动条混。切换器加「样式」组：有框 / 一框列表 / 无框行。没上：小气泡（读作又一条消息，子任务分量反升）、胶囊（待办方框与「取消」放不进小签）、子任务回执里实时显示每一步（179 拿掉的第二行）。

## 定一框列表（裁决 182，票 133）

JC：「我在一框列表和无框行自己纠结。」主会话截了他停着的窗口，拆开看：两档空间几乎一样（派活两张 58 对 56px），差的是框。日常是一件：主对话 286 条回复里 32 条挂卡片，29 条只挂一张（待办 14、提醒 6、文件 5、子任务 4、备忘 4）。拿 JC 的原话打表：「卡片的毛病只是大」说框不是毛病；框还在做两件无框行做不到的事，把回执和行动条隔开（他的窗口里行动条就贴在框下面）、让交出的文件像一件东西。JC：「定了，按一框列表吧。」

- **写定**（`ReplyCards.tsx`）：一条回复一个框，框照过程卡片（细线、`rounded-md`、页面底、4px 内边距），宽度随最宽那一行，上限是气泡上限；一件一行 24px，字号同过程卡片的步骤（标准档 12px），名字 `ink-soft`，后面 8px 浅色写对象；能打开的行整行可点、悬停整行出底色。规格在 `docs/design/conversation.md`「回复下的卡片（一框列表）」，文件卡片补了自己的一节。
- **翻车点**（裁决 182 第 3 条）：一件也套个框还像卡片，就换无框行；文件 12px 不像成果，就让文件那一行回到 13px `ink`。

## WebKit 里才有的两个坑（票 132b）

票 132 合入后主会话截 JC 真窗口，「制作76人赛季战况网页」被截成省略号、框右边还空着一截；代理一直用无头 Chrome 量，全对。改用系统 `swift` 起一个不上屏的 WKWebView 做量具（加载同一份静态页，`evaluateJavaScript` 读宽度与截断），坐实两处：

- **绝对定位的伪元素让 WebKit 漏算中西文间距**：为了整行可点，标题按钮加了铺满整行的 `::after`；盒子里有绝对定位的子元素时，WebKit 算 max-content 不计 `text-autospace` 的间距，每处中西文交界差约 1.5px（「预约11月8日上午9点的体检」差 9px），随内容宽的框就截出省略号。改成按钮用内边距伸满整行、同样大小的负外边距收回、行 `overflow: hidden`。写定时又发现块级按钮在标题比上限还长时会冲出行外、被硬切而没有省略号，改成 flex 项、字单独一层截断。
- **百分比上限在随内容宽的框里不生效**：文件夹的 `max-width: 40%` 在内在尺寸里算不出，框按文件夹全长撑宽，渲染时文件夹又被截，留一截空白。改成 16em。

## 过程里记下的

- 推荐乙时没写出「长的那张把短的撑宽」，旁路代理提醒后补成切换器上的「混排」。
- 推荐无框行后，JC 自己提的过程卡片写法更好，当场改推荐。
- 「整行亮、只有标题能点」是代理报的 Open risk，在真机路径上，合入前让它补；补的写法（`::after`）正是 WebKit 截断的来源，第二次截真窗口才抓到。量宽度只用 Chrome 是这次的漏洞，量具留在记忆里，以后这类票写进票面。
- 欠着：一框列表的日常观感（一件的框、文件 12px、展开「过程」时两个框）；长标题悬停给全文与整行点击只在静态页判过，要在真窗口点一遍。

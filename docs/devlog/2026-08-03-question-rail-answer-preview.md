# Question Rail：tooltip 加回答预览，用 final answer 而非 summary

日期：2026-08-03
状态：已实现，随本条目 commit
相关：`gui/src/components/conversation/UserQuestionRail.tsx` ·
`gui/src/lib/rail-preview.ts` · `docs/design/conversation.md`
§Right Question Rail

## Context

JC 提出：rail 的 dot 只索引历史提问，看不到模型回答；回答很长，是否只放
开头一两行。讨论中先定位了真正的缺口——dot 的**导航**职能不缺（回答就在
提问底下，跳到提问即跳到那段回答的开头），缺的是**辨识**：hover 一个 dot
只看到自己当年问了什么，看不到那次得到了什么。这是 tooltip 的信息量问题，
不是标记数量问题。

## Decisions

- **只改 tooltip，不加 dot**：tooltip 从一行变两行（`序号 │ 提问` +
  缩进对齐的回答预览），dot 仍是一问一个。用增加标记去解决辨识问题会把
  rail 密度翻倍，而 cluster 合并机制是为"提问连发"设计的，不是为 Q/A 对；
  且 2026-07-21 已拍定 dot 位置是等比映射的缩略地图，新增异质标记要发明
  第二套视觉语言，与 rail 的克制相悖。
- **预览用 final answer 首个正文行，不用 `AgentTurn.summary`**（本轮
  最大的一次改判）。初判推荐 summary，理由是"它是专为一句话概括生成的、
  与 Sidebar 同源"。翻代码后推翻：
  - `managed-ga/code/llmcore.py` 的协议 prompt 要的是"极为简短的单行
    物理快照：**上次工具调用结果产生的新信息 + 本次工具调用意图**"，
    `ga.py` 拿到后直接 `history_info.append(f'[Agent] {summary}')`——
    它是**喂回给 agent 自己的工作记忆**，语义前瞻，指向下一步工具调用。
  - 最终答案轮是 `no_tool`，"本次工具调用意图"不存在，prompt 的框架在
    这一轮结构性失配。
  - `ga.py` 的 fallback（模型没写 `<summary>` 时）恰好就是正文剥壳后
    前 80 字——所以选 summary 等于选了一个"有时是 GA 的编辑批注、有时是
    final answer 截断"的混合体，行为不可预期。
  - "与 Sidebar 同源"这条权重给高了：Sidebar 那一格的语义是 session 的
    进行状态（`第 N 步 · …`），与"某次问答的内容"不是同一个语义槽，不该
    为同源而对齐。
  - 同时纠正一处初判说重的话：我曾说 summary 有退化成"直接回答了用户
    问题"这句空话的风险——查证后该分支只在正文全是代码块时触发，比原先
    暗示的窄得多。改判理由是语义槽对齐，不是空话风险。
- **跳过 ATX 标题取首个正文行**：长回答高频以 `## 结论` 开头，而既有
  `buildPreview` 会剥掉 `#` 留下"结论"两字，信息量为零。规则**只跳标题**，
  不跳代码围栏 / 列表标记 / 引用——一句话说得完的规则才能从原文预测输出。
- **配对取"最后一个 `finalAnswer !== null` 的 agent turn"**（JC 拍板
  (a) 案）。`ipc-handlers.ts` 对每个 `turn_end` 都算 `finalAnswer`，不只
  最终轮，所以中间工具轮偶尔会漏出散话形成非 null 值。备选 (b) 是再加
  `isFinalAnswerTurn(tools)` 门槛、只认收口轮，异常路径（run 被中断）下
  留空；选 (a) 是"有总比没有强"。
- **先做一行**：回答预览一行而非两行。两行信息量更足但盒高再翻倍，且会
  放大与 cluster 列表的不一致。留作后续按真实使用再谈。
- **回答缺席不渲染第二行**，不留幽灵空行。
- **两行层级差拉满 ink 两档**（`text-ink` / `text-ink-muted`）——本轮
  dev 验收后的返工，见下「层级返工」。
- **配对逻辑抽进 `lib/rail-preview.ts`**（含从组件搬出的 `buildPreview`）
  并单测。理由：配对的 edge case 值得钉住，而 `components/conversation/`
  目前没有测试文件，仓库的纯逻辑测试惯例在 `lib/` 与 `stores/`。
- **tooltip 竖直定位阈值 6/94 → 10/90**：旧值按单行盒高（~24px）调，
  两行盒（~44px）在窄窗口下会探出对话区上下边——半个盒高占 rail 的百分比
  随窗口变矮而变大。这不是打磨，是不改就看得见的缺陷。
- **cluster 展开列表保持单行只显示提问**：cluster 是密集区的快速定位面，
  不是阅读面，5 条 × 2 行会变成一堵墙。不一致是刻意的。
- **回答预览不进 aria**：button 的 aria-label 是导航目的地
  （`跳到第 N 条提问`），本就不含提问正文，加回答会让 label 变长且破坏
  既有惯例。

## 层级返工（同日 dev 验收后）

初版两行是 `text-ink-soft`（提问）+ `text-ink-muted`（回答），一档色差。
JC 实机反馈：「回答的视觉层级太强，除了稍微字体淡了一点点，并没有拉开
差距」。

诊断：**根因是结构并列，不是色阶不够**。两行同字号、同起始列、同 50 字
预算、均匀行距——视觉系统读到的是"一个两行段落"，不是"主信息 + 附注"。
其中**等长**这条是 agent 上一轮亲手引入的：把两行设成同一个 50 字预算，
还把由此得到的"盒宽变稳"当作好处报出，而等长即等重。

出路只能换维度，因为色阶本身已到底：ink 只有
`ink` / `ink-soft` / `ink-muted` 三档，回答行已在最底，再淡就要为一个
tooltip 造全局新档，不划算。

- **裁决：走加法，把提问行提到 `text-ink`**（JC 拍板）。两行差距从一档
  变两档，且不触碰字号与字数。
- **否掉（本轮）：降回答行字号 11.5 → 10.5px**。tooltip 内部本来就有
  10.5px 这一档（序号在用），是复用不是新增——agent 上一轮"11.5px 是
  可读下限"的说法是错的，序号就在 10.5px。但序号是 tabular-nums 数字，
  数字比汉字耐小；对 CJK 正文下探一档是实打实的代价，JC 选择先不付。
- **否掉（本轮）：回答行字数预算 50 → 30 字**。agent 主推的减法方案，
  理由是"等长即等重、右边缘参差本身就是层级信号"。JC 判先不动，留作
  加法不够时的下一手。
- **反对且未采纳：`opacity-70`**——绕过 token 体系直接调视觉，与色阶
  手段重复，是廉价解。
- **反对且未采纳：Newsreader italic**——该 register 已被 thinking
  summary 占用，语义是"过程材料 / 想看才看"；回答是**结果**，套上会
  误导 register。
- **反对且未采纳：拉大 `gap-y`**——方向相反，离得越远越读作独立块；
  要从属该更紧凑。
- **暂不加：从属标记（`↳` / 短左规线）**。留作加法仍不够时的第三个
  维度；一次上三个手段容易过冲到"回答淡到看不见"的另一边。

## Rejected alternatives

1. **每个 final answer 加第二类标记**——标记翻倍，逼迫 cluster 机制处理
   它没被设计过的 Q/A 对，且要发明第二套视觉语言。为一个辨识问题付这个
   代价不成比例。
2. **按 AgentTurn 逐步打点（"跳到第 7 步"）**——"索引回答"的最强版本，
   但一次 20 步的 run 会让 rail 变噪声条，与 cluster 的压缩逻辑打架。
3. **把 Q→A 的纵向跨度画成脊线上的浅色区段**——不加可交互标记，还能表达
   "这个回答有多长"，是唯一值得留作**独立后续议题**的方案。它解决的是
   另一个问题（rail 无法表达两问之间的体量差），不该与本轮捆绑上车。
4. **取 final answer 前 N 字符**（不跳标题）——见上，`## 结论` 会退化成
   零信息预览。

## 已知遗留

- **回答以代码围栏开头时预览质量差**：首个正文行会是 ` ```python `，
  `buildPreview` 剥掉反引号后剩 "python"。与被跳过的标题同属"开头行无
  信息量"这一缺陷类，但本轮明确只跳标题以保持规则可预测。若真实使用中
  常见，再回来谈是否扩展跳过规则。

## Context

After `file_patch` proved the write-approval path, `file_write` was the next
high-risk local executor. The user-facing problem is not just "require
approval"; approval must show what will be written. A hidden native runtime that
asks the user to approve an opaque full-file write would be technically gated
but still product-unsafe.

This slice keeps the scope narrow: create a new file or deliberately overwrite
an existing file. It does not introduce append/prepend, process execution,
Browser Control, memory writes, Goal Hive, or Morphling behavior.

## Decisions

- Hidden `galley_native` now implements `file_write` as preview-first
  create/overwrite.
- Omitted `mode` defaults to `create`; `overwrite: true` normalizes to
  `mode: "overwrite"`.
- Core enriches pending approval args with `existing_content` before persistence
  and event emission.
- Model-supplied `existing_content` or `preview_error` fields are discarded;
  the approval preview is always generated by Core.
- The GUI `file_write` approval renderer reuses `PatchView`, so create shows an
  empty old side and overwrite shows existing content against proposed content.
- Missing-preview and invalid-mode writes fail without approval.
- `append` and `prepend` remain unsupported in native Slice 4B5.
- Approved create writes only if the path still does not exist.
- Approved overwrite rereads the target and writes only if current content still
  matches the preview.
- Successful writes record `sideEffectsPerformed: true`.
- Managed GA and external GA behavior is unchanged.

## Rejected Alternatives

- **Default to overwrite.** That is closer to a loose "write file" tool, but it
  makes model omission dangerous. Default create fails safely when a path already
  exists.
- **Support append/prepend immediately.** Those modes are not full-file previews
  unless Core first computes the final content. They can land later as derived
  preview forms, not as opaque write modes.
- **Approve missing-preview writes.** Rejected for the same reason as opaque
  patch strings: the user would be asked to approve a write without seeing the
  result.
- **Continue the model after successful write.** Deferred. This slice is about
  reliable mutation and audit; continuation policy should be decided once all
  local file write semantics are stable.

## Open Questions

- Should successful write tools trigger one continuation like approved
  `file_read`, or wait for the full autonomous loop?
- Should `file_write` later support append/prepend by computing a full previewed
  replacement internally?
- Should Core persist a compact file fingerprint alongside `existing_content`
  for larger future write previews?
- Should `file_write` eventually create parent directories, or should directory
  creation stay a separate explicit tool/action?

## Next

- Decide write-tool continuation policy.
- Implement `code_run` as its own slice with cwd, timeout, cancellation,
  stdout/stderr, and exit-status semantics.
- Keep Browser Control as Slice 4C.
- Keep memory, Goal Hive, and Morphling in later slices.

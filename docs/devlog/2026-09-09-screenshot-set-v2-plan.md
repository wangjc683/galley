# README 截图 v2：从零重设场景、种子与版面

**日期**：2026-09-09
**范围**：`docs/screenshot-playbook.md` 重写、`scripts/seed-screenshots.py`
重写（3 项目 / 16 会话 / 3 定时任务 / 演示仓库）；截图本身待 JC 实拍

## 背景

README 定位切到「Less harness. More model.」之后，五张截图成了最明显的
过时资产：2026-07-03 拍的，之后经历了 run 折叠（v0.4.3）、暗色画布提亮
与侧栏重设计（v0.4.10）、阅读面板（v0.4.12），右上角的 YOLO 药丸在
2026-07-20 就改名了。JC 提出最大难点是 mock 数据「充实、好看、多样」，
并决定不沿旧编号覆盖，从零设想。

放大看旧图，问题不全在数据：项目视图和「安静待命」两张 80% 是空白画布；
hero 是一堵思考摘要的文字墙，结果表不在画面里；五张里三张侧栏同源。

## 决策

1. **每张图替一个卖点作证。** 导览网格的六张图一一对应 Highlights 的卡片
   （工具时间线 / 阅读面板 / 项目 / Goal / 定时任务 / 搜索），读者扫网格
   等于扫功能列表。没有卖点对应的画面不拍——「安静待命」因此出局。
2. **版面：hero 独立 + 2×3 导览网格。** 否决全宽堆叠：六张 1600 宽叠起来
   把 Quick Start 推得更远；网格单张约 400px，读者点开看细节是 GitHub
   的常规阅读方式。
3. **按场景命名，不按编号。** `hero` `hero-dark` `tools` `reading`
   `projects` `goal` `scheduled` `search`。旧的 01–05 在新图提交时删除，
   历史保留，符合资产政策。
4. **Hero 换生活服务类 prompt**（本周末上海展览按地铁可达排表）。准入
   标准不变（答案依赖实时数据）；路人对「查展览」比对「豆瓣译本评分」
   更能代入。**维特根斯坦彩蛋挪到 `projects.png`**，整张图都是它，比在
   hero 里当 prompt 更显眼。
5. **Hero 真跑到结束再拍**，而不是 v1 的「跑到第 5–8 步」。理由：新定位
   要证明「真的做完了事」，折叠后的 run 头 + 结果表比进行中的步骤墙更有
   说服力；「进行中」的活感由侧栏的 running 行承担。
6. **领域配比按新定位三分**：知识（维特根斯坦项目）、生活（九月搬家项目
   + 支出 / PDF / 报销）、Dev（galley-site 项目）。每类一个项目，散置会话
   补状态与形态。
7. **多样性按四个维度铺**：领域、工具组合（每条会话工具序列不重样）、
   产出形态（表格 ×5、清单 ×3、代码块、短文、一句话结论）、状态与来源
   （running / 未读 / 置顶 / supervisor / 定时任务创建 / Goal 完成态）。
8. **新增两个可种的新界面**：定时任务（`scheduled_tasks` 表直接种，三种
   重复方式各一，含一条已停用与一条「尚未运行」）；阅读面板（需要真
   Git 仓库，脚本 `--demo-repo` 生成一个 2 提交 + 3 改 1 新的静态站小仓库，
   与 `sess_tour_page` 会话的 final 文件清单一致）。
9. **每条 final 种 telemetry**（`telemetry_json`，镜像 runner 的 turn_end
   形状），让「N 步 · 用时」页脚出现在画面里。v1 的种子写了 telemetry
   字段但从未写入数据库。

## 否决与边界

- **Channels 设置页不拍**：四张渠道卡在未连接态是空卡，连接态需要真实
  账号入镜。留给演示 GIF 或以后。
- **审批 dock 不拍**：延续 v1 口径，自动执行是默认姿态。
- **「等你回复」态不拍**：ask_user 是内存态不可种，v1 已验证。
- **不做「截图模式」之类的 GUI fixture 机制**：DB 种子 + 真界面已经够用，
  且保证画面里的每一行都是产品真能渲染出来的。
- 「轻」的边界同 README：种子内容里的任务都是 Galley 真能跑的；对比表里
  的公司名与数字是样板间布置，不是抓取结果。

## 起因

JC：「现在主对话还是在形式上太接近于普通会话，好像是一个顶置的会话一样……把它变成一个类似的 IM，也就是跟一个助理，真人助理类似的一个长期对话……习惯于之前 Galley 会话管理跟使用方法的还是可以像之前一样……让它独立于之前我们 Galley 传统的会话管理」

## 方向（裁决 60）

主对话像置顶的会话，是因为它每一层都借会话的壳：侧栏里一行、同一套对话画法、同一个输入框与顶栏。只改一层改不掉。改为两样东西：**助手**是长期在的一个「人」，对话手感照 Telegram、iMessage；**工作台**是今天的 Galley，会话、项目、侧栏、步骤照旧。

依据三条：宪法的产品形态本来就是两层（「轻量的个人助手……一个不够时扩成本地的 agent 团队」）；关于页现在写「本地全能 AI 助手」，10-07 之前写「开源的本地 Agent 工作台」；手机首屏早就是主聊天，会话列表在第二层（裁决 1）。

顺序：先比壳，再比 IM 画法（气泡、过程藏到什么程度、日期条、输入框）。数据层不动，助手底下仍是那条主对话会话，CLI 与 Agent API 不变；外置运行时没有助手。

**跟着变：主对话不显示问题轨**（`1f721ed2`）。问题轨按已加载内容的比例摆点，两点不到 14px 就并成胶囊（`UserQuestionRail.tsx:71`）；按 650px 的轨道模拟，50 条提问时 85%–90% 的点落在胶囊里，往上翻一页整条轨道换比例尺，「第 N 条」也跟着变。JC 库里最长的普通对话只有 21 条提问，主对话会是第一个长期超过 50 条的。往回找靠 ⌘K 全文搜索、发送时间行、⌥↑ / ⌥↓。按发送时间行打点的 B 没做：拥挤能缓解，坐标照样会变。

## 第一轮：两个空间的壳（票 16，两档都被否）

三档从最克制排起：现状 / 乙 红绿灯右边一个两段开关 / 甲 窗口最左一条图标栏（飞书、企业微信式）。助手空间暂用现有对话画法铺满、没有会话侧栏；切换器带「演示」开关与 ⌘1 / ⌘2。我推荐甲：两个空间对等、徽标有现成地方挂、以后有第三个空间也放得下。

JC 真机看过：「甲和乙两个方案，我现在觉得都不满意……应该还是让 Sidebar 来做这个切换，这样最简洁直观，而不是新增一个侧边栏……助理还是应该变成一个主要入口，在 Sidebar 上作为一个明显存在，然后再是新对话和下面的传统的 Galley 的对话区域」（裁决 62）。

我认：两档都加了一样新东西（一列、一个开关），侧栏里的旧东西却一样没挪走；「对等、可扩展」这类结构论证压不过「少一样东西」。试验代码 `847be65f` 由 `ed708645` 撤掉，问题轨的改动保留。裁决 62 同时定字标退役、「Galley」成为助手的名字，以及书眉三个按钮按服务对象重排（搜索留顶，定时与新建项目进新对话行，后被裁决 64 改回）。

## 第二轮：侧栏上半块（票 17）

四档：现状 / 方案 2 书眉就是助手（字标的位置换成头像加名字）/ 方案 3 书眉下一张助手卡片 / 3′ 同 3、头像放大居中（参照 macOS「信息」侧栏的置顶联系人）。三档共用：卡片照票 14 的 A 只说状态，空白新对话时「新对话」行亮着，取代票 13 的按下加号与「其他对话」分区头。

JC：「我有点选不出来，想再听听你的想法」。我拿裁决 62 里 JC 自己的「主要入口」「明显存在」「两个区域」当尺子：

- **方案 2**：入口就在字标原来的位置、差不多大（按钮 80×28，头像在 88px），读起来像应用名；侧栏左上角的「头像加名字」在 Slack、Notion、Linear 里是切换工作区或账号的地方；它没有状态那一行，在跑、等你回复只剩头像角上 12px 的标记。
- **3′**：比 3 多占 54px；内置运行时启动就落在助手上（`gui/src/lib/hydrate.ts:108`），一打开就是 282×112 的选中底色。
- **3**：列表只比现状低 18px，主对话行的位置换成卡片，三个新档里改动最少。第一个时间桶标题的位置：现状 y147、方案 2 y94、3 y165、3′ y219。「最克制」有两种量法：比占地是 2，比改动是 3。

JC：「我也认可 3」。随后提两点：「新对话还是单独一行一个按钮更合理，定时和项目可能还是更适合放回到 sidebar 顶部」；以及「这个卡片占据空间依然不小，可以怎么样更合理利用」「粗一看 sidebar，用户是否能懂的这个 Galley 是一个持久助理对话 IM 的入口」。

## 书眉与新对话行（裁决 64）

第一点我同意：卡片下面直接就是外置运行时的侧栏（`sidebar-width.ts` 开头那套：书眉三个图标，「＋ 新对话 ⌘N」独占一行，窄了图标挪进这一行），裁决 60 的「工作台就是原来的 Galley」成了字面意思；新对话独占一行，字始终放得下。没有字标后门槛重算：mac 80 + 92 + 12 = 184px，窄于它三个图标挪进新对话行；Windows（16 + 92 + 22 = 130px）与 Linux（120px）都低于最窄的 133.4px，没有窄态。

主区开着助手时顶栏是身份行，点开是原来主对话的标题菜单（没有改名），补上方案 3 缺的「重新注入工具」「桌面宠物」入口，像 IM 里点对方名字进资料页。卡片与会话行一样按下就打开。

## 卡片做成 IM 列表的一行（裁决 65）

第二点我的回答是多半看不懂：名字「Galley」就是应用名，杏色底上一个「G」像应用图标；静止时只有头像和名字，是资料卡或账号入口的结构。IM 列表的一行一眼能认成对话，靠的是最后一句话和时间，微信、Telegram、iMessage 都有这两样。卡片这一块只比现状的主对话行那块高 12px（71 对 59），显得大是因为第二行静止时空着，所以用满、不压矮。

JC：「先不做切换器，卡片的空间，我觉得你的方向是对的，就是让他的 IM 感更强烈，也就和之前 Galley 普通会话形成了区别」。六条按建议推进：

1. 第二行静止时写这条对话的最后一句：纯文字一行，去掉 markdown，附件写「[图片]」「[文件] 名字」，是你说的加「你：」；第一次打开就是问候。这条**推翻裁决 58 的「静止时不写」**：票 14 没让「写最后一句回复」进切换器，理由是回复开头常带 markdown（JC 库里 16 条末轮回复有 12 条）和「太好了！」这类开场、侧栏会有两种第二行、静止时重复主区；现在 markdown 去掉了，开场白是它对你说的话，卡片本来就要和会话行不一样，开着时重复主区是 Telegram、iMessage 的常态，人在工作台时这是唯一看得到它刚说了什么的地方。规则一句话、没有例外（A′ 当时输在「看过就消失」的例外）。
2. 名字右边写那句话的时间：今天「11:50」、「昨天」、一周内「周一」、更早「10月7日」、跨年带年份。
3. 优先级：出错 > 在问你（「等你回复：问题原文」）> 在跑 > 草稿 > 最后一句。
4. 助手没开着时有没发出的草稿，写「草稿：……」，前缀用品牌色（红色留给出错）。
5. 头像 32 → 40px，卡片高度不变。
6. 未读照旧挂头像右上角、名字加粗，不写条数。

不做：在线点（助手一直在，还会和未读的点撞）、已读回执、置顶与免打扰标记。

## 票 18 的实现

子代理一张票做完：撤掉票 17 的试验，以及票 07、08、13、14 为「主对话在顶上」搭的结构（主对话行、「其他对话」分区头、按下的加号、窄时书眉下多出的那一行），保留票 08 的侧栏收起和票 09 的 `bg-app`；做书眉、新对话行、卡片、顶栏身份行。外置运行时 54 个画面与开工时的 main 逐像素一致（主会话复核）。交给它定的：第二行 12px（11px 的对照在 40px 头像旁像注脚）、时间 11px `ink-muted`（与侧栏的计数同一档）、卡片 58px。

与票不一样的三处，JC：「三处都保留，我真机看了 OK」。

1. **新主对话打开时主区是空的**（第一次启动、重置之后）：问候不算一轮，Core 让新主对话的 `turn_count` 为 0，而激活时只在大于 0 时读回对话。卡片会显示问候，主区却空着；改为主对话缓存为空时一律读回（`932340c5`）。票 15 验收「新主对话从问候开始」是查库确认的，主区当时多半一直是空的。
2. **回复里的 `[FILE:路径]`**：runner、Core、界面三处都会清掉这个标记，卡片拿不到；给 `AgentTurn` 加了可选的 `files`（只在界面），实时与读回各有测试。
3. **名字一行放不下时，时间整个让位**，「Galley」不截断：中文 167px、英文 188px 以下看不到时间。

## 被否与没做的

- 甲 左侧图标栏、乙 左上两段开关（票 16）；方案 2 书眉就是助手、3′ 大头像（票 17）。
- 裁决 62 的「定时与新建项目进新对话行」：裁决 64 改回书眉。
- 裁决 58 的「静止时不写」：裁决 65 推翻。
- 问题轨按发送时间行打点（B）。
- 卡片上的在线点、已读回执、置顶与免打扰标记。

## 遗留

- 主区的 IM 画法：气泡、过程藏到什么程度、日期条、输入框，是下一步。
- 叫法定稿（D3），以及界面上其余的「主对话」字样：输入框忙碌提示、子任务卡片与来源提示、设置里的重置。
- 助手的形象（真实头像）；手机端跟进。
- 有新回复又有草稿时，第二行照优先级写草稿，那一刻看不到新回复的字，留观察。

## 教训

- 加新容器的方案被否，要在现有容器里解；JC 选不出来时，拿他自己的原话当尺子打表。两条都已进记忆。
- 用户看得到的东西要在界面里验收，查库只是代理：票 15 查库确认问候在，主区却一直是空的，到票 18 子代理截图才发现。

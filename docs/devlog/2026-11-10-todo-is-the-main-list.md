# 待办是主清单：清单是你的，打理是它的

## 起因

JC：「我们来探讨下主对话待办面板的功能、UI/UX 提升，怎么样更靠齐成熟的待办类工具，也方便用户上手，但另一方面又保留我们 AI Agent 内置待办设计的产品差异化……目前有一个常用可能是缺失，就是循环任务」。聊到第二轮，JC 把问题往上提了一层：「很多这种裁决点，更重要的是背后的产品设计逻辑和理念，Galley 待办功能的定位与追求的目标，这个对齐和明确后，很多后面的 UI/UX 与功能才好推进」。

## 定位漂了

写下来的定位有两版：10-17 裁决 91「记事本，你只能勾掉自己的事」，判法是「不需要判断的就地做，要判断的靠说」；10-22「不是让你自己管任务的 todo 应用，是助理的账本，你来核对」。之后 JC 连着五次把「靠说」改成「就地做」：删除（裁决 132）、改标题与备注（裁决 153）、子项增删勾（裁决 157）、子项排序（票 112）、这一轮的改日期。改日期按旧判法算「要判断」（提醒得跟着挪），JC 仍要它能动手。实际在用的判法是「已经在清单上的东西，我要能自己动」；再拿「账本、你只核对」推后面的裁决，只会一条条被推翻。

## 岔路口与一句话（裁决 202）

- **随手单还是主清单**：随手单只收对话里带出来的事，正经的待办另有地方记，10-17 的设计照这个做；主清单是信得过、不在别处另记一份。JC：「选主清单」。待办是主动的根（助手 PRD 裁决 10），半张清单没人看，它能推的事就少。门槛是信任：有重复、能改日子、到点那一条一定在。靠齐成熟工具，对齐的是这几样基本功，不是组织能力。
- **清单是你的，打理是它的**：成熟工具里用户是管理员，记、定日子、设重复、回顾都是用户的活，清单烂掉多半因为没人打理；这里用户是主人，它是管家。四条推论：主人的手够得着一切（清单上已有的每一样都能就地改）；打理不落到主人头上（手动是出口，不是必经之路；项目、标签、优先级不做）；那一条一定在（日子、提醒、下一期由 Core 算，模型负责理解与准备）；样子认得出来（显示照苹果「提醒事项」）。
- **目标**：成熟工具的成功是你勾掉了更多事；这里的成功是需要你的事变少，剩下的每一件到你手里时是备好的。
- **新建仍靠说**：理由从「会滑向表单」（面板有了日期控件之后弱了一半）换成「每一件都经过它，它才知道来龙去脉」。代价是记一件约半分钟，靠提速还。
- **上限**：提醒只响在桌面，手机上记不了；现阶段是「桌前这些事的主清单」，等 iOS 端。

## 清单上放谁的事（裁决 203）

JC：「这个主清单里面，是用户要做的事情，还是助理自己要做或者帮用户做的事情？……有的待办条目好像是助理完全可以自己做掉，那是否还要成为一个 todo 条目增加用户的某种负担呢？」

主会话拿库里的真待办对了一遍（去掉测试数据后 8 件）：只有用户能做的 4 件，到日子要用户确认结果的 1 件，混合的 3 件；完全归它的本来就在「Galley 在办」，没占方框。纯粹的事现有分法已经分对，模糊的是混合的事：同一件事的下一步在谁手里随时间变，「这是谁的事」这个问法本身不对。

- 事都是用户的，分的是下一步在谁手里。负担来自三样：方框、顶栏的「今天 N」、逾期变色，只给需要用户动手或点头的那一步。
- 判法，记的时候问一次：这件事里有没有只有用户能做的一步？没有、现在能办的是差事，办完交代，不上清单；没有、要等的是它自己的提醒；有，才是带方框的待办，它能做的先做。
- 模糊时默认保守：用户说「我要…」「记一下…」的仍是用户的，它只铺垫；说「帮我…」「你去…」才整件归它。没选更激进的一档（三道闸以内它都直接办掉并勾掉）：接管错的代价比多一行大。
- 差事办完不在「已完成」留一行。
- 只记方向：一件事一行、看得出现在等谁；问了没回的事进清单。都在 deferred。

## 重复的待办（裁决 204）

- **缺口**：按手册自己的判法（你不理这次提醒，这件事还要留在清单上吗），「交周报」是待办；手册却把它归成重复提醒，因为待办记录里放不下规则。落到「例行」以后没有方框、不进「今天 N」、不会逾期、每期叫醒模型一轮，那天电脑没开过了午夜就丢。库里三周一条重复的都没建过，主会话没拿它推「不做」。
- **「不用学规则」成立到哪**：写规则交给模型成立，但别的工具的自然语言重复做了很多年，不是护城河；到点那一条必须是确定的，所以规则由它写、日子由 Core 算。真正别人做不到的是三样：引擎表达不了的规则、每一期是备好的、规则会过期。第三样（连着跳过几期它来问要不要停）JC 没要。
- **三案**：甲只改手册（例行到点叫醒它自己记）；乙一行滚动（苹果、Todoist 式）；丙规则加「这一期」。定丙：这一期是一件完整的普通待办，了结时 Core 在同一个事务里生出下一期，不靠定时器、不调模型。
- **不堆积**：这一期没了结，下一期不另起一行；下一期从「今天与这一期到期日里较晚的那一天」之后算。
- **规则**：先做 Core 会算的（每天、每周几、每月几号、每 N、每年）。表达不了的用「日子串」（它算一次、存成一串日子、Core 照单发），挂信号。JC 第一次没听懂「日子串」，主会话用「每月最后一个工作日」重讲了一遍。
- **主动发现到第 2 档**：说出了周期的直接记成重复；话里带出周期没明说的只记这一次、同一句里问。从历史看出来的不做。
- **界面**叫「重复」；「跳过这一次」「不再重复」「删除」是三个分开的动作。

## 改日期重开（裁决 205）

JC：「改日期重开，这个和条目编辑一样，还是给用户自己手动修改的空间比较好」。推翻裁决 153 第 5 条。改日子时提醒跟着挪同样的时长。仓库里没有日历控件，先出文字稿。

## 收起的一行不画备注（裁决 206）

JC：「目前还是有点点吵，不知道是不是每个条目显示三行信息，尤其是第三行备注是一长显示不全的句子」。

- 主会话截了 dev 窗口量：带备注的一行约 68px，不带的约 51px；备注那一行放约 21 个汉字，库里两条备注的首行都只露出一半。
- 对三家（凭主会话对三款的了解，没截窗口核）：苹果把标题、备注、日期都画在行上；滴答清单与 Things 行上只有什么事、什么时候，其余点开看。苹果的行安静是因为备注要人自己写，少而短；这里的备注是它写的，有备注的件件是长句。显示密度的问题是「打理是它的」带出来的：它写备注不花力气。
- 定：收起只画标题与时间那一行，打开照旧。裁决 128 第 5 条显示备注的前提（当时备注哪儿都看不到）与裁决 146 否掉「收成图标」的理由（只在悬停时读得到）在有了点开之后都不成立。
- 不留「有备注」的记号（JC），不上切换器（JC：「直接改」）。

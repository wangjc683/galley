## 框架：信任三问

v0.4.0 上线的定时任务把「调度正确性」做透了（补跑边界、DST、失败不重试、
模型降级，全有测试），但从底层逻辑看，功能对用户的核心契约是**无人值守
也可信**，拆成三问：

1. 它跑了吗？——v1 已覆盖。
2. 没跑的时候，我知道吗？——本轮 A（失败可见性）+ D（自启引导）。
3. 我能快速验证和修复吗？——本轮 B（立即运行）+ C（触发预览）。

PRD 原话「静默跳过会摧毁信任」当时只用于合盖睡眠；本轮把同样的逻辑推广
到失败与 app 未运行两个场景。执行顺序 A → C → B → D：A/C 纯收益先行，
B 依赖 A（先亮出失败，再给修复入口），D 分歧最大留到最后单独对齐。

## 本轮否决 / 关键裁决

| 提案 | 结论 |
|---|---|
| 角标同时显示总任务数（JC 提议） | 否。常亮静态数字造成 alarm fatigue，稀释 warning 数字的警示力；角标只放「需行动数」，总数留在 dialog 标题旁。JC 被论证说服撤回 |
| 失败通知加独立偏好开关 | 否。错误类通知不做配置项——罕见且必须被看见；沿用聚焦/权限/节流门控 |
| 「立即运行」不盖 `last_fired_at` 戳 | 否。盖戳让手动运行进入「上次运行」信任闭环、成功重跑清除失败角标，且 due 数学天然保证未来计划触发不被吃掉（单测 `manual_fire_before_planned_time_keeps_today_due` 钉死）；唯一被吸收的是已到期 catch-up，正是应有行为 |
| 首次创建任务时弹自启确认框 | 否。footer 条件式提示同时机可见，模态多余 |
| 静默自动开启开机自启 | 否。改登录项不告知是坏公民 |
| 运行历史列表（task ↔ sessions） | 继续按兵不动（PRD 决策 11 范围刹车）；`reason` 字段已带 task id，等真实使用暴露需求 |

## 工程要点

- 失败通知走「Core 发 Tauri 事件 → GUI 门控管线转 OS 通知」，遵守
  issue 05 定下的不双发规则（GUI 独占 OS 通知）。
- 触发预览新增只读命令 `preview_scheduled_fire`：日历数学（小月钳制、
  DST）保持 Rust 单一权威，不在 TS 复刻——预览与调度循环共用同一
  `due_fire` 语义，编辑态用真实 baseline，「改到今天更晚时刻会立即
  补跑」被如实预告。
- 手动运行 `run_task_now` 复用 tick 的 HandlerCtx 组装 + `fire()`
  同一条路，零新语义。

## Dogfood 教训：footer 按钮两轮返工

自启引导的行内按钮先后两次被 JC 打回，轨迹值得记：

1. 手搓下划线文字按钮 → 「不像按钮、hover/按压无反馈」。根因是发明了
   系统外的第四种按钮样式，违反「不发明新样式」纪律；下划线透明度
   40%→100% 的 hover 变化低于感知阈值。
2. 改用 `Button secondary` + `justify-between` → 「层级太抢、和提示文字
   断裂」。`justify-between` 把「问题陈述 → 修复动作」一个语义单元拆到
   对话框两端，破坏邻近性；secondary 的描边+抬升阴影在安静 footer 里
   过重。
3. 终稿：`ghost` + 紧邻句尾（`gap-2`）。视觉重心留给警示句，按钮静息
   安静、hover/按压反馈完整——落在「零反馈」与「太抢」之间的正确区间。

教训一句话：**先查设计系统有没有现成 variant，再决定层级；行内动作与
其所属语句保持邻近。**

## 起因

JC 问：普通侧栏要不要只显示非项目会话，项目会话交给项目视图。

本机 workbench.db（只读）：160 个会话、1 个项目「v0.6.1 发版回归」19 个会话，全是 10-07 CLI 代跑回归时建的；近 7 天
未归档 25 条里 19 条是它（76%），JC 手建项目 0 个。同样的形态以后会常见：Supervisor SOP 把复杂任务拆成「项目 + 2～4 个子
会话」（`docs/integrations/galley-supervisor-sop.md`「Split Into A Project」），每拆一次时间线多几行。

当时的结构：时间线列出全部未归档会话、行上不标所属项目；项目要按书眉「项目」进 Project Review 模式看，进去后时间线整个
隐藏（05-22 起）。

## 讨论与裁决

**直接隐藏（B）被否。** 项目会话的正在工作 / 等你回复 / 出错会在默认视图里失明——「项目」图标没有徽标，项目行也不汇总状态，
要展开才看得到，而 Supervisor 拆出来的子会话正是最想盯的；从 ⌘K / 搜索 / 通知打开一个项目会话，时间线里没有它，破坏
「选中行必在侧栏里」（10-03）；两个视图都残缺，切换成了必须。把这些补齐（项目图标徽标 + 选中会话借位）的成本接近折叠方案，
信息却更少。

**JC 选折叠（C），并提出：既然折叠，是不是不必分两个界面。** 讨论结论是合一、删掉项目视图：C 之后项目视图只剩「全部项目
清单」和「只看项目」两样独有价值，前者是翻档案（05-13「侧栏是当前工作面，不是档案浏览器」），后者没有使用证据；05-22 做
项目视图的理由「同时盯几个项目」，时间线里同时展开几个组即可。C 与项目视图并存会让同一个项目抽屉出现在两处，撞 05-13
删 ProjectsDialog 就地展开时的「避免两种交互并存」。

逐条定下的规则（第一轮；组行落桶交错、桶计数按顶层行两条在同日第二轮被改，见「真机翻案」；现行全文在设计文档「Project 组行」）：

- 一个项目只出现一次，组按最新子会话的活动时间落桶、与会话行交错；置顶项目进置顶区；活动时间在「更早」的项目不出现。
  被否：每个桶各一个组（项目名重复）。
- 置顶会话留在置顶区、不进组（置顶优先于日期）。
- 组内平铺、不再套时间分组（Project Review 的抽屉里是按今天 / 本周分组的，搬进时间线就成了时间分组套时间分组）；
  窗口外的会话放在尾行「更早 N」，就地展开。
- 状态汇总沿用会话行的优先级与三通道（状态条、名字字重、pop）；组行永远不用 `bg-selected`，侧栏里恰好一行在说「你在这里」。
- 折叠时，等你回复 / 出错的子会话和选中的子会话挂在组行下面，每个只挂这一份；正在工作与未读不露。规则一句话：需要你处理
  的会话永远不会被折叠藏起来。这一条同时补上了 B 的失明问题。
- 展开 / 收起组不设项目上下文（Project Review 时代展开即软设）：时间线里展开多半只是看一眼，不该顺手把新对话行改成
  「新对话 · 项目名」。只有组行 `+`、空项目 CTA、书眉菜单里的项目项设项目上下文。
- 展开状态只在本次运行内记住。
- JC 提到的「隐藏」不新增隐藏状态，改为组行菜单「归档全部对话」：折叠已经把一组压成一行，真想让它消失的多半是一批跑完的
  子会话，归档才是对的语义。
- 书眉「项目」从模式开关改成菜单：新建项目 + 全部项目，点项目 = 在该项目里新建对话并展开它的组。已知代价：沉到「更早」的
  项目，它的旧会话只能靠搜索 / EarlierDialog 找。
- 桶标题计数改为顶层行数（一个组算一行）；「更早」入口计数不变。

## 真机切换器（JC 定）

| 维度 | 档位 | JC |
|---|---|---|
| 组行 | 单行（图标 + 名称 + 右侧计数）/ 双行（第二行写汇总） | **双行** |
| 折叠门槛 | 一律折 / ≥2 才折 | **一律折** |
| 默认 | 折叠 / 展开 | **折叠** |
| 演示状态 | 无 / 正在工作 / 等你回复 / 出错（dev 伪造第一个组最近一条子会话的状态） | 只用于查看，不裁决 |

单行把组当容器标题（比 48px 会话行矮），双行把组当会话的同级行，是「相对角色」分歧，按惯例真机定；JC 选了与会话行同级的
双行。

## 执行中与 PRD 的出入（主会话认可）

- 「时间线全空时从更早补 10 条」按会话补完再折叠，补出来的行可能少于 10；换来「更早」入口计数与 EarlierDialog 列表仍由
  同一份计算得出。
- 「归档全部对话」不含置顶会话（它们不在组里）。
- 组的汇总也算尾行里的旧会话。

## 真机翻案：项目成为分区（同日第二轮）

第一轮提交（`1943932e`，未推送）后 JC 真机用了一阵：「项目文件夹和非项目会话放到一起并不理想，甚至对普通用户有些认知负荷
负担」，提出让项目成为类似「本周」的折叠头，放在非项目会话上方。

被推翻的是第一轮的这条论证：侧栏只有一条按最近活动排序的时间线，组行作为会话的同级行，跟着最新子会话落进今天 / 本周 /
本月、与会话行交错——最近在做的项目就出现在最近的位置。混排为什么累，我的归因（JC 未逐条确认）：

1. 一个列表里混了两种东西，扫一行之前得先判断它是对话还是文件夹。
2. 项目没有固定位置，组行跟着最新子会话在时间桶之间跳。项目是长期存在的东西，05-13 的理由「持续性 > 近期性」在这里
   成立：用户会想记住它在哪。
3. 时间分组的意思被打破：「本周」下的一个组里装着本月甚至更早的会话。

新方向就是 05-13 的 PROJECTS 区位置（新对话之下、时间分组之上），区别是不走当年的筛选模式，项目就地展开。05-22 离开那版
的五条理由（[devlog](./2026-05-22-project-review-sidebar-ux.md)）里，前四条出在筛选交互上（项目名重复显示、在空新对话里点
项目像按钮坏了、创建 / 展开 / 新建对话混在一起、不能同时盯几个项目），这次没有筛选，都不存在了；剩下「列表最多 8 个、扩
不上去」，用「只列近 30 天活跃的项目，全部项目在书眉菜单」解决。第一轮否掉「直接隐藏」的两条理由，分区同样满足：需要你
处理的会话挂在组行或分区头下面，位置还更靠上；选中的会话一定在侧栏里。

定下的规则（全文在设计文档「Project 组行 · 项目分区」）：

- 顺序 置顶 → 项目 → 今天 / 本周 / 本月 / 最近 / 更早；时间桶不再有项目会话，计数改回会话数；置顶的项目会话仍在置顶区。
- 分区列置顶项目、30 天窗口内有活动的项目、窗口内新建的空项目；计数 = 列出的项目数；没有可列的项目时不出现分区。置顶项目
  在前，再按内容活跃度（与书眉菜单同序）。
- 分区头与时间桶标题同款，不放「+ 新建项目」（右侧是计数）。
- 分区可折叠、默认展开、跨重启记住；折叠时出错 / 等你回复 / 选中的项目会话挂在分区头下面。
- 组行沿用第一轮：双行、一律折、启动折叠、组折叠时露出。

### 第二轮切换器（JC 定）

| 维度 | 档位 | JC |
|---|---|---|
| 位置 | 置顶之下 / 置顶之上 / 混排（第一轮，对照档） | **置顶之下** |
| 分区头 | 可折叠 / 只是标签（不可折叠） | **可折叠** |
| 项目行 | 双行 / 单行（图标 + 名称 + 右侧计数） | **双行** |

我推荐置顶之下：置顶是用户逐条挑出来放在手边的，数量少；项目区可能有好几个 48px 的行，放在置顶之上会把置顶挤下去。分区头
可折叠我当时拿不准（两层折叠 vs 一层），交给真机定。项目行重比一次单行，是因为进分区后组行的角色从「会话的同级行」变成
「分区里的一项」；JC 仍选双行。

实测时提给 JC、未改的三点：

- 分区头的 caret 在计数之后，「项目」的数字因此比「本周」的数字往左偏一个 caret 宽（「更早」入口同样如此）。可改为 caret
  放标签左边或只在悬停时显示，JC 未提，保持。
- 分区折叠时挂出来的会话不缩进、不带引导线，看不出属于哪个项目（它们可能来自不同项目，组内那种缩进会误导）。
- 分区展开 / 折叠没有高度动画：折叠时组整个卸载，保证每个会话只挂一份。

## 后续讨论：其他分区要不要也可折叠（同日）

JC 问：项目分区能折，顺着这个操作逻辑，置顶和时间桶是不是也该能折。结论是不跟，现状保持，规则写进设计文档
「项目分区」一节。

本机库快照（10-08，只读）：置顶 0、项目 1、今天 0、本周 6、本月 36、更早 62。

- **容器才折，刻度不折。**项目分区能折靠三条同时成立：在今天之上且高度不定、内容是长期对象且常是副产品、折叠时有挂出
  兜底。时间桶是同一条时间线上的刻度：折今天是自我否定（挂出规则不露正在工作；05-13 否掉整个侧栏可折叠用的是同一个理由），
  折叠状态跨重启记住还会让次日新建的对话落进折着的桶；本周 / 本月在主要内容之下，折了不提上来任何东西，本月 36 条长是长，
  但 09-09 加本月桶的理由正是 8–30 天是「上次那个任务」最常落的区间。置顶算容器，可折叠也说得通，但折它等于撤销置顶，库里
  0 条置顶，没有理由做。被否：全部可折（Slack 式；Slack 的分区是频道容器，不是时间刻度，照搬要给今天开例外，一致性反而又破）。
- **折叠后「项目 N ›」与「更早 N ›」同形不改。**我先推荐过把折叠 caret 挪到标签左边（A），理由之一「Finder 的展开三角在左」
  说错了：Apple 支持文档写的是悬停时箭头出现在分区名右边（support.apple.com 127254），现状正是 mac 侧栏惯例，左置是 IDE 惯例。
  再看歧义出现的条件：分区默认展开、caret 朝下，与「更早 ›」本就不同；只有用户亲手折过才同形，而这个人已经知道它是折叠头，
  剩下的误判是以为「更早」也会就地展开、结果弹出一个能关的对话框。A 收回。JC 的顾虑是开发者没有新用户的认知困惑，这里不构成
  盲区：会遇到歧义的人恰好是已经学会的人。
- 计数偏一个 caret 宽（上一节第一点）仍未改。修法可以不动 caret 惯例：让 caret 伸进右侧 18px 边距，数字回到网格。JC 真机看着
  别扭再做。

## 后续：删除项目的确认框加「同时归档」（同日）

JC 问：项目菜单里「归档全部对话」和「删除项目」会不会让用户困惑。会，而且后果撤不回来：

- 删除项目不删对话，对话脱离项目（外键置空）、按最后活动时间倒回今天 / 本周 / 本月；重新归组只能逐条「移到项目」（GUI
  与 CLI `session move` 都是单条）。已归档的对话也一并脱离项目。
- 「删文件夹连内容一起删」是通用直觉，ChatGPT 删项目即连对话一起删（第三方指南，未找到官方文档）。想清理的人选了最彻底的
  红色按钮，得到的是被刷满的时间桶：拿 JC 的回归项目算，19 条倒回本周 / 本月，正是这一轮做项目分区要解决的事。
- 原确认框没说清后果：不写数量，「解绑」「时间线」是开发者词，侧栏上没有叫「时间线」的东西；按钮写「删除 Project」，违反
  文案规范（中文界面写「项目」）。

选项：A 只改文案；**B 确认框加勾选「同时归档里面的 N 个对话」、默认勾上（推荐，JC 按推荐）**；C 菜单项改名「解散项目」
（一个词说不清对话去哪，确认框照样要写，可叠加不单做）；D 项目整体归档（最正确的模型，要动 Core 数据结构与 CLI 契约，进
[deferred](./deferred.md#项目整体归档)，PRD 在 `.scratch/project-archive/`）。推荐 B 的理由：困惑发生在做决定的那一刻，确认框
是唯一一定会被读到的地方，B 把藏着的分叉摆成带数量的选择。默认勾上是推测（删项目的人多半想让它消失），库里不记删除动作，
没有数据。

实现（纯 GUI，Core / CLI / Agent API 零变化，外置 / 内置两种运行时一致）：

- `archivableProjectSessions`（`gui/src/lib/sidebar-timeline.ts`）：未归档、未置顶的项目会话，与组行「归档全部对话」同一组；
  vitest 断言它与 `buildSidebarSections` 的组会话 + 尾行一致，两处计数不会分家。
- `ConfirmDeleteProjectDialog`：「项目删除后无法恢复。」+ ArchivedDialog「清空」同款的下沉勾选框，第二行随勾选切换后果文案，
  勾上且有运行中的会话时接上归档全部对话的同一句提醒（`useSessionsAttention` 的 `runningCount`）；N 为 0 不出勾选框。
  App 以项目 id 作 key，每次打开都从勾上开始。确认时先 `archiveSessionsBulk` 再 `deleteProject`。
- 编辑项目对话框里删除按钮下的提示改为「里面的对话不会被删除，确认时可以一并归档」；「删除 Project」改为「删除项目」。

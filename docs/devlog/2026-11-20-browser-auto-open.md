# 浏览器没连上时自动打开它（issue #33 第二轮）

日期：2026-11-20
关联：`.scratch/browser-auto-open/`（PRD、票 01）· [浏览器控制](../managed-ga-runtime/browser-control.md)「Opening The Browser When A Tool Needs It」·
[deferred](./deferred.md)「火狐浏览器扩展」「主题按日出日落切换」· [Windows 清单](../windows-build-checklist.md)「Browser auto-open」

## 起因

issue #33 的提出者在 v0.7.10 之后回了三条建议：浏览器扩展支持火狐（他主用火狐、备用 Edge，Edge 不常开，对话时常忘了先打开）；
深浅色按日出日落切换；打赏 / 推广位。同日第二轮回帖已发（用「我」：Galley 是 JC 的个人项目），issue 保持 open。

## 裁决

1. **火狐不做**，进 deferred 挂信号。扩展离不开 `chrome.debugger`（页面禁止 `eval` 时的兜底执行、模型直接发的调试命令），火狐没有；
   火狐正式版只装 Mozilla 签过名的扩展；两个扩展不能连同一个主进程；上游没有火狐版，做就是一份分叉。JC 本机库里直接发调试命令
   的只有 1,996 次 `web_execute_js` 里的 4 次，兜底执行的次数库里看不到。
2. **主题不加定时**，进 deferred。Galley 默认「跟随系统」且实时跟随；macOS 外观「自动」、Windows 的 PowerToys Light Switch 已能按
   日落到日出切。JC 当天在 Windows 上手动切系统深浅色，Galley 实时跟随（补进 Windows 清单）。
3. **「忘了开浏览器」拆出来做**：浏览器工具发现没有可用标签页、扩展又没连上时，Galley 打开扩展所在的那个浏览器，等它连上再继续。
   JC 定：默认开，不加开关（它替用户做的是本来就要做的一步，浏览器弹出来本身就看得见）。
4. **打赏 / 推广**：回帖先感谢，说会考虑建一个用户群收集反馈，暂时没有财务压力，会尽力持续更新。

## 做法

两项探针先在 macOS 上过了：

- **认出浏览器**：扩展的握手不带浏览器身份，UA 也分不出 Vivaldi。但连接认得出来：按扩展那一端的端口反查进程，对端是
  `Vivaldi.app` 里的 Helper，往上取最外层 `.app` 就是要打开的程序。这样不限于 Core 原本会开的 Chrome / Edge。
- **连上要几秒**：退出 Vivaldi 后 `open -a` 打开，1.86 秒扩展连上（扩展在 `onStartup` 里直接连）。

票 01（提交 `0565566f`、`414b7bcf`、`6a7d819a`）：

- 浏览器桥在扩展每次新连上时认出程序（macOS `lsof` + `ps`，Windows `ctypes` 调 `GetExtendedTcpTable`），状态行带 `browserApp`，Core 存进
  偏好 `browser_control_last_browser_app`，下次起桥时用 `--known-browser-app` 传回。
- 内置补丁 `0035`：`TMWebDriver` 的 `/link` 加 `galley_browser_wanted`，`ga.py` 在没有标签页、扩展又没连上时问主进程；浏览器桥的钩子
  回「在开」就移动 `browserWantedAt`，工具每 0.5 秒查一次、最多等 20 秒。Core 看到 `browserWantedAt` 移动、扩展未连上，就打开那个浏览器。
- `first_init_driver` 原来的 12 秒等待只留给「这个进程刚成为主进程」的情况（扩展要过一会儿才找到新主进程）；连常驻主进程的会话不再空等。
- 只在内置模式；没有新增监听（走 GA 已有的 `127.0.0.1:18766/link`）；IM 渠道的 GA 进程也是常驻主进程的远程客户端，同样会触发（读代码得出）。

## 验收时的两处更正（JC 当天裁定保留）

1. **打开时带测试页地址，去掉「已在运行就不打开」。** 票面原写「不带网址、浏览器已在运行就不打开」，前提错在：扩展只认 `http` / `https`
   标签页（`background.js` `isScriptable`），Chrome / Edge 默认启动只开新标签页，不带网址等于打开了也没有可用网页。改为总带
   `https://example.com`（设置页「测试页」用的同一个）。网页的 `content.js` 会发 `wake`，后台休眠的扩展因此醒来重连；给运行中的
   Chromium 一个网址会开成新标签页；Edge 的启动加速会让它没有窗口也在运行，原来的检查正好漏掉这种情况。代价：会恢复上次标签页的
   浏览器每次被打开多一个标签页。
2. **一次断开只打开一次。** 去掉运行检查后，扩展被禁用或路径打不开时，每次浏览器调用都会多一个测试页、再空等 20 秒。改为 30 秒内没
   连上就不再打开，扩展重新连上或 Galley 重启后恢复。

## macOS 真机（主会话代验）

- 冷：退出 Vivaldi，经 CLI 新建临时会话发一件要用浏览器的事。5.5 秒 Vivaldi 被打开，约 7.3 秒扩展连上，任务答对；第一步落库在发出后 34 秒。
- 热：浏览器开着时再发一句，进程号不变，第一步 6 秒。
- 与预期不符的两处（Chrome 上的结果见下一节）：
  - **冷启动时没开出 `example.com`。** Vivaldi 恢复了上次的标签页，这里不碍事；Core 是否带上了地址没有看日志。这个地址正是给 Chrome / Edge
    准备的，Windows 上的 Edge 要看它出没出现（已写进 Windows 清单）。
  - **冷启动第一步慢约 28 秒。** 工具结果是「页面变化监控不可用」（执行前抓基准页面失败），用的标签页是恢复出来的第一个；推测是恢复的
    标签页还没载入，抓页面等到超时。上游原有行为（默认标签页取第一个），没改；要改得让扩展报出哪个标签页已载入。

## macOS Chrome 真机（同日，JC 在 Chrome 装上扩展）

- Chrome 默认只开新标签页，正好是 Vivaldi 造不出的状态。票 01：退出 Chrome 后发任务，4.9 秒 Chrome 被打开、再 1.8 秒连上，`example.com`
  出现，第一步 12 秒，答对。带网址打开在 Chrome 上成立；Vivaldi 冷启动没开出它是 Vivaldi 的行为。第一步不慢，支持上面「慢在恢复出来的
  未载入标签页」的推测。
- 票 02（扩展连上了但没有可用网页时也打开，提交 `efcfc4ac`）：正常打开的 Chrome 只有新标签页，发任务后 4.3 秒出现 `example.com`，第一步
  7 秒，答对；仍是 1 个窗口。
- 两个浏览器都装了扩展时会同时连浏览器桥，命令可能串到另一个浏览器；测完建议 JC 在 Chrome 里停用扩展。

## 没做的

- 扩展已连上、但用户自己开的浏览器里只有新标签页时，仍立刻回「插件已连接，但没有可用网页」。同一机制可以顺带覆盖（Galley 自己开一个网页），
  超出这次批的范围；JC 当天裁「这个也做」，开成票 02。
- Windows 三步（Edge 关着时自动打开且出现 `example.com`、开着时不多开窗口、弹出来的感受）JC 定在下一版草稿时验。

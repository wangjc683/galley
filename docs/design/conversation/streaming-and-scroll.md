# 行动条、滚动与流式

> [Conversation 主区与 Composer](./README.md) 的一篇：2026-11-10 从 `docs/design/conversation.md` 拆出，正文原样搬过来。

#### Message Actions（reply 级行动条）

每段 agent final answer 下方一行 muted 行动条（DESIGN.md §4.3 dogfood 反馈：用户经常想保留 reply 内容），**悬停该回答时才显示**（2026-09-28 起；此前常驻，见下方「视觉」）。助手的对话里行动条只有图标（复制 · 引用 · 保存 · 过程 · ⋯，「过程」只在两步以上的回复；引用见下表，裁决 99），不带 token 与上下文，步数、用时与 token 在点开后的过程卡片第一行；你的气泡悬停时也有一排复制 · 引用 · ⋯（裁决 105，推翻裁决 73 的「没有悬停复制」）；两者 2026-11-06 起挂在气泡外侧，回复的在右、你的在左，底边对齐、离气泡 6px、不占版面（裁决 199）。选中文字照旧弹选中工具条，工具条在时那条消息的悬停行让位（裁决 108，见下「复制入口统一」）。见「[助手的对话](./assistant.md#助手的对话2026-10-15)」：

| 按钮 | 行为 |
|---|---|
| `Copy` | 复制原始 markdown source（带 `**bold**` `## headers`），不是渲染后纯文本——用户粘贴目的地（Notion / Obsidian / Slack / 邮件）多数能 re-render markdown |
| `Save` | Tauri save dialog → `.md` 文件。默认文件名 `galley-{YYYYMMDD-HHmmss}.md`（产品名前缀；`ga` 保留给内核，与图片保存的 `galley-image-` 同族），用户可改 |
| `Quote` | 只在助手的对话里，排在复制与保存之间（2026-10-19，裁决 99，票 47），只在消息菜单有「引用」时出现：跑菜单的「引用」，整条放进输入框上方的引用条，长的截断（`wholeMessageQuote`，见「助手的对话」的「引用整条」）；不闪对勾 |

**复制入口统一（`ActionChip`）** —— 按"行动条 vs 触发浮现"两类组织，全部共用一个
`ActionChip`（Copy thin 14px → Check success，1.5s 回落，quiet 1px press）：

- **行动条**：assistant 回答末尾的 reply 行动条（`Copy` + `Save`；助手的对话里是
  复制 · 引用 · 保存 · 过程 · ⋯，裁决 99），bare chip、工作台里贴答案
  下方左对齐（助手的对话里在气泡右边，裁决 199）、悬停该回答时显示（2026-09-28 前一直可见）。
- **触发浮现**：用户做动作才出现的复制，贴相关内容浮出：
  - assistant 里**选中**文字 → 浮在选区旁（gutter）的**选中工具条**（`SelectionCopyToolbar`）：
    **一个浮起的小壳，壳里是与悬停行同款的裸图标**（2026-10-19，
    [主聊天 PRD](../../../.scratch/main-chat/PRD.md) 裁决 108，票 56）。
    出现的范围照旧：工作台只在选中回复时，助手的对话里选中回复或你的气泡都出现
    （`lib/selection-copy.ts`），选区要起止在同一条消息里。**两颗，竖排**（2026-10-16，
    [Telegram 细节](../../../.scratch/telegram-details/PRD.md)票 02）：上面是复制，位置同
    以前（中线对着选区最后一行）；下面是「引用」（Phosphor `Quotes`，tooltip 与
    读屏名「引用」/「Quote」），贴视口上下各留 12px。竖排是因为侧沟只有
    一颗按钮宽（离栏 10px、离视口 12px 的规则不变）。
    - **壳**（裁决 108）：实底 `bg-elevated`（不做毛玻璃，08-10 的「非 glassmorphism」）、
      1px `border-line`、`--shadow-float` 投影（与「回到底部」按钮同一个 token）。圆角
      `rounded-md`（12px），取菜单那一档：壳和菜单一样是装着几个各有悬停底色的控件的面，
      套法也同菜单的「外圆角 = 里面的圆角 + 内边距」（菜单 12 = 8 + 4，这里是 chip 的
      `rounded-sm` 6 + 6）；tooltip 的 6px 给只装一行字的标签，拿来装 6px 的 chip，壳会比
      里面的 chip 还方。内边距 `p-1.5`（6px），两颗之间 `gap-0.5`（2px，同悬停行）：14px
      的图标在 24px 的 chip 里四周各留 5px，于是两个图标相距 12px（5 + 2 + 5），与悬停行
      一样，图标到壳的外缘也是 12px（5 + 6 + 1）：悬停行的节奏收进一个框。壳 38 × 64px，
      只有复制一颗时 38 × 38；复制那颗的中线离壳顶 19px（1 + 6 + 12），位置常量照此重算，
      「中线对着选区最后一行」不变，侧沟要放得下 38px 才放（离栏 10、离视口 12）。
    - **壳里的 chip** 就是悬停行那一颗（`ActionChip`：24px、14px thin 图标、`ink-muted`、
      悬停 `bg-hover` 提墨、复制后闪对勾 1.5 秒、`tabIndex={-1}`），tooltip 照旧朝外。
      按在壳上 chip 以外的地方不清选区，同按在 chip 上。此前每颗各穿一身装甲
      （`floating` 变体：28px、各带边框与投影），两个带框的方块读作另一族按钮；
      这个变体已删，`ActionChip` 只剩裸的一种。
    - **让位**（裁决 108）：选中工具条为哪条消息出现，那条消息的悬停行就不出现：回复的
      行动条（工作台与助手的对话都是）、你的气泡旁边那一排（助手的对话）。同一刻只有
      一套动作，不再同时有两个「复制」两个「引用」，一套管整条、一套管选中的那段。判定
      就是工具条自己的：它出现、收起（选区取消、选到别处、点了引用、按 Esc、滚动、
      按在消息以外的地方）都跟着走；工作台里选中你的消息没有工具条，悬停复制照旧。
      悬停行自己钉住常显时（「已复制 / 已保存」闪现、过程展开）也让位：要消除的正是
      两套同时出现，钉住时一样；过程卡片照旧开着，工具条一收，行回到原样（还钉着的照旧
      常显）。「⋯」菜单开着时碰不上：让位时「⋯」点不到，菜单开着时页面也拿不到指针。
      隐藏照旧用透明度占位，不跳；长消息的「展开 / 收起」不是悬停动作，不让位。做法：
      能弹工具条的消息在悬停区挂一个自己的键（`data-selection-yield`，`useId`），工具条
      从所选的范围往上找到它、记下（`lib/selection-copy.ts`），行只问「是不是我」；只在
      键变时通知，只有离开与来到的那一两条重渲染，拖选时其余消息不动。
    - **引用**（2026-10-16 改，[PRD](../../../.scratch/telegram-details/PRD.md) 裁决 3a、票 07；票 02 原来把 `> ` 一行行写进输入框的文字，JC 真机嫌简陋）：把所选（与复制拿到的同一段文字）加进输入框的**引用条**，不碰你打的字；聚焦输入框，光标回到文字末尾，清掉对话里的选区，工具条收起。走 `ComposerHandle.quote`。同一段再引用一次不重复；满 3 段时不加，弹一条提示「最多引用 3 段，先移除一段再引用」。引用条、发出时怎么拼、气泡里怎么画，见 §4.4「引用条」与「气泡」里你的那条。
    - 学的是 Telegram 选中正文后「回复」变「引用并回复」；不做点引用跳回原文（要记住来源消息，改库、碰 Core；按文字匹配是猜）；助手的对话里，气泡的消息菜单（右键或回复行动条的「⋯」）另有「引用」，引的是整条，见「[助手的对话](./assistant.md#助手的对话2026-10-15)」的「消息菜单」（票 38）；回复的行动条上也有这一颗（票 47）。
  - user 消息上 **hover**（工作台）→ 在气泡**下方**、右缘对齐气泡右缘，离气泡
    6px，`inline` 变体（2026-10-16，工作台对话票 01：气泡靠右后，原来的右下角外侧
    正对问题轨；与回复的行动条同一种几何，气泡下 6px、chip 24px）。长消息的
    「展开 / 收起」在同一行、最右，chip 在它左边：「展开」常显，占住气泡右缘，
    chip 悬停才出现；chip 放最右的话「展开」静止时离右缘悬空 28px，分两行的话长
    消息下面到 58px。隐藏时 `opacity` 占位，悬停不跳。悬停区是整行连上气泡下面
    30px 那条带子（一块看不见的命中区，正好盖住下外边距 `mb-7.5`，不占版面、不改
    间距，也碰不到下一条），指针从气泡走到 chip 一路都在区内；离开即收起，同回复的
    行动条（2026-10-19，[PRD](../../../.scratch/main-chat/PRD.md) 裁决 109，票 57）。此前
    外边距不算悬停区，穿过气泡下 6px 就算离开，所以离开后等 600ms 才隐（2026-05-21
    起）。钉住常显照旧：复制后对勾 1.5 秒、「⋯」菜单开着；选中工具条在时让位；菜单
    关掉时指针不在区内就立刻收起。复制的是原文全文，折叠的长消息也是。

    空白拖尾）；09-18 前在右上外侧；09-18 到 10-15 在右下外侧、中心对准末行（右中
    被否：两行消息上卡在行间）。助手的对话里是复制 · 引用 · ⋯ 三颗（2026-10-19，裁决 105），2026-11-06 起在气泡左边、底边对齐、离气泡 6px（裁决 199；此前与这里同一处、同一套几何），见上。

两条正交的规则（2026-08-10 拆开；此前误绑成「常驻=bare／触发=floating」的等式，
导致 user hover chip 长期穿错皮）：

1. **何时出现**：回答级操作在回答末尾的 bar 里（悬停回答时显示）；触发式复制贴着触发它的内容浮出。
2. **穿哪身皮**——只看**背后是什么**，与生命周期无关。原则不变，2026-10-19 起装甲从
   每颗按钮挪到外壳（裁决 108）：
   - **装甲**（实底 `bg-elevated` + `border-line` + `--shadow-float`，非
     glassmorphism）**仅**用于会压在任意内容之上、必须把自己从中切出来的场合。
     目前只有 portal 出去的选中工具条属于此类。装甲穿在**壳**上，一次；壳里的
     chip 是裸的。此前每颗 chip 各穿一身（`floating` 变体，已删）。
   - **裸**（原 `inline` 变体，现在是 `ActionChip` 唯一的样子：muted 图标，hover
     才有淡底）坐在干净画布留白里时什么都不加——reply bar，以及 user 消息的悬停行。
     不需要的装甲会读作 UI 机件压在内容上，正是高亮笔改版要消除的寄存器倒挂。

   故选中工具条与 user 消息的悬停行同为「触发浮现」，chip 同款，差的只是有没有
   那层壳，各有其理由。

**间距注意**（2026-10-16，工作台）：user hover chip 那一行不在文档流里，挂在你这一行的下边距
（`mb-7.5`，30px）里。这 30px 就是你 → 下一样东西（折叠头、live 行、回复、提问块）的
间距：下一样东西自己的上边距（最多 `mt-6`）跟它合并，不再另加 `my-5` 的下半；放进
文档流的话会叠在它们的上边距上。当时助手的对话也是这个思路（「它 → 你 30px 由
行动条占着」）；裁决 199 起主对话的悬停行挂到气泡外侧，不再占位（`assistantRowGap`）。量得（主区 1220 宽、标准字号）：气泡到折叠头 24 → 30px，
到 live 窗口 24 → 30px，到一步的回复 30px（原来先隔一个折叠头：气泡到回复正文
60px）；长消息气泡到折叠头 54.6 → 30px（原来「展开」一行之后再隔 24）。回复 → 你
照旧：行动条 30 + `mt-5` 20。（高亮笔时代 chip 用 `ml-3` 补偏移 box-shadow 的 4px
出头，09-17 换成气泡后已是 `ml-1.5`，这条注意随之作废。）

视觉（2026-07-05 回写为 icon-only 现状）：

- 位置：工作台在 reply markdown 渲染**正下方**，gap 6px（`mt-1.5`）；助手的对话在气泡右边，见「助手的对话」的「行动条」（裁决 199）
- icon-only chip（14px Phosphor thin），无文字标签；标签在 Radix
  tooltip / aria-label 里
- **悬停回答时显示**（2026-09-28 起，此前常驻可见）：悬停区是 `MessageAgent` 外层 `group/answer`（答案正文 + 行动条）。隐藏时保留占位（`opacity-0` + `pointer-events-none`，不卸载），悬停不引起位移；「已复制 / 已保存」反馈的 1.5s 内保持可见（选中工具条为这条回复出现时例外，让位，见上「复制入口统一」）；不做键盘聚焦显形（06-29 指针优先规则，chip 本就 `tabIndex={-1}`）。内容不变：复制、保存 | token 与上下文（助手的对话例外，只有图标，见上）。V0.1 常驻的理由是「只在悬停出现，用户得到处找」；JC 嫌它时常吵、长答案下还好（约 27% 的回答只有一两行，栏和回答一样大），真机比过现状 / 最新一条常显 / 常显只留图标后选悬停，见 [devlog](../../devlog/2026-09-28-answer-action-bar-on-hover.md)
- chip 静息 text-ink-muted；hover 升 ink-soft + bg-hover
- 点击后 icon 变 Check（`text-success`）1.5s 后回 idle；tooltip 随状态
  切换（悬停绿勾时读到「已复制」而非「复制」）

工程：
- Copy 走 `navigator.clipboard.writeText` web API（Tauri webview 支持）
- Save 走 `@tauri-apps/plugin-dialog` `save()` + `@tauri-apps/plugin-fs` `writeTextFile`
- Capabilities 加 `dialog:default` / `fs:allow-write-text-file` + `fs:scope` 限制到 `$HOME` / `$DOCUMENT` / `$DESKTOP` / `$DOWNLOAD`（保留用户常去的目录）

V0.1 **不做**：

- **Regenerate 按钮**：需要 GA history 回滚 + 跨 turn 状态管理，工程量大；推后到 V0.2 跟 multi-session / session 恢复一并设计
- **Continue 按钮**：用户自己输入"继续"即可，不需要专用按钮
- **Pin / 收藏**：需要数据模型扩展，V0.1 单 session 不值
- **Branch（从这里分叉新 session）**：跟 multi-session 深度耦合，V0.1 没法做
- **TTS / 翻译 / Share**：依赖外部服务，跟产品定位不符

ReactNode children（非 markdown string）的 reply 不渲染 actions——demo fixture 没 markdown source 可复制。

#### Scroll behaviour（stick to user message top）

Conversation 主区是 `overflow-y-auto` 的列。用户提交新消息时**不**滚到底部（reply 还没生成，跳到一片空地）；**也不**被动什么都不做（user message 出现在视口外，看不到反馈）。**正确做法**：把刚 submit 的 user message 顶端贴到 viewport 顶部下方 32px 处；它正上方挨着一条时间条时，停的是时间条（见下「停一条你的消息」）。下面留白到输入框，live 窗口与回复在留白里往下长，视口不动；回复超出一屏也不跟随（2026-10-16 起才真正做到，见下「发出后留白」）。

助手的对话不这样：对话贴着输入框，发出后滚到底，跟随到回复的开头为止（贴底），见「[助手的对话](./assistant.md#助手的对话2026-10-15)」。本节讲工作台的对话。

跟 Claude.ai / ChatGPT 收敛的同一模式。理由：

- 用户提交完立刻能看到自己的提问
- 长 reply 不会推走问题——问题永远在视口顶端附近
- 短 reply 用户也不必往下找答案——它就在问题正下方
- 阅读 reply 期间**不被打扰**（不跟随）

实现细节（`hooks/useStickyScroll.ts`）：

- messages store 的 `userSubmitTick` 计数器在三处 +1：`appendUserTurn`（输入框发出、ask_user 的回答）、`appendSideQuestionUserTurn`（`/btw`）、`applyUserMessagePersisted` 第一次见到别处写下的一行（只限当前会话，子任务汇报除外）；同时记 `lastSubmitSource`，决定这次怎么滚（见下「发出后留白」的表）
- effect 监听 `userSubmitTick` 变化（不监听 `turns.length`——避免 `turn_end` 也触发滚）
- RAF 推迟到 `<MessageUser>` 真实 mount 后
- 找最后一个 `[data-role="user-msg"]` / `[data-role="user-msg-reply"]`，落点是 `userMsgParkOffset`（见下「停一条你的消息」），滚动交给 `animateScroll`（见下「平滑滚动」）
- 只认没处理过的 tick（模块级的 `scrolledForSubmitTick`，在 RAF 里记，StrictMode 第一次执行的 effect 被取消也不会漏）：MainView 按会话重挂载（App 用会话 id 给它 key），tick 是全局的，2026-10-16 前每次切换会话都会重放上一次发出，把那个会话最后一条你的消息停到顶上，而不是落到底部。主对话那一支照旧每次都走（它本来就是到底）
- 不用 `scrollIntoView({block: "start"})`：它没法控 padding
- **停一条你的消息**（2026-10-16，工作台对话票 01）：一条规则，提交贴顶、⌥↑ / ⌥↓、问题轨的点击与高亮的点、⌘K / ⌘F 定位到你的消息都走它，两种对话都是：它正上方挨着一条时间条时，时间条上缘停在视口顶下 16px，气泡在它下面 30.5px（时间 10.5px、间距 20px），落在 46.5px；没有时间条，气泡上缘照旧停在 32px。规则在 `lib/conversation-anchor.ts` 的 `userMsgParkOffset`，哪个节点是锚不变（气泡的 `data-role="user-msg"`），时间条靠「气泡所在那一行的前一个兄弟」认出来。起因：时间改成两条消息之间居中的一行后，照旧把气泡停在 32px，时间条只剩视口顶下 1.5px，半露不露；原来时间行在气泡上方 4px，停在 17.5px，16px 是挨着它的 4px 一档。⌥↑ / ⌥↓ 判断「上一条 / 下一条」和问题轨判断当前的点都按同一个落点算，停在这里的消息算「已停住」，不会卡住或认错。实测（主区 1220 宽）：有时间条的消息从「时间条 1.5px、气泡 32px」变成「时间条 16px、气泡 46.5px」（滚动位置取整，个别差 0.5px），没有时间条的照旧 32px；助手的对话里 ⌥↑ / ⌥↓ 与定位同样变（助手没有提交贴顶和问题轨）。
- **平滑滚动**（2026-10-16，[向 Telegram 学的对话细节](../../../.scratch/telegram-details/PRD.md) 裁决 5，票 04）：对话里程序发起的平滑滚动只走一个函数，`lib/animate-scroll.ts` 的 `animateScroll`，不再用引擎的 `behavior: "smooth"`（时长与曲线由引擎定，也不认「减少动态效果」）。走它的五处：提交贴顶、⌥↑ / ⌥↓、问题轨的点击、「回到底部」（下面「Sticky-bottom」一节），以及助手的对话里回复从三点气泡撑开的那一次落地跟随（`useStickyScroll` 的 `startLanding`，2026-10-19 起，裁决 103、110，票 51、58，见「助手的对话」里「在跑时：三点气泡」的「交接」）。前四处的时长、曲线与远跳照下面的数值；落地那一处用定时模式 `ScrollTiming`：时长与曲线跟气泡展开走（`--motion-slow`、`--ease-pop`），整段都动画、不远跳，中途改目标不改结束时刻，谁说了算与减少动态照下面的规则。数值学 Telegram Web A（`src/util/animateScroll.ts` 与 `config.ts`，只学思路与数值，代码自写）：
  - **远跳先瞬移**：目标超过 800px 时，先瞬移到离目标 800px 处，只动画最后 800px。远处的一条消息是一次跳转，不是一路刷过去的几十条消息。
  - **时长**：300ms + 动画距离 ÷ 800px × 300ms，最长 600ms（100px 约 338ms，300px 约 413ms）。
  - **曲线**：ease-out。300px 以内 `1 − (1 − t)^3.5`；更远用更陡的 `1 − (1 − t)^6`，前段走完大半、收尾放慢。
  - **减少动态效果**：系统开着时直接写 `scrollTop`，没有动画。每次调用实时读 `matchMedia`，不缓存，改了设置立即生效（[foundations](../foundations.md) §2.7「只淡不移」）。
  - **谁说了算**：用户中途滚轮、触控板、触摸、按住滚动条、按滚动键（方向键、Page Up / Down、Home / End、空格；在输入框里打字不算）立刻放手，不和人抢。两帧之间 `scrollTop` 被别的代码挪了（跟随贴底、切换会话、往上加载一页而垫层接不住时的保位）也放手：那是别人的决定，同原生平滑滚动被一次 `scrollTop` 写入打断一样。同一容器上新的请求接替旧的。
  - **中途改目标**：`retarget` 从当前位置按同一套规则重新起步，「回到底部」追移动靶用它。
  - **⌥↑ / ⌥↓ 连按**：动画途中再按，从这次跳转的目的地（`scrollDestination`）算上一条 / 下一条，每按一下多走一条，不会重瞄同一条。
  - **不走它的**：⌘K / ⌘F 定位照旧硬写 `scrollTop`（新挂载的会话要靠一次真实的 `scrollTop` 变化触发 WKWebView 重绘，落定后 500ms 内还要按停靠位置重停，见 [overlays-and-settings](../overlays-and-settings.md)「关键交互」的「对话内容命中 → 定位到那条消息」与 `useStickyScroll` 里的注释）；切换会话落到底、跟随贴底、视口变矮保持贴底、往上加载保位、助手发出后到底，本来就是瞬时写。跟随贴底只有一个例外：助手的对话里回复从三点气泡撑开的那一次落地是平滑的（上面第五处，裁决 103、110，票 51、58），其余跟随照旧瞬时。对话区以外的列表内滚（侧栏、设置页、提示词管理、文件预览里的标题跳转、diff 的 hunk 跳转）不在这条规则里。
- **发出后留白（live tail）**（2026-10-16，[向 Telegram 学的对话细节](../../../.scratch/telegram-details/PRD.md) 裁决 2，票 06）：只在工作台。起因：列表底下没有留白，你的话后面内容不够一屏时滚到底就停了，消息停在靠底的位置（JC 真机确认）；随后在底部、跟随把它一路推上去，长回复的开头也被推出视口。规则与实现在 `lib/live-tail.ts`。
  - **留白**：对话列（滚动容器的第一个子元素）上的 `min-height`：列至少要从停靠线往下够一个视口，`scrollHeight − clientHeight` 才到得了停靠位置。内容不够时补足，超过时不起作用。不用列后面的 spacer：`min-height` 只取决于锚点上方的内容和视口高度，这一轮自己的变化（换步、思考预览、流式回复、落定收合）都不用重算，浏览器也就没有机会在变化与重算之间把 `scrollTop` 夹回去；spacer 要随下面的内容一起伸缩，落定收合先发生、夹住滚动位置，消息就会跳收掉的那段高度。Telegram 也是给最后一段 `min-height`（Web A `MessageList.scss`）。
  - **实时更新**：视口变高变矮（输入框长高、发出后缩回一行、排队条、窗口）在 ResizeObserver 回调里当帧重算，停在线上的那条留在线上，中间那帧不会画出来；锚点上方的行变了（加载更早一页、上方迟到的排版）下一帧重算：在那个回调里改更浅一层元素的尺寸，ResizeObserver 会报 loop。
  - **停靠**：`animateScroll` 到 `userMsgParkOffset` 的落点；减少动态效果时瞬时。
  - **不跟随（A）**：跟随贴底的四条路（每次提交后的 layout effect、内容列的 ResizeObserver、视口变高变矮保持贴底、切换会话后 500ms 的窗口）在留白期间都不动。内容还在留白里时视口本来就在底部，「回到底部」不出现；超出一屏后视口不动、按钮出现（在跑带脉冲圈，跑完未读有圆点，规则照旧）——没有滚动事件告诉它，所以由内容列的 ResizeObserver 重读一次离底距离。
  - **例外：跑的途中问你**（2026-10-16，裁决 2a，票 09）：ask_user 的提问块一出现（从无到有，或换了一个新问题），没完整露出就滚到完整可见；理由是问题会卡住这一轮，没看到就一直等着。「完整露出」= 上缘不高于视口顶，下缘不低于回到底部按钮那一条（底下 48px：按钮离底 16px、高 32px）。滚到时下缘停在那一条之上 24px（同对话区 `py-6`），内容到头时停在内容末尾；提问块高过这段空间时，改为上缘停在锚线（32px）。用 `animateScroll`，减少动态效果时瞬时。**你往上翻过这一轮时不动**：以这一轮最后一条你的消息（你发的那条，或你上一个回答）的停靠位置为界，`userMsgParkOffset(它) > USER_MSG_ANCHOR_TOLERANCE_PX`（它在线下 8px 以上，即视口在停靠位置之上）就不动；停着或在它下面读这一轮的过程与回复，就滚。出现后 600ms 内每帧再看一次（这一轮刚停下，上面那段会重画，问题会挪位）；这期间你滚动、按 ⌥↑ / ⌥↓、点问题轨或回到底部，就交给你，不再管。滚过去之后照旧不跟随：停在内容末尾不算你要跟随，你自己滚到末尾或点回到底部才挂上。一轮里每个新问题都照这条。只在留白不跟随的时候：主对话、Supervisor / CLI 发起的那一轮、你已经重新挂上跟随的，照跟随规则（在底部就跟到底、问题露出来；往上翻着就不动）。规则在 `lib/live-tail.ts` 的 `askUserRevealTop`、`scrolledAboveRound` 与留白的 `reveal`。
  - **重新挂上跟随**：你自己滚到、或点「回到底部」到**内容真正的末尾**（内容已超过留白）时挂上，此后照旧「在底部就跟」。留白还露着时，底部就是停靠位置本身，到那里不算要跟随。往上翻过照旧不跟。
  - **落定**：过程收成折叠头时 `min-height` 不变，你的话不动，回复往上挪收掉的那段高度；内容缩回留白里也不会夹住 `scrollTop`。滚动锚定（`overflow-anchor`）不用关：Chrome（与 Windows 的 WebView2 同内核）里 `auto` 和 `none` 量出来一样（停住时、往下读到步骤里 150px 时各落定一次，`scrollTop` 都不变，锚点选在收合的那段上方）；WKWebView 没有滚动锚定（`lib/scroll-anchor.ts`）。
  - **寿命**：切到别的会话再回来就没有了（MainView 重挂载，照旧落到底部）；下一次发出跟着新的那条走；不落盘。加载更早一页时留白不变、视口照旧不跳（保位之后锚点跟着下移，`min-height` 跟着加）。锚点那条被重新渲染成新节点时按 `data-message-id` 找回；那条没了（Core 把它排进了队列、撤掉了回显）留白就撤掉。
  - **谁发的**（`submitScroll`，来源记在 `lastSubmitSource`）：

    | 来源 | 怎么滚 |
    |---|---|
    | 输入框发出、ask_user 的回答（`composer`） | 停靠，留白，不跟随 |
    | 排队的消息在上一轮跑完后自动发出（`queued`：Core 发出的、来源记为 GUI、本页没有回显的一行，也包括 Core 自己发出的「发进刚结束的那一轮」、手机发的） | 在底部：留白挪到它下面，视口不动，不跟随——你多半正在读上一轮刚落定的回答；往下滚或点「回到底部」它就停到线上。不在底部：什么都不动 |
    | `/btw`（`side`） | 照旧：朝它的停靠位置滚（没留白时夹在底部），留白与跟随状态不变 |
    | CLI、Supervisor、system 发进来的（`external`） | 照旧：同上，且跟随回到「在底部就跟」 |

  - **主对话不走这里**：`stickBottom` 时提交那一步在最前面就返回，留白永远不会开始，主对话的跟随路都不读它。
  - **实测**（Chrome 临时 harness，真实的 `useStickyScroll` 与 `Conversation`，StrictMode，窗口 1220 × 900、输入框 48px，前面四轮旧对话）：发出后约 0.6 秒停住，隔了时间断点的气泡在 46px、同一分钟内的在 32px，此时正好在底部、按钮不出现；思考行、换步、live 区长到 120px 视口不动；长到超出一屏（900、1600px）`scrollTop` 不变、按钮出现；输入框长高 45px 再缩回，留白 2015 → 1970 → 2015px，消息一直在 46px；落定（过程收合、回答 3 段或 40 段）消息不动；读到内容末尾后再长，跟着走；排队的消息在底部到来，视口不动、留白挪到它下面，往下滚它停在 32px；往上读 400px 时到来，什么都没动；重挂载（切换会话）落到底部、没有留白；减少动态效果下两帧内就停住。

边界：

| 场景 | 行为 |
|---|---|
| 第一次提交（EmptyState → MainView 切换） | 同样停靠并留白（MainView 先挂载还是 tick 先到都一样：只认没处理过的 tick） |
| `turn_progress` chunk 流入 / `turn_end` 来 | 不触发（store 状态变了但 tick 没变） |
| 用户主动向上翻历史 | 不打断（仅 submit 触发） |
| 切换历史 session（multi-session 后） | 落到底（看到最后 turn），没有留白；重挂载不重放上一次发出 |

#### 会话切换：原子换入，不做 skeleton（2026-07-15）

首次访问某会话（本次启动内未加载过、SQLite 有历史）时，`activateSession` **先等转录进内存、再翻 `activeSessionId`**：旧会话画面保持到新转录可以一次 commit 整体换入，"新会话 + 零消息"的空白帧不存在于渲染序列。冷启动（无旧画面可保留）与回访 / 新会话（无需恢复）仍即时翻转。延迟翻转的竞态守卫有两重：activation epoch（快速连点时新点击拥有指针）+ 指针快照（`createSession` / 删除等旁路直写 `activeSessionId` 时过期恢复不得翻回）。

**Skeleton 被明确否决**（决策留痕）：本地 SQLite 读是几十毫秒级，为"本不该被感知的等待"做占位是把它制度化；聊天转录结构不可预测，灰条必然与真实内容对不上（双重跳动）；shimmer 属于动效分类学要删除的 B 类环境动效。正确野心是**让加载态不存在**，而非装修加载态。spinner 保持只用于真慢的事（LLM / 工具 / bridge / 网络），SQLite 路径上不出现任何 loading 指示。

#### 长对话按轮分页（2026-10-13）

主聊天是首页、一直累积，一次读出、渲染全部消息迟早拖慢打开（主聊天 PRD 裁决 51，`.scratch/main-chat/issues/12-paged-conversation-history.md`）。所有对话（主聊天与普通对话、内置与外置运行时）走同一条路径：

- **按轮切页**：打开对话（上面的「转录进内存」）只读最近 50 轮（Tauri `session_message_turns_page`，常量 `MESSAGE_TURN_PAGE`）。一轮 = 一个 `turn_index`（用户消息与回复第一步同轮，主聊天问候是 -1），一轮的所有行在同一页。页界不切断 run：页首落在 run 中间（多步 run 的后续步、ask_user 回答续接的段）就往前补到该 run 的开头那条用户消息。所以一页可能多于 50 轮。每页由 Core 判定，规则与 `run-groups` 同一套，页拼起来与整段读出的 turns 完全一样。
- **往上翻自动加载**（2026-11-02 改，[主聊天 PRD](../../../.scratch/main-chat/PRD.md) 裁决 170、172，票 123）：视口顶离已加载内容的顶（垫层不算）不到 10 屏就读上一页、前插（`hooks/useEarlierTurns.ts`），一次一页，读完再看。打开对话落定后不等滚动就照此看一次（挂载时 `useStickyScroll` 在绘制前已经贴底，它的那一帧先排；恢复还在读时不读，读完的那次提交再看），所以主对话打开后会先补一页。原先离顶一屏才读、要等第一次滚动，往回甩总撞到已加载的顶：macOS 回弹、上面空着，页落地后上面才长出来（JC：「先空白一下在显示出更多新的」）。
  - **前插后视口内容不动，靠垫层，不写 `scrollTop`**：WebKit 没有 CSS `overflow-anchor`，原先前插的那次 commit 在绘制前写 `scrollTop`，把视口顶部那一行放回原位。可 macOS 的滚动不归主线程管，惯性滚动途中页面写的 `scrollTop` 会被 WebKit 的滚动线程按它自己的位置盖掉。探针实测（dev 版，主对话两周约 30,480px、6 页）：读一页 12–74ms，渲染一页主线程停 150–280ms，滚动在这段时间照走；往回甩每秒一万到三万多像素，起手那一下到五万；离顶一屏才补时 3 次补页都撞顶、3 次修正都丢，落在新页的顶上，等于跳过一页；提前到 6 屏补，途中补的几次也乱（闪一两帧更早的内容再跳回，或跳过一页）；停手时写都没丢。所以现在：还有更早的页时，已加载内容上面垫一段空白（垫层，对话列的 `padding-top`，`lib/scroll-runway.ts`）；补页那次 commit、之后 1.5 秒内新页的晚到排版（代码高亮、图片解码）、删掉上面的消息让上面变矮，这三处放回原位共用一个函数（`keepInPlace`，经 `lib/scroll-anchor.ts`）：上面长高多少垫层缩多少，变矮多少垫层长回多少，内容在文档里的位置不变，不写 `scrollTop`。探针里垫两万像素后，途中补的 3 次总高一像素没变、位置逐帧连续。
  - **从第一次显示更早的页起就在**：对话列的 ref 挂上时就垫好，早于贴底和它对列的测量；冷启动先画骨架、恢复读完才知道有更早的页时，在那次提交的 layout 阶段垫上，`scrollTop` 同时加上同样的量。
  - **停手时补回、最后收掉**：「停手」= 200ms 没有滚动事件（惯性滚完也就不再有滚动事件），而且此后滚动位置连着 3 帧没动，这时写 `scrollTop` 写得进去。只看滚动事件不够：渲染一页让主线程停两三百毫秒，这期间滚动事件到不了页面、惯性却照走，计时器在主线程一恢复就先触发（2026-11-02 真机：这样补的一次垫层写在惯性途中被盖掉，跳了约 9,000px）。停手时垫层离目标超过一屏，就调到目标，`scrollTop` 同时加减同样的量，内容不动；在底部也调（离底距离不变，不影响贴底）。目标按剩下的历史估：已加载部分每个 `turn_index` 的平均高度 × 还没读的 `turn_index` 数 × 1.2，不少于 20,000px 和这次挂载里见过的最高一页的两倍（一页多高 = 补那一页时要放回原位的量），不多于 200,000px。所以一口气连着往回翻、中间不停手也用不完，滚动条也大致是整段对话的长度。（2026-11-02 JC 真机甩第一遍正式代码时改的：原定「在底部不补、目标取 20,000px 与最高一页两倍的大者」，打开时先补的两页用掉约 1.4 万，停在底部不补，从底部起手的第一串连甩只剩约 5,500px，一页就用完，下一页退回写 `scrollTop`、被惯性盖掉，跳了约 4,000px。）最开头那一页插上后（没有更早的页了），停手时收掉垫层，`scrollTop` 减同样的量。一口气甩过最开头那一句、滑进剩下的垫层时不等停手：把滚动容器的 `overflow-y` 临时设成 `hidden` 掐断惯性，两帧后收掉垫层（这时写 `scrollTop` 写得进去），读者停在最开头那一句，像撞到顶；再过一帧还回滚动（2026-11-02 JC 真机甩过：原先要等惯性停下，空白约 1 秒；改后探针记到只露 354px 一帧，JC 没看到空白）。还有更早的页要来时翻进垫层不掐（页落地后在原地长出来）。平滑滚动（`animateScroll`）、气泡动效（裁决 138）进行中，或主对话的三点气泡在屏上时（交接与气泡动效记着它在列里的位置），先不动，过 200ms 再看。工作台发出后的留白（`min-height`，见上「发出后留白」）跟着挪同样的量。
  - **退路与代价**：一页比垫层剩下的还高时，垫层缩到 0，剩下的照旧写 `scrollTop`，途中可能跳（探针里一页 6,995px、垫层剩 5,106px 那次就是）。滚动条把上面剩下的多算最多两万像素（macOS 的滚动条只在滚动时露出，拖滚动条的人才会察觉）；一口气甩过最开头会先进空白，停手时落回开头（只在翻到底那一次）；打开后先补的那一页在 dev 下让主线程停两三百毫秒。问题轨按已加载内容摆点，扣掉垫层（见上「Right Question Rail」）。170 第 2 条第③条「顶端不回弹」撤掉：有更早的页时滑不到顶。
  - **垫层放哪**：对话列的 `padding-top`。不放在滚动容器自己的内边距上（滚动容器是 `absolute inset-0`，内边距一大整个盒子被撑到那么高，画面全白，探针第一次就这样）；不做成一个空元素（它变高变矮会改动对话列的内容盒，惊动盯着对话列的 ResizeObserver，在它们的回调里改就成环）；不放进 `[data-role="conversation"]` 里（锚点按它的子元素找行）。内边距不改对话列的内容盒，垫层为一页缩时，垫层下面每样东西离对话列顶的距离也不变（交接、气泡动效靠这个量）。
  - 没有更早的页的对话没有垫层，与原先一样。没有加载提示、没有「加载更早」按钮、没有更早的了也什么都不显示。票 12 留的「真机看出停顿再议」已在 2026-11-02 再议（裁决 170、172，票 123）。
- **行不重挂载**：Conversation 的行 key、折叠开关、live 窗口状态都按「下标 − 已前插轮数」记，前插一页不会让已渲染的行重挂载，也不会把用户展开的折叠挪到别的 run 上。
- **⌘K 跳转**：目标还没加载就一页页往上读，直到包含它，再照常定位、高亮。
- **其余只看已加载部分**：问题轨（见上）、写过的文件名解析与浏览器标签页站点（`written-files` / `browser-site`，引用在更早未加载的页里时，那一页加载后才解析）。发送时间断点不受影响（见上）。运行中的事件照旧追加在末尾，分页只管更早的部分。
- **不做**：虚拟列表（已加载的照常渲染在 DOM 里）。垫层不是虚拟列表：它只是已加载内容上面一段固定的空白，不代表没加载的内容有多高，也不按滚动位置挂上、卸下行。手机端（`session.messages`，按行分页）与 CLI 的读取不变。

#### Streaming generation（流式 partial 渲染）

助手的对话不流式显示正文，也没有思考行、思考预览与右下角计时：在跑时对话里只有三点气泡（你发起的一轮下面一行「在做什么 · 用时」），见「[助手的对话](./assistant.md#助手的对话2026-10-15)」。本节与下面的 Thinking Placeholder、Live Thinking Preview 讲工作台的对话。

Bridge 订阅 GA 的 `display_queue`（`agentmain.put_task` 返回），把每个 partial chunk 通过 IPC `turn_progress` event 推给 desktop。这里的流式单位是 GA display_queue chunk，不是 token-level 合约；desktop 累积成 `inFlightContent`，跑 `cleanPartialContent` strip 掉 GA 内部 tag 后用 `MarkdownView` 实时渲染，并可用本地 typewriter 平滑 chunk 间隔。

| 时机 | 显示 |
|---|---|
| User 提交 → bridge spawn → LLM TTFT | `NN 思考中 · 12.3 秒` TurnMarker（thinking 态，序号 gutter） |
| 推理流出（`<thinking>` 未闭合） | 思考行保持「思考中」，其下三行滚动预览（见 [Live Thinking Preview](#live-thinking-preview实时思考预览)）；回答 partial 为空 |
| 推理结束（`</thinking>` 到达） | 预览 0fr 收合；有回答正文流出时思考行换「正在回答…」 |
| 第一批回答 chunk 到 | partial markdown 开始流出 |
| 流式过程中 | partial 持续增长，Markdown re-render（行内 / 列表 / 代码块都跟着出现） |
| `turn_end` 到 | partial 被 finalized AgentTurn **替换**（store `appendAgentTurn` clear inFlightContent） |
| 工具执行完 → bridge 继续 → 下一 turn | 新 turn 的 partial 重新开始流（store `turn_start` clear inFlightContent） |

**关键 robustness**：partial 输入是 GA-raw（`<thinking>` / `<summary>` / `<tool_use>` / `<file_content>` / `[FILE:...]`），且**可能 mid-tag**（比如刚收到 `<thi` 没 close）。`cleanPartialContent` 的 4 步算法：

1. Strip 完整的 `<tag>...</tag>` block
2. 找 leftmost unclosed open tag → 截断
3. 找 trailing partial open-tag start（"<thi" / "</sum"）→ 截断
4. Strip `[FILE:...]` refs + 折叠空行

效果：用户在任何 sampling instant 都看不到 GA 内部 scaffolding 闪过。

#### Sticky-bottom + Scroll-to-bottom 浮动按钮

- 助手的对话照这套跟随，但不把这一轮回复的开头推出视口（停在视口顶部下方 32px，「回到底部」照常出现），见「[助手的对话](./assistant.md#助手的对话2026-10-15)」。回复从三点气泡撑开的那一次跟随是平滑的：与气泡长出来同一个时长、同一条曲线（`--motion-slow`、`--ease-pop`；减少动态时照旧瞬时），见「助手的对话」里「在跑时：三点气泡」的「交接」（裁决 103、110，票 51、58）；途中先说的一句长出来的那一次同此（裁决 200，票 149）。这一次跟随途中对话的宽度变了（回复落定时待办面板在旁边打开，或拖窗口、收侧栏），就不再按开始时量的回复开头重新瞄准，当即结束平滑、照平常的规则跟到底；本来要落到底的那一次，走完时落在当时真正的底部，不落在最后瞄准的位置（2026-10-22，票 87 真机走查发现：只自动开一次的面板在回复落定那一刻打开，对话变窄、上面整体变高约 300px，跟随停在原处，新回复和它的待办卡片被挤出视野；`useStickyScroll`）。
- **视口自己变矮或变高**（2026-10-15，票 27）：输入框长高、附件条或队列条出现、窗口变矮时内容没变，下面两条都不触发；滚动容器自身的 ResizeObserver 接住，原本在底部就钉底，往回翻着时不动，主对话与工作台都是。见「[会话里的输入框](./composer.md#会话里的输入框2026-10-15)」的「长高时保持贴底」。
- 流式过程中**默认跟随**：`atBottom` flag 通过 scroll listener 维护（24px tolerance），在底部时 `useLayoutEffect` 把 `scrollTop = scrollHeight`——依赖覆盖**所有底部锚定增长源**（streaming partial、turn_end 落定、AskUserBubble），不只 streaming buffer；**提交之间的增长**（2026-09-16：live 窗口的入场 / 出场 / 完成收合 sweep、DetailPanel 与 pill 展开、Shiki 回流）由内容列上的常驻 ResizeObserver 接住，仍在底部时每次尺寸变化重新钉底，否则新步比被顶掉的步高时底部会被作曲区盖住：tool-heavy 多步 run 的 partial 长期为空，只看 buffer 会让每步落定悄悄沉到折叠线下
- **用户向上滚 → 不跟随**：`atBottom = false`，stream 继续但视图不动
- **工作台发出之后 → 不跟随**（2026-10-16，票 06）：你的话停在顶上，这一轮在下面的留白里长、长出一屏也不拉视口，直到你到内容真正的末尾；见上「Scroll behaviour」的「发出后留白」
- **浮动按钮**：`atBottom = false` 时出现。32px 圆形**浮起按钮**，不是 ghost（2026-10-16 按代码回写，`MainView.tsx` 的「Scroll-to-bottom floating button」）：1px `line` 边框、`elevated` 92% 底加 `backdrop-blur-md`、`--shadow-float` 投影，图标 ⬇ ArrowDown thin 14px、`ink-soft`；悬停上浮 2px、边框换 `line-strong`、底变实、字色 `ink`、投影换 `--shadow-float-hover`（瞬时，无过渡）；按下回落并缩到 95%（`--motion-press` + `--ease-firm`）。它浮在对话上，与右下角的运行计时同一套材质。读屏念「回到最新」 / "Scroll to latest"（`copy.conversation.scrollLatest`；2026-10-16 前中文界面也念英文）。**水平居中、贴对话列底部 16px**——实现时从"右下角"改为居中（代码注释记录了理由：右下角与 Composer 动作簇视觉打架），2026-07-05 回写
- **双态信号**（2026-08-07，[devlog](../../devlog/2026-08-07-scroll-button-two-state-signal.md)）：箭头永不变（永远回答"点了去哪"），按钮上叠加状态信号，两种视觉语法各自自解释——
  - **运行中**：圆周向外扩散的 pulse ring（`scroll-live-ring`，动 = 内容正在下方落地）；run 结束 200ms 淡出
  - **完成且未读**：右上 45° 静态杏色小圆点，pop 弹入后落定（`scroll-unread-pop`，静态徽标 = 有完整答案在下面等你）——**边沿触发的真未读**：仅在 run 结束瞬间用户不在底部时置位，回底即清，全程看着答案生成的用户永远不会见到它
  - reduced-motion：ring 退化为静态低透明度光环、dot 跳过弹入，语义靠存在本身承载

- ESC / 任何手动 wheel 不影响按钮可见性（仅 scroll position 决定）

#### Thinking Placeholder（in-flight 占位）

用户提交消息后到 `turn_end` 到达之间存在显著延迟（LLM TTFT 可达几秒到十几秒）。如果不显示状态指示，用户会觉得 UI 卡住。

- 用户提交瞬间 store 设 `agentRunning = true`（不等 `turn_start` IPC，避免一次往返延迟）
- conversation 末尾立即渲染 `TurnMarker` 的 thinking 态：单行直立 12px ink-soft，内容「序号栏 `··` + 思考中」（2026-09-16 前是「第 N 步 │ 思考中」；同日先试过空 gutter，真机看是个洞）+ 状态文字 shimmer（2026-08-12 前是三点 `LiveDots`）；不再用逐字 opacity 波浪
- 触发条件：`agentRunning && !visiblePartial`
- `turn_end` 到达时，落定的 AgentTurn（同一 step number 的 TurnMarker + tools）在占位行**上方**以 0fr 展开长出，占位行本身不重挂载、留在原地等下一步的 `turn_start` 原地归零时钟（2026-09-16 live 窗口）。**before/after 视觉一致**——同一个 TurnMarker 组件的两态，用户感受到的是一个步骤的进展，不是两个独立的 UI
- **计时从 0.0 立即起跳**（2026-08-12 起，[devlog](../../devlog/2026-08-12-thinking-timer-and-shimmer-verdict.md)；2026-10-16 按代码回写，此前这里写的「3 秒后才读秒、60 秒后追加仍在运行、三点」是 08-12 之前的样子）：状态文字后面接 ` · ` 和这一步的计时，`ink-muted`、tabular 等宽。一分钟内带十分位，跳动的十分位本身就是「还在动」的证明，所以不等 3 秒；满一分钟改整秒（整分也写 `1 分 0 秒`，每秒都在跳），不加「已」，也没有「仍在运行」。在动的指示是状态文字上的扫光（[foundations](../foundations.md) §2.7 的豁免），没有三点。每步独立计时：live 行整个运行只挂一个实例，换步时按 `index` 原地归零（2026-09-16 起，不再靠 `key` 重挂载）。代码在 `Conversation.tsx` 的 `ThinkingStatus`、`useElapsedDeciseconds`、`formatElapsedDeciseconds`。
  - `0–59.9s` → `思考中 · 12.3 秒`（状态文字也可能是「正在回答…」或这一步的说明，见下「状态行优先级」）
  - `60s+` → `思考中 · 1 分 23 秒`
  - 整个运行的用时另在对话右下角的浮起计时（`RunElapsedHud`）：`工作中 1 分 23 秒`，整秒，没有动画。
  - 助手的对话没有这一行和右下角计时：你发起的一轮，用时在三点气泡下面那一行（「{在做什么} · {用时}」，整秒，1 秒起，与右下角计时同一个数、同一套字，各段相加、等你回答的时间不算；`TypingBubble.tsx`），落定后在过程卡片的第一行，见「[助手的对话](./assistant.md#助手的对话2026-10-15)」的「在跑时：三点气泡」（2026-10-23 裁决 134、135）。历史：2026-10-15 到 10-19 对话末尾那一行灰字过 3 秒接这一轮的整秒用时，裁决 110 随那一行去掉，此后在跑时哪里都不计时；[deferred](../../devlog/deferred.md)「顶栏在跑超过 1 分钟接用时」作废：用户不看顶栏，用时挪进对话。

历史设计（已废弃）：原本占位走 ThinkingSummary callout（bg-surface + 左竖条 + 💭 emoji），跟正式 ThinkingSummary 块视觉同款。问题是 callout chrome 是给"GA 真实 emit `<thinking>` 多段内容"设计的容器，套在 10 字占位上视觉权重严重失衡。2026-05-14 改成 TurnMarker thinking 态。

- **状态行优先级**（2026-09-23）：in-flight buffer 里有未闭合的 `<thinking>` 时，状态固定为「思考中」，压过 send phase 与 preamble 压缩行（推理是这一步最新的事实，那两者在推理期间都已过时）；「正在回答…」只绑回答 partial 非空，因此只会在推理闭合之后出现。此前原生推理不带标签、被当成回答 partial，状态行在模型思考时写着「正在回答…」

#### Live Thinking Preview（实时思考预览）

2026-09-23 起（[devlog](../../devlog/2026-09-23-live-thinking-preview.md)）。推理是过程材料，不是交付物：流式期给看，但永远不用回答的寄存器、永远不无上限地占高度，落定后必须有去处。

- **数据**：内置运行时的补丁 `0016` 把原生推理（Anthropic `thinking_delta`、OpenAI 兼容 `reasoning_content` / `reasoning`）边到边包成带内 `<thinking>…</thinking>` 流出，推理开始时开标签、回答或工具调用开始前闭合；推理里的字面 `</thinking>` 转成 `</ thinking>`（跨 chunk 也成立）。模型按提示词自己写的 `<thinking>` 本来就这样流。`extractLiveThinking(inFlightContent)` 取出所有块的内文 + 末尾未闭合块，给出 `{ text, open }`；扫到工具派发标记 / 5 反引号围栏即停（工具输出里读到的源码可能含 `<thinking>`）
- **形态**：in-flight 思考行正下方、同一 `StepRegion` 内、`pl-(--step-gutter)` 对齐 DetailPanel 那一列；`MarkdownView variant="thinking"`（Newsreader italic、ink-soft）。固定三行高的窗口：短推理从顶部读起，溢出后底部锚定、旧行从顶部滚出，顶边 mask 渐隐锚在文字底边往上 2.25–3 行。行盒 = 思考字号 × **正文**行高（段落继承 `PROSE_BASE` 的 body leading，thinking leading 只落在根元素上），标准档一行 23.8px。不可展开、不可交互、`aria-hidden`——全文在落定步的 caret 后面
- **收合**：推理块闭合即 `ExpandSection` 0fr 收合（`--motion-slow`），腾出的位置给回答正文；不等 `turn_end`——最后一步的回答可能流几十秒，等落定才收会让读到一半的正文整体上移
- **管线**：打字机（每帧 8 字，比回答的 3 字快：快速推理会把 3 字打字机甩在后面）→ 只渲染尾部约 1500–2000 字（切点优先段落边界、每 500 字才前移一次防止逐 token 重排）→ `useMarkdownStream` 节流 → `mendStreamingMarkdown`。不加 `streaming-prose` 的光标与块淡入：状态行的 shimmer 与滚动的行已经说明「在动」，过程区保持两路流里更安静的那一路
- **裁决**：行数 1 / 3 / 全文 × 收合时机 思考结束 / 落定，临时切换器真机实测后 JC 定 3 行 + 思考结束（即推荐项）
- **外置 GA**：上游仍把原生推理不带标签地流出，前端分不出，流式期照旧按回答正文流出；落定后的 `responseThinking` 两种模式都有，推理进 caret。按「内置优先」不追平
- **Responses 模式**（Codex 后端等）：推理累积不流出，只有落定后进 caret

Composer 状态同步：`agentRunning = true` 时 Submit 按钮切到 Stop 模式，LLM dropdown disable。

# Conversation 主区与 Composer

> Galley 设计系统 · 原 DESIGN.md §4.3–§4.4 与 §7（2026-07-04 拆分）：turn 结构、Markdown / 代码块渲染、滚动与流式行为、Composer、Empty State。

### 4.3 Conversation 主区

#### Turn 结构

```
▸ 3 步 · 用时 42 秒 · …                          ← RunFoldHeader（settled run 完成即折；live 时是「已完成 N 步」）
│ 01 summary ›                                   ← 序号栏（mono 补零）+ 12px ink-soft summary；› = DetailPanel（推理 / preamble）
│    旁白                                         ← 模型另写了 summary 时才单独成行；回声步的旁白就是 summary 行
│    [Tool pill / callout]                       ← 行动序列
│ 02 …                                           ← run 内步间 mt-2.5
─────────────────                                ← 稍深 1px 全宽 hr（行动 → 结论）
[Final answer，浮在文档里]                       ← 满宽，不放 callout
```

2026-09-23 按现状重画（此前的示意仍是「第 N 步 │」+ 独立 Thinking callout 的旧形态）。过程区的缩进、rail、live 两行窗口、裸步合并、旁白回声步见下文 TurnMarker 与 Thinking Summary 各节。

**一步就答完的运行只有回复**（2026-10-16，[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 7，票 01）：落定的运行只有收口那一步时，不画折叠头、步骤标记和 StrongHr；token 与上下文照旧在回复的悬停行里。判据只看步数（`lib/run-groups.ts` 的 `answeredInOneStep`），有没有推理都一样：库里 46 个一步回复里 0 个带推理或开场白。这样的运行也不会带工具：收口那一步按定义全是 `no_tool`（`isClosingTurn`），调过工具就多一步。代价是那一步的推理与开场白（DetailPanel）看不到，这一轮的用时也看不到：用时 2026-08-06 起只在折叠头上。在跑到落定的那一下，回复从 live 行下面滑上来，不跳：live 行占的那一行加一个段落间距在落定的那次收合里扫掉（`SettleGap`，同 `ExpandSection` 的动画）。两步以上照旧折叠；没有回答的运行、`/btw` 照旧整段平铺；助手的对话本来就不画。

**没有 turn 之间的 SoftHr** —— TurnMarker 自带视觉重量 + 上方间距，承担 turn-to-turn 的章节分隔。不再有水平横线。

助手的对话不画折叠头和步骤区：在跑时只有一行，落定后两步以上的回复，悬停行里有一个「过程」按钮，点开是一张过程卡片，头一行是这一轮的步数、用时与 token，下面每步一行，点一行才展开那一步在本节步骤区里的样子，见「[助手的对话](#助手的对话2026-10-15)」。

#### User vs Agent 三重区分（单侧容器，不是 IM 双侧气泡）

| 维度 | User | Agent |
|---|---|---|
| 字体 | Inter 500 | Newsreader 400 |
| 字重 | medium | regular |
| 锚点 | 杏沙气泡：`rounded-md`（12px）+ `bg-brand-tint` 平涂，无边框无投影 | 无 |
| 对齐 | 右对齐 · 容器靠栏的右缘、宽度随内容，上限 `min(80%, 560px)`，文字随内边距缩进 | 左对齐 · 满栏 |

**用户在容器里、助手是散文**（2026-09-17 起）。这是用户在 Claude.ai / ChatGPT / Codex 里早已习得的心智，也是我们两个设计源头之一（Claude.ai）自己的形态。它不是 IM：IM 是**双侧**气泡，工作台只借单侧容器（2026-10-16 起靠右，是 ChatGPT「你的在右、回复是散文」的样子），助手回复保持纯散文无底色，"提问（色块锚）→ AI 回复（要读的内容）" 的层次不变。

**靠右**（2026-10-16，[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 2，推翻 2026-09-17 起的「不要 right-align」）。原来的两条理由：「一份文档一个阅读左缘」，760px 栏里用户的话靠右、Composer 满宽左起、agent 散文左起，眼睛要两边跳；气泡右缘会与 Question Rail 的点挤在一起。前一条的代价小：你的话中位 19 字，ChatGPT 就是你的在右、回复是散文，是用户最熟的样子；后一条只在栏宽撑满主区时发生，气泡自己内缩就解开（见「[Right Question Rail](#right-question-rail)」）。助手的对话先改到右边（2026-10-15），从助手点子任务卡片进工作台，你的话从右跳到左，读作割裂，这是改的起因。**不要边框、不要投影**——content 是纸、chrome 是材质（2026-08-21），投影在 Galley 是控件语汇，平涂是气泡不滑向卡片的那道线。**不要小尾巴**——纯 IM 装饰。

**两边的分界：语法统一，密度按关系与工作分**（2026-10-16，[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 1，取代[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 73 第 4 条里的「助手像 IM、工作台是文档」）。语法两边一样：你的话在右，发送时间是两条消息之间居中的一行，一步就答完的回复上面什么都不画。密度各按各的：助手管关系，回复也装进气泡，过程收进悬停行里的按钮（裁决 66–69）；工作台是办公室，回复是纸上的散文（47% 带表格、23% 超过 1500 字），过程常显一个折叠头，在跑时有 live 窗口，你的消息照旧有悬停复制。「不要边框、不要投影、不要小尾巴」两边都守。见「[助手的对话](#助手的对话2026-10-15)」。

长对话里气泡是用户**回找自己提问**的主视觉锚（08-06 A/B 证明色彩面积是滚动扫视真正依赖的信号，容器的色域比逐行笔触只多不少），也是 submit 置顶、Question Rail、`data-role` 的锚对象。

#### 杏沙气泡（2026-09-17 起；此前 08-06 高亮笔、05-14 callout 色板）

起因：「死板 / 硬 / 平」的实感在 08-05、08-06、08-21 出现三次，两轮实验（高亮笔重设计、沉积 × 圆角质感实验）后仍未落地，说明治的不是病根；而**真正的容器形态从未进过切换器**——08-06 测的是 slab vs 纯排印 vs 笔触，08-21 测的是 5px 纵向 padding 的笔触加 4/6px 圆角。「经典气泡」拆成零件看，只有投影与我们的纸墨寄存器硬冲突，容器、平涂、圆角在内容层本来就存在（Notion callout、ToolCallout）。真机三变体（A 高亮笔 / B 左气泡 / C 右气泡）× 两档圆角（12 / 16）实测，我的推荐与 JC 裁决一致：**B 左气泡、12px**。全过程见 [devlog](../devlog/2026-09-17-user-message-bubble.md)。

定案形态：

- 容器 `w-fit rounded-md bg-brand-tint px-3.5 py-2.5`，无边框无投影，靠对话栏右缘（`ml-auto`），宽度随内容、上限 `min(80%, 560px)`（2026-10-16 起；此前贴左缘、`max-w-full`，见本节末条）；
- **圆角 12 不取 16**：单行短消息高约 45px，16 已近半高，「好」「继续」会变成一颗药丸进 chip 语汇；12 与 ToolCallout 同档，机器与人同样圆润，08-06「机器圆润、人方正」的倒挂反向解除；
- **文字左缘随内边距缩进 14px**，不再与 agent 散文栏对齐（那是高亮笔时代靠偏移 box-shadow 出头换来的性质，随笔触一起退出）；
- 粘贴内容里的空行留在容器内（高亮笔不给空行上色，一条消息在视觉上碎成几截，是气泡补上的具体缺口之一）；
- `line-clamp-6` 折叠、附件缩略图、`data-role` / submit 置顶 / Rail 机制全部不变；悬停复制 2026-10-16 起在气泡下方、右缘对齐气泡右缘（此前在气泡右下角外侧 `left-full ml-1.5`，09-18 前在右上），见下方「复制入口统一」；
- **不给普通消息加 eyebrow / 图标**。断点发送时间行不算，见下方「发送时间」。（2026-08-06 定这条时的理由是不稀释 Goal 委派标记的加冠行；Goal 已于 2026-10-13 移除，再有给消息加装饰行的提议时，先重审这条。）
- **助手的对话里**没有悬停复制，改为选中文字时弹浮动复制，见「[助手的对话](#助手的对话2026-10-15)」。
- **2026-10-16 改到右边**（[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 2）：09-17 真机比过 C 右气泡，输给 B 左气泡，理由是一个阅读左缘与问题轨；10-15 助手的对话先改到右边（主聊天 PRD 裁决 66、67），两边一左一右读作割裂。两条旧理由为什么不再成立，见上「User vs Agent 三重区分」。

随之继承 / 消解的旧决定：

- **2026-06-20 排印统一不动**：Inter medium 同字号保留。容器加上后字重对比是否成了双重信号，是独立重审（见 deferred「用户消息排印微调」），本次不捆绑。
- **2026-08-06 高亮笔的方法资产保留**：「滚动回找靠色彩面积、静读辨声靠排印」的任务拆分与 A/B 结论仍成立，气泡是在这个结论上换了形状；「人的声音不穿机器外衣」的寄存器论证仍成立，所以气泡无投影。
- **2026-08-21「不给抬升」仍有效**：以后再有「让用户消息更立体 / 更有卡片感」的提案，先回到那一条。

#### 发送时间（2026-09-28 起：只在断点常显）

用户消息只在**断点**显示发送时间，其余消息不显示，也没有悬停时间。讨论、数据与两轮真机见 [devlog](../devlog/2026-09-28-user-message-send-time.md)。

- **断点**：会话第一条用户消息；距上一条用户消息**超过 60 分钟**；与上一条用户消息跨了本地日期（兜底，保证「今天 / 昨天」不缺席）；Supervisor 来源消息（图标行本来就在）。ask_user 回复也算用户消息、参与比较。规则与格式在 `lib/message-time.ts`，Conversation 算一次、往下传字符串。历史分页加载时（见[长对话按轮分页](#长对话按轮分页2026-10-13)），第一条已加载的用户消息与 Core 给出的「页前最后一条用户消息」的时间比较，断点与整段加载时相同，往上翻加载更多不会让时间行出现或消失。
- **格式**：精确到分钟的绝对时间，不用「3 小时前」（会漂移、截图失真）。当天 `16:05`；当天但上一条在之前某天 `今天 09:10`；`昨天 21:14`；今年更早 `9月21日 14:32`；往年 `2025年9月21日 14:32`。中文 24 小时制补零，英文按 en-US 12 小时制。「今天 / 昨天」过零点经 `useDayStamp` 刷新。
- **位置**：两条消息之间居中的一行（`MessageTimeDivider`），属于整段对话，不贴在你的气泡上；上面 16px、下面 20px，紧接在回复下面时上面不再加（回复的行动条隐藏时照旧占着 30px，工作台量得同样成立：回复正文到时间条 30px）。2026-10-16 前工作台画在气泡上方独占一行、左对齐（`mb-1`），与 Supervisor 图标同一行；现在 Supervisor 与「主对话派来的」图标留在气泡上方、靠右，与时间分开（[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 3）。断点规则不变：工作台没有问候，照旧只跟你的消息比。助手的对话问候上面也有一条，第一条用户消息跟问候比，见「[助手的对话](#助手的对话2026-10-15)」。
- **样式**：`text-ui-micro`（10.5px）+ `text-ink-muted/70`，sans、tabular、`select-none`、`<time dateTime>`；悬停给带星期的完整时间。对比度约 2.3:1（浅）/ 3.2:1（深），低于 AA——只因它是可有可无的辅助信息、tooltip 兜底才成立，**不是正文元数据降透明度的先例**（09-23 折叠头气味段降到 70% 就因不可读被否）。
- **与「不给普通消息加 eyebrow / 图标」的关系**：那条防的是每条消息都戴的装饰行；时间行稀疏（首条 + 断点）、最浅墨色、无品牌色与大写字距，不算。
- **不做**：悬停时间（真机「有点吵，也没有必要」）；助手回答的时刻（长运行完成时刻见 [deferred](../devlog/deferred.md)「长时间运行的完成时刻」）；问题轨卡片里的时间。

#### 助手的对话（2026-10-15）

内置运行时、主区开着助手（主对话）时，对话画成和一个人的长期 IM，不再是工作台的任务记录（[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 60、66）。JC 在 tauri dev 里比完四件各自可切的试验（票 19），四件都取推荐档（裁决 67）：气泡 C、过程一行、时间居中、滚动贴底；定稿是票 20。随后裁决 68（票 21）把看过程的入口从常显的「N 步 ›」改成悬停行里的一个按钮，步数、用时与 token 收进展开区的第一行，上下文百分比不画，卡片与顶栏在跑时说主区那一行的同一句；裁决 69（票 22）把点开后的步骤区换成一张过程卡片：每步一行，最多 8 行，超出在卡片里滚动。工作台的会话、从助手点开的子任务、外置运行时照本文其余各节；2026-10-16 起两边语法统一（你的话在右、时间居中、一步的回复上面什么都不画），密度各按各的，分界见「[User vs Agent 三重区分](#user-vs-agent-三重区分单侧容器不是-im-双侧气泡)」。门只有一个，`MainView` 的 `isMainChat`；规则在 `lib/assistant-conversation.ts`（过程卡片的在 `lib/assistant-process.ts`），部件在 `components/conversation/AssistantParts.tsx`（过程卡片在 `AssistantProcessCard.tsx`）。

**为什么这里是双侧气泡**：工作台的回复是纸上的散文（单侧容器），助手的回复也装进气泡（裁决 66）：「对话是一份文档」正是助手要改掉的（裁决 60：像跟一个真人助理的长期对话），它的回复也短（中位 390 字）。这是密度的差别，不是语法的：你的话在右，2026-10-16 起两边一样（[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 2）。「不要边框、不要投影、不要小尾巴」照守，助手也守。

- **气泡**（两边都是，不放头像，也不写名字：一对一的 IM 都不放，顶栏已经有它的身份行）：
  - **你的在右**：杏沙 `bg-brand-tint`，圆角、内边距、字体同「杏沙气泡」；宽度随内容，上限 `min(80%, 560px)`。560 约一行 37 个汉字，是手机 IM 的行宽，宽屏 1200 栏下也停在 560；80% 只在栏宽不到 700 时起作用（960 × 600 小窗口栏宽 699，上限 559）。Supervisor 来源的图标行与长消息的「展开 / 收起」跟着靠右。**没有悬停复制**（2026-10-15，裁决 73；票 20 时把它镜像到气泡左下角外面，离气泡 6px）：回复的动作在气泡下面、你的悬在气泡旁的空白里，同一段对话两套位置，按钮也看不出归属；挪到气泡下方又会在连发时盖住下一条（同一边只隔 4px）。复制换到选中：选中气泡里的文字时弹出与回复同一个浮动复制（`SelectionCopyToolbar`，范围 `user-message`），你的消息是纯文本，选中复制拿到的就是原文；回复的悬停复制照留，它复制的是 markdown 源码。IM 都不在自己的消息上挂悬停按钮。工作台里你的消息照旧有悬停复制（2026-10-16 起在气泡下方、右对齐），**有意不统一**（JC 2026-10-15；理由 2026-10-16 改说为密度差异，[工作台对话 PRD](../../.scratch/workbench-conversation/PRD.md) 裁决 1）：工作台常贴长文档、长提示词，超过 6 行就折叠，折叠后选中拿不到全文，悬停复制能整段复制；助手里是短的来回，长消息要先点「展开」再选中。
  - **它的在左**：回复、它问你的问题、问候都是同一种气泡，底色 `bg-assistant-tint`（浅 `#F0F0F0`、深 `#24272C`，[foundations](./foundations.md) 色表），离页面底 ΔL* 浅 −3.2、深 +8.0，离杏沙 ΔE 两种主题都约 12，两边靠色相分开，不只靠深浅。圆角 12px、内边距 10 / 14px，与你的同档。宽度上限栏宽的 `88%`：比你的宽，因为它的内容是 markdown、列表和表格；右边至少留 12%（760 栏是 91px），读得出在左边。不设像素上限（2026-10-15，裁决 79）：阅读宽度切到「宽松」就是要给代码块和表格更多地方，而它们都在回复气泡里，所以回复跟着栏变宽，1200 栏下到 1056；紧凑栏 760 的 88% 是 669，原来的 680 上限只在宽松下起作用，作用是把宽松抵掉，只剩两边拉开。你的气泡照旧停在 560。字体与排版照回复正文，markdown 的列表、标题、引用、加粗、链接照旧，只是装进气泡；选中文字后的浮动复制照旧。
  - **气泡里的代码和表格**：在纸上比纸深一级的东西，进了气泡就比气泡再深一级。行内代码和代码块的底换成 `bg-line`（浅色比气泡深 ΔL* 3.1，深色亮 4.6，方向同页面上「行内代码比纸深一级」），代码块去掉 hairline，读作气泡里的一段，不是框里套框；放不下时照旧在块里横向滚动、可切换行。表格保留格线（那是它的结构），表头去掉比气泡亮的 `bg-surface`、坐在气泡底上，靠字重区分；表格本来满宽、单元格折行，所以宽表格把气泡撑到上限，真放不下时在气泡里横向滚动，不让气泡撑满栏宽。图片照 `MarkdownImage`，最宽是气泡的内宽、最高 420px。
  - **提问也是气泡**：它问你的问题在问你时与答完后都是普通的左侧气泡，问题用回复的字号与墨色；候选照旧排在气泡下面（在问你时是可点的 chip，悬停色照旧；答完是浅色的列表，选中的那条打勾）；不再有黄色竖条、「等你回复」「曾向你提问」，侧栏卡片和输入框占位已经在说。
  - **问候**也是一条普通的左侧气泡，上面有它的时间（见下「时间」）。
  - **子任务卡片**放进派活那条回复的那一组：紧贴气泡下面 12px，在行动条之前，最宽同气泡的上限。

#### Right Question Rail

主区右侧 rail 的职责有两个：**question index**（一颗 dot / 一段 cluster marker 对应一次或一组 user message，多问题间回跳）和**回到提问开头的跳转锚**（单问题即成立）。它不是第二个 Sidebar，也不是 session 状态队列。

**为什么在右侧**（2026-08-10 裁决，维持右侧）：三条独立理由——① 滚动条家族语义：dot 按 `scrollHeight` 百分比定位，是位置比例型导航（滚动条 / minimap / scrollbar marker 家族，惯例在右），不是语义目录（Google Docs 大纲家族，惯例在左）；② 单侧单层级：左 = Sidebar 的会话间导航，右 = 会话内导航，改左会形成双 rail 贴排；③ 注意力分区：左缘是视线回扫路径，标记会被读作内容（git gutter 效应），右缘是「可及可忽略」的仪器位。唯一真实代价是 Windows 常驻滚动条的拥挤风险——解法是调 inset，不是换边。

- 自第 1 条 user message 起显示（2026-07-21 起；原门槛"少于 3 条隐藏"按 index 职能设定，误伤了锚职能——深度研究型对话恰是一问 + 数千字长回答，最需要回跳时 rail 缺席。单点 rail 不再是索引，但作为锚成立，且与长对话中已学会的交互完全一致）。键盘路径 ⌥↑/⌥↓ 与对话长度无关，始终可用。
- **主对话不显示**（2026-10-14，[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 60，JC 同意）：rail 按已加载内容的比例摆点，主对话是一条没有尽头、从底部按页往上加载的对话——50 条提问时 85%–90% 的点并进胶囊，往上加载一页，每个点的坐标和序号都会变，索引和锚两个职能都立不住。`MainView` 在主对话里不渲染 `UserQuestionRail`；⌥↑/⌥↓ 在主对话里照常可用。其他对话照旧（含主对话派出的子任务）。
- 只含已加载部分的提问（[长对话按轮分页](#长对话按轮分页2026-10-13)），往上翻加载了更早的页就跟着变多；序号按已加载的数。
- **气泡不贴轨**（2026-10-16，工作台对话票 01）：你的气泡靠右后，栏宽撑满主区时（小窗口；宽松档在不够宽的窗口）气泡右缘正好落在轨的点击区左缘：栏是 `px-8`，轨是 `right-3 w-5`，都在离主区右缘 32px。做法是气泡自己让出来，轨不动：往右挪会压到 Windows 常驻滚动条（离右缘 0–10px）与 macOS 悬停展开的滚动条，上面「为什么在右侧」的 inset 余量就是为它们留的。工作台的滚动容器是 `@container/conversation`，带上栏宽上限 `--conversation-column`（760 / 1200）；你这一行的右外边距取 `clamp(0, 8px − (100cqw − 上限) / 2, 8px)`，补足栏自己的外边距差的那部分，窗口比栏宽多出 16px 以上就是 0。回复散文照旧满栏，没有轨的助手对话不变。量得（Chrome，主区 640–1700 宽每 2px 一档，两档阅读宽度）：气泡右缘到点击区最近 8.0px，到点 14.0px，气泡最多内缩 8px。Windows 上滚动条已在内容与轨之间占了 10px，同一条规则下气泡离点击区 18px。
- 历史 dots 永远只表达导航位置：active = brand filled，inactive = hollow ring，cluster = vertical capsule。
- 只有最新 tail marker 可以临时承载 live 状态：running 时 single dot 替换为 Sidebar 同源的 brand `CircleNotch` spinner；waiting（ask_user）时替换为 warning `PauseCircle`。状态结束后恢复普通 dot / cluster。
- 最新提问落在 dense cluster 里时，保留 cluster capsule 和 hover list，再叠加同源状态图标；不能让状态图标吞掉“这里是一组提问”的导航语义。
- 右 rail 不展示 subline / badge / row tint。状态文案只进入 tooltip / aria：`进行中` / `等你回应`。跨区记忆来自同一套状态图标语法，而不是把 Sidebar row chrome 搬进文档区。

##### Hover tooltip 的内容契约

单 dot 的 hover tooltip 是**两行**（2026-08-03 起）：`序号 │ 提问` + 下方缩进对齐的**回答预览**。dot 数量不变——加第二行补的是**辨识**（"这一问我当时得到了什么"），不是导航；用增加标记来解决 tooltip 的信息量问题会把密度翻倍去换一个它解决不了的东西。

- 回答预览 = final answer 的**首个正文行**（跳过空行与 ATX 标题），再走与提问同一套 `buildPreview`（折叠空白、剥首个 markdown 标记、50 字预截）。跳标题是因为长回答高频以 `## 结论` 开头，预览成"结论"两字等于零信息。规则只跳标题、不跳代码围栏或列表标记——一句话能说完的规则才可预测。
- **不用 `AgentTurn.summary`**：它是 agent 的工作记忆而非给读者的概括。managed runtime 的 prompt 要的是"上次工具调用结果产生的新信息 + 本次工具调用意图"，GA 直接把它 append 进自己的 `history_info`；它指向下一步工具调用，而最终答案轮是 `no_tool`，没有"本次意图"可指，框架失配。预览应当是用户点进去会看到的东西的缩略图，那就是 final answer 本身。Sidebar 显示 summary 不构成同源理由——Sidebar 那一格的语义是 session 的**进行状态**（`第 N 步 · …`），不是某次问答的内容。
- 配对规则：取该提问与下一条提问之间**最后一个** `finalAnswer !== null` 的 agent turn。`finalAnswer` 每个 `turn_end` 都会算（不只最终轮），中间工具轮偶尔会漏出散话；取最后一个在正常情况即真正的收口轮，在 run 被中断的情况下也还留得下预览。
- 回答缺席（仍在进行 / run 中断 / 首行无可预览正文）→ **不渲染第二行**，盒子缩回单行，不留幽灵空行。
- 两行的层级差**拉满 ink 三档中的两档**：盒子设 `text-ink`（提问继承），回答行覆盖为 `text-ink-muted`（色阶底）。字号、字数预算两行相同。先试过 `text-ink-soft` + `text-ink-muted` 的一档差，实机上"除了稍微淡一点点并没有拉开差距"——两行在结构上完全并列（同字号、同起始列、同 50 字预算、均匀行距），一档色差压不住这种对等。修法在**加大反差**与**缩小回答**（降字号 / 砍字数）之间选了前者：后者要把 CJK 推向 10.5px 的可读边界，而 tooltip 的正文字号只有一档余量。
- 回答预览只进视觉，不进 aria——button 的 aria-label 是导航目的地（`跳到第 N 条提问`），本来就不含提问正文，塞回答会让 label 变长且与既有惯例不符。
- **dense cluster 的展开列表保持单行只显示提问**。这个不一致是刻意的：cluster 是密集区的快速定位面，不是阅读面，5 条 × 2 行会变成一堵墙。

#### ask_user 提问气泡（`AskUserBubble` / `AnsweredAskUser`）

Agent 经 `ask_user` 停下来问人的那条：实时态是 warning 左条 + `PauseCircle` +「等你回复」+ 候选 chip；回答后（或重启恢复后）退成 `AnsweredAskUser` 回显——2px 30% warning 细规线、无底色、echo 字号 ink-soft、无 chip（交互已结束，再摆 chip 会暗示可重答）。助手的对话里两种状态都是普通的左侧气泡，提问与回答不折进步骤，见「[助手的对话](#助手的对话2026-10-15)」。

- **问题正文走 `MarkdownView variant="agent"`，不再是裸 `<div>`**（2026-09-14）。直接原因是社区反馈「AskUser 界面不能复制文字」：`body` 全局 `user-select: none`（foundations.md §2.6），内容面靠 `select-text` 逐个开回来，用户消息 / agent 正文 / 工具输出都开了，唯独 ask_user 问题漏了。顺带收益：GA 提问里常见的编号选项、路径、行内代码得到与正文相同的 markdown 排版（暖褐行内代码、列表缩进），字体寄存也与同一黄框里的 side_question 一致（CJK 衬线）。
- **单换行保留为换行（`softBreaks`，remark-breaks）**。GA 的 `ask_user(question)` 只是透传字符串，TUI / Telegram 前端按纯文本打印，从没承诺过 markdown；LLM 写「第一行\n第二行」时若按 markdown 软换行合并，两个问句会并成一句、改变问题意思。remark-breaks 只碰段落内的软换行，列表 / 代码块 / 空行分段不受影响，所以 markdown 形状的问题仍得到完整处理。这是 `MarkdownView` 上的 opt-in prop，**只给 ask_user 用**——agent 回答是按 markdown 写的，软换行就该是折行。
- **回显与实时态同一条渲染路径**：`AnsweredAskUser` 同样走 `MarkdownView` + `softBreaks`，用 `[&_p]/[&_li]` 覆盖到 echo 字号 + ink-soft，同一段文字实时与回显只差大小和墨色。
- **Composer 占位随候选数变**：有 chip 时「回复，或选择上方候选」，无 chip 时「回复上方提问」（`composer-register.ts` 的 `reply` / `replyOpen`）。`candidates` 是可选参数，模型对开放式问题常不给；无条件的「选择上方候选」会让人去找不存在的选项（2026-09-14 真机验收即如此）。
- **候选两种排布，由 `candidateLayout` 按内容定**（2026-09-14）：短标签（是 / 否 / 方案 A）走行内 chip，句子级选项（单条超 20 字、合计超 60 字）或 5 条以上走**竖排列表**，每行全文不截断、左对齐；列宽取最长一条（容器 `inline-flex` 收缩、各行拉齐），不撑满对话列——撑满时短选项后面留一整片空白（2026-09-14 真机）。横排一行句子会折成标签云，丢掉模型写的 A / B / C 顺序。阈值是导出常量，dogfood 后可调。同一函数同时喂实时气泡和回显，两处永远做同一个判断。
- **chip 两条路径**：点击 = 直接发送（快路径，保留）；右键「填入输入框」或 ⌘ / Ctrl + 点击 = 填进 Composer 不发送（慢路径），给「选 B 但改两个字」留出口。走 `ComposerHandle.prefillText`，不加新的 store 状态。chip 仍是按钮、不可选中（foundations §2.6 chrome 不可选）；复制 chip 文字的需求由填入路径覆盖。
- **回显列出当时的候选并勾出所选**：`AnsweredAskUser` 用同一排布把候选以 ink-muted 列在问题下方，用户点选的那条 ink-soft + `Check`。判定是「回复用户消息全文 === 候选全文」（`chosenCandidateIndex`），自由回复或填入后改过的都不勾——用户消息就在下面。一个月后回看只见「B」不知 A、C 是什么，这是档案价值。回复消息由 `askUserReplyContent` 按 run-groups 的成员规则定位（ask_user 之后的下一条 user turn，跳过 system），与折叠 / 问题轨共用同一份 replySet。
- **同一轮多次同问题 ask_user 视为一个**（2026-09-14）：有模型把候选拆成 N 个单候选调用（grok-4.6），runner 与 GUI 读取侧都按「问题相同则合并候选、不同则取首个」处理（`mergedAskUserArgs`），折叠头「提问 N 次」按问题数计。持久化的 tool_calls 不动。
- **不接的东西**：不开 `selectionCopyScope`（浮动复制工具栏语义是「复制回答」），不挂 `MessageActions` 的 Copy；不给候选加数字键（暂不考虑键盘用户，2026-09-14 JC 裁决）。
- **提问不切断 run 的计数**（2026-09-18，[devlog](../devlog/2026-09-18-ask-user-run-continuity.md)）：ask_user 让 GA 循环退出、回答再起一个循环，引擎侧步号与计时都按「段」重来；GUI 把段合回一个 run——序号栏与侧栏「第 N 步」按 run 内位置连续编号，折叠头用时、答案脚注的 token 数、右下角运行中 HUD 都是各段之和（等待回答的时间不计，只算 agent 在跑的时间）。settled 数字缺任一段的 telemetry 就整体留空，不显示部分和；HUD 是活体信号例外，缺段按 0 继续走。

#### 子任务卡片（2026-10-13，主聊天票 06a）

#### 流式回溯抖动（2026-08-12）

流式输出时未闭合的 ``` `代码` ``` 和 `[文字](链接` 按字面渲染，闭合的瞬间标记
字符消失、字体切换，**已经排好的文字被改写 → 段落在光标后面重排**。
`mendStreamingMarkdown` 只对**流式 partial**（`MainView` 那一条路径）补合成
闭合符；落定的 turn 渲染原文，所以真的永不闭合的标记在结束时诚实地翻一次，
而不是全程抖。这个「显示态 / 落定态」的分离在 Galley 是白得的——两者本来就是
两条渲染路径。

只补**代码 span 和链接目标**，实测这两类占位移的 94%。强调（`**`）只占 6%
却是复杂度的大头（CommonMark 定界符消解需要开定界符栈 + 欠闭合计数，补错了
文字会先斜后粗地闪），性价比不成立，明确不做。表格（`| a | b |` 在分隔行到达
前是段落）是 GFM 语法要求，补不出来，只能接受。

链接补完**必须配 pending 哨兵**：`markdownUrlTransform` 把
`galley:pending-link` 映射成 `null`，`href` 整个不出现——锚点仍匹配 `[&_a]`
样式所以 URL 落定时零位移，但点不了。注意这修的是一个**已经存在**的问题：
GFM 的 autolink literal 本来就会把半截 `https://exa` 变成活链接。

回归测试 `mend-streaming-markdown.stream.test.tsx` 逐前缀渲染并统计
「新一帧不是旧一帧纯追加」的次数：落地时 16 次 / 位移 230 字符 → 6 次 /
位移 20 字符（**次数降 63%，位移降 91%**）。

#### 纵向节奏（2026-08-12）

markdown 的每一个块间距都是 `--conversation-block-gap` 的倍数，该基数随
三档字号缩放（10.5 / 12 / 13.5px），倍数阶梯写在 `MarkdownView` 的
`PROSE_BASE` 注释里。

**为什么必须跟随档位**：字号和行高本来就随档位走（13.5/15/16.5px ×
1.65/1.70/1.75），但 2026-08-12 之前所有块间距都是写死的 Tailwind 值
（`my-3` = 12px 三档不变）。段间距除以行盒高，small 档 0.54 行、large 档
只剩 0.42 行——**用户把字号调大（想要更松），文档反而更挤**，相对分离度
掉 23%。现在三档都稳在 0.47 附近。

这是 2026-07-05「块代码硬编码 13px」那个教训的第二层：那次修的是**尺寸**
不跟随，这次是**间距**不跟随。规则统一为：阅读面上任何随档位有意义的量，
都必须挂 `--conversation-*`，不能是固定 Tailwind class。

倍数阶梯保留了原有的全部区分，没有压平：代码块 / 表格（1.1667×）比正文多
喘一口——它们是嵌入的另一种介质；标题的 close 阶梯 12/10/8/6 也原样保留，
标题越大下方留白越多。`:root` 里有一个 12px 兜底值，因为 `MarkdownView`
也会渲染在注入档位变量的根之外（`TutorialModal`），而变量缺失会让 `calc()`
整体失效、margin 归零。

#### 行内代码的暖色预算（2026-08-12 定案）

底色一直是 `--color-hover`，没变；变的是**用什么维度把行内代码和正文区分开**。

- **色相区分，不是明度降级**。2026-08-12 之前行内代码是 `ink-soft` + 0.86em——比正文更淡更小，读作"这个不太重要"。但 coding agent 回答里的行内代码几乎全是**路径 / 文件名 / 版本号 / 命令**，恰恰是读者最需要认清和复制的内容。改为 `--color-code-ink` 暖褐（浅 `#9A5528` / 深 `#E0A882`）+ 0.92em：亮度对比反而低于正文（纸上约 5.6:1 vs 正文 15.7:1），**靠色相而非亮度承载区分**，读作"另一类对象"。
- **收益随密度放大**。单个 token 差别不大；一行七个文件名时，暖色让它变成可扫描清单，`ink-soft` 会糊成一片灰。这才是本次改动的真实场景。
- **暖色预算是零和的，链接让位**。同一段里两种暖色，读者分不清哪个能点。链接改为 `text-ink` + `ink-muted` 下划线，hover 才转 `brand-strong`——下划线本来就是承载可点性的 affordance，颜色是冗余的。频率决定分配：agent 回答里路径多、外链少。
- **`box-decoration-clone` 必须带着**。长路径经常软换行，没有它续行会丢掉横向 padding 和圆角。

参考来源与三变体实测过程见
[devlog 2026-08-12](../devlog/2026-08-12-inline-code-warm-ink.md)。

#### Scroll behaviour（stick to user message top）

Conversation 主区是 `overflow-y-auto` 的列。用户提交新消息时**不**滚到底部（reply 还没生成，跳到一片空地）；**也不**被动什么都不做（user message 出现在视口外，看不到反馈）。**正确做法**：把刚 submit 的 user message 顶端贴到 viewport 顶部下方 32px 处。

助手的对话不这样：对话贴着输入框，发出后滚到底，跟随到回复的开头为止（贴底），见「[助手的对话](#助手的对话2026-10-15)」。本节讲工作台的对话。

跟 Claude.ai / ChatGPT 收敛的同一模式。理由：

- 用户提交完立刻能看到自己的提问
- 长 reply 不会推走问题——问题永远在视口顶端附近
- 短 reply 用户也不必往下找答案——它就在问题正下方
- 阅读 reply 期间**不被打扰**（不跟随）

实现细节：

- store 加 `userSubmitTick` 计数器，`appendUserTurn` 时 +1
- MainView `useEffect` 监听 `userSubmitTick` 变化（不监听 `turns.length`——避免 `turn_end` 也触发滚）
- RAF 推迟到 `<MessageUser data-role="user-msg">` 真实 mount 后
- 找最后一个 `[data-role="user-msg"]`，算 offset (`top - container.top - 32`)，`container.scrollBy({ top: delta, behavior: "smooth" })`
- 不用 `scrollIntoView({block: "start"})`：它没法控 padding
- 2026-10-16 气泡靠右后锚不变：仍是气泡本身（`data-role="user-msg"`）的上缘，提交贴顶、⌥↑ / ⌥↓、问题轨跳转都量它。断点处的时间条在你这一行之前另起一行（下面 20px），贴顶后落在视口顶部下方约 1.5px，看得见、但贴边；原来时间在气泡上方 4px，落在 17.5px。

边界：

| 场景 | 行为 |
|---|---|
| 第一次提交（EmptyState → MainView 切换） | 同样滚一次（保险，user message 已经在顶部时 delta 接近 0，相当于 noop） |
| `turn_progress` chunk 流入 / `turn_end` 来 | 不触发（store 状态变了但 tick 没变） |
| 用户主动向上翻历史 | 不打断（仅 submit 触发） |
| 切换历史 session（multi-session 后） | 默认滚到底（看到最后 turn）；不属于此 spec 范畴 |

#### 会话切换：原子换入，不做 skeleton（2026-07-15）

首次访问某会话（本次启动内未加载过、SQLite 有历史）时，`activateSession` **先等转录进内存、再翻 `activeSessionId`**：旧会话画面保持到新转录可以一次 commit 整体换入，"新会话 + 零消息"的空白帧不存在于渲染序列。冷启动（无旧画面可保留）与回访 / 新会话（无需恢复）仍即时翻转。延迟翻转的竞态守卫有两重：activation epoch（快速连点时新点击拥有指针）+ 指针快照（`createSession` / 删除等旁路直写 `activeSessionId` 时过期恢复不得翻回）。

**Skeleton 被明确否决**（决策留痕）：本地 SQLite 读是几十毫秒级，为"本不该被感知的等待"做占位是把它制度化；聊天转录结构不可预测，灰条必然与真实内容对不上（双重跳动）；shimmer 属于动效分类学要删除的 B 类环境动效。正确野心是**让加载态不存在**，而非装修加载态。spinner 保持只用于真慢的事（LLM / 工具 / bridge / 网络），SQLite 路径上不出现任何 loading 指示。

#### 长对话按轮分页（2026-10-13）

主聊天是首页、一直累积，一次读出、渲染全部消息迟早拖慢打开（主聊天 PRD 裁决 51，`.scratch/main-chat/issues/12-paged-conversation-history.md`）。所有对话（主聊天与普通对话、内置与外置运行时）走同一条路径：

- **按轮切页**：打开对话（上面的「转录进内存」）只读最近 50 轮（Tauri `session_message_turns_page`，常量 `MESSAGE_TURN_PAGE`）。一轮 = 一个 `turn_index`（用户消息与回复第一步同轮，主聊天问候是 -1），一轮的所有行在同一页。页界不切断 run：页首落在 run 中间（多步 run 的后续步、ask_user 回答续接的段）就往前补到该 run 的开头那条用户消息。所以一页可能多于 50 轮。每页由 Core 判定，规则与 `run-groups` 同一套，页拼起来与整段读出的 turns 完全一样。
- **往上翻自动加载**：滚到距顶部一屏以内就读上一页、前插（`hooks/useEarlierTurns.ts`）；已加载的内容本身不比这段距离长（页太短、滚不动）时，不等滚动直接接着读。**前插后视口内容不动**：WebKit 没有 CSS `overflow-anchor`，前插的那次 commit 在绘制前把视口顶部那一行放回原位（`lib/scroll-anchor.ts`），之后 1.5 秒内新页的代码高亮、图片解码在上方长高也照此压住，读者自己的滚动照常。没有加载提示、没有「加载更早」按钮、没有更早的了也什么都不显示（真机看出停顿再议）。
- **行不重挂载**：Conversation 的行 key、折叠开关、live 窗口状态都按「下标 − 已前插轮数」记，前插一页不会让已渲染的行重挂载，也不会把用户展开的折叠挪到别的 run 上。
- **⌘K 跳转**：目标还没加载就一页页往上读，直到包含它，再照常定位、高亮。
- **其余只看已加载部分**：问题轨（见上）、写过的文件名解析与浏览器标签页站点（`written-files` / `browser-site`，引用在更早未加载的页里时，那一页加载后才解析）。发送时间断点不受影响（见上）。运行中的事件照旧追加在末尾，分页只管更早的部分。
- **不做**：虚拟列表（已加载的照常渲染在 DOM 里）。手机端（`session.messages`，按行分页）与 CLI 的读取不变。

#### Streaming generation（流式 partial 渲染）

助手的对话不流式显示正文，也没有思考行、思考预览与右下角计时：在跑时只有一行，见「[助手的对话](#助手的对话2026-10-15)」。本节与下面的 Thinking Placeholder、Live Thinking Preview 讲工作台的对话。

Bridge 订阅 GA 的 `display_queue`（`agentmain.put_task` 返回），把每个 partial chunk 通过 IPC `turn_progress` event 推给 desktop。这里的流式单位是 GA display_queue chunk，不是 token-level 合约；desktop 累积成 `inFlightContent`，跑 `cleanPartialContent` strip 掉 GA 内部 tag 后用 `MarkdownView` 实时渲染，并可用本地 typewriter 平滑 chunk 间隔。

| 时机 | 显示 |
|---|---|
| User 提交 → bridge spawn → LLM TTFT | `NN 思考中 · 12.3 秒` TurnMarker（thinking 态，序号 gutter） |
| 推理流出（`<thinking>` 未闭合） | 思考行保持「思考中」，其下三行滚动预览（见 [Live Thinking Preview](#live-thinking-preview实时思考预览)）；回答 partial 为空 |
| 推理结束（`</thinking>` 到达） | 预览 0fr 收合；有回答正文流出时思考行换「正在回答…」 |
| 第一批回答 chunk 到 | partial markdown 开始流出 |
| 流式过程中 | partial 持续增长，Markdown re-render（行内 / 列表 / 代码块都跟着出现） |
| `turn_end` 到 | partial 被 finalized AgentTurn **替换**（store `appendAgentTurn` clear inFlightContent） |
| 工具执行完 → bridge 继续 → 下一 turn | 新 turn 的 partial 重新开始流（store `turn_start` clear inFlightContent） |

**关键 robustness**：partial 输入是 GA-raw（`<thinking>` / `<summary>` / `<tool_use>` / `<file_content>` / `[FILE:...]`），且**可能 mid-tag**（比如刚收到 `<thi` 没 close）。`cleanPartialContent` 的 4 步算法：

1. Strip 完整的 `<tag>...</tag>` block
2. 找 leftmost unclosed open tag → 截断
3. 找 trailing partial open-tag start（"<thi" / "</sum"）→ 截断
4. Strip `[FILE:...]` refs + 折叠空行

效果：用户在任何 sampling instant 都看不到 GA 内部 scaffolding 闪过。

#### Sticky-bottom + Scroll-to-bottom 浮动按钮

- 助手的对话照这套跟随，但不把这一轮回复的开头推出视口（停在视口顶部下方 32px，「回到底部」照常出现），见「[助手的对话](#助手的对话2026-10-15)」。
- **视口自己变矮或变高**（2026-10-15，票 27）：输入框长高、附件条或队列条出现、窗口变矮时内容没变，下面两条都不触发；滚动容器自身的 ResizeObserver 接住，原本在底部就钉底，往回翻着时不动，主对话与工作台都是。见「[会话里的输入框](#会话里的输入框2026-10-15)」的「长高时保持贴底」。
- 流式过程中**默认跟随**：`atBottom` flag 通过 scroll listener 维护（24px tolerance），在底部时 `useLayoutEffect` 把 `scrollTop = scrollHeight`——依赖覆盖**所有底部锚定增长源**（streaming partial、turn_end 落定、AskUserBubble），不只 streaming buffer；**提交之间的增长**（2026-09-16：live 窗口的入场 / 出场 / 完成收合 sweep、DetailPanel 与 pill 展开、Shiki 回流）由内容列上的常驻 ResizeObserver 接住，仍在底部时每次尺寸变化重新钉底，否则新步比被顶掉的步高时底部会被作曲区盖住：tool-heavy 多步 run 的 partial 长期为空，只看 buffer 会让每步落定悄悄沉到折叠线下
- **用户向上滚 → 不跟随**：`atBottom = false`，stream 继续但视图不动
- **浮动按钮**：`atBottom = false` 时出现 32px 圆形 ghost 按钮（⬇ ArrowDown thin），**水平居中、贴对话列底部 16px**——实现时从"右下角"改为居中（代码注释记录了理由：右下角与 Composer 动作簇视觉打架），2026-07-05 回写
- **双态信号**（2026-08-07，[devlog](../devlog/2026-08-07-scroll-button-two-state-signal.md)）：箭头永不变（永远回答"点了去哪"），按钮上叠加状态信号，两种视觉语法各自自解释——
  - **运行中**：圆周向外扩散的 pulse ring（`scroll-live-ring`，动 = 内容正在下方落地）；run 结束 200ms 淡出
  - **完成且未读**：右上 45° 静态杏色小圆点，pop 弹入后落定（`scroll-unread-pop`，静态徽标 = 有完整答案在下面等你）——**边沿触发的真未读**：仅在 run 结束瞬间用户不在底部时置位，回底即清，全程看着答案生成的用户永远不会见到它
  - reduced-motion：ring 退化为静态低透明度光环、dot 跳过弹入，语义靠存在本身承载
- 点按钮 → smooth scroll + 监视器**追移动靶**：流式增长时对新 `scrollHeight` 重发 `scrollTo`，1600ms 超时则瞬时 snap；除用户中途主动上拉外，点击的结局必然是 `atBottom = true`（重新挂上跟随）——点击语义是"挂上尾部"，不是"滚到某个坐标"（2026-08-07 修复追不上快流式的 bug）
- ESC / 任何手动 wheel 不影响按钮可见性（仅 scroll position 决定）

#### Thinking Placeholder（in-flight 占位）

用户提交消息后到 `turn_end` 到达之间存在显著延迟（LLM TTFT 可达几秒到十几秒）。如果不显示状态指示，用户会觉得 UI 卡住。

- 用户提交瞬间 store 设 `agentRunning = true`（不等 `turn_start` IPC，避免一次往返延迟）
- conversation 末尾立即渲染 `TurnMarker` 的 thinking 态：单行直立 12px ink-soft，内容「序号栏 `··` + 思考中」（2026-09-16 前是「第 N 步 │ 思考中」；同日先试过空 gutter，真机看是个洞）+ 状态文字 shimmer（2026-08-12 前是三点 `LiveDots`）；不再用逐字 opacity 波浪
- 触发条件：`agentRunning && !visiblePartial`
- `turn_end` 到达时，落定的 AgentTurn（同一 step number 的 TurnMarker + tools）在占位行**上方**以 0fr 展开长出，占位行本身不重挂载、留在原地等下一步的 `turn_start` 原地归零时钟（2026-09-16 live 窗口）。**before/after 视觉一致**——同一个 TurnMarker 组件的两态，用户感受到的是一个步骤的进展，不是两个独立的 UI
- **等待 ≥ 3 秒时显示 elapsed 计数，≥ 60 秒后追加仍在运行**——立即显示读秒会
  太机械，但 5 秒空等又明显让人产生等待感；3 秒是当前 dogfood 后的中点。
  `仍在运行` 是更强的长等待确认，只在 60 秒后出现，避免前一分钟显得啰嗦。
  Caller 用 `key={currentTurnIndex}` 让每步独立计时（step 1 等 40s，step 2 时钟归零）
  - `0-2s` → `思考中` + 三点指示
  - `3-59s` → `思考中` + 三点 · `32 秒`（tabular 等宽）
  - `60s+` → `思考中` + 三点 · `已 1 分 23 秒` · `仍在运行`

历史设计（已废弃）：原本占位走 ThinkingSummary callout（bg-surface + 左竖条 + 💭 emoji），跟正式 ThinkingSummary 块视觉同款。问题是 callout chrome 是给"GA 真实 emit `<thinking>` 多段内容"设计的容器，套在 10 字占位上视觉权重严重失衡。2026-05-14 改成 TurnMarker thinking 态。

- **状态行优先级**（2026-09-23）：in-flight buffer 里有未闭合的 `<thinking>` 时，状态固定为「思考中」，压过 send phase 与 preamble 压缩行（推理是这一步最新的事实，那两者在推理期间都已过时）；「正在回答…」只绑回答 partial 非空，因此只会在推理闭合之后出现。此前原生推理不带标签、被当成回答 partial，状态行在模型思考时写着「正在回答…」

#### Live Thinking Preview（实时思考预览）

2026-09-23 起（[devlog](../devlog/2026-09-23-live-thinking-preview.md)）。推理是过程材料，不是交付物：流式期给看，但永远不用回答的寄存器、永远不无上限地占高度，落定后必须有去处。

- **数据**：内置运行时的补丁 `0016` 把原生推理（Anthropic `thinking_delta`、OpenAI 兼容 `reasoning_content` / `reasoning`）边到边包成带内 `<thinking>…</thinking>` 流出，推理开始时开标签、回答或工具调用开始前闭合；推理里的字面 `</thinking>` 转成 `</ thinking>`（跨 chunk 也成立）。模型按提示词自己写的 `<thinking>` 本来就这样流。`extractLiveThinking(inFlightContent)` 取出所有块的内文 + 末尾未闭合块，给出 `{ text, open }`；扫到工具派发标记 / 5 反引号围栏即停（工具输出里读到的源码可能含 `<thinking>`）
- **形态**：in-flight 思考行正下方、同一 `StepRegion` 内、`pl-(--step-gutter)` 对齐 DetailPanel 那一列；`MarkdownView variant="thinking"`（Newsreader italic、ink-soft）。固定三行高的窗口：短推理从顶部读起，溢出后底部锚定、旧行从顶部滚出，顶边 mask 渐隐锚在文字底边往上 2.25–3 行。行盒 = 思考字号 × **正文**行高（段落继承 `PROSE_BASE` 的 body leading，thinking leading 只落在根元素上），标准档一行 23.8px。不可展开、不可交互、`aria-hidden`——全文在落定步的 caret 后面
- **收合**：推理块闭合即 `ExpandSection` 0fr 收合（`--motion-slow`），腾出的位置给回答正文；不等 `turn_end`——最后一步的回答可能流几十秒，等落定才收会让读到一半的正文整体上移
- **管线**：打字机（每帧 8 字，比回答的 3 字快：快速推理会把 3 字打字机甩在后面）→ 只渲染尾部约 1500–2000 字（切点优先段落边界、每 500 字才前移一次防止逐 token 重排）→ `useMarkdownStream` 节流 → `mendStreamingMarkdown`。不加 `streaming-prose` 的光标与块淡入：状态行的 shimmer 与滚动的行已经说明「在动」，过程区保持两路流里更安静的那一路
- **裁决**：行数 1 / 3 / 全文 × 收合时机 思考结束 / 落定，临时切换器真机实测后 JC 定 3 行 + 思考结束（即推荐项）
- **外置 GA**：上游仍把原生推理不带标签地流出，前端分不出，流式期照旧按回答正文流出；落定后的 `responseThinking` 两种模式都有，推理进 caret。按「内置优先」不追平
- **Responses 模式**（Codex 后端等）：推理累积不流出，只有落定后进 caret

Composer 状态同步：`agentRunning = true` 时 Submit 按钮切到 Stop 模式，LLM dropdown disable。

#### Turn 编号 + 间距

**不是**用户↔agent 对话轮次，**是 GA 内部 agent loop 的 turn 计数**——每次 LLM call + dispatch = 1 turn。一个 user message 可以触发 GA 跑 N 个 turn（agent 不断 reflect + 调 tool 直到出 final answer）。这跟 PRD §7.5 sidebar session row 显示的 "Turn N · summary" 同一个 N。

- 数据来源：每个 IPC `turn_start` / `turn_end` event 都带 `turnIndex` 字段
- AgentTurn type 持有 `turnIndex`（一个 user message 在 conversation 里可能产生多个 AgentTurn）
- 渲染（2026-09-16 序号栏形态）：每个 AgentTurn 的 thinking summary 之上一行，左侧是**两位补零序号**（`01`…，`lib/step-numeral.ts`）占一格固定宽度的 **`--step-gutter`（24px）**，**JetBrains Mono、`--conversation-tool-mono-size`（标准档 11px，与行右端的工具名同一寄存器）**、regular、`text-ink-muted`，行高钉到 summary 的行框（`calc(step-size * 1.6)`）让两者基线同高；summary（ink-soft，12px 档，**行高 1.6、自动换行不截断**）从 gutter 右缘起笔。序号与 summary 之间**没有分隔符**——固定列宽本身就是分隔。DetailPanel 的 caret **紧跟 summary 文字末尾**（inline-block，随末行换行；裸数字步则单独立在 gutter 右侧），不停在列右缘——披露 caret 贴着它所属的文字，与 pill 行、折叠头同一条规则（2026-09-16）。**不用 italic、不用 serif、不用 uppercase tracking**——结构 metadata 冷静直立，与下方 Newsreader 衬线正文形成对比张力
  - **可展开行的应答**（2026-09-23，[devlog](../devlog/2026-09-23-step-marker-hover-affordance.md)）：有 DetailPanel 内容的 marker 行是 `role=button` 披露控件（Tab 可达、Enter / Space、`aria-expanded`，可访问名取行内容，不设 `aria-label`），与 pill 行、折叠头同族：hover / focus-visible 在**内容列**（summary + caret）画 `bg-hover` 并提墨到 ink，即时无过渡；序号在框外，但悬停整行任一处都点亮内容框（`group-hover`）。框左缘 = 内容列 −10px，与 inline pill 的 hover 框同一条边，负 margin 抵消、文字 x 不变；上下不外溢，框即行框（live 窗口的裁剪框顶边贴着 marker 行，上溢会被切平）。summary 保留可选中，行内拖选不触发展开。提墨必须落在自带墨色的子元素上——行级 `hover:text-ink` 继承不到它们，此前正是这样悄悄失效的
  - **过程区 = StepRegion（缩进 + rail）**（2026-09-16 第二轮）：一个 run 的整个过程体（marker、narration、inline pill、block 卡片、ask_user 回显与用户回复、DetailPanel 原文）包在 `StepRegion` 里，整体缩进一格 `--step-gutter`，左侧 x=5（折叠头 caret 中心）有一条 1px `bg-line` 竖向 rail 贯穿全高。于是序号落在 24–48、内容从 48 起笔，和折叠头文字（起于 19）形成「把手在左、列表在右」——与参考 trace 组件的 24 / 47 同比例。**live 与 settled 同构**：未完成的 run（以及 /btw 等不可折 run）走 flat 的 StepRegion，rail 从第一步顶起；settled 可折 run 的 StepRegion 在 RunFoldSection 内，rail 从折叠头下缘（`-top-2.5`）挂下来。run 完成被重新包进折叠段时 x 不动。MainView 的 in-flight marker 也包一层 StepRegion（与上方 rail 之间有一小段断口，已知）。
  - **最终回答满宽**：StrongHr 之后的回答不在 StepRegion 里。为此 `answerOnly` 拆分扩展到**所有**有收口 turn 的 group（原只对可折 group）：收口 turn 的 marker 以 `markerOnly` 进区域，回答 flat 渲染。StrongHr 自己 `-ml-(--step-gutter)` 从缩进里破出来铺满列宽——「行动 → 结论」的横线属于回答的宽度。
  - **内容列 x 的两处细节**：pill 按钮保留 `px-2` hover 外溢，外层 `-ml-2.5` 拉回 8px 外溢 + 2px Phosphor 字形内留白，图标可见笔画正好落在 summary 首字的 x；裸步合并的 pill 行自画 gutter。
  - **锚点靠对齐，不靠墨量，层级为 头 → summary → 序号**：summary 是这一行的句子，序号是页边序号栏，是这一步里最轻的元素（第一轮曾保留 medium 以保 Windows 可扫性，真机看后层级比可扫性重要，改 regular 并降 1px）。RunFoldHeader 的「N 步」是计数、sidebar 的「第 N 步 · summary」是独立语境需要单位，均不跟随；「第 N 步」文案（`copy.conversation.step`）保留为序号旁的 sr-only 文本，屏幕阅读器仍念完整语义。序号栏在 `index` 未知的 pre-turn_start 窗口也占位（`··`），步落地时状态文字不右跳。
  - **真机 A/B 裁决（2026-09-16，临时切换器已拆）**：序号字体 **mono 胜** Inter tabular——行的左右两端都是机器元数据说得通，mono 序号读作页边序号而非数量；折叠头计数段**保持 ink-muted regular**，ink-soft medium 的「把手比列表深」方案被否，08-06「安静眉头」定案维持。
  - **折叠头行内分层（2026-09-23，[devlog](../devlog/2026-09-23-run-fold-header-hierarchy.md)）**：整行不加深，只让**数字**（步数、用时的 9 / 2 / 27）走 ink-soft，「步」「用时」「分」「秒」仍 muted regular——与 09-16 被否的整段加深加粗是两回事，行仍是安静眉头，视线在数字上有落点；数字 span 自带墨色，靠具名 `group/fold` 跟随整行悬停提墨。气味段、提问数、拒绝徽标降到 `--conversation-tool-label-size`（与它们概括的 pill 标签同档），`×N` 等宽；竖线两侧各 12px，行按基线对齐，读作「结构 | 气味」两组。气味段里 `file_write` / `file_patch` 排最前，其余仍按次数降序，省略号只吃泛泛的尾巴。live 变体同样适用。
  - **before/after 一致的新口径**（2026-09-16 二改）：thinking 态是「`··` 思考中 · 12.3 秒」，落定后是「03 summary」——同一组件、同一位置、同一寄存器，序号是落定时才出现的唯一差异（盖章）。这与外部 ReasoningTrace 参考组件（thinking 态无号、只给 settled 列表编号）同构；第一版曾让 thinking 态也带号，真机看 in-flight 的「01 正在处理」像提前盖章而改。**序号位的 `··`**（2026-09-16 三改，`PENDING_STEP_NUMERAL`）：同列同 mono 同 muted、两个中点正好两位序号宽，读作「下一项待落定」的空章。参考组件那一格放的是 Sparkles 脉冲，Galley 按 §2.7 不加动效源；空 gutter 曾是第一版答案，真机看是一段洞（刚提交、尚无落定步时最明显），三态真机 A/B（空档 / `··` / 无 gutter 齐序号列起笔）JC 明确选 `··`——守住网格，而无 gutter 的「状态行不是步」叙事要靠寄存器差异撑一整行。
  - **裁决史**：2026-06-09 瑞士化定「第 N 步 │ summary」（hairline 取代中点）；2026-08-23 裁「裸数字永久否决」；2026-09-16 JC 真机看过淡一档版本仍嫌繁琐，翻案为补零序号 + 去 hairline + gutter 对齐（见 [devlog](../devlog/2026-09-16-step-marker-recede-and-reference-audit.md)：08-23 的「读者只扫数字」论据其实在替裸数字辩护；「3 │ 思考中 · 12.3s 两个数字打架」由补零 + 计数器带单位化解）。明知代价：run 边界处第 1 步的 chapter-break 分隔力略弱，靠 `mt-6` 与 settled run 折叠兜住；ink-muted 约 3.4:1 低于 AA，是既有的元数据档位。

- **裸步合并**（同一 pass）：GA 未产出 summary 的步，marker 行只剩纯数字——此时若该步恰好只有一个 settled-success 的 inline 工具、且无 DetailPanel 内容 / 无 narration，则 marker 整行取消，由 InlineToolPill 自渲染序号 gutter 前缀（`Conversation.tsx` `mergedStepTool` → `ToolCallout` `stepIndex`）。前缀在 button 之外，保住序号栏对齐、hover 目标仍是工具区。任一条件不满足（有 summary / 有 detail / 多工具 / block 态）都维持两行——两行形态仍是常态

- **流式正文与思考行之间留一个段落间距**（2026-09-18，`--conversation-block-gap`，随字号档走）：思考行按步内节奏没有下边距（工具行要贴着它），但流式正文是 15px 衬线正文而非工具行，零间距贴着 12px 状态行、又满宽压过缩进的标记左缘，JC 真机嫌挤。三案：A 流式态直接套最终回答的 StrongHr（同构零跳动，但中间步叙述也会顶一条假结论线）、B 只加段落级上边距、C 加边距并缩进到内容列（翻 09-16「流式正文满宽」案）。裁 B：不押注流式正文最终落成叙述（6px 缩进）还是回答（StrongHr），两种结局都语义中性；取 12px 段落档而非 16px 的 StrongHr 档，避免暗示一条不存在的线。落定时的跳动与此前相同，只是起点不再贴着。
- in-flight 状态：`currentTurnIndex` 从 `turn_start` 读取，用于给 thinking 占位 `key`（每步时钟归零）与 `mt-*` 档位；**thinking 行不显序号，序号位放 `··`**（2026-09-16）——序号是落定的盖章，in-flight 行挂「01」等于宣告一个项目还不存在的单项列表；用户感知跑到第几迭代由上方已落定的 01、02 承担，turn_end 替换时序号在原位出现。此前「占位顶部显示 Turn N」的要求废止
- **live 两行窗口**（2026-09-16，[PRD](../../.scratch/live-run-window/PRD.md)）：正在进行的 run 不是越长越长的清单，而是固定大小的状态面板——最后一个落定的步以阅读形态留在 MainView 思考行之上，之前的步折进 `RunFoldHeader` 的 live 变体「已完成 N 步 · 气味段」（不带用时，步时钟与 HUD 已够两只表；第一步折进去时才出现，单步 run 不受影响）。点头展开是 opt-in，之后落定的步继续追加，完成时保持展开；中止（既不 running 也不 askUserPending）则窗口撤掉、整个 run 平铺。rail 从头 caret 中心贯到思考行（MainView in-flight 区从第 2 步起 `railFrom="header"`）。窗口包在自己的 ExpandSection 里并承担头到窗口的间距（marker `mt-*` 经 `data-role="step-marker"` 归零；折叠头下 `-mt-2.5` + `pt-2.5`，padding 在 overflow 盒内让 rail 穿过间隙），因为挂着的 0fr 折叠段会阻断 margin 穿透。**完成瞬间**：run 完成的那次渲染保持 live 结构一次 sweep（窗口收合、头换 settled 文案、答案平铺），300ms 后切到 settled 结构。**步完成的窗口滑动**：被顶掉的步留一次 sweep 关闭（出场）、新步 0fr 展开（入场）、头首次出现淡入、思考行不重挂载只原地归零时钟（run 开始首次出现淡入一次）；展开态不做出场。每步 `pb-2.5` 自带步间距，region `-mb-2.5` 抵消末步。只对可折 run（`foldEligible`）生效。
- `run_complete` / `error` 时清空 currentTurnIndex
- **没有 turn 之间的 SoftHr**——TurnMarker 自带 chapter-break 视觉重量，水平横线已删除

#### 间距演化历史

`turn 间分隔`经过四次调整：

1. v0.1 初版：SoftHr `my-9`（72px）—— dogfood 反馈"每个 turn 浪费 1/3 屏"
2. SoftHr `my-6`（48px）—— 仍反馈"还是大"
3. SoftHr `my-5`（40px）—— 仍反馈"还是大"
4. 删除 SoftHr，TurnMarker `mt-7`（28px）+ tracking 加大承担分隔
5. 2026-06-09 瑞士化：直立 sans + tabular 数字 + 竖向 hairline 分隔，去掉 italic 与 uppercase tracking。间距曾短暂提到 `mt-9`（36px），但实测 turn 间隙 ≈ 42px 又触到当年被拒的 SoftHr `my-5`（40px）量级；dogfood 后一路收到 `mt-6`（24px）。结论：瑞士 marker 自带分隔力，结构清晰度承担分隔，不需要靠大留白
6. **现行（2026-08-23 密度 pass）**：`mt-6` 的适用域重新限定为 **run 边界**；run 内步间收到 `mt-3`（12px），marker `mb-2.5`→`mb-1`，inline pill `my-1.5`→`my-0.5`。动因：第 5 条的 24px 裁决隐含「章节有正文」的前提，多步工具 run 里一步只有两根细线（marker + pill），叠上 24px 后留白占一步高度 ~55%，13 步的 live run 超过一屏——纵向体量本身是层级信号，过程日志的体量压过 final answer 把主次滚反了。提密度即降层级。第 5 条「结构承担分隔」的论证方向不变，恰好支持 run 内更紧

教训：当用户反复反馈"间距大"时，缩 hr 到极小已经不是答案；该思考"分隔信号"是不是必须靠 hr 承担。结果：TurnMarker 的章节标识 + 间距 + 字号已经足够。第二层教训（2026-08-23）：一条间距裁决要连同它的内容前提一起记——「turn 间 24px」在 turn 有正文时成立，turn 退化成日志行时同一个值就是另一个设计。

#### 会话里的输入框（2026-10-15）

会话里的输入框是一行式：工作台的会话、从助手点开的子任务、外置运行时的会话、主对话，都是这一条；新对话的空状态照旧是居中的大卡片，发出第一句后变成底部的一行（ChatGPT、Claude.ai 同样过渡）。本节以外 4.4 各条写的卡片，就是空状态的那张。

由来：主对话先定（[主聊天 PRD](../../.scratch/main-chat/PRD.md) 裁决 71、72：JC 在 tauri dev 里比完「现状 / 一行式」两档，选一行式；试验是票 24，定稿是票 25）；工作台跟上（裁决 74，票 27：卡片约 108px 加提示行，空着时上半截大片空白，工作台的会话常是长串工具步骤，更缺竖向空间；空状态只有一个输入框，大卡片正合适）。门在 `MainView`：会话里的 Composer 一律设 `oneLine`；`isMainChat` 只管主对话与工作台的差别（提示行、底边距、占位，见下）。一条的排法在 `ComposerOneLine.tsx`，量值（`ONE_LINE_*`）在 `composer-styles.ts`。

```
┌──────────────────────────────────────────────────────────┐
│ ＋  发消息…                     gpt-6.1-sol · 默认   (↑)  │
└──────────────────────────────────────────────────────────┘
```

- **一条**：从左到右是 ＋（同下「＋ 菜单」）、输入、「模型 · 强度」（同下「LLM 切换器」与「推理强度 pill」，短语原样）、发送 / 停止。输入起一行，随内容长高，8 行后在框里滚动（卡片的上限是 280px，约 12 行）；长高时 ＋、模型短语、发送贴底，与最后一行齐平（`items-end`，同 Claude.ai、Telegram）。
- **尺寸**：一行时高 48px（上下各 7px 内边距加 1px 边框，中间是 32px 的按钮行；输入的上下内边距按对话字号算，小、标准、大三档都是 48）；三行 93px（字号小 90、大 98）；8 行 205px。圆角 24px：一行高度的一半，又正好和 ＋、发送这两个 32px 的圆同心（离框外缘 8px，16 + 8 = 24），两端读成一个形状；长高后四角照旧 24。底色、边框、投影、杏沙 focus ring 同卡片。满栏宽，宽屏 1200 栏下也是。
- **附件条**在框内、输入上方，缩略图离框外缘 12px，和 24px 的角同心，下面留 8px 再接输入那一行（两张图时框高 124px）。**幽灵文字**照旧在输入里，「按 → 填入」照旧跟在它后面。**拖放浮层**画成一行（16px 回形针 + 字），圆角 23px 贴着框。草稿照旧按会话驻留。
- **模型短语的弹层**向上开、居中对准按钮（`LLMPill` / `EffortPill` 的 `popoverAlign="center"`，裁决 76）：模型弹层的中线对准模型名的中线，强度弹层对准强度，弹层底在按钮上方 6px。票 24 起是右对齐（只顾着短语靠近条的右缘时不伸出条外），弹层比按钮宽得多，右缘对齐后整个往左伸：模型弹层左边多出约 65px，强度弹层盖到模型名上方，看着不挂在按钮上（JC：「它的左边那个条线应该是对称于按钮，现在是靠左」）。居中后两侧对称，模型弹层各伸约 32px、强度弹层各约 21px。左对齐（卡片的排法）不选：会往右盖住发送键，强度弹层的右缘贴到条边。实测（Chrome）：默认窗口、960 × 600 小窗口、宽屏，加 42 个字符的长模型名（弹层到 320 上限），两个弹层都在条内，离条右缘最近时模型弹层 41px、强度弹层 21.6px，中线与按钮中线相差不到 0.3px；不另设碰撞参数，Radix 默认的碰撞避让（以视口为界）照旧兜底。运行中照旧封锁换模型，强度照旧可点。小窗口下短语最多占这一行的四成，超出时截断模型名（省略号），「·」、强度、发送、＋ 都不收缩：不设上限的话，输入是 `flex-1`，会先被挤到 0 再轮到模型名（960 × 600 下 42 个字符的模型名截成约 233px）。
- **工作台：提示行留着**（裁决 74 第 2 条）。它是活的图例，内容规则照旧（`lib/composer-hint.ts`）：空着时「拖入任意文件或文件夹，发给 AI」（07-29 裁决 A，永不退休；空状态卡片下方刻意全空，这里是全应用唯一教拖放的地方）、打字时 Enter / Shift+Enter、在跑时「Enter 排队」、停止中「正在停止，排队的消息会自动发出」。不选「一行式也去掉提示行」：等于推翻裁决 A。
  - **左对齐到输入文字的起点**（裁决 74 第 3 条）：＋ 右边、与占位文字同一条线，离条左缘 44px（1px 边框、7px 内边距、32px 的 ＋、4px 间距，`ONE_LINE_HINT_CLASS`），延续「对齐卡片内容边」。居中（ChatGPT 底下那行声明的做法）作备选，真机验收时看。
  - **离条 6px**（`mt-1.5`，同 §7「Composer hint 槽统一语法」与空状态卡片下的那一行），字形顶离条的下缘约 9.5px；下面照旧 16px 到窗口底边（`pb-4`）。
  - 静止时整个输入区（条加提示行）从条顶到窗口底边 86.5px，卡片时 147.5px（卡片 109 加提示行 22.5 加 16），对话区多出 61px。
  - 停止中且有排队时那句由提示行说，只说一次：队列条照旧写「排队中 · N」。
  - 占位照旧：「继续…」，在跑时「/btw 顺便问一句，不打断任务…」，在问你时「回复上方提问」（有候选时「回复，或选择上方候选」）。
- **主对话：离窗口底边 24px**（裁决 72）：外层 `pb-6`；工作台照旧 16（`pb-4`）再加提示行。一行式撤掉了提示行（约 22px），底下的 16 不变的话，整条往下沉约 22px，JC 真机嫌太靠下。取 24：浮起的圆角条底下要有呼吸，16 只有条高的三分之一、贴着窗口的圆角；24 是条高的一半、等于它自己的圆角半径；仍比卡片加提示行省约 14px。32 接近原来卡片的感觉，留作真机嫌挤时的下一档。输入框上方与对话之间不动：对话照旧贴底（「助手的对话」的「滚动：贴底」），最后一条消息离输入框的距离前后一样，整段对话跟着输入框上移 8px。
- **主对话：没有提示行**（裁决 71 第 3 条）：拖入文件、Shift+Enter、在跑时的 Enter 排队，主对话里都不说。IM 里没有这一行；拖放到处通用，＋ 菜单也在。它与 07-29 的裁决 A（`.scratch/composer-file-drop/issues/06`：这一行是「当下为真的能力图例」，拖放提示永不退休）的关系：那条管的是行里的提示要不要过期，这里是主对话的版式里没有这一行；代价是从不尝试拖放的人在主对话里少一个教学面，工作台的输入框照旧教，＋ 菜单与拖放浮层也在。差别沿着裁决 66、67、73 的分界：主对话像 IM、没有提示；工作台是工具、带图例（裁决 74 第 4 条）。
- **主对话：停止中且有排队**时那句「正在停止，排队的消息会自动发出」回答的是「我发的丢没丢」，不能跟着提示行丢：它挪到输入框上方队列条的标题（`ComposerQueueStrip` 的 `heading`），取代「排队中 · N」。条件是一行式且没有提示行（`oneLine && !showFooterHint`），工作台由提示行说，同一句不说两遍。用提示行原来的字号与墨色（11px、`ink-muted`，不用标题的大写字距），行高同原标题（15px），换上换下不跳；停下来、队列发出后回到「排队中 · N」或整条消失。放在排着的那几条正上方最近，标题本来就在说这几条的状态。
- **主对话的占位文字**「发消息…」（en「Message…」）：空闲与在跑时都是，不写 `/btw`（`/btw` 照旧可用）；在问你时照旧「回复上方提问」（有候选时「回复，或选择上方候选」）。语域在 `lib/composer-register.ts`（`messaging`）。
- **主对话在忙时按 Enter 直接排队**（裁决 71 第 4 条）：同普通会话，进输入框上方的队列条；不再有「排队 / 开新对话 / 继续编辑」三选一（票 02）。当初怕主对话被长任务占住，给一个开新对话的出口；现在重活派给子任务（裁决 53），另起话题走侧栏的新对话。带图的消息在跑时照普通会话的规则拦下（队列只收文字），草稿留着。
- **主对话的模型也留在输入框，不进顶栏菜单**（裁决 71 第 2 条，推翻裁决 66 第 5 条的「挪进顶栏菜单」）：顶栏写的是「Galley ⌄」，看不出背后还有模型（ChatGPT 把模型放顶栏成立，是因为它的顶栏写的就是模型名）；最需要换模型的时候（额度用完、Key 失效、服务商故障）最难找；主对话记着自己的模型，改设置里的默认模型它不跟，挪走后顶栏菜单就成了唯一入口。推理强度跟着模型短语留下：「模型 · 强度」是 09-22、10-03 两轮定下的整体。
- **长高时保持贴底**（票 27，主对话与工作台都是）：输入框长高或变矮时（打字、附件条或队列条出现、发出后缩回一行，窗口变矮也一样），对话原本在底部（`atBottom`，24px 容差）就保持贴底，往回翻着时不动。以前视口变矮时 `scrollTop` 不变、内容也没变，跟随的几条路都不触发，最后一条消息被压到输入框上沿以下；一行式从 48 长到 93，三行就压掉 45px。做法：滚动容器自身挂一个 ResizeObserver（`lib/viewport-resize.ts`，`useStickyScroll` 接上），只在它的高度变了时动，回调在排版之后、绘制之前，长高的那一帧就已钉底。实测（Chrome）：对话在底部时打三行，对话栏的底离输入框照旧是静止时的 24px（对话区的 `py-6`）；不跟的话，栏底被压到输入框上沿以下 21px（长高的 45 减去这 24）。主对话这里也直接到底，不用「跟随到回复开头为止」（`assistantFollowTop`）：那条管回复在读者眼前长，这里读者在打字，要回的那条得留在输入框正上方。
- **不做**：排队的消息挪进对话、显示成带「排队中」标记的气泡（裁决 71 第 6 条，晚点再谈；在那之前照旧用输入框上方的队列条）；手机端；工作台的提示行改居中（裁决 74 的备选，真机验收时再看）。

#### Submit 按钮（杏沙 CTA 例外）

- **Submit 是全局唯一用杏沙作为 CTA 填充的元素** —— 用户最高频元素，杏沙带来"亲和体温"
- Phosphor `ArrowUp` **bold** / 32px circle / 杏沙填充 / charcoal icon（thin 在 16px 实心圆上过细，落地时升 bold——刻意，勿"修"回 thin）
- Enter 触发，Shift+Enter 换行；**输入法组字中的 Enter 交给 IME**（`isImeCompositionKeydown` 守卫，中文优先产品的硬约束）
- agent running 时**位置替换为 Stop 按钮**（深琥珀填充 / Phosphor `Stop` **fill**，同上刻意加重），点击触发 abort。运行态里「Enter 发送」是谎言：消息队列（galley#19 / #20）以后 Enter 不发送而是排队，工作台的提示行随之换（`lib/composer-hint.ts`）：空着时「Shift+Enter 换行」，打了字「Enter 排队 · 本轮结束后自动发送」，打的是 `/btw` 时回到「Enter 发送」（顺便问一句立刻发出），停止中且有排队时「正在停止，排队的消息会自动发出」。`/btw` 由占位文字教（「/btw 顺便问一句，不打断任务…」，它就在要打前缀的位置，本身就是格式示例），提示行不重复。主对话没有提示行，占位也不写 `/btw`，见「[会话里的输入框](#会话里的输入框2026-10-15)」
- **Composer 里凸起的键只留给发送位**（2026-10-03）：发送 / 停止 / 去配置模型，凸起即「这会把东西发出去」。其余按钮（＋ 等）是无底色图标钮（`COMPOSER_TERTIARY_ICON_BUTTON`），静止无底色、无描边、无投影，hover 才出 `hover` 底。

#### ＋ 菜单（2026-10-03）

位置：**Composer 按钮行最左**，紧贴模型短语（两者之间不留行间距——留 8px
时 ＋ 与模型名的视觉空白约 31px，读作一个离群的控件）。左边是「放进什么、
谁来回答」，右边只剩「怎么发」（发送位）。与 ChatGPT /
Claude.ai 的 ＋ 同位，借用户已有的肌肉记忆。以上是卡片（新对话的空状态）；会话里的一行式里
＋ 照旧在最左，模型短语挪到发送键左边，见「[会话里的输入框](#会话里的输入框2026-10-15)」。

- 形态：Phosphor `Plus` thin 17px，`COMPOSER_TERTIARY_ICON_BUTTON`（无底色
  32px 圆），打开时 `bg-hover`；tooltip「添加文件或提示词」。pointer-first：
  不进 Tab 顺序、mousedown 不抢焦点。
- 菜单三行（向上开、左对齐）：
  1. 「文件或图片…」（不支持图片的运行时写「文件…」）——原生多选面板，
     **按扩展名分流，与拖放同一条规则**：图片进附件条，其余插 `[File #N: …]`。
     不支持图片的运行时选中的图片也作路径引用（标签没许诺图片；拖放则仍按
     原规则拒收并提示）。
  2. 「文件夹…」——原生面板 `directory: true` 多选，插 `[Folder #N: …]`。
     单列一行是因为原生面板不能文件、文件夹混选；用户真正懂的分界正是
     文件 vs 文件夹。
  3. 分隔线后「常用提示词…」——打开提示词库 dialog（见下节）。
- 文件两行**不受运行中门控**：路径引用是纯文本，和拖放一样可以进队列；运行
  中带图片发送仍在发送处被拦（既有规则）。
- 菜单关闭后焦点回到输入框（保留原选区），所以选中的文件落在光标处、或替换
  预设刚选中的 `[…]`；打开提示词库时不抢焦点，交给 dialog。
- 由来：此前右下是 🔖 书签（常用提示词）+ 📎（两项菜单「添加图片 / 添加
  文件…」），两颗不带字的图标要悬停才认得；书签读作「收藏」；📎 菜单逼用户
  在「图片 / 文件」之间选（背后是「内容 vs 路径」），同一张 PNG 拖进来是图片、
  从「添加文件…」进来却是模型看不到的路径；点击路径还选不了文件夹，而
  「整理本地文件」预设要的正是文件夹路径。决策全程见
  [devlog](../devlog/2026-10-03-composer-plus-menu.md)。
- Rejected：**`/` 快路**（空输入框首字符 `/` 或行首「、」就地弹提示词列表）——
  进 [deferred](../devlog/deferred.md)，本机自定义提示词为 0 条，受益者尚不
  存在；**拿掉所有可见入口只留 `/`**——对新手等于藏起提示词库；**只修语义不动
  布局**——右侧仍是四颗圆。

#### 常用提示词入口（V0.2.16；2026-10-03 移入 ＋ 菜单）

位置：**＋ 菜单第三行「常用提示词…」**（分隔线之后）。常用提示词属于
「往输入框添加内容」的工具，和添加文件同组；LLM picker 属于模型选择，
不和它绑定。

- 形态：没有独立的图标钮，入口是 ＋ 菜单里带字的一行（`BookOpenText` thin
  14px + 「常用提示词…」）。2026-10-03 前是右下角的 `BookmarkSimple` 图标钮，
  书签读作「收藏」、要悬停才认得，见 [devlog](../devlog/2026-10-03-composer-plus-menu.md)。
  用户为加文件打开 ＋ 时会顺路看到这一行——借高频入口给能力发现。
- 点菜单行直接打开提示词库 dialog；没有 hover 预览（quick-fill popover 早已
  移除，避免鼠标擦过 Composer 工具区时误弹大浮层）。
- 内置预设共 9 个，固定目录、只读、不可置顶排序。**这一板块同时是 Galley
  的能力发现 / 教学面**（2026-07-04 重构）：不再是「教用户把 prompt 写规整」
  的填空模板，而是「让用户一眼看到 Galley 能替他做什么」的能力菜单。因此
  每条预设写法上从「能替你做什么」切入，其中三条是**差异化能力展演**——
  整理本地文件（读本地文件夹 + 系统级、plan-first）、网页信息抓取（真实
  浏览器 + 登录态）、多源调研对比（多步 agentic 调研）。顺序：
  整理长文、事实查证、**整理本地文件**、翻译润色、**网页信息抓取**、
  审阅草稿、**多源调研对比**、整理表格、执行前检查清单——三条差异化项
  交错在 3 / 5 / 7 位，而非按频率堆在末尾（改了此前「严格按频率排序」的
  约定；理由：920 dialog 一屏看全 9 张，交错让惊喜卡片在动线里更显眼）。
- 每条预设带一个面向用户的 `description`（一句话，「Galley 用这条能替你做
  什么」），随 UI 语言本地化；数据模型上 `description` 是 `PromptPreset` /
  `ResolvedSavedPrompt` 的可选字段，只有预设携带，自定义不带。
- 入口的 pointer-first 规则随 ＋ 按钮（不进 Tab 顺序、不显示 focus ring，
  避免桌面 WebView 把焦点态误读成“选中”）。
- Dialog 顶部不显示可见副标题；尺寸约
  `920x680`，读作 Settings / Earlier / Archived 同族的工作台，而不是小确认窗。
  主体为工作台式 `bg-app` 画布 + 卡片平铺，分两个 group：上方「预设」（常驻
  可折叠的模板库，固定顺序），下方「自定义」（用户可上移 / 下移调整顺序）。
  整张卡片点击即预填 Composer，不自动发送；hover 卡片时显示查看 / 管理按钮。
- 卡片承载摘要，两种形态：**预设**卡片显示 标题 + `description`（面向用户的
  能力一句话，正文指令原文移到阅读页——卡片更干净、读作能力菜单）；
  **自定义**卡片无 description，保持 标题 + 4 行正文预览（用户自己写的正文
  即摘要）。**卡片高度贴内容、不定高**（2026-07-04）：预设卡片一到两行内容
  自然收紧，自定义卡片按正文预览撑高，两者在各自 group 内一致、跨 group 不
  强求等高。hover 操作按钮放**右上角**（不占底部预留带——底部留带在短卡片上
  读作浪费），24px 命中区（在 20px 太小误触、28px 太笨重之间），标题
  hover 时右侧留出空位让 truncate 省略号避开按钮。操作区整块吞点击——角落
  near-miss 不会穿透触发整卡的「填入」，避免误触。需要看完整 prompt 时，hover 点“查看”进入同一 dialog 内的完整
  阅读页（预设阅读页在标题下也显示 description）；阅读页提供返回、填入输入框，
  以及预设复制为自定义 / 自定义编辑。复制预设为自定义时只带 title + body，
  description 不带（复制后它就是用户的一段文本，回退正文预览）。
- 卡片管理动作按 group 分：预设只读，可复制为自定义；自定义可新增、编辑、删除、
  上移 / 下移调整顺序。复制预设或新增自定义后，新项落在自定义列表最前并短暂
  高亮、自动滚到该卡片。
- 数据存在 GUI prefs `saved_prompts_v1`（schemaVersion 2），只保存用户自定义
  prompt；内置 preset 不写入 prefs，随 UI 语言本地化。没有置顶 / pinnedIds
  概念——早期版本的置顶机制在首次发布前移除，pinnedIds 字段一并删除，旧 prefs
  落到 v2 默认值（空自定义）。
- 若 Composer 已有非空草稿，选择 prompt 先确认再覆盖；图片附件保留，
  paste-fold registry 重置。
- **填入后选中末尾的填空**（2026-10-03）：正文最后一行若是 `[…]`（九条预设
  都以「[写下要查证的问题]」这类方括号收尾），填入后它被选中而不是光标停在
  末尾——直接打字即替换，拖入文件 / 从 ＋ 选文件也替换它，不用手动删、也不会
  连方括号一起发出去。只认「独占最后一行的方括号」，行中的方括号是内容不是
  填空（`findPromptFillSlot`，`lib/saved-prompts.ts`）。
- 首版明确不做：分类、搜索、变量、使用次数 / 最近使用排序、import/export、
  cloud sync、Agent API / CLI surface。

设计判断：这既是高频便利入口，也承担能力发现（2026-07-04 起，见上文预设
重构）。但它仍留在 Composer 的 ＋ 菜单里、按点击展开，**不回到 Empty State 下方的
quick prompt 建议**——能力发现靠"用户主动打开库时看到能力菜单"，而不是把内容
铺在空状态里打断安静书桌（空状态保持安静的决策见 Empty State 一节）。

#### Trigger 与弹层（2026-07-20 定稿；2026-10-05 移出审批模式）

审批模式（自动执行 / 逐步审批）曾并入这个 pill：偏离默认时 trigger 上的
`HandPalm` / `Lightning` 图标、弹层动作栏的「改为逐步审批 / 改为自动执行」
行。2026-10-05 随审批整体移除，见
[tools-and-approvals.md](./tools-and-approvals.md) §4.6。

- **Trigger**：模型名，无箭头、无图标。推理强度**不**进这个 pill（见下方
  「推理强度 pill」，2026-09-22）。**有推理强度 pill 跟在后面时**
  （`phraseLead`），左右内边距对称收到 `px-1`：两者加中间的「·」合成一个
  短语「gpt-6.1-sol · high」。没有强度 pill（无模型可选）时内边距恢复 `px-2.5`。
- **Popover 结构**（自上而下，主从分层）：
  1. 模型列表（主，12.5px）。**勾号在右、文字齐左**（2026-09-22 重审）：原
     左侧勾号列每行保留 22px 只为一行画勾，文字距弹层边缘 36px，JC 嫌浪费
     且占视野；改为 web 模型选择器惯例的尾随勾号（ChatGPT / Claude / Codex /
     Cursor），文字距边缘 14px，hover 浮出的服务商名排在勾号之前、勾永远
     贴右缘；**去掉最小宽度**（先收到 160 仍在短模型名旁留出 60px 空白，
     截图 2x 量得），宽度由最长模型名决定，长模型名仍可撑到 320 上限。勾走后
     模型行与下方动作栏的文字同一条左线。
  2. 分隔线 + 动作栏（11px `text-ink-muted/70`——全 popover 只有"内容 /
     动作"两个字号层级，不设中间档）：「配置模型…」（`Gear`）。
- **运行中语义**：`stopMode` 封锁模型切换（模型行置灰 + 区顶一行「运行中
  无法切换模型」小字），popover 本身照常打开。

**推理强度 pill**（2026-09-22，社区第二次提出后从 deferred 拎出）：LLMPill
右侧一个**独立** pill，成熟产品的「模型选择器 + 强度选择器」并排惯例。它不
并进 LLMPill 的理由：强度是会被拧的旋钮，且值本身有信息量（HIGH = 更慢更贵），有信息量的状态值得自己的
位置。真机先验过「藏在模型弹层里一行」——模型一多它像挂在最后一个模型
下面，且新对话里根本看不到，两条都被 JC 否掉。

- **Trigger**：当前生效档的普通文字，无箭头，**字体字号与模型名一致、
  墨色低一级、全小写**（12.5px `text-ink-muted/80`，hover 抬到
  `text-ink-soft`；
  档位文案是 Models 设置里的词转小写：`low` / `medium` / `high` / `xhigh`）。
  小写的理由（第五轮真机）：首字母大写让强度的视觉质量取决于模型名有没有
  大写——「grok-4.7」旁边显得重、「GPT-5」旁边就不重；小写把强度钉在 x 高度，
  层级不再看模型名的脸色。设置编辑器保留 `High` 的拼法，Composer 是自己的
  语域。层级低一级的
  理由与 09-08「Provider 是身份，推理强度是状态」同源：模型名回答「在跟谁
  说话」，强度是它的参数。只降墨色不缩字号——同一行两个字号在这个尺度读作
  没对齐，11px 是弹层动作栏的字号。这是常量层级，不随跟随 / 覆盖状态变。模型配置留空且无覆盖时显示「默认」——pill **永远在**，
  不忽隐忽现。第二轮真机否掉了徽标 chip 字形（灰底等宽大写）：它在设置里是
  附在模型行上的标签，搬到 Composer 与正文字号的模型名并排就成了第三种字体
  风格，读作杂乱。跟随与偏离**不画在 trigger 上**（这个字号下墨色深浅要么看
  不出、要么像按钮坏了），也不进 tooltip（第十轮：tooltip 只剩动词「调整推理
  强度」，与模型 pill 的「切换模型」同句式（2026-10-03 JC 把「LLM」改成「模型」）；跟随 / 覆盖只留在 aria）。
- **一个短语**（第四轮真机，对表 Codex「GPT-6 Astra Medium ⌄」）：
  与 LLMPill 之间**不留行间距**（先前 28px 读作两个不相干控件，12px 仍是两个
  相邻控件）。2026-10-03 加「·」后，两 pill 改为**左右对称的 `px-1`**、点自带
  `px-0.5`：此前模型 pill `pl-2.5 pr-0.5`、强度 pill `pl-0.5 pr-2.5`，是为了在
  无分隔时把两个词压到一个词距、hover 框内侧相接，代价是悬停时模型框往左、
  强度框往右各多出 10px，JC 嫌怪；对照页比过 4 / 6 / 8px 三档，4px 时字距最接近
  正常排版的「 · 」、点距两个框各约 3px 不归属任何一边，6px 以上点两侧拉到
  10px 以上、短语又散成两个控件；
  两半各有 hover 底色框、互不重叠，告诉用户是两个目标。
- **无箭头**（2026-10-03，JC 真机提出、按推荐裁）：09-22 第四轮让模型 pill 去掉
  箭头、短语末尾只留一个 `CaretUp`，并否掉零箭头（读作状态行、成熟产品都留
  chevron、上限 pill 带箭头）。加「·」后短语明确分成两项，悬停框又改成各自
  对称，末尾那个箭头落在强度的框里，读作强度自己的箭头——模型没有、强度有，
  JC 指出不统一。两个都加（「gpt-6.1-sol ⌃ · high ⌃」）在短短一句里挤三个小记号，
  且是 09-22 被否的两箭头形态；故两个都去。可点的提示交给悬停框 + tooltip（模型
  名自 09-22 起本就如此）。风险知情：成熟产品的模型选择器几乎都带箭头，这里是
  少数派，首次使用要悬停才知道可点；同一行的 ＋ / ↑ 都是明确的按钮，文字
  在工具栏里本身暗示可操作。
- **中间一个「·」**（2026-10-03，JC 裁）：「gpt-6.1-sol high」两个词同字号同字体、
  只差一级墨色，强度词读起来像型号后缀——low / high / mini / max 本来就常出现在
  模型名里（ChatGPT 有过「o3-mini-high」）。于是两 pill 之间加一个不可点的「·」
  （`text-ink-muted/60`，`px-0.5`，两侧各约一个词距），读作「gpt-6.1-sol · high」；
  两个 hover 框不变。同轮比过的「强度改四格刻度」与「人话档位（轻 / 标准 /
  深入 / 极深）」落选，见 [devlog](../devlog/2026-10-03-composer-model-effort-display.md)。
- **Popover**：与模型弹层同一套行语法的竖列，**从上到下由高到低**：`max` / `xhigh` /
  `high` / `medium` / `low`，最下面是 `默认`（仅模型配置留空时出现）（2026-10-15 裁决 78，
  此前由低到高、`默认` 在最上）。弹层总是向上开，倒过来以后紧挨按钮的是 `默认`（9 月以来
  75 个内置会话没有一个手动改过强度，几乎都停在它），往上移就是往上加，「上即多」同任何
  纵向刻度；由低到高时最贵最慢的 `max` 反而紧挨按钮。模型弹层不跟着倒：那是「我的模型」
  里用户自排的偏好顺序，不是大小。文字齐左、勾号在右（与模型弹层同一次重审），不设最小
  宽度、按词宽走（约 100px），点即选即关，无说明行、无设置深链。给**五档**
  （`gui/src/lib/reasoning-effort.ts` 的 `COMPOSER_EFFORT_TIERS`，09-22 起如此）：两种协议都认
  这五个，引擎把 Claude 的 `xhigh` 与 `max` 映射到同一最高档；`none` / `minimal` 留在设置里。
  （此前这里写「只给四档、`max` 留在设置里」，与代码不符，2026-10-15 更正。）
- **覆盖 = 偏离**：选到与模型配置相同的档写 NULL，而不是写一个恰好相等的
  覆盖——切去再切回必须完全复原、零残留。
- **运行中可点**（内核每次请求才读该值，作用于下一次调用）；LLM 切换封锁
  不波及它。切模型后覆盖保留。
- **不等 ready**：内置模式的「模型配置值」直接从模型配置读，runner 上报后
  校正；外置模式 ready 前显示「默认」，ready 后校正。
- **EmptyState 同一个 pill 配置下一个会话**（`pendingReasoningEffort`，与
  LLM 预选同生命周期：createSession 消费、必清除）。
- 对所有模型一律显示（JC：low / medium / high 各家都认；第三方兼容端点认不认
  由用户判断，设置里的提示已交代）。

## 7. Empty State（无 session 时主区）

主界面没 session 时**不放大段欢迎文案**，**Composer 浮在视口中部**（不在底部正常位置）。提交第一条后切入 conversation。

参考 Claude.ai / ChatGPT / Cursor 标准模式，跟"对话工作台"心智一致。

### 视觉

```
             语词的意义，在于它在语言中的用法。       ← 题词：状态绑定的维氏句（serif italic ink-muted）
             Die Bedeutung eines Wortes …             ← 德文原句常驻副行（更轻一档）

            ┌─────────────────────────────┐
            │ Composer (居中，560px max)   │
            │ [Cube] LLM dropdown │ [+]   │
            │                       [↑]   │
            └─────────────────────────────┘
```

- Composer 居中（含 LLM 切换器，跟 in-session 对称），placeholder 是 "交代什么？"（commissioning 语气；en "What should Galley do?"）。与项目内变体 "在 {Project} 里交代什么？" 同构。2026-07-04 收口：此前实现漂移成 21 字的本地文件功能问句，按 austerity 回归纯 affordance；本地文件能力的教学由 saved prompts 预置模板承担（「本地文件整理」等四条含路径提示），不占空状态。
- **Composer hint 槽统一语法**（2026-07-04）：composer 下方的小字提示全应用只有一种长相（主对话的输入框下面没有这一行，见「[会话里的输入框](#会话里的输入框2026-10-15)」）——会话内「Enter 发送」hint 的 footer 槽（`mt-1.5 text-[11px] text-ink-muted`；卡片下与卡片左缘齐平，会话里的一行式下左对齐到输入文字的起点、＋ 右边 44px），Composer 以 `staticHint`（ReactNode）对外开放。每条 hint 自带一个**内容级体裁记号**，形式自我说明、不加「tip:」类元标签：键盘 hint 用 mono 键位词，项目态「将创建到 {Project}」用 11px 文件夹小图标（提交后果陈述）；项目绑了文件夹时后面接 ` · ~/…/文件夹名`（2026-10-09，挤压时路径先缩，项目名与 × 不让位）。
- **全局空状态卡片下方刻意全空**：能力 tip 不放这里——2026-06-03「新人能力发现留给非空状态机制」的决策仍然生效。2026-07-04 曾试放一行本地文件 tip，三轮打磨（居中独立行 → 统一 hint 槽 → 拟加体裁记号）仍破坏构图协调，当日删除。与 quick prompt 建议、快捷键 chrome 并列为勿回退项。
- **题词（epigraph）浮在 Composer 正上方**：一行状态绑定的维特根斯坦句（译文跟随软件语言）+ 德文原句常驻副行（更轻一档）。`font-serif italic text-[12.5px] text-ink-muted`，视觉明显次于 Composer——读作安静题铭，不是 header / banner；入场即冻结，不随状态实时变、不轮播（live pulse 归 sidebar status spine）。状态绑定：`silent`（无 session）→ Tractatus 7「凡不可说的，应当沉默」；`quiet`（有 session 但无运行）→ PI §19；`working`（≥1 运行）→ PI §43（也是 Composer 运行态声音所依的同一命题 *meaning is use*）。策展集与逐条理由在 `gui/src/lib/epigraphs.ts` 注释 + 2026-06-03 devlog。
- **题词可静默点击**（2026-07-21）：点击题词把一段解读请求预填进 Composer，用户按 Enter 才发出——空状态的本职是引出第一条消息，装饰自身成为零打字入口；用产品解释产品，而非手写静态注释。预填模板（通用增强版，二轮定稿）：完整出处署名 + 译文 + 德文原文 + 通用三问「在说什么 / 针对什么问题或立场提出 / 与今天的 AI · 大语言模型有什么关联或启发」。三味信息各有功能：署名解决弱模型识别（`epigraphs.ts` 每句带 `citeZh/citeEn` 完整引用——"PI §43" 弱模型展不开）、原文解决译本歧义、三问给答案结构；AI/LLM 关联一问是这些句子入选题词的真实理由，且不依赖产品自指。静止态与纯铭文逐像素一致（无下划线、无边框、无提示文案），hover/focus 才有极轻墨色上浮 + pointer——可发现性靠自选择：会被句子困住的用户恰是盯着它看的用户。守卫：composer 已有用户草稿时点击不覆盖（仅聚焦）；重复点击自身预填幂等。未配模型走 requiresModelConfig 正常降级。对 PI §43 这一交互即命题自身的演示（meaning is use——点击即用法）。Rejected：点击即发送（误点烧会话 + 模型调用，不可反悔）；隐藏上下文注入（明面短句暗里附加——违背"用户所见即所发"的诚实原则）；逐句定制阐述维度（策展负担 ×3 句 ×2 语言，且预填越像 prompt 模板越不像用户自己的话）；一行短问句「这句话是什么意思？」（一轮方案，弱模型识别不稳）；hover 显示人工策展释义（在 AI 工作台手写注释自我否定）；保持纯装饰（晦涩对掠过者是氛围，对驻足者是痒处，而驻足者恰好会 hover 到）。
- 阅读宽度（「显示」popover / Settings → General / View 菜单）同样影响 Empty State：compact = 560px，wide = 1200px。用户在空状态切宽度必须看到变化，否则像坏了。
- **不放 quick prompt 建议**（勿回退）：早期在 Composer 下方放过 4 条 serif italic 引导 prompt，2026-06 与题词打架——两坨安静 serif 夹住 Composer 稀释焦点，且在"沉默"题词下放"快说点什么"自拆其台——整段移除；新人能力发现留给独立的非空状态机制（详见 2026-06-03 devlog）。
- Sidebar 正常显示书眉 Header（字标 + 搜索 / 定时 / 新建项目）/ 新对话行 / timeline；项目会话折在「项目」分区的组行里；没有 session 时只出现一句 muted empty hint。有主对话时书眉没有字标，书眉下是助手卡片，新对话行这时整行亮着（[layout-and-chrome.md](./layout-and-chrome.md)「有主对话时」）。

### 主对话的问候（例外，2026-10-12，PRD 裁决 47，票 04c；2026-10-13 裁决 49 只留第一段）

主对话不受上面「不放欢迎文案」的约束：它不是一次性的对话，以后什么事都往这里说，第一句由 AI 说，教用户怎么用它。

- **什么时候**：内置运行时建出主对话的那一刻，Core 在同一个事务里写入一条 AI 消息（`core/src/db/main_chat.rs`）。
  从归档恢复、本来就在的主对话都不写；外置运行时没有主对话，也就没有问候。
- **说什么**：固定文案，中英两版，按界面语言选（桌面调 `get_or_create_main_chat` 时传解析后的界面语言，不传用英文）。
  中文是 JC 定稿的原文，只有一段：「你好，我是你的私人助理。以后有什么事，直接在这里跟我说就行。费时间的活我派出去办，办完回来告诉你。」
  英文：「Hi, I'm your personal assistant. Whatever comes up, just tell me here. Longer jobs I'll hand off, and come back to you when they're done.」
  2026-10-15 改（[助手 PRD](../../.scratch/assistant/PRD.md) 裁决 7）：开头先说它是谁，侧栏助手卡片第一次打开时第二行就是这句，角色词不进卡片的名字行；末句是「事事给你交代」，用「派出去」不用「安排人」（子任务是 AI 对话，不是真人）。
  此前（10-12 起）：「你好。以后有什么事，直接在这里跟我说就行，不用再想是开新对话还是接着哪个旧的。」已建出的主对话里那一条不变，新建与重置后才是新版。
- **怎么显示**：按普通 AI 回答显示——没有步骤标记、横线、运行折叠、步数和用时，只有回答本身和它的行动条（复制、保存）。在助手的对话里它是一条左侧气泡，上面一条居中的时间，取这一行的 `created_at`（[助手的对话](#助手的对话2026-10-15)）。
  识别靠消息的来源（`created_via = 'system'`、`supervisor = 'galley-greeting'`），不靠位置。
- **只给人看**：不回放进模型上下文（Core 重启、runner 变冷后的历史回放都跳过它），
  不算一轮问答（`turn_count` 仍是 0，第一条用户消息仍是第 0 轮）。
- 所以主对话从来不是空的；本节以上的空状态规则只管没有会话的主区和其他对话。问候不算一轮，激活时的读回此前只看 `turn_count > 0`，新建与重置后的主对话打开是空的，2026-10-14 起主对话一律读回（票 18）。侧栏助手卡片的第二行第一次就是这句问候（[layout-and-chrome.md](./layout-and-chrome.md)「有主对话时」）。
## 本地文件引用与 Markdown 预览

2026-09-08 首版：文件引用属于消息正文，入口是明确 Markdown 链接和行内代码中的
完整路径。支持当前机器的绝对路径、`~/…`、`file://`；包含空格、中文、Windows
盘符与 UNC。聊天中的相对路径保持文本，不搜索项目目录、工作目录或同名文件。
普通正文、代码块、工具日志不做路径扫描；旧消息复用相同渲染规则。

- 文件夹：点击文字打开目录。可预览的文件点击进入右侧阅读面板；其余文件在
  系统文件管理器中显示并选中。
- 可点击路径自身也有独立反馈：hover 瞬时显示浅品牌色底并强化字色和下划线，
  按下加重底色；内联代码的灰底同步让位给该底色。文字位置、尺寸、间距和换行
  保持稳定。路径与相邻文件夹按钮分别响应 hover，不联动点亮。
- 可预览的文件（2026-09-09 从「仅 Markdown」扩展）：`.md` / `.markdown`
  按文档渲染；PNG / JPEG / GIF / WebP 直接显示原图；文本、代码、数据文件
  （`.txt` `.log` `.csv` `.tsv` `.json` `.yaml` `.py` `.rs` `.ts` 等扩展名
  白名单，`Makefile` / `Dockerfile` / `LICENSE` 等约定名，`.gitignore` 类
  点文件，以及无扩展名且开头 8 KiB 是无 NUL 的 UTF-8 的文件）按带行号的
  纯文本显示。扩展名未知的文件不猜内容，一律走文件管理器。判定归 Core
  （`local_file.access` 的 `kind`），GUI 按文件名镜像同一份表只决定 tooltip
  （「预览 Markdown」/「预览图片」/「预览文件」/「在文件夹中显示」）和
  是否显示旁边的文件夹图标；点击后以 Core 的答案为准。
- 消息旁与预览顶部的文件夹按钮共用反馈：静止透明底，hover 瞬时显示浅品牌色
  圆角底并强化图标颜色，按下加重底色并下沉 1px。保留箭头光标、原尺寸和 tooltip；
  打开成功由文件管理器承接反馈，失败沿用错误提示。
- 文件引用右键菜单提供复制路径。明确但不存在的路径仍可复制；点击失败给出错误反馈。
- 文件名不等于“产物”身份；本功能不建立产物列表、文件树、版本库或编辑器。
- **本会话写过的文件按名解析**（2026-09-17）：bridge 在 `file_write` / `file_patch` 落定时把 GA 实际写入的绝对路径记进 `tool_calls[].resolvedPath`（[IPC §4.7](../ipc-protocol.md)）。回复正文里的相对路径或裸文件名，只在与本会话已写文件的相对写法或文件名**完全相等**时解析成该绝对路径并按上述规则可点；同名多文件不解析、不做模糊匹配。这是查表不是猜基准目录，09-08「相对路径保持文本」的边界不变——聊天里出现的其他相对路径仍是文本。起因是 Goal 收尾把交付物写成 `./汕尾旅游指南.md`，用户追问完整路径后才能点开（[devlog](../devlog/2026-09-17-written-file-references.md)）。
- **过程区的写入步骤自带入口**：settled 的「写入文件 / 修改文件」pill 行尾有一颗打开按钮（可预览的显示文档图标进阅读面板，其余显示文件夹图标在文件管理器中定位），展开体第一行是完整路径的文件引用。这是不依赖模型把路径写对的那一半：即使回复里连文件名都没提，步骤本身也能打开产物。按钮是 toggle 行的兄弟节点（button 不能嵌套），有它时 pill 行收缩到文字宽度，让按钮贴着 caret 而不是漂到列的远端（09-16 的孤立控件教训）。

预览仅在当前会话按需出现。主区宽度至少 880px 时，两侧通过可拖拽分隔线调整，
首次默认对话/预览为 54%/46%；对话至少 440px，预览至少 400px（2026-09-08 从
1080 / 480 / 420 下调：侧栏默认占 20%，1280 宽的窗口主区只有 1024，原阈值下
永远走 dialog、盖住对话，边看边写不成立）。比例作为全局
阅读偏好保存在 localStorage，跨文件、会话和重启复用；单栏布局单独保存，关闭
预览不会覆盖分栏比例。双击分隔线仅复位这两个区域的比例，悬停说明操作；
分隔线也支持键盘方向键。窗口和左侧会话栏不受此复位操作影响。两侧独立滚动，
输入框仍可使用；主区不足 880px 时用 920px × 最高 680px 的内容工作台档 Dialog。
普通段落、标题、列表和引用居中，最大行宽 76ch；表格、代码块和图片可利用完整
预览宽度。
点击另一个文件替换当前文件；重复点击当前引用保留阅读位置；切换会话关闭预览。
关闭恢复来源引用的焦点；覆盖预览使用 Dialog 焦点约束，并支持 Escape。分栏
模式下 Escape 在焦点不在文本框时也能关闭面板（2026-09-08 起，原先只在焦点
落在面板内时生效）。

顶部是文件名、完整路径、定位文件、刷新、更多、关闭，走阅读面板共享的
header 外壳（`ReadingPanelHeader`：标题、带 tooltip 的副标题、右侧动作组、
宿主提供的关闭控件；Git 审阅同一外壳）。更多包含复制路径，以及**仅对文档类
文件**显示的「用默认应用打开」（Markdown、图片、`.txt` `.csv` `.json`
`.yaml` 等数据文本）；脚本类（`.sh` `.py` `.bat` `.ps1`…）不给这一项——
部分桌面的默认应用会直接执行它们，聊天里的路径不能变成执行快捷方式。Core
按同一张表拒绝，GUI 隐藏菜单项是为了不弹「不支持」的提示。
正文显示打开/刷新时的磁盘内容，非消息发送时的历史快照；不自动刷新——这句
说明放在刷新按钮的 tooltip 里，不再作为每个文档顶部的常驻一行。加载 / 空 /
错误态统一走 `PanelNotice`（加载灰字、信息行、错误行、居中空态）。
文本类 UTF-8（含 BOM）上限 2 MiB，图片 10 MiB。不存在、无权限、超限、无法
解码等错误在预览内说明，保留文件定位和复制出口。空文件有独立提示。

文本预览（`TextPreview`）与 Git 审阅的未跟踪文件同一寄存器：`PlainFileLines`
等宽、带行号、软换行、无语法高亮（首版与 diff 一致，两个视图读起来是同一
个面）。顶部一行说明「N 行」。两个可读性特化：`.csv` / `.tsv` 按 RFC 4180
解析（引号内的分隔符、换行、双引号转义），列数规整时渲染成表格——表头
粘顶、行号列、单元格截断带 title，说明行写「N 行 × M 列」；超过 1000 行只
显示前 1000 行并用信息行说明；解析不规整（列数参差、引号未闭合、不足两列）
就退回纯文本并说明「未按规整的分隔格式解析」。单行 JSON 重新缩进两格显示
并说明「磁盘上是单行」；已格式化或非法 JSON 原样显示。图片预览
（`ImagePreview`）按原尺寸（不超过面板宽度）显示，加载后在图下用
tabular-nums 标出像素尺寸。

文档内相对链接和图片以文档目录解析，同页标题锚点在当前预览内跳转。
本地 PNG/JPEG/GIF/WebP 图片按接近可见区域加载，上限 10 MiB，读取走 Core，
因此支持外接盘等 WebView asset scope 以外的位置。SVG 和 HTML 脚本不执行。
图片下方的「在文件夹中显示」只在 hover / 聚焦时出现，多图报告不再长出一列
链接。消息行内的文件夹按钮是 20px（图标 13px、压到基线），不撑正文行距。
跨文件锚点首版打开目标文件顶部，不定位目标章节。

## Git 工作区改动审阅

- 复用现有 54%/46% 默认比例、拖拽/双击复位、宽窄布局规则。右侧一次显示
  Markdown 或 Git 审阅。Git 审阅属于窗口，切换会话或项目保留当前仓库、文件与
  面板状态，不自动追随新会话目录；Markdown 仍在切换会话时关闭。宽窄布局切换保留仓库、所选文件和
  单双列偏好并重新读取。主对话组件不因面板打开/关闭而重新挂载。
- 面板 header 就是仓库：标题为仓库名（tooltip 完整路径），副标题为「相对最近
  一次提交 · 短 ID」或无提交说明，右侧切换仓库、刷新、关闭——用与 Markdown
  预览同一个 `ReadingPanelHeader` 外壳（2026-09-08 合并，原来「工作区改动」
  标题行 + 仓库行 + 文件带三层叠在内容之前）。HEAD 在读取期间或文件选择前
  改变时要求刷新，不能静默混用比较基准。
- 文件选择器是 Galley 自己的列表（`GitFileList`），不是浏览器原生 `select`：
  「已跟踪文件的改动」「未跟踪文件」两组 eyebrow 组头带计数，一行一个文件，
  状态 chip（新增 / 未跟踪偏 success，删除偏 error，冲突 warning，其余灰）+
  等宽相对路径，当前行 `bg-selected`，上下方向键切换，列表高度封顶 38vh 内
  滚动。未跟踪项遵守 Git 忽略规则，并在下降前排除隐藏目录和系统数据目录
  （I12）；组头 tooltip 提示此范围。已跟踪隐藏文件的变化不受此过滤影响。
- tracked diff 默认单列，单/双列用 `SegmentedControl` 切换（不是文字随状态
  翻转的按钮）；显示行号、相邻三行上下文、小型 patch 的行内差异。hunk 头
  显示为「第 N 行起」（原始 `@@` 头留在 title），顶部粘住一条「第 i / n 处
  改动」计数 + 上一处 / 下一处。未跟踪项以带行号的纯文本显示当前 UTF-8 内容
  （`PlainFileLines`），不声称它是相对提交的新建文件。重命名首版显示为
  删除/新增。
- 无提交的仓库，已跟踪且仍存在的文件按新增呈现。二进制、非 UTF-8、冲突、
  子模块及不支持类型用 `PanelNotice` 信息行说明；「没有未提交改动」和「选择
  仓库」是居中带图标的空态，错误走错误行。命令/文本上限 2 MiB、文件列表 5000 项、
  patch 5000 行，超限不展示截断的伪完整 diff。
- 只读、按需加载、手动刷新；没有暂存、撤销、合并、提交、自动快照和编辑功能。
